## 1. What this is

The context assembler already exists and is one of the platform's few genuinely converged spines: `ContextService.build_context` is the single prompt-building path for every live execution surface — chat, headless task execution, heartbeats, recipes, routing, NL2SQL, and the PRD-164 planning pack. This PRD does not build a second assembler. It makes the one we have **honest, observable, and cheap**: persist what it assembled so "what did Auto know?" is answerable; count tokens **one way** and delete the char/4 estimator that makes every cap dishonest; size budgets to the actual model window instead of a hardcoded 128k; capture the prefix-cache cost saving on the highest-volume plane; and adopt the Anthropic **context-editing** and **memory-tool** primitives on the headless loops that today get no runtime context lifecycle at all.

**Framing (CLAUDE.md §3):** this is **Refactor + Extension**, not net-new. The refactor is subtraction and unification — one tokenizer (delete the others, §5), one budget definition derived from the model window, cache-aware section ordering. The extension is three narrow provider-seam adoptions (prompt caching, context editing, the memory tool) that no vendor sells at this seam and that ride the existing LLM-client layer. Almost nothing here is a new engine; the net-new is one persisted trace, one client-seam `cache_control`, and two beta-parameter integrations.

**Build size:** M (seam reuse + one migration-or-JSONB + a client-seam cache header + two beta-param integrations; the deletion is the estimator, not a rewrite) · **Risk:** Medium — unifying the tokenizer changes what "capped" *means* on the live build path (char/4 under-counts JSON/markdown, so honestly-counted sections will trim differently — a behavioural shift that must be measured, §7); the cache-aware reordering must change section **order** without changing section **content**; and the headline cost prize is **conditional on provider routing** (prompt caching is an Anthropic-API feature — see §8 Q1).

**Why now / why measured:** the ~15–22k-token static system prefix on every Auto chat turn is re-paid in full today, because no `cache_control` is ever emitted (`llm_usage` carries 31,081 real rows, `request_type='chat'`, so the volume is real — dossier `auto-core` §H). Anthropic cached reads price at ~0.1× of input, so cache-aware ordering is a ~85–90% saving on the static prefix within the 5-minute TTL — **the single largest cost lever in this module**, and the measured prize this PRD exists to capture. The second prize is answerability: today the assembler computes `sections_included / sections_trimmed / token_estimate / preparation_time_ms` on every build and **throws them away**, so no operator or engineer can reconstruct what any agent knew on any turn. Both prizes are numbers, and both are frozen as before-values in §7.

## 2. Current reality (grounded, not the review's July snapshot)

- **One assembler, one entry point — verified.** `ContextService.build_context` (`orchestrator/modules/context/service.py:71`) runs the 10-step pipeline (mode lookup → section fan-out → budget allocation → prompt concat → tool load → message trim → attachments → immutable `ContextResult`). `MODE_CONFIGS` (`modules/context/modes.py:36`) maps 10 `ContextMode`s (`modes.py:13`) to section lists; the CHATBOT caller is Auto's orchestrator (`consumers/chatbot/smart_orchestrator.py:222`), and TASK_EXECUTION is the AgentFactory default for every headless surface. Two modes are dead config (`COORDINATOR` `modes.py:22`, `ORCHESTRATOR_STAGE` `modes.py:20`). The "one assembler" claim holds — this PRD does not fork it.
- **Two definitions of "how many tokens is this."** The **live build path** budgets with a char/4 heuristic: `TokenEstimator.estimate` returns `len(text) // 4` (`modules/context/estimator.py:16-20`), instantiated as a module singleton in **two** places (`service.py:57`, `budget.py:22`) and called at `service.py:133,147,407` and `budget.py:84`. Truncation is a **character slice** — `content[: section.max_tokens * 4]` (`budget.py:83`) — which cuts mid-word and mid-JSON. Meanwhile the **planning pack** (`service.py:271-288`) and **RAG** (`modules/rag/budget.py:35-37,178`) already count with tiktoken via `core/context_guard.py:49`. So the platform has an assembly-time budgeter on char/4 and a planning/RAG budgeter on tiktoken that do not share a definition of size. The estimator's own tiktoken path, `TokenEstimator.precise` (`estimator.py:22-31`), exists but **nothing calls it** — dead.
- **Budgets are not model-aware.** `DEFAULT_BUDGETS` hardcodes `total=128_000` for every live mode (`budget.py:152-190`), `131_072` for the dead COORDINATOR (`budget.py:198`), and `12_000` for the planning pack (`budget.py:207`). The platform's own `ContextGuard` already resolves the real window from the `LLMModel.context_window` DB column — `get_context_window(model)` (`core/context_guard.py:130-146`) + `_thresholds_for_model` (`context_guard.py:179`) — and uses it for chat-only runtime compaction. A small-window model overruns at assembly and gets emergency-compacted later; a 200k/1M-window model leaves capacity unused. The model-aware plumbing is one import away.
- **The assembled trace is not persisted — "what did Auto know?" is unanswerable.** `ContextResult` (`modules/context/result.py`) carries `sections_included / sections_trimmed / token_estimate / preparation_time_ms`; `build_context` computes and logs them (`service.py:186-210`) and **no consumer outside the module persists them.** The one frontend surface built for this, `frontend/components/context/context-engineering.tsx` (773 lines), has zero importers — an orphaned page. (Note: `modules/context/instrumentation.py` is a `SharedContextPort` field-metric A/B wrapper, **not** an assembly-trace persister — don't confuse the two.)
- **No prompt caching anywhere.** A source grep for `cache_control` across `core/`, `modules/`, `consumers/`, `api/` returns exactly **one** hit — a Bedrock `cachePoint` passthrough at `core/llm/clients/bedrock_client.py:371` that no caller ever populates. The Anthropic client (`core/llm/clients/anthropic_client.py`) builds its `system` parameter (`:67-75`) with no `cache_control`. The ~15k stable prefix is re-billed every turn on every plane.
- **Runtime context lifecycle is chat-only.** `ContextGuard` compaction (tiktoken-counted, model-aware, Mem0 fact-flush) is invoked only on the chat path (`consumers/chatbot/service.py`); missions, heartbeats, and recipes get no compaction, no context editing, and no note-taking primitive. Anthropic ships both server-side (context editing, the memory tool) and the platform consumes neither.
- **The observability plane exists — reuse it.** PRD-185 S9 built `core/observability/tracer.py`: a `TRACING_ENABLED`-gated (default **OFF**, `tracer.py:176`) Langfuse seam — `get_tracer()` (`:221`) returns a `NoOpTracer` (`:77`) until enabled, `LangfuseTracer` (`:87`) imports `langfuse` lazily (`:198`). Its public method today is `trace_tool_call` (`:51,102`); the assembly trace is a **new record shape on the same seam**, not a second vendor.
- **The platform is genuinely multi-provider.** `core/llm/manager.py` routes to OPENAI/ANTHROPIC/GOOGLE/AZURE/HUGGINGFACE/AWS_BEDROCK/GROK/OPENROUTER (`manager.py:500-529`), with an OPENROUTER fallback path (`:467`); `AnthropicProvider` is imported and live (`manager.py:19`). Prompt caching is an **Anthropic-API** feature — which means the cost prize is realizable on the Anthropic-routed (and Bedrock-`cachePoint`) share of traffic, and is a routing question, not an assumption (§8 Q1).

## 4. Stories (test-first; CI is the only gate — no local runs)

### S1 · Persist the assembly trace — answerability — S · _context-assembly J1_
The assembler already computes everything worth recording and throws it away (`service.py:186-210`). Persist a narrow trace per turn/run: `turn_id/run_id`, `mode`, per-section `{name, priority, token_estimate, rendered_nonempty, trimmed}`, injected memory item ids, `prep_ms`, `model`, and the resolved `budget.total`. Route it through the **PRD-185 observability seam** (`core/observability/tracer.py`), not a parallel plane: the tracer gains an assembly-trace record shape alongside its existing `trace_tool_call`; a Langfuse span is emitted when `TRACING_ENABLED` (default OFF), and the **durable row is written regardless** so the trace is answerable offline even with tracing off. `build_planning_context` (`service.py:217`) emits the same trace shape so approvers can later judge a plan against the pack the planner saw (PRD-163 card). Storage is JSONB on an existing per-turn table where one fits (reuse over a new table — §8 Q4).
**Test:** `test_assembly_trace_persisted` (a build writes a durable row carrying the expected section/token/trim fields, tracing OFF); `test_trace_span_emitted_when_tracing_on` (Langfuse span emitted only when `TRACING_ENABLED`, via a mocked tracer). Pure — no live Langfuse, no DB.
**Notes:** reuse the PRD-185 seam; do **not** add a second observability vendor. The tracer singleton is `config` not `settings` (PRD-185 gotcha). The orphaned `context-engineering.tsx` is the natural read-only Inspector seed for this trace — wire or delete, don't leave unmounted (§8 Q5).

### S2 · One tokenizer + token-aware truncation — S · _context-assembly J2_
Unify the live build path onto the tiktoken counter the planning pack and RAG already use. The two `TokenEstimator()` singletons (`service.py:57`, `budget.py:22`) delegate to `core.context_guard.count_tokens` (`context_guard.py:49`); the char-slice truncation `content[: max_tokens * 4]` (`budget.py:83`, `base.py`) is replaced by `truncate_to_token_budget` (`modules/rag/budget.py:178`), which lands on a token boundary rather than mid-JSON. **Delete** `modules/context/estimator.py`'s char/4 `TokenEstimator.estimate` and its dead `precise()` in the same commit — repoint every reader (§5, no `_legacy` shim). The redundant char-budget rival budgeters (F079: `ContextAssembler`, `ContextOptimizer`) are a *second* definition of tokens but their deletion belongs to the review's PRD-184 kill-list, not here — flagged so it is neither double-claimed nor silently dropped (§8 Q7).
**Test:** `test_estimator_delegates_to_count_tokens` (same content → same number as `count_tokens`); `test_truncation_lands_on_token_boundary` (a JSON section truncates to valid-prefix tokens, not a mid-object char cut); `test_no_char4_estimator_callers` (source-grep guard: no `* 4` char-slice or `TokenEstimator.estimate` call sites remain). Pure.
**Notes:** this is the story that makes every cap and budget honest — and it *will* shift trim behaviour on the live build path (honestly-counted markdown/JSON was previously under-counted), so §7 measures the assembled-vs-actual delta before and after. Repoint the grep guard in the same commit its symbol moves (recurring F070 lesson).

### S3 · Model-aware budgets — S · _context-assembly J3_
`TokenBudget.total` resolves from the actual model window at build time via `get_context_window(model)` (`context_guard.py:130-146`), replacing the hardcoded `128_000` (`budget.py:152-190`). The agent `llm_config` already carries the model; the mode config supplies the fallback when the model is unknown. The dead COORDINATOR `131_072` (`budget.py:198`) is removed with its mode (§8 Q7-adjacent) or left untouched if the mode-deletion is out of this PRD's scope.

**Notes:** stops over/under-provisioning per model; this is the plumbing `ContextGuard` already proves works, lifted to assembly time.

### S4 · Prompt caching — the cost prize — M · _context-assembly J6 / auto-core J12_
Order the assembled prompt for cache stability and emit Anthropic `cache_control` on Anthropic-routed calls. **Ordering (the real design work):** the static, high-value blocks (identity/personality, the agent's SKILL.md bodies, the full platform-action catalog) render first — before the last `cache_control` breakpoint — and the volatile blocks (memory excerpts, KG snippet, datetime, per-turn context) render last, after the breakpoint or in the user message. `cache_control: {type: "ephemeral"}` (5-minute TTL; `{type: "ephemeral", ttl: "1h"}` optional) is placed on the last stable block at the `anthropic_client.py` seam (`:67-75`), reusing the render order tools → system → messages so the marker caches tools + system together. The **measured prize** is the ~85–90% prefix-cache cost delta on the highest-volume plane, read from the Anthropic `usage.cache_read_input_tokens` / `cache_creation_input_tokens` fields and surfaced through S1's trace. **The tension** (dossier D + J6): the per-query FILTERED tool list and the embedding-ranked top-15 action catalog (`SEMANTIC_TOOL_ROUTING` default on) render at position 0 and **bust the cache every turn** — so per mode, per-query tool filtering (token saving) and prefix stability (cache saving) must be traded off explicitly (§8 Q3).
**Test:** `test_stable_prefix_single_breakpoint` (a build places exactly one `cache_control` on the last static block); `test_volatile_change_preserves_cached_prefix` (changing a memory/graph section does not alter the bytes before the breakpoint); `test_cache_control_only_on_anthropic_route` (mocked client — the header is emitted for the Anthropic provider and not for a non-caching route). Pure/mocked — assert the request shape, never call a provider.
**Notes:** `cache_control: {type: "ephemeral"}` is GA Anthropic API and grounded — do **not** invent parameters beyond it. The Opus-class minimum cacheable prefix is ~4096 tokens; the ~15k static prefix clears it. Max 4 breakpoints per request. Realizability is provider-conditional (§8 Q1); the Bedrock `cachePoint` passthrough (`bedrock_client.py:371`) is the analogous seam for Bedrock-routed traffic.

### S5 · Adopt Anthropic context-editing + memory-tool on headless loops — M · _context-assembly J7 / auto-core J12_
Generalise the runtime context lifecycle beyond chat. On the shared tool loop for Anthropic-routed headless runs (TASK_EXECUTION via AgentFactory, HEARTBEAT_AGENT), adopt Anthropic **context editing** — beta `context-management-2025-06-27`, `context_management={"edits": [{"type": "clear_tool_uses_20250919"}]}` — to clear stale tool results cache-preservingly, and the **memory tool** — `{"type": "memory_20250818", "name": "memory"}`, client-executed against a `/memories` directory — as a durable note-taking primitive. Generalise `ContextGuard` (`core/context_guard.py`) so missions/heartbeats get compaction too, not just chat. The memory-tool backend is client-side and must reuse the platform's existing durable-memory plane (PRD-187) rather than open a parallel file store where it fits (§8 Q6); every model-supplied memory path is canonicalised and confined to `/memories` (traversal guard).
**Test:** `test_context_editing_on_headless_anthropic_loop` (the beta `context_management` edit is present on the request for an Anthropic-routed headless run, absent otherwise — mocked client); `test_memory_tool_declared` (the `memory_20250818` tool is declared on the eligible loop); `test_memory_path_traversal_rejected` (a `../` path outside `/memories` is rejected). Pure/mocked.
**Notes:** context editing is **not** compaction (`compact_20260112`/`compact-2026-01-12` is the separate feature — do not confuse). Context editing and S4's caching interact by design — context editing is cache-preserving — so S5 lands after S4. The exact beta strings/params are Anthropic **beta** surface: spec the seam and confirm the versioned parameter names against the live API at build (§8 Q2) — do not invent shapes.
