## 1. What this is

A **make-it-real** PRD, not a new engine. The NL2SQL engine already exists and is the *right shape*: PRD-160/172 built a workspace-scoped pipeline with the best AST validator and tenancy discipline in its class, self-correction, EXPLAIN dry-run, value sampling, verified-only few-shot with persisted embeddings, and a dual-entry audit choke-point. What is broken is the **accuracy machinery bolted onto that engine**: the highest-leverage feature — a per-connection semantic layer — is a four-layer placebo that can neither load nor save (its save path calls two methods that do not exist), and the module's own quality number is a `0.0` placeholder that has never been measured because the generation eval is opt-in and skipped in CI. This PRD makes the semantic layer **writable and persistent**, **runs the eval for real** to put the first honest number on NL2SQL accuracy, measures whether the semantic layer actually moves that number on *this platform's* schemas, and **deletes** the decoy surface (a 1,687-LOC dead package, a legacy limb with a crash path, a false-advertised linker) that misleads reviewers, agents, and users.

**Framing (CLAUDE.md §3):** this is **Refactor + Extension**, not net-new. The engine is PRD-160's; the semantic-layer *read* side is already wired into generation (`nl2sql_service.py:204-218`); we are fixing a 100%-broken *write* side, wiring an eval instrument that already exists (`tests/nl2sql_eval/`), and **deleting** superseded/dead code (§5, no shims). The only genuinely new code is small: a GET route, a persisting write path, an instructions-first editor field, one A/B eval mode, and a benchmark endpoint re-pointed at the harness that already sits 30cm away.

**Build size:** M (mostly fixing a broken write path + wiring the existing eval + grep-proven deletion) · **Risk:** Low-Medium. The NL pipeline is held constant; the semantic write path is *currently 100% broken* (every save raises `AttributeError`), so repairing it cannot regress a working path. The kill-list is dead-code deletion, grep-proven before removal. The one real "risk" is the eval revealing that the semantic layer *doesn't* pay for itself here — which is a **finding that decides scope (§8-Q1)**, not a regression.

**Why now / why measured:** the point of Wave 0 was to make quality a number. NL2SQL is the platform's most *advertised* capability with the *least* evidence — `database_query_audit` has **0 rows** across 21 workspaces, `baseline.json` still reads `accuracy: 0.0` (the 2026-06-12 placeholder), and the feature every best-in-class analyst (Cortex, Genie, Wren) treats as the accuracy foundation ships here as a UI that can neither read nor write. Uniquely for a Wave-3 PRD, the "before" is not a bad number — it is *no number*. So the first deliverable is the first honest measurement, and everything after is a **measured delta** against it.

## 2. Current reality (grounded, not the review's July snapshot)

- **The engine exists and is workspace-scoped.** `modules/nl2sql/service.py` (the pipeline spine, `query_database` at `:372-618`), `modules/nl2sql/query/nl2sql_service.py` (generation/prompt-assembly), `modules/nl2sql/query/validator.py` (the real sqlglot AST validator — single-statement, read-only-roots, ~40-name side-effect denylist, table allowlist, LIMIT inject/cap; the strongest artifact in the module). Production constructs the pipeline with **no linker and no example store injected** (`service.py:492`; benchmark route likewise `api/database_knowledge.py:1000`).
- **The semantic layer's *read* side is real and already integrated.** `nl2sql_service.py:199-218` renders `semantic_layer['instructions']`/`business_context` as authoritative business definitions, then `metrics` (as a **dict**: `for name, metric in semantic_layer['metrics'].items()`, `metric.get('sql')`) and `dimensions` (nested dict) — injected at generation. This reader is the integrated consumer and the de-facto canonical format.
- **…but nothing can ever reach it (J1 — why the semantic layer "can't be written"):**
  1. **Load 405s:** the editor GETs `/{id}/semantic`; **only `POST` exists** (`api/database_knowledge.py:295`) — no GET route. The load fails and is swallowed to console.
  2. **Save crashes:** `service.update_semantic_layer` (`service.py:654-678`) calls `self._get_schema_context(source)` (`:666`) and `self._validate_semantic_definitions(...)` (`:667`) — **neither method is defined anywhere in the orchestrator** (repo-wide grep: zero definitions). Every save raises `AttributeError` → the route 400s (`api:332-333`); the frontend swallows that too, so the admin believes it saved.
  3. **Even if it ran, it wouldn't persist:** `_get_source` closes its session in `finally` (`service.py:127-128`); the writer then assigns `source.semantic_layer = {...}` (`:670-674`) onto a **detached** ORM object with **no session and no commit**.
  4. **Even if it persisted, the reader would crash:** the writer stores `metrics` as a **list** (`[m.__dict__ for m in metrics]`, `:671`) and the field is `sql_expression`; the reader calls `.items()` (dict protocol) and `metric.get('sql')` (different key) — format mismatch. And the one field that matters most, `instructions`, has **no write path at all** (`:670-674` writes only `metrics`/`dimensions`/`updated_at`), though the reader already renders it (`:204-207`).
- **The eval reads 0.0 because it has never run (J3 — why the number is a placeholder):**
  - `tests/nl2sql_eval/baseline.json` = `{"accuracy": 0.0, "recorded_at": "2026-06-12", "note": "0.0 until a generation run with a real LLM records a number"}`.
  - The *generation* accuracy test (`tests/nl2sql_eval/test_eval.py:69`, `test_generation_accuracy_no_regression`) is **skipped unless `RUN_NL2SQL_EVAL=1`** (`:66-67`) — and the CI lane `nl2sql-eval` (`.github/workflows/test.yml:150`, **non-required**) never sets it, so the LLM generation eval **never executes**. The always-on part is only the *identity* eval (golden SQL executes on the SQLite seed → `1.0`, `test_eval.py:24-27`) — a goldens-integrity check, not a measure of the model.
  - The gate is toothless anyway: `assert report.accuracy >= baseline - tolerance` (`test_eval.py:104`) with `baseline = 0.0` passes for essentially any output until the baseline is bumped.
  - The set is toy-tier: **20** single/two-table golden questions (`questions.json`); PRD-160's own success metric (in `baseline.json`) is "≥ baseline+15pts on a **30**-question set."
- **The decoy surface is real dead weight (J4 — kill-list inputs):**
  - `modules/nl2sql/intelligence/` — **1,687 LOC**, zero external callers, still **exported** (`modules/nl2sql/__init__.py:61-68`) — the package whose capabilities the `smart_query_database` tool card still advertises.
  - Legacy PRD-21 limb inside `service.py:680-883`: `_execute_query` (`:753`) calls `self._build_connection_string` (`:762`) which **has no definition** (`AttributeError` if ever reached); `_validate_sql` and `_build_sql_generation_prompt` are shadow duplicates of the real pipeline.
  - `query/schema_linker.py` `SchemaLinker` — production never injects it (`service.py:492`), so its use-site branch (`nl2sql_service.py:131-133`) is dead; its docstring claims "embedding-based ranking" but `embedding_manager` is assigned and **never used** (`schema_linker.py:44-45`) — the claim is false.
  - `training/example_store.py` `add_ddl`/`add_documentation` (`:307,:324`) — Vanna's training triad imitated, zero callers, would pollute few-shot if called.
  - The benchmark endpoint measures the wrong thing: `benchmarks/runner.py:82-87` sets `exec_match = exact` (normalized string match) with a `TODO` to add real execution matching — while the *correct* execution-accuracy harness sits unused in `tests/nl2sql_eval/harness.py`.
  - Fake stats `total_queries_executed` / `avg_query_time_ms` (`core/models/database_knowledge.py:69`) — never written, permanent zeros in the UI.

## 4. Stories (test-first; CI is the only gate — no local runs)

## 7. Baseline capture + the accuracy bar

This PRD's "before" is not a bad number — it is **no number**. Establishing the first honest one is the first deliverable; everything after is a measured delta.

**Freeze the pre-state (the explicit before-numbers):**
1. **Offline generation accuracy: `UNMEASURED` (0.0 placeholder since 2026-06-12).** `baseline.json` = `0.0` is a placeholder, **not** a measured 0%. The always-on lane proves only that goldens execute on the SQLite seed (identity eval = `1.0`) — it says nothing about whether the LLM *generates* them. Record "NL2SQL generation accuracy: unmeasured" as the honest before, and note the toothless gate (`>= 0.0`) as the reason the number never moved.
2. **Online: `n/a` — 0 audited queries ever.** `database_query_audit` = 0 rows across 21 workspaces; `nl2sql_benchmark_runs` = 0; `nl2sql_training_examples` = 2. The whole learning/verify/benchmark loop has never processed real traffic. (PILOT lens: this is cold-start, not defect — the choke-point is wired correctly; it has simply never been exercised.)

**Then measure (the point of building this):**
3. **First honest baseline `B0`** — S3's scheduled lane runs the generation eval on the platform LLM and records `B0` into `baseline.json`, replacing `0.0`. **`B0` is the before-number every later story is measured against.**
4. **The semantic lever `ΔS`** — S4 runs semantic-on vs semantic-off on the same set → measured uplift. The ~20% figure (Snowflake, dossier D1) is the **hypothesis**; `ΔS` is the **fact on this platform's schemas**. §8-Q1 decides scope on `ΔS`.

**Success = the measured delta (not asserted):**
- NL2SQL accuracy goes from **unmeasured** to a **real number** (`B0`) with a scheduled lane keeping it live — the single most important outcome.
- With a semantic doc authored (S1/S2), accuracy ≥ `B0 + ΔS`. PRD-160's own bar — "≥ baseline **+15pts** on a **30**-question set" (`baseline.json`) — is the aspiration, **re-set as a measured target after `B0` is known**, not pre-committed against a placeholder.
- Kill-list success is accuracy-independent: **~1,900 LOC** of decoy removed (`intelligence/` 1,687 + limb + linker + stubs), **0** importers of the deleted symbols (grep-proven), the `_build_connection_string` crash path gone.
- Benchmark-in-product (S6) reports **execution** accuracy, not string match — the product's number becomes trustworthy.
- Semantic layer goes from **un-writable** (save crashes) to **writable and persistent**, with honest UI state.

*(The eval-gated Wave-3 bets — Graphiti P2-17, NL2SQL P2-18 — share this discipline: measure first, then decide scope. Freezing NL2SQL's baseline via S3 serves the T3 harness, not just this PRD.)*
