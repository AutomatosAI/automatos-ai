## 1. What this is

A **loading-model** PRD, not a new skills engine. The platform already has a real skills system — DB-backed `Skill` rows, a 3-level progressive-disclosure loader, per-workspace forks, an audited 2-stage security scanner, and (post PRD-191) deduped attachments with a real `priority` column and a `UNIQUE(agent_id, skill_id)` constraint. What it does **not** have is the part the rest of the industry standardised on: the skill body and its scripts are *always in context*, every turn, whether or not the task needs them. This PRD adopts the **Agent Skills open standard** (the SKILL.md progressive-disclosure model: `name`+`description` metadata always loaded → body loaded only when the task triggers it → bundled scripts executed on demand, only their output entering context) **on top of** the existing system — keeping the DB as source of truth and running L3 scripts through the workspace worker that already exists.

**Framing (CLAUDE.md §3):** this is **Extension + Refactor**, not net-new. The L1/L2/L3 loader functions already exist (`skill_loader.py` `load_skill_metadata`/`load_skill_core`/`load_skill_resource`/`get_skill_script_path`); the frontmatter parser already captures `name`+`description`; the sandbox already exists (`core/workspace_client.py` → the workspace worker). The increment is: (a) make the schema/import-export spec-conformant so cross-vendor skills are importable and Automatos skills are portable, (b) change *when* the L2 body loads (triggered, not always), and (c) connect the already-resolved L3 script path to the sandbox that can actually run it. Where a path is replaced — the always-inject L2 render in `SkillsSection`, the orchestrator-local script resolver that nothing executes — the old path is **deleted in the same PR** (§5), no `_legacy` shim.

**Build size:** M (a schema/loader alignment + one activation change + two thin tools + scanner wiring — no new tables, no new sandbox) · **Risk:** Medium (the L2 activation change touches every skill-bearing agent's prompt; correctness is proven by the eval + the token-cost baseline holding capability flat while cost drops — a capability regression is the signal, not the goal).

**Why now / why measured:** the measured prize is the **order-of-magnitude per-skill prompt-cost cut**. Today an assigned skill's full L2 body renders on every turn (Auto's `platform-management` body ≈ 6.6k tokens/turn, dossier §H); under trigger-based L2 the idle cost of an attached-but-unused skill drops to its ~50–100-token L1 metadata, and the body enters context only when the task matches. That delta is directly measurable per turn, so this is the cleanest kind of change to build against a live baseline — freeze the current per-turn skill token cost, then prove the drop while task-completion quality stays flat-or-better. The ecosystem payoff (any standard-conformant catalog becomes importable content) is real but secondary to the cost number.

## 2. Current reality (grounded, post PRD-191)

- **Skills are DB rows with the 3-level shape already modelled.** `Skill` (`core/models/core.py:349`) stores the SKILL.md body in `prompt_template` (`:373`, tagged "Level 2 progressive disclosure"), tool defs in `tools_schema` (`:374`), provenance in `skill_source` (`:376`), the on-disk directory in `filesystem_path` (`:380`), a flexible `skill_metadata` JSONB (`:382`), and `content_hash` for freshness (`:384`); L3 files are `SkillFile` rows (`:399`), with `SkillSource`/`SkillVersion`/`SkillAuditLog` (`:419`/`:456`/`:474`).
- **The loader already implements L1/L2/L3 — but nothing triggers L2.** `parse_yaml_frontmatter` (`modules/agents/services/skill_loader.py:133`) captures `name`+`description` (the standard's trigger signal). `load_skill_metadata` (`:860`) is the L1 layer ("always loaded — very lightweight (~50 tokens)"); `load_skill_core` (`:976`) is L2 ("loaded when the skill is relevant to a task"); `load_skill_resource` (`:1059`) + `get_skill_script_path` (`:1137`) are L3. **The design is there; the activation is not.**
- **Activation today = all-in-context, every turn.** `SkillsSection` (priority 4, `modules/context/sections/skills.py`) renders the agent's attached skills' **full L2 bodies** on every turn — `_get_skill_content` reads `prompt_template` directly (`:131`), primary uncapped, auxiliaries under a 5,000-token aux budget (`:32`). PRD-191 fixed the *duplication* tax (dedup by id then `(name, content_hash)`, `:70-95`) but the *always-injected* cost remains: an attached-but-irrelevant skill still pays its whole body every turn. There is **no trigger-based activation** and **no `load_skill` tool** (grep-confirmed absent).
- **The L3 sandbox exists — it is the workspace worker — but L3 scripts do not reach it.** `core/workspace_client.py` is an async proxy to a **separate workspace-worker HTTP service** (`WORKER_INTERNAL_URL` / `WORKER_INTERNAL_TOKEN`, `config.py:553-554`); its `exec_command` (`:159`) "Run[s] a sandboxed shell command in the workspace" — per-workspace scoped, token-gated, 600s-capped. But `get_skill_script_path` (`skill_loader.py:1137`) resolves a path on the **orchestrator's** local ephemeral disk, in a different process from the worker sandbox — so L3 scripts are resolved and **nothing executes them** (dossier C.9). (A second, older in-process executor exists — `ActionExecutor`, `modules/agents/services/agent_action_executor.py:66`, with a command whitelist + `workspace_root` path-jail `:307-312`, surfaced as the `execute_command` tool `modules/tools/registry/tool_registry.py:919`; the review row directs L3 at the *worker*, not this in-process path.)
- **The genuinely valuable part — tenanted, governed, scanned distribution — is real and kept.** Every import runs the 2-stage scanner: static `quick_scan` (`core/services/plugin_security_scanner.py:154`) then `llm_security_scan` (`:300`), `scan_plugin` (`:462`) auto-blocking on critical static findings. Skills are workspace-scoped with per-workspace forks (`api/workspace_skills.py`), RBAC'd attach (PRD-191 S5 visibility gate on the canonical router), and four audited ingestion paths (git `skill_loader.py:249`; plugin-materialize `core/services/skill_materializer.py:162`; builtin-seed `core/seeds/seed_auto_agent.py`; workspace-authored `api/workspace_skills.py`). **The open standard deliberately has none of this** (claude.ai custom skills are per-user, no org admin) — so "import an ecosystem skill, scanned and scoped, before any agent sees it" is a real capability this PRD preserves, not a pitch.

## 4. Stories (test-first; CI is the only gate — no local runs)

### S1 · Spec-conformant SKILL.md schema + import/export — M · _agents-skills J4_
Align the skill schema and ingestion with the Agent Skills open standard so any standard-conformant folder (`SKILL.md` with `name`+`description` frontmatter, optional `scripts/` and resource files) imports cleanly, and Automatos skills **export** to the same shape (portable out). The mapping is mostly already there — `parse_yaml_frontmatter` (`skill_loader.py:133`) reads `name`+`description`; `prompt_template` is L2; `SkillFile`/`filesystem_path` are L3 — so this story canonicalises it: one `skill_source` provenance scheme (`git:`/`plugin:`/`builtin:`/`workspace:`), the frontmatter `description` persisted as the L1 trigger text (into `skill_metadata`/`description`), and a loader-side **export** that emits a standard folder from a `Skill` row + its `SkillFile`s. The DB stays the source of truth (the standard has no tenancy — that is Automatos's addition). Delete the PRD-22-only divergences replaced here (no `_legacy` dialect kept alongside).
**Test:** `test_import_standard_skill_folder_roundtrips` (a conformant folder → `Skill`+`SkillFile` rows with `description` as L1 trigger text) and `test_export_skill_emits_standard_folder` (row → folder an external runner would accept); `test_skill_source_scheme_canonical` (provenance resolves). Pure — fixture folders, mocked session; no git/network.
**Notes:** ~90% format-compatible already (dossier D.1) — this is alignment + export, not a rewrite. No new table. Existing skills' migration to the canonical `skill_source` scheme is a data concern surfaced in Open Questions (Q3), not a silent reshape.

### S2 · Trigger-based L2 activation — the per-skill prompt-cost cut — M · _agents-skills J4/E/H_
Change `SkillsSection` (`modules/context/sections/skills.py`) so that each turn it renders only the **L1 metadata** — `name` + `description` (~50–100 tokens/skill) via the existing `load_skill_metadata` (`skill_loader.py:860`) — for **all** attached skills, plus a one-line instruction that the model may pull a skill's full body when the task matches. The full **L2 body loads only when triggered**, via a new `load_skill(name)` platform tool (3-file registration pattern) whose result injects `load_skill_core` (`:976`) output for that turn. This replaces the always-inject render (`_get_skill_content` reading `prompt_template` for every skill, `:131`) — which is **deleted**, not flagged. The uncapped-primary/aux-budget split PRD-191 built is superseded by "L1 always, L2 on trigger", so the 5,000-token aux path goes with it. Record a skill-activation signal (which skill, which turn) so §7's cost delta and activation rate are measurable.
**Test:** `test_skills_section_renders_l1_only` (attached skills contribute metadata-sized text, not full bodies); `test_load_skill_tool_injects_l2_body` (calling the tool yields the `prompt_template` body for that skill); `test_untriggered_skill_costs_l1_only` (asserts the token delta vs the old always-inject path). Pure/mocked — token counts via the section test harness, no live model.
**Notes:** This is the story that must hold **capability flat** — an agent that needed a skill still gets it (the model triggers `load_skill`), it just isn't pre-paid. The eval + baseline (§7) is the guard: task success flat-or-better, per-turn skill tokens down an order of magnitude on the idle case. Auto's `platform-management` (its core operating instructions) may warrant staying always-on — surfaced as Q4, not decided here.

### S3 · L3 script execution via the workspace worker — M · _agents-skills J4/E/C.9_
Connect L3 scripts to the sandbox that can run them. A new `run_skill_script(skill, script, args)` platform tool materializes the skill's `SkillFile` bundle (`get_skill_script_path`'s resolution logic, `skill_loader.py:1137`, but targeting the worker) into the **workspace worker** filesystem and invokes `WorkspaceClient.exec_command` (`core/workspace_client.py:159`) — the existing sandboxed, per-workspace, token-gated (`WORKER_INTERNAL_TOKEN`), wall-clock-capped exec path. Only the script's **output** returns to context (the standard's "no practical limit on bundled content" property — the body/scripts never sit in the prompt). This replaces the dead orchestrator-local resolver (which resolved a path in the wrong process and executed nothing); that behaviour is removed. L3 execution is **opt-in per skill per workspace** and gated on a scanner-pass (S4).
**Test:** `test_run_skill_script_invokes_worker_exec` (the tool calls `WorkspaceClient.exec_command` with the materialized bundle path; worker mocked); `test_run_skill_script_returns_output_only` (context gets stdout/stderr, not the script source); `test_l3_execution_requires_enablement` (a non-enabled or unscanned skill's script is refused). Pure — worker HTTP mocked at the client boundary; no live worker.
**Notes:** Uses the **workspace worker**, not the in-process `ActionExecutor` (`agent_action_executor.py`) — the worker is the isolation boundary the review row names ("via workspace-worker") and is the per-workspace jail. No `os.getenv` — the worker URL/token are already canonical config (`config.py:553-554`). Security posture (network, resource caps, enablement) is S4 + Q1.

### S4 · Preserve tenanted, governed, scanned distribution on the import path — S · _agents-skills J4/§2_
Keep everything the open standard lacks, on every path this PRD adds. Spec-conformant folder imports (S1) run the **same** 2-stage scanner as today's git/plugin imports — static `quick_scan` (`plugin_security_scanner.py:154`) then `llm_security_scan` (`:300`), auto-block on critical (`scan_plugin:462`) — with the **LLM stage ON for third-party/external sources** (not skipped as it is on trusted hot paths, `:199`). Skills stay workspace-scoped with per-workspace forks (`api/workspace_skills.py`), RBAC'd attach (PRD-191 S5 gate), and audit (`SkillAuditLog`). L3 **execution enablement** (S3) is a workspace-admin action recorded to the audit log: importing/reading a skill as L1/L2 is always allowed once scanned; running its L3 scripts requires explicit per-workspace enablement — import ≠ executable.
**Test:** `test_standard_import_runs_two_stage_scan` (a conformant import hits `scan_plugin`); `test_external_source_forces_llm_stage` (third-party provenance → LLM stage not skipped); `test_l3_enablement_is_audited` (enable/disable writes `SkillAuditLog`). Pure/mocked — scanner LLM call stubbed.
**Notes:** This is the product value in plain terms: an org admin imports an ecosystem skill and it is scanned, workspace-scoped, forkable, and its scripts are inert until an admin turns them on — the safe on-ramp the per-user standard has no answer for. No new scanner (dossier E: "do not adopt an external scanner"). The dossier's ClawHub incident (D.3) is the argument for LLM-stage-ON on untrusted imports.

## 5. Sequencing
- **S1 first** (schema/import-export) — S2 and S3 both assume the canonical L1/L2/L3 mapping and provenance scheme. **S2** (trigger activation) and **S3** (L3 worker execution) are independent of each other and parallel-safe once S1 lands. **S4** (governed distribution) rides the S1 import path and the S3 enablement gate — it lands with or just after them, not before (there is nothing new to scan until S1's import exists).
- **S2 is the value story** and should land with §7's baseline already frozen, because its whole proof is the measured token-cost delta. **S3** unlocks the ecosystem-scale payoff (runnable bundled scripts) but is not on the cost-cut critical path.
- No new tables and no data-moving migration. The only schema touch is S1's provenance-scheme canonicalisation, which is a backfill (Q3), not a structural change; PRD-191's `agent_skills` constraint/priority stay exactly as built.

## 7. Baseline capture / measurement — freeze the cost before, prove the drop after

The point of building this now is a **measured per-skill prompt-cost delta**, so the before-numbers are captured against live Auto usage before any S-story lands.

**Capture NOW (before S2 especially):**
1. **Per-turn skill token cost, current (all-injected).** From context assembly, the tokens `SkillsSection` contributes per turn, per skill-bearing agent — freeze as `baseline/skill_tokens_per_turn_2026-07.json`. The headline before-number: on affected Auto turns the `platform-management` body alone ≈ 6.6k tokens/turn (dossier §H), plus any auxiliaries. This is the number S2 must cut.
2. **Skill-attachment vs skill-use ratio.** For a sample of skill-bearing agents, how many attached skills are actually *needed* in a given task (i.e. how much of the always-injected cost is dead weight today). This bounds the achievable idle-cost drop.
3. **L3 reality check.** Count skills with a usable `filesystem_path`/`SkillFile` bundle vs skills whose scripts have never run (they can't — S3 is why). Records the pre-state so S3's "scripts now execute" is provably new capability, not a re-label.

**Success = the delta (measured, not asserted):**
- **Idle per-skill cost: order-of-magnitude down** — an attached-but-untriggered skill drops from its full L2 body (thousands of tokens) to ~50–100 tokens of L1 metadata. ← the core number.
- **Capability: flat-or-better** — task-completion quality on the skill-using cases holds (the model triggers `load_skill` when it needs the body). A drop here is a regression signal, not an accepted cost.
- **L3: from 0 executable → runnable** — bundled scripts execute in the worker sandbox, output-only into context (was: resolved-but-never-run).
- **Distribution: unchanged guarantees** — every import still scanned; skills still workspace-scoped/forkable/RBAC'd; L3 execution gated behind admin enablement (import ≠ executable).

**PILOT lens:** the module shows few skills and ~0 marketplace installs today (dossier B.5) — that is **cold-start, not a defect** (`feedback-pilot-usage-not-quality-signal`). The cost cut is real and measurable on the *one* heavily-loaded case that exists (Auto + `platform-management`); the ecosystem-scale payoff is capacity the standard unlocks, measured by activations once trigger-loading exists, not back-graded for low current supply.

## 8. Open questions — Gerard's call (decide, don't let me defer — CLAUDE.md §12)

1. **L3 sandbox security posture (the big one).** Recommendation: run L3 scripts **only** through the **workspace worker** (separate process, per-workspace filesystem jail, `WORKER_INTERNAL_TOKEN`, wall-clock-capped exec) — **never** the in-process `ActionExecutor` — with **network default-deny** (mirroring the `http_request` internal-only whitelist posture), **no platform secrets/credentials in the exec environment**, output-size capped, and **execution opt-in per skill per workspace** gated on a scanner-pass (import/read L1+L2 freely; run L3 only after a workspace-admin enables it, audited). Confirm this posture, and whether any command class beyond the worker's existing surface (it already runs `python`/`npm`/`docker`) should be denied for skill-authored scripts specifically.
2. **Compatibility scope with the external spec — full adoption or a subset?** Recommendation: adopt the **loading model** fully (L1-always / L2-on-trigger / L3-output-only) and the **folder+frontmatter format** for import/export, but keep the **DB as source of truth** and **do not** adopt the standard's per-user/no-governance distribution model (that is the part we deliberately improve on). Confirm we are not also expected to expose a spec-shaped external *Skills API* surface in this PRD (I would scope that as a separate decision, not silently include or exclude it).
3. **Migration of existing skills to the canonical schema.** Recommendation: a one-time backfill normalising `skill_source` to the `git:`/`plugin:`/`builtin:`/`workspace:` scheme and persisting each skill's `description` as its L1 trigger text — in-PR, Gerard-applied. Confirm cadence and whether the ~stale/duplicate-provenance rows the dossier noted (C.9) get repaired in the same backfill or left for a data pass.
4. **Does Auto's `platform-management` stay always-on?** It is Auto's core operating instructions, not an optional capability — trigger-gating it could strand Auto on a turn where it hasn't yet pulled its own manual. Recommendation: mark a small set of **core** skills (Auto's `platform-management`) as always-L2, and trigger-gate everything else — capturing most of the cost cut (the auxiliaries and every other agent) without risking Auto's baseline behaviour. Confirm the always-on set, or decide that even core skills trigger-load.
5. **Baseline metric set (§7).** Confirm the three capture items (per-turn skill token cost, attach-vs-use ratio, L3 executable-count) are the right before-numbers, and the success bar (idle cost order-of-magnitude down **and** task quality flat-or-better as the paired guard).
