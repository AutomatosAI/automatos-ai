## 1. What this is

A **wire-what's-already-written** PRD, not a new engine. Missions, the cross-model verification judge, and the checkpoint apparatus **all already exist as code** — they just don't do their job at runtime. The judge is fully built (different-family verifier selection, relevance/completeness/accuracy scoring, thresholds, an output-hash cache) and then the reconciler **always** waves the verdict through to VERIFIED, so a FAIL — even *empty output* — flows into synthesis unchanged. The checkpoint service, model, endpoint and counter column all ship, and `write_checkpoint` has **zero callers**, so "resume" everywhere means "restart the task from scratch." And the approvals inbox Wave-2 shipped (`ApprovalsInbox`, PRD-196 S1) is a real front door — but only for durable board/tool *grants*; the 47% of missions parked at their own approval gate never appear in it. This PRD makes the three flagship muscles do work: **gate the judge once** on FAIL (the retry-with-feedback code is already written and tested-shaped), **delete the decorative checkpoint surface** (it advertises crash-recovery it does not provide and serves an always-empty endpoint), and **feed parked missions into the inbox that already exists** so they are reachable and actionable.

**Framing (CLAUDE.md §3):** **Refactor + Extension**, not net-new. S1 wires one dead branch (`_apply_verdict_fail`) that is already written; S2 is deletion-led (§5 — the checkpoint code is vestigial and the wrong shape for real resume); S3 extends a shipped inbox to aggregate a second, already-queryable plane. Almost nothing here is new code — the net-new is one config cap, one coordinator sweep, and one composed query.

**Build size:** M (wire one branch + a deletion + one inbox-feed extension + one re-notify sweep) · **Risk:** Medium — the only story that can move a client-visible number is S1 (a verification requeue that storms would burn tokens), held down by a **cap of 1** verification retry, keeping PARTIAL advisory, and reusing the existing `required_sections` retry-storm carve-outs (`reconciler.py:365-371`) that document exactly what not to re-judge.

**Why now / why measured:** the Mission outcome funnel is fully measurable *today* from existing tables (`orchestration_runs.state`, `OrchestrationEvent` payloads) — no new instrument needed. Three of its numbers are currently zero-or-parked by construction: **0** verdicts gate, **0** resumes continue, **47%** of missions sit at a one-shot approval. This is the cleanest possible thing to build against a live baseline — every story targets a number that starts at a known, frozen value (§7). Under the PILOT lens the 47%-parked is a cold-start **unblock**, not a defect: the engine works when driven (2/2 completed missions verified every task) and is simply never reachable past its gate.

## 2. Current reality (grounded, not the review's July snapshot)

- **The judge is built and gates nothing.** `VerificationService.verify_task` (`modules/coordination/verification.py:356`) runs a cross-model judge — the verifier is deliberately a *different family* than the executor (`_select_verifier_model`, `:102-104`; mapping in `config.py:779-791`), scored against thresholds 0.7 pass / 0.4 fail / 0.5 confidence-escalation (`config.py:774-776`), with a per-run output-hash cache (`:315-347`). Its own system prompt states the retreat: *"Your feedback is ADVISORY ONLY — it will NOT reject or retry the task"* (`:158`). The reconciler confirms it: after computing the verdict it **always** calls `_apply_verdict_pass` (`modules/coordination/reconciler.py:479`); a non-PASS verdict merely stashes `review_feedback` into `output_metadata` (`:461-472`, comment *"Apply verdict — ALWAYS pass through to VERIFIED"*). Even the empty-output hard-FAIL (`verification.py:385`) is marked VERIFIED and flows into synthesis.
- **The gate's retry machinery is already written — and dead.** `_apply_verdict_fail` (`reconciler.py:521`) and `_apply_verdict_partial` (`:600`) implement the full requeue-with-feedback path (stash `previous_output`, inject `verification_feedback` into `input_context`, increment `attempt_number`, transition to RETRYING) — and have **zero production callers**. The only references are `tests/test_mission_retry_feeds_critique.py`, which statically AST-inspects the handler bodies to prove they are *shaped* correctly. The consumer side is already live too: `_prepare_task`'s revision-prompt path reads `verification_feedback` — but today only agent-error retries ever populate it.
- **Checkpoints do not exist at runtime.** `write_checkpoint` (`services/checkpoint_service.py:40`) has **zero callers**; `SessionCheckpoint` (`core/models/orchestration.py:535`) is a plain frozen dataclass (S3 blobs, **not** a DB table); `GET /{mission_id}/checkpoints` (`api/missions.py:1949`) always returns an empty list plus `run.checkpoint_count` — a column (`orchestration.py:112`) that nothing ever increments. Real recovery is coarse: a RUNNING task past the 300s stall threshold (`config.py:768`) is recovered to assigned and **re-runs from scratch** (tokens re-burned, partial tool work discarded). Critically, the existing checkpoint shape (per-verified-task S3 snapshots) would only ever resume *from the last completed task* — which the in-DB stall-recovery already does for free — so wiring it buys almost nothing over today's behaviour. True in-flight resume needs a different mechanism entirely (see S2 + Q1).
- **Missions park at a one-shot approval — and the inbox that exists can't see them.** The default policy is `always_ask` (`core/services/approval_policy.py:42-47`, DEFAULTS); a parked plan transitions to AWAITING_APPROVAL and fires exactly **one** `mission_plan_ready · action_required` notification (`coordinator_service.py:2401,2413,2419`). The tick loop only processes RUNNING runs (`:1262`), so a parked run is invisible to the coordinator forever; the only auto-exit is the opt-in `check_approval_countdowns` sweep (`:2438`, wired at `:1290`), which nothing sets by default. There is **no re-notify, no reminder, no default expiry** (grep-confirmed absent).
- **The approvals inbox is real — and grants-only.** Wave-2 shipped `ApprovalsInbox` (`frontend/components/command-center/governance/approvals-inbox.tsx`, PRD-196 S1 / P2-15), mounted in the Command Center governance tab (`governance-tab.tsx:33`), fed by `GET /api/v1/approval-grants` via `useApprovalGrants` (`api-client.ts:2117`). It aggregates only `ApprovalGrant` rows (`core/models/approval_grants.py:58`) — the durable board/tool grants. Parked *missions* are a separate plane, decided only through the mission-detail approval bar (`mission-detail-page.tsx:391-392`) and the in-chat card (`chat.tsx:203`, PRD-163). The front door exists; the 47% aren't behind it.
- **The approve/edit/reject APIs already exist.** `POST /api/missions/{id}/approve` (`api/missions.py:1270`), `reject` (`:1316`), `PATCH /{id}/plan` (`:1229`, pure `apply_plan_task_edits`), `import-plan` (`:442`), and the state-filtered list `GET /api/missions?state=awaiting_approval` (`:515-517`) — the inbox extension composes these, no new route required.

## 4. Stories (test-first; CI is the only gate — no local runs)

### S1 · Make the cross-model judge gate once — S · _missions-orchestration C.3/J2_
Change the reconciler's always-VERIFIED block (`reconciler.py:457-479`) so a **FAIL** verdict routes through the already-written `_apply_verdict_fail` (`:521`) — requeue the task once with the verifier's feedback (the handler already stashes `previous_output` and injects `verification_feedback` into `input_context`; the `_prepare_task` revision prompt already consumes it), capped at a new `COORDINATOR_MAX_VERIFICATION_RETRIES = 1` (in `config.py`, alongside the existing thresholds). At the cap, or for **PARTIAL**, keep today's advisory behaviour (transition to VERIFIED, feedback annotated in `output_metadata`) — PARTIAL churn is the documented token-burn risk. Reuse the `required_sections` synthesis carve-out (`:365-371`) so the retry can never fire on heading-name guessing (the scar tissue that caused the original retreat). Empty output (`verification.py:385`) becomes the highest-value catch: it now requeues once instead of flowing into synthesis.
**Test:** flip `tests/test_mission_retry_feeds_critique.py` from AST-static to behavioural — mock `verify_task`→FAIL, assert the task requeues once (RETRYING, `attempt_number+1`, `input_context` carries `verification_feedback` + `previous_output`), then VERIFIED-with-annotation at the cap; mock→PARTIAL asserts advisory pass-through unchanged; mock→empty-output asserts one requeue. Pure — mock `verify_task` + session at the boundary.
**Notes:** Gate FAIL only, cap 1 — this is the single lever on client-visible output quality without re-opening the retry-storm the advisory retreat closed. No `os.getenv` outside `config.py`.

### S2 · Delete the decorative checkpoint apparatus — S · _missions-orchestration C.5/J3_
Remove `services/checkpoint_service.py` (`write_checkpoint` + `list_checkpoints`, zero real callers), the `SessionCheckpoint` dataclass (`core/models/orchestration.py:535`), the `GET /{mission_id}/checkpoints` route (`api/missions.py:1949`), and the `checkpoint_count` column (`orchestration.py:112`, drop migration). Strip the PRD-123 Pattern #8 "checkpoint after each verified task for crash recovery" claims from the coordinator/service docstrings — the honest state is that stall-recovery restarts the task, and the UI stops shipping an endpoint that always returns `[]` (a support-ticket factory). **This is deletion, not descope:** it removes a misleading surface. Whether to *also* build true in-flight resume (tool-boundary transcript persisted on `OrchestrationTask`, replayed on stall-recovery) in this PRD is a genuine scope fork — surfaced as Q1, not silently taken either way (§12).
**Test:** `test_no_checkpoint_service_imports` (source-grep guard, PRD-185 S5 shape — repoint in the same commit the symbols move); `test_checkpoints_route_removed` (the app no longer exposes `GET /{id}/checkpoints`). Pure.
**Notes:** Deletion-led, no `_legacy` shim (§5). The drop-column migration self-applies on Railway (`alembic upgrade heads` on boot). No data migration — checkpoints were S3 blobs never written.

### S3 · Surface parked missions in the approvals inbox + coordinator re-notify sweep — M · _missions-orchestration C.1/J1_
**Frontend:** extend `ApprovalsInbox` (`approvals-inbox.tsx`) to aggregate a second pending source — `awaiting_approval` missions from the existing `GET /api/missions?state=awaiting_approval` — into the same Pending rail as durable grants, each showing subject, estimated cost (already priced on the plan), age of the request, and inline **approve / edit / reject** wired to the existing `POST /api/missions/{id}/approve|reject` and `PATCH /{id}/plan`. Reuse the existing `GrantCard` presentation and `oversightTierLabel`; do not fork a rival card. **Backend/coordinator:** add an awaiting-approval **re-notify + optional expiry sweep** beside `check_approval_countdowns` in the tick (`coordinator_service.py:1288-1290`) — re-dispatch the `mission_plan_ready` notification after a configurable reminder interval (`config.py`) so a parked plan re-pings, and (per policy) auto-cancel or auto-proceed past a max-age. The default approval posture (`always_ask`) stays as-is unless Gerard changes it (Q2).
**Test:** frontend — extend `__tests__/governance-approvals-inbox.test.tsx`: mock the missions query returning an `awaiting_approval` mission, assert it renders in Pending with approve/edit/reject actions calling the mission APIs. Backend — `test_approval_renotify_sweep`: a parked run older than the reminder interval gets a re-dispatched notification; a fresh one does not; the sweep never touches non-AWAITING runs. Pure/mocked.
**Notes:** No new backend route under this mechanism (Q4) — so `orchestrator/reports/route-manifest.json` is untouched; if the aggregation is instead done via a new endpoint, that manifest **must** be updated (route-contract CI lane). This story un-parks the 47% and is the highest-impact of the three.

## 7. Baseline capture / measurement — freeze the funnel, then measure the deltas

This PRD moves three numbers that all start at a known, frozen value. Capture them **before any S-story**, from existing tables:

1. **Approval-parked share** — `% of missions in awaiting_approval` = **47% today** (8 of 17 all-time; some parked since April), plus **median time-to-approval: unbounded** and **0 missions created in the last 21 days, 1/21 workspaces ever active**. Freeze as the pre-state for S3.
2. **Judge gate counts** — verdicts are already persisted in every `TASK_VERIFICATION_COMPLETED` event payload, so first-pass PASS/FAIL/PARTIAL rates are extractable now; **blocks/requeues today = 0** (the gate acts on nothing). Freeze the first-pass PASS rate as the S1 baseline.
3. **Resume success rate = 0** — `write_checkpoint` never runs; every stall-recovery is a full restart (`config.py:768`). This is the S2 pre-state (and the Q1 evidence).

**Success = the measured delta:**
- Approval conversion: parked-share **down** and a non-zero count of missions approved *from the inbox* (was: unreachable except via the detail page) — the single number to move first.
- Verification: requeue count **> 0** on FAIL, with a re-verify PASS-rate on requeued tasks (was: 0 gating, judge tokens bought only annotations); empty-output-into-synthesis **eliminated**.
- Resume honesty: the checkpoint apparatus **gone** (endpoint no longer returns `[]`); the docstrings no longer claim recovery the runtime doesn't do. Real in-flight resume remains **0** until Q1's trigger-gated build (measured, not hidden).

*(No offline gold set is needed — for this module the funnel is the eval, per the dossier §G. Freezing it now also serves P2-20's context-trace work, which reads the same events.)*

## 8. Open questions — Gerard's call (decide, don't let me defer — CLAUDE.md §12)

1. **Real in-flight resume: build now, or gate on the named escalation trigger?** S2 deletes the *decorative* checkpoints (in scope, done). True resume — persist each task's tool-loop transcript at tool-call boundaries on `OrchestrationTask` and replay on stall-recovery so crash = *continue*, not *restart* — is a distinct **M** build that touches the shared `AgentFactory.execute_with_prompt` executor (the same engine chat uses). **Recommendation: do not build it in this PRD.** The dossier's §E.4 names the trigger explicitly — *multi-hour client DAGs with an SLA where re-running a half-finished task is unacceptable* — and the pilot has not hit it (2 completed missions all-time, rare crashes, cost of a re-burn = "some re-burned tokens"). Touching the shared executor for a not-yet-needed capability is the wrong trade now. **This is a surfaced fork, not a settled deferral** — if you want real resume in this PRD, it becomes a fourth story.
2. **Flip the default approval posture?** The single biggest lever on the 47% is the `always_ask` default (`approval_policy.py:47`). **Recommendation (your call per the dossier):** default `auto_below_budget` with a small ceiling + a short countdown for cheap plans, so trivial missions self-proceed while priced/expensive ones still park. This changes autonomy behaviour, so it is explicitly yours to set — S3 makes parked missions *reachable* either way.
3. **Gate FAIL only, or also PARTIAL?** **Recommendation: FAIL-only requeue, PARTIAL stays advisory.** The `required_sections` carve-outs (`reconciler.py:365-371`) are scar tissue from a PARTIAL-driven retry storm; gating PARTIAL re-opens exactly that. Confirm FAIL-only + cap 1.
4. **Inbox aggregation mechanism.** **Recommendation: client-compose** the existing `GET /api/missions?state=awaiting_approval` inside `ApprovalsInbox` (no new route, no manifest change, least risk). **Alternative:** have the coordinator mint an `ApprovalGrant` when a mission parks, unifying the data plane behind the one endpoint — cleaner long-term but it double-writes the mission approval flow and changes `approve` semantics. Which posture?
5. **Re-notify cadence / expiry policy for parked missions.** Proposal: re-notify once per 24h, auto-cancel (or auto-proceed per policy) at a 7-day max-age, both configurable in `config.py`. Adjust the interval, the terminal action, and whether expiry is on by default.
