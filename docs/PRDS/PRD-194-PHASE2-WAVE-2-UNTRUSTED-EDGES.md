## Overview

The security appendix's one-line verdict on the whole platform is **"careful engineering, wired but not armed"** (`security-hardening-appendix.md` §0). The hard, easy-to-get-wrong primitives — fail-closed tenant resolution, server-minted actor identity, a Fernet credential store, SSRF-blocked rendering — are done well and credited (§7). What is missing is **enforcement-by-default at the untrusted edges**: the three surfaces reachable by parties the platform does not control — the open internet (storefront widget), external platforms and any URL-poster (channels/webhooks), and third-party SaaS events (Composio). Today each one **fails open** in its resting state.

This PRD arms those three edges. It is the **P2-13** leg of Wave 2 and folds in the security appendix's **top-3 risks #1 and #3** (webhook trust, widget edges) plus the **§1.4.a** destructive-gate feeder defect:

- **Webhooks (§1.1, CRITICAL).** Three inbound lanes turn an unauthenticated HTTP POST into a real agent or playbook run. The Composio trigger webhook *logs and proceeds* on a V3 signature mismatch (`api/composio.py:630`) and on the verification exception (`:632`), and runs no verification at all when signature headers are absent (the whole block is gated on `if webhook_secret and v3_signature:` at `:618`). The channels and playbook lanes skip HMAC when no signature header is present (`webhooks.py:67-68`; `workflow_recipes.py`). A forged Jira/agentic event dispatches a real agent or recipe as a background task (`api/composio.py:771-786`). The GitHub lane already does it right — mandatory HMAC, 401 on missing/bad (`github_webhooks.py:60-70`) — **its posture is the template.**
- **Storefront widget (§1.2, HIGH).** The only surface exposed to arbitrary browsers has three compounding fail-open defaults: a public `ak_pub_` key **skips the origin check when `Origin`/`Referer` is absent** (`api/widgets/auth.py:182-183`) — the fail-*open* direction on the key type whose entire security model *is* the origin lock; CORS **allows all origins when the allowlist is unset** (`api/widgets/cors.py:48`), which is the default; and the rate limiter is **per-process and largely inert by its own docstring** (`api/widgets/rate_limit.py:90-98`). A scraped public key (they ship in page HTML by design) replays from anywhere, burning the merchant's LLM budget.
- **Composio destructive gate (§1.4.a, HIGH).** The daily classifier that is supposed to populate `composio_action_metadata` — the table backing the fail-closed destructive-action gate (F018) — **never writes a row**: `_get_all_enabled_apps()` returns a hardcoded 8-app placeholder (`composio_action_sync.py:336-340`) and `_fetch_app_actions` `await`s a **synchronous** method (`:207` calling `core/composio/client.py:775`, a plain `def` returning a list) → `TypeError` for every app, caught and logged as a failed sync. So the gate operates permanently on an 8-keyword *intent-text* heuristic — a destructive action under neutral wording ("issue a refund", "create a 10% discount") is exactly what slips through, **forever, not just at cold-start.**

Judged against the **North Star** — *does this make Auto more autonomously capable and the agents' output higher-quality for clients?* — the honest framing is that these are not *capability* additions; they are the **enabling guardrails without which client-facing autonomy cannot be turned on safely.** Auto cannot be trusted with autonomous, client-visible action across a webhook, a storefront, or a third-party action lane until the inbound leg can trust what it receives, the internet-facing plane fails closed, and the destructive gate can actually see. This is the fortnight that converts "wired but not armed" into "armed at the edges that face customers first."

**PILOT lens (locked):** the pilot's real traffic is low today — channels has 2 connections ever (`channels.md` C1), the widget's live traffic could not be banked in the census (`storefront-widget.md` §C.4), and Composio shows 13 live trigger dead-letters (real, but modest). **Low traffic is not a deferral reason and is not a mitigation.** These are the exact surfaces the deep review folds into Wave 2 *"because they must precede the widget and channels going hot with real customers, not because current traffic is high"* (`PLATFORM_MODULE_DEEP_REVIEW_2026-07-04.md` §239). Every finding here is an **architecture/wiring defect verified in live code paths** — a fail-open default, a deleted-guard fall-through, a dead feeder — **not** cold-start emptiness (`feedback-pilot-usage-not-quality-signal`). The exposure window is small *today*; it goes hot the day the first real customer's storefront or channel does. We arm before scale, not after.

### Interaction with PRD-189 (compose, do not collide)

PRD-189 S3 (PR #528) added a **per-workspace debounce + already-running guard + coalescing** to the **Shopify catalog** webhook at `api/shopify.py:355` (`POST /events`, `forward_event`), so a bulk merchant edit emitting N webhooks produces **one** re-sync instead of N (`PRD-189-PHASE2-WAVE-1-SHOPIFY-INTEGRITY.md` S3). **#528 is now merged to `origin/main` (`8e68b0157`)** — note it is **not** yet in this worktree's base (`d26ce039d`, the PRD-187 memory merge); when `feat/p2-w2-untrusted-edges` is cut fresh from `origin/main` it will include PRD-189 S3.

The interaction is **complementary, not conflicting**, and on **different endpoints**:

- PRD-189 S3 debounces the **Shopify internal** `/events` lane (`api/shopify.py`, auth = `_verify_internal_key`) — it coalesces *distinct* catalog events in a burst window.
- This PRD's **S2** adds a **replay/dedup guard** to the **three external** webhook lanes (Composio `/webhook`, workspace `/ws/{key}`, recipe `/recipe/{id}`) — it rejects *the same* event redelivered (retry-replay), keyed on `webhook-id`/`event_id`.

They touch **disjoint files** (`api/shopify.py` vs. `api/composio.py` / `api/webhooks.py` / `api/workflow_recipes.py`) and solve adjacent halves of the same "don't double-execute on a burst" problem. **Design S2 to compose:** its dedup key is per-lane (`platform + event_id`), it does not touch the Shopify path, and it is the durable (store-backed) sibling of PRD-189's in-process debounce. If a later wave consolidates both into one webhook-ingest dedup surface (the appendix's §1.3.c "unique on `platform + event_id`" is the same idea), that is a **P2-25 topology decision, surfaced not pre-empted** — S2 ships the external-lane guard now without blocking it.

## Success metrics (the definition of "armed at the edges")

- **Every external webhook lane rejects a forged event** — a mismatched or absent-when-required signature returns 401 and **dispatches nothing**, on Composio V3, workspace, and recipe lanes; Slack inbound is actually signature-verified; GitHub stays correct (S1).
- **A redelivered event is a no-op** — the same `webhook-id`/`event_id` executes once; a stale-timestamp replay is rejected; the Shopify `/events` debounce (PRD-189 S3) is untouched (S2).
- **The widget public key fails closed** — an `ak_pub_` key with no origin is denied; an empty-permission widget key is denied; the real browser path from a listed origin still works (S3).
- **The public plane is not default-open in production** — a `saas` boot with an empty widget allowlist fails (or loud-degrades, per the chosen posture); dev keeps its permissive default (S4).
- **Rate limiting actually bites** — the widget/callback limiter is shared across workers, gates the first request, and enforces a per-IP ceiling on the two money-spending endpoints (S5).
- **The destructive gate can see** — `composio_action_metadata` is populated for connected apps by the daily sync; an empty table for connected apps fails loudly; the gate stops running permanently on the 8-keyword heuristic (S6).

## Gerard's call (open questions — surfaced, not deferred per CLAUDE.md §12)

These are **decisions**, not descopes. Each blocks or shapes a story and is yours to make:

1. **CORS allowlist enforcement posture (S4) — boot-abort vs. loud-degrade.** The strict, in-tree-consistent reading (matching `SHOPIFY_INTERNAL_API_KEY` and the Clerk edition guard) is: a `saas` boot with an empty `WIDGET_ORIGIN_ALLOWLIST` **aborts boot**. The softer reading is: **log a loud error and default-deny** (serve no permissive CORS) without bricking the deploy. Boot-abort is safest but can take a running production down on a bad env push; loud-degrade keeps the service up but relies on someone reading logs. **Default in this PRD is boot-abort in saas** (consistency with the two existing guards) — say the word if you want loud-degrade instead.

2. **Widget public-key rotation comms (S3).** Denying public keys when `Origin`/`Referer` is absent is fail-closed-correct, but it **will break any existing integration that calls the widget from a non-browser context** (a merchant's server-side script omitting the header). Before this ships to the live `inbuilduk` storefront: do we (a) audit current `ak_pub_` usage for header-less callers, (b) send a rotation/heads-up note to affected merchants, and (c) offer a server key (`ak_srv_`) for legitimate server-side callers? The code change is small; the **rollout/comms** is the risk. Your call on sequencing the enforcement flip vs. the merchant notice.

3. **S2 dedup store — Postgres table vs. Redis TTL.** A `webhook_event` table (`UNIQUE(platform, event_id)`) is durable and auditable but adds a migration + a row per event; Redis `SETNX` with a TTL (reusing `core/redis/client.py`) is lighter and self-expiring but loses the audit trail and depends on Redis being up. Both compose with PRD-189. **Lean:** Redis for the replay/dedup guard (ephemeral by nature), Postgres only if you want the audit trail. Your call.

4. **§1.4.b — route the Composio chat shortcut through the executor chokepoint (NOT in this PRD).** The preferred chat execution path (`consumers/chatbot/service.py` → raw `client.execute_action`) bypasses the per-action scope check, the destructive gate, file-upload resolution, **and** `ToolExecutionLog` telemetry — so even after S6 fixes the feeder, the gate is still bypassed on its highest-volume path. This is the single structural fix that restores enforcement + telemetry everywhere, **but it overlaps P2-11 (§2.2) and the tool-runtime dossier J-2** and is a bigger change than a feeder fix. **I scoped it out of S6 to respect the P2-13 line — confirm you want it in P2-11, or say the word and I fold it in here.**

5. **Adjacent channels-hardening (§1.3.a / §1.3.b) — in or out?** The channels lane has two more trust gaps the P2-13 line does *not* name: **§1.3.a** "whoever messages the bot is the workspace" (no inbound-sender allowlist/pairing — `ingestors/webhook.py:101`) and **§1.3.b** credentials stored plaintext while the schema comments claim encryption (`core/models/channels.py:26` vs. `api/channels.py:362`). Both are real and both bite the day a channel goes live. They are **out of scope as written** (P2-13 = webhook reject-on-mismatch + widget + Composio), but flagged here rather than silently dropped — fold into this wave, or track as a separate channels-trust PRD?
