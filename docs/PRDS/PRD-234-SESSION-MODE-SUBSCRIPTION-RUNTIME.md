## Framing (CLAUDE.md §3)

**Extension — connect the manager plane that already exists to a new, local-only runtime module.** Automatos already has the board, tickets, the dispatch contract (PRD-224/226), questions (225/229), board events (227), fleet (228), memory and Deliverables. New: a **CLI host** process on the user's machine that runs the user's own coding CLIs as *supervised interactive sessions*, a claim/heartbeat/result contract on the backend, provider adapters as data, and the honesty states around them. Code Canvas is **not** touched. **Build size:** L (S1b is the substance). **Risk:** Medium-High — a second execution runtime, and a queue that runs commands on the user's machine; the terms invariant (§Terms) and the security model (§Design 6) are what keep it honest.

## Overview

Automatos is a **hybrid manager**: `runtime: api` is today's path (the factory; BYOK/OpenRouter, 400+ models) and `runtime: cli` is this PRD — an agent's ticket executes as **the user's own Claude Code session on their machine, under their own login**, with Automatos above it as manager: Auto assigns the ticket and writes the dispatch contract, the board tracks it, memory and Deliverables work as before. Auto and any agent may stay on the API ("DeepSeek reading my mail, Kimi writing reports") while Claude Code sessions do the code work — one board, one manager, mixed runtimes (owner, 2026-08-30). Claude Code first, Codex second, the rest as community adapters.

The reference implementation is **munder-difflin** (MIT, read as code @ fc436bd; `src/` unchanged at HEAD cc741fe3). Adopted: interactive sessions on the user's own CLI login, hooks as the lifecycle channel, the transcript as the record, providers as data, fail loudly, never touch credentials, pre-accept only what the user has already decided. Not adopted: PTY typing and idle heuristics (our sessions are per-ticket turns, so they are not needed), the file mailbox, the Electron UI, auto-installing CLIs.

## Terms — how session mode stays inside Anthropic's rules (the invariant)

**What Anthropic has written (quoted; sources in Traceability):**
- *"Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow."* — and in the same section — *"Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code."* Conditions: *"The Claude Code binary must not be modified"*; usage limits *"assume ordinary, individual usage of Claude Code and the Agent SDK"*; enforcement *"without prior notice"*. (Claude Code docs, Legal and compliance)
- *"Applications that misrepresent their identity to Anthropic's servers, attempt to route third-party traffic against subscription limits, or otherwise violate applicable terms or policies are prohibited."* (Help Center, 2026-05-19)
- Metering: *"Using Claude Code in the terminal or your IDE continues to use your subscription usage limits exactly as before."* The announced move of `claude -p` and Agent SDK usage to a separate monthly credit at API rates was **paused 2026-06-15** (*"For now, nothing has changed"*) — paused, not withdrawn. (Help Center, updated 2026-06-16)

**The invariant (every line has a source guard in S1b):**
1. **Unmodified binary.** The host runs the `claude` the user installed (login-shell `PATH`); never a bundled, patched or proxied one.
2. **Login only through Anthropic's own flow.** The user runs `claude login` themselves. The host never reads, copies, forwards or sets a credential: no `~/.claude/.credentials*`, no keychain, no `CLAUDE_CODE_OAUTH_TOKEN` set by us, no `ANTHROPIC_API_KEY` in a session's environment (v1), never `--bare` (it disables OAuth by design).
3. **No identity games.** No `CLAUDE_CODE_ENTRYPOINT`, no user-agent changes, no `ANTHROPIC_BASE_URL` redirection, no traffic proxying.
4. **Interactive sessions for agent work.** Agent turns run Claude Code's normal interactive mode (the surface Anthropic keeps on the plan); `claude -p` and the Agent SDK are **not** used for agent work in v1.
5. **One user, one machine.** The host serves the local instance's single operator; SaaS never runs it (boot gate). Automatos never pays for, resells or intermediates anyone's usage.
6. **Concurrency is the user's choice, stated honestly.** No cap in software (owner, 2026-08-30); the docs quote the "ordinary, individual usage" line so the user sets it knowing the terms.

The same posture applies to Codex: OpenAI documents `codex exec` for non-interactive use under a ChatGPT-plan login and has published no rule on third-party orchestration; the adapter reads nothing from `$CODEX_HOME` — the CLI does. This section describes the design, not legal advice.

**Non-goals (owner decisions):** no SaaS-side session mode; no credential handling of any kind; no auto-installing CLIs (honest "install X" hints); no `-p`/SDK agent work; no multi-user hosts; teams connecting local hosts via the SaaS = future funnel; Auto on the subscription = a later story (Q6).

## Design (one page)

**1. Vocabulary.** *CLI host* — the local Python process (`services/cli-host/`, `python -m automatos_cli_host`, `make cli-host`). *Adapter* — one provider's data row: binary, argv builder, driver, prompt delivery, event mapping, resume, auth check, install hint. *Driver* — how a process is run: `interactive-pty` (Claude) or `headless-json` (Codex). *Structured channel* — what every driver must deliver: a session id, lifecycle events, a result (final text, files touched, usage, exit reason). The word "session" already names Code Canvas sessions in code, so the runtime value is `cli`; "Session Mode" stays the feature's name.

**2. A turn (Claude adapter).**
1. The backend pre-assigns a session id and hands the host a claimed ticket: contract, `cwd`, agent config (`provider`, `model`, allowlist), attempt number.
2. The host prepares the directory (registered directory or `./workspaces/<id>`; `--worktree` for git repositories), writes `<cwd>/.automatos/ticket-<id>.md` (the contract; durable, user-readable) and a per-session `settings.json` whose hooks all call one shim that forwards the payload to the host's loopback socket; if the directory is not yet trusted it records the user's registration decision where Claude Code reads it (`~/.claude.json` → `projects[cwd].hasTrustDialogAccepted`, backup-first, atomic, nothing else in that file).
3. The host spawns, under a pseudo-terminal it only drains: `claude --session-id <id> --permission-mode acceptEdits --allowedTools <allowlist> --append-system-prompt-file <soul+doctrine> --settings <file> --setting-sources user --strict-mcp-config [--mcp-config <curated>] --model <alias> --name "automatos #<ticket>" [--worktree <name>] "Work the ticket in .automatos/ticket-<id>.md"`. The positional prompt is a short pointer (nothing sensitive in argv); the contract body is also injected as `additionalContext` from the `UserPromptSubmit` hook. Continuation, redo and answered questions respawn the same way with `--resume <id>` and the next pointer prompt.
4. Hooks carry the turn: `PreToolUse` is the policy gate (allow inside the allowlist; deny with a reason; **hold** while the approvals inbox answers — never `ask`, nobody watches the TUI); `PostToolUse` on Edit/Write/MultiEdit = files touched; `Notification` text = needs-a-human / limit reached; `Stop` = turn finished; `PreCompact`/`PostCompact` exempt the loop guards.
5. On `Stop` the host reads the transcript at the `transcript_path` the hooks reported (final assistant text, per-message usage and model), terminates the process (SIGTERM, then kill), and posts the result. Cancel = the same signal at any time.

No typing into the TUI, no output parsing; the pty exists only because interactive mode needs one. This is munder's mechanism minus the parts a per-ticket turn does not need.

**3. Environment rules (host → session).** Inherit the user's login-shell environment (munder `shellEnv.ts` PATH probe), then: strip `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL` and every `CLAUDE_*`/`CLAUDECODE*` session marker (an inherited `CLAUDE_CODE_CHILD_SESSION` silently disables transcript saving and breaks `--resume` — munder `ptyEnv.ts:29-44`; this host will often be started from inside a Claude Code terminal); keep the operator's own configuration keys (`CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`) — the host never sets them. Never `--bare`; never override `CLAUDE_CONFIG_DIR`.

**4. Policy, denials, approvals.** v1 policy = `acceptEdits` inside the working directory + a Bash allowlist (git read-only verbs, the project's test/build commands from agent config); everything else is denied with a reason unless the agent config marks it *ask*, in which case the `PreToolUse` hook holds while `create_grant(kind=tool_call)` (PRD-193) puts the request in the approvals inbox — answered there or in Telegram, timed out to **deny** (fail closed). Any denial during a turn lands the ticket in `review`, never auto-`done`. Sessions never push (allowlist), the manager integrates.

**5. The board is the queue.** The dispatcher's `claim_tasks` excludes tickets whose agent runtime is `cli`; a paired host claims them through `POST /api/v1/cli-hosts/{host}/claim` (same statement, runtime filter) and renews the lease with every event batch. `_launch_task_execution` returns without running for a `cli` agent (task stays `assigned`, `notify_task_available`) — one check covering all four launch sites. `POST …/tasks/{id}/events` (hook events; its response carries control: cancel, approval decisions), `POST …/tasks/{id}/result` (idempotent per `(task_id, attempt)`), `POST …/heartbeat` (capabilities + running sessions → reconciliation). Host death: the lease lapses, the sweeper requeues as today; on reconnect the host reports sessions still alive and the backend re-attaches instead of re-dispatching; on restart the host kills its own orphans first (pid file). One migration, two additive objects: the `cli_hosts` table (pairing state, host-token digest, capabilities, last seen) and a nullable JSONB column `board_tasks.runtime_ref` (session id, host id, attempt, provider, cwd, transcript path, exit reason).

**6. Security model.** Threat: the queue runs commands on the user's machine, so whoever can enqueue a ticket for a `cli` agent has a shell there; today anyone reaching port 8000 on the LAN is the local edition's `super_admin`. Controls (all S1a/S1b): (a) **pairing** — Settings → Session mode shows a one-time code (10 min TTL); `make cli-host PAIR=<code>` exchanges it for a host token stored `0600` in `~/.automatos/cli-host.json`, required on every host call, never an empty default; (b) **loopback bind by default** in the local edition — compose publishes backend, Redis, Postgres and MinIO on `${BIND_ADDRESS:-127.0.0.1}`; `BIND_ADDRESS=0.0.0.0` is a documented, deliberate choice; (c) **directory allowlist on both sides** — registered directories are stored in the backend *and* in the host's own allowlist file; the host refuses any `cwd` outside its list, so a compromised backend cannot point it at `~`; (d) **config surface decided** — `--setting-sources user` (the operator's own policies apply; a cloned repo's hooks and MCP servers do not) and `--strict-mcp-config`; (e) **no push** through the allowlist; (f) **HTTP-only host transport** — one port, one token, no Redis on the host. Source guards pin (a), (d) and the §Terms invariant.

What the run settled: (1) the positional pointer prompt with `--session-id` works in interactive mode; (2) the keychain-backed login works when the parent is the host process, not a terminal; (3) `--worktree` needs no extra trust decision — recording trust for the registered directory was enough; (4) the board's approval policy (`always_ask` on this workspace) applies to `cli` tickets exactly as to API tickets — the claim parks the ticket `blocked` behind a grant, the operator approves in the Command Centre, the host claims it again (the host now logs a parked ticket once instead of polling in silence); (5) `ANTHROPIC_API_KEY` was not set on the machine, so the sessions could only have used the owner's own login.
