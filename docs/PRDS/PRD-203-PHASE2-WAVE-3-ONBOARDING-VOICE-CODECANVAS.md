## 1. What this is

Three **small unblocks**, not three new features. Each of onboarding intake, streaming voice, and the code-canvas prompt loop is a surface that is **already built and architecturally sound**, but is not wired to a live entry point — so in production it has run for **nobody**: `business_profiles` is absent from the 152-table census, `voice_profiles` is absent, `task_executions` holds 9 lifetime rows and 0 canvas sessions. In every case the gap between "dead code" and "live capability" is a **single deliberate act**: an uncommented CTA, a vendor swap behind an existing seam, and a `client.query(...)` wire. This PRD does those three acts (plus the minimum that makes each one honestly *work* end-to-end and *measurable*), and nothing more.

**Framing (CLAUDE.md §3):** all three are **Extension / activation**, not net-new. The engines exist and are clean (async intake pipeline with a boot reaper; a voice I/O skin that correctly reuses the one agent loop; a versioned, drift-guarded canvas event stream with diff-approval + commit already wired). What is missing on each is the *first mile* — the ingress that turns the assembled machine on. The net-new code is tiny: one uncommented block, one vendor adapter behind the existing `VoiceServiceClient` contract, one worker message route + `client.query` call, plus the intake surface's **first tests**.

**Build size:** M overall (mostly wiring + the intake test suite; the archetype framework is the one M-sized piece) · **Risk:** Low-to-Medium — each surface ships independently, and "dark → exercised" is a strict improvement over "never ran." The one genuine risk is the voice vendor fork (a cross-repo delete) and the canvas prompt loop touching an unattended-execution lane — both are surfaced to Gerard in §8, not pre-decided.

**Why now / why measured:** the review's whole thesis is that these are *unproven, not broken* (all three score 2/5 on delivered capability, 4/5 on architecture). The only way to learn whether they earn their place is to **turn them on and watch a number move** — from 0 intake sessions to a first-run funnel, from 0 voice turns to a latency-and-truncation signal, from 0 canvas runs to a prompt→work→approve→commit funnel. Success here is not "a better feature" — it is **a surface that goes from dead to exercised**, so the next decision about it is made on evidence.

### 2B · Streaming voice — a correct, cold I/O skin with the worst-case latency posture

- **Voice reuses the one agent loop (this is the good part).** `POST /api/chat/voice` (`orchestrator/api/chat_voice.py:155`) is gated by `config.VOICE_ENABLED` (default **true**, `config.py:1160`), does a live pod health check that fails honestly with a 503 (`chat_voice.py:187,191`), then routes the transcript through `_collect_streaming_response` (`:33`, called `:231`) — the *same* `AutoBrain` routing + `StreamingChatService` as text chat. Voice inherits agent selection, tools, memory, context. The design intent — "an I/O skin over the proven loop, not a parallel stack" — is faithfully implemented. `/api/chat/voice` is already in the route-manifest; routers registered at `router_manifest.py:68-69`.
- **But it never streams, and it truncates.** `_collect_streaming_response` **collects the entire** agent stream into a string before a single TTS byte is requested — so perceived latency = STT + full LLM (incl. tool round-trips) + full TTS + S3 upload, serially. Then the spoken reply is **hard-cut at ~500 chars** (`chat_voice.py:287`) with no "…see text" cue, and every turn returns `audio_base64` **and** an S3 upload **and** a presigned URL (`:338`) — redundant work on every turn.
- **The transport is behind a clean, swappable seam.** `orchestrator/modules/voice/client.py:35` `VoiceServiceClient` speaks an OpenAI-audio-compatible HTTP contract (`transcribe`→`/v1/audio/transcriptions`, `synthesize`→`/v1/audio/speech`, `health`) to the self-hosted pod. **This is exactly where a hosted transport (Vapi/Retell) lands** — the contract is already the integration boundary. The live-call Path-2 pipeline (Pipecat/VAD) lives in the sibling `automatos-voice` repo (not read here) and is the piece a vendor adoption would retire.
- **It is cold and unmeasured.** `voice_profiles` is absent from the census; voice writes **no** voice-specific telemetry (only ephemeral log lines carry `stt_latency_ms`/`tts_latency_ms`). "Is voice any good?" is unanswerable from data — the pod was built to working order in Q1 and then idled (`config.py:1162` `AUTO_VOICE_PROVIDER=chatterbox`).

### 2C · Code-canvas — well-built scaffolding that cannot yet be instructed

- **Nothing ever sends the agent a turn.** `services/workspace-worker/canvas_session_service.py:289` `start_session(self, workspace_id)` takes **only** a workspace id (no prompt), connects a real `ClaudeSDKClient` (`:350`), and pumps *received* messages (`_pump:452` — `client.receive_messages()` only). A grep for `.query(` / `user_message` / `send` / `send_message` across `services/workspace-worker/*.py` returns **nothing but comments**. A streaming-mode SDK client does nothing until it receives a query — so a started session **connects and idles**. The PRD-170 headline demo ("*add validation to X and push*" → streamed work) is unreachable through the shipped surface.
- **The gap is end-to-end, four layers deep.** No worker send endpoint; no `WorkspaceClient` method (`orchestrator/core/workspace_client.py:56` exposes `canvas_session_start/status/stop/decide/auto_accept` — no `send`); no proxy route (`orchestrator/api/workspace_files.py` canvas routes are sessions/decision/auto-accept/events/commit-preview/commit — **no message route**); and the frontend `useCanvasSession.ts:116-119` exposes `start/stop/decide/setAutoAccept` with **no `send`**, beside a panel whose empty state literally reads *"Ask Auto to change this workspace"* (`CanvasSessionPanel.tsx:119`) — with no box to ask in.
- **Everything downstream is already wired to fire.** The versioned event stream (`canvas_events.py:34` `CANVAS_EVENT_SCHEMA_VERSION=1`, FE-mirrored + drift-guarded), diff-approval registry, and branch-per-session commit/push are built and tested. The first turn is the only missing link — every piece after it works.
- **The worker has no model credentials.** `docker-compose.yml:250-263` (the `workspace-worker` env block) sets DB/Redis/volume/quota vars and **no `ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN`** — only the *api* service gets a key (`:158`). `start_session` builds `ClaudeAgentOptions` with cwd/env/permission_mode/resume but no key. So even after the prompt wire lands, the SDK subprocess in the worker has no committed auth — a second end-to-end gap that must close in the same wave for the loop to actually run.
- **It is unrun.** 0 canvas sessions in production; the underlying compute substrate has 9 lifetime `task_executions`. Dark, cold, but — per the PILOT lens — not defective.

## 5. Sequencing

- **The three surfaces are fully independent — each ships alone and delivers its "dark → exercised" flip on its own.** There is no cross-surface dependency; they can be built in parallel or in any order, and any one can merge without the others.
- **Within onboarding:** O·S1 (CTA) and O·S2 (first tests) should land **together** — turning the path live and covering it in the same wave means the newly-exercised surface is not also the untested one. O·S3 (generalise) is independent and can follow, but the depth decision (§8-Qc) gates how much of it ships now.
- **Within voice:** V·S5 (truncation/triple-return) and V·S6 (telemetry) are **vendor-independent and land first** — they are pure correctness + the measurement instrument, and they make even the cold surface honest. V·S4 (streaming) is **gated on §8-Qa** (vendor identity / adopt-vs-self-host) and is the larger piece.
- **Within code-canvas:** C·S7 (prompt wire) and C·S8 (worker auth) are a **single indivisible unblock** — ship them together or the loop still cannot run.
- No migrations here except V·S6's `voice_turns` (if a new table is warranted after the §4 reuse check) and any O·S3 archetype seed data — both authored in-PR; the deploy entrypoint runs `alembic upgrade heads` on boot, so a merged migration self-applies.

## 8. Open questions — Gerard's call (decide, don't let me defer — CLAUDE.md §12)

The review states plainly that **voice and code-canvas scope decisions are Gerard's**. The three headline choices below are genuine forks, each with a recommendation — none is pre-decided, and none of the three surfaces is dropped on my initiative.

**(a) Voice transport — Vapi vs Retell vs stay self-hosted (the vendor fork).** V·S4 needs this decided before it can be built. **Recommendation: adopt a hosted transport — Retell or Vapi.** Both are explicitly LLM-agnostic (they call *your* endpoint via a custom-LLM webhook), both hit sub-600ms with real turn-taking/barge-in, and adopting one **deletes** the self-hosted GPU pod, the Pipecat pipeline, the VAD tuning, and the "pod is asleep" ops problem — while the deep Automatos agent (the one real differentiator) stays ours. Lean **Retell** if telephony/PSTN reach matters, **Vapi** if barge-in/endpointing quality leads. **Do not defer voice entirely** — even if the vendor decision waits, V·S5 (kill truncation) and V·S6 (telemetry) are cheap, vendor-independent, and make the cold surface honest and measurable now. *Alternative:* stay fully self-hosted (a hard data-residency/cost-at-scale constraint would justify it) — then V·S4 becomes sentence-streaming in the pod instead of a vendor swap. Which branch ships? *(My lean: adopt Retell/Vapi; the voice-native hard parts are not where Automatos should spend.)*

**(b) Code-canvas scope — minimal wire vs fuller prompt-loop.** **Recommendation: ship the minimal wire now (C·S7 + C·S8) and gate the fuller loop behind it proving the surface is used.** The minimal wire genuinely makes the canvas *work* — prompt → streamed turns → diff-approve → commit+push, all downstream already built — which is the "dead → live" flip this PRD is for.
