## Overview

The tool-runtime dossier's sharpest finding is that **the confirmation gate is a dead end — there is no way to say yes** (`tool-runtime.md` §C.2). Twelve platform actions are gated behind `requires_confirmation`; when one fires, the executor returns errors-as-data, S15 makes the ask legible to the model — and then nothing can ever *satisfy* it: the executor consults no token, no grant, no caller field (grep: no `user_confirmed`/`confirmation_token`/`confirmed=` anywhere in `modules/tools/` or `consumers/chatbot/` — re-confirmed in this worktree); the W11 `ApprovalGrant` surface is consumed only by the board-task subject; and the frontend has **zero** components handling `requires_confirmation` (grep over `frontend/` returns nothing, re-confirmed). When the user replies "yes, delete it," the retried call hits the same gate again. The **only** route through is the workspace-wide full-autonomy dial (`platform_executor.py:673-679`) — an all-or-nothing knob that *also silently elevates the agent to admin* as a side effect (`:677-679`). Supervised workspaces structurally cannot let Auto complete any destructive action, ever. The dossier calls this "the single sharpest autonomy ceiling in the module"; §6 calls the fix "the biggest single unlock for client-safe autonomous operation."

The competitive read (dossier §D.1/§E.1) says adopt the **pattern, not the product**: OpenAI's Agents SDK pauses the run, records an approval interruption, and resumes the same run on `state.approve(...)`; LangGraph persists the pending call and resumes on `Command(resume=…)`. Automatos already owns every part needed to build that shape in-house — and this is the load-bearing reuse finding of this PRD, **verified against the live tree, not the review's pinned one**: PRD-181 S2 shipped the grant substrate *tool-agnostic and beyond what the dossier credited* — `SUBJECT_TOOL_CALL` is already a defined subject kind (`core/models/approval_grants.py:55`), the model already carries `risk_tier`, `details` JSONB, and the hot lookup index (`:75,93,97`), and a complete lifecycle service already exists (`create_grant` / `find_pending_grant` / `find_active_grant` / `grant_grant` / `deny_grant` / `revoke_grant` / `is_authorising`, `core/services/approval_grants.py:43-171`) with a 24h TTL default in canonical config (`config.py:692`). PRD-163 shipped the exact in-chat approval card this needs — `MissionApprovalWidget` with AI-Act oversight fields, wired from `format_for_frontend` through `chat.tsx` (`result_formatter.py:771-791`, `chat.tsx:204-207`). And the board lane already demonstrates the full approve→resume loop: grant → un-block → `notify_task_available` re-queue (`api/approval_grants.py:142-160`). **Grep-proven delta: `ApprovalGrant` has *zero* references anywhere in `modules/tools/` or `modules/policy/`.** The gate and the grant substrate have never met. This PRD is the wiring between three already-built things, plus the one genuinely new seam: pause/resume for an interrupted tool execution.

Judged against the **North Star** — *does this make Auto more autonomously capable and the agents' output higher-quality for clients?* — this converts the 12 dead-end confirmation actions from "impossible unless full autonomy" into **supervised autonomy that completes**: Auto asks, a human taps approve on an in-chat card, the action executes and the run carries on — durable, scoped, expiring, revocable, audited. It also retires the perverse incentive the dead end creates today, where the only way to let Auto finish a job is to flip the dial that grants blanket admin. **No moat framing; no new capability invented** — the deliverable is that a supervised client workspace can finally say yes.

**PILOT lens (locked):** `approval_grants` has 0 rows ever and the confirmation-conversion funnel is structurally 0 — these are **not** cold-start numbers. The gate has no consult path and the card has no component *by construction* (grep-proven above), so the zeros are architecture findings squarely in scope; the funnel/latency numbers that follow the fix are pilot signals to watch, not targets to chase. See `feedback-pilot-usage-not-quality-signal`.

**Boundary with what's already built (do not redo):** PRD-163's mission approval flow stays exactly as is — missions keep their card, their `useApproveMission` PATCH, and their plan-edit path; this PRD *clones the presentation* for a different subject, it does not touch mission approval. PRD-181's grant model/service/API/migration are **reused, not re-authored** — no schema change, no new table, no new migration. The Command Center approvals **queue** (list/filter/audit UI over pending grants) is **P2-15's row in this same wave** (`§6`, governance dossier §I.1) — this PRD's human surface is the in-chat card; the pending `tool_call` grants it creates will appear in P2-15's queue for free via the existing list API (`GET /api/v1/approval-grants`, which today has zero frontend callers — this PRD's card hooks become the API's first consumer).

## Stories (test-first — write the failing test, make it green, refactor)

### S1 · Issue a durable grant at the ask — S · _tool-runtime J3/C.2 + PRD-181 reuse, P2-12_

When the confirmation gate fires, stop returning a dead-end ask: create (or reuse) a **pending** `ApprovalGrant` with subject `tool_call` and return the ask *with the grant attached*, so there is finally something a human can act on. One new shared helper module owns subject-key derivation + issue/consult so PRD-192's `ask` verdicts later reuse the identical seam.

**Files:** new `orchestrator/modules/tools/execution/tool_grants.py` (pure-ish helper: `tool_call_subject_id(workspace_id, action, params)` — deterministic hash of workspace + action + canonical **model-provided** params (hash *before* the server-side param injection at `platform_executor.py:867-888`, so the ask and the retry produce the same key); `issue_tool_grant(db, …)` wrapping `find_pending_grant`-then-`create_grant` (`core/services/approval_grants.py:114,43`) with `risk_tier` from `classify_action` (`modules/policy/policy_document.py:215-242`), `agent_id` from the server-minted identity (`exec_platform.py` strips caller-supplied identity — trust the runtime's), and `details` = `{params, params_hash, lane, conversation_id, turn_id, board_task_id?, action_description}` from `caller_context`); `modules/tools/discovery/platform_executor.py` (`:711-722` confirmation return and `:724-739` registry-miss return — call the helper, add `grant_id`, `risk_class`, and the `oversight_for_risk` fields to the returned dict).
**Test:** `test_ask_issues_pending_tool_grant` — a `requires_confirmation` action returns the ask **and** a pending grant scoped to (workspace, `tool_call`, deterministic subject_id, tool_name, risk_tier). `test_repeat_ask_reuses_pending_grant` — the same call asked twice yields **one** pending row (no grant spam). `test_deny_paths_issue_no_grant` — the su-gate and admin-deny returns create nothing (a deny is not an ask). `test_grant_issue_failure_still_asks` — if grant creation raises, the ask is still returned (fail-safe: the ask is the floor, never an exception, never an execution). All pure — in-memory session / mocked service at the boundary.
**Notes:** Generic by flag, not by list — any action carrying `requires_confirmation` (the 11 live ones, the registry-miss fail-closed path, the destructive backstop `:846-862`, and any future gated action) gets the loop with **zero per-action code**. No new config: TTL comes from the existing `APPROVAL_GRANT_TTL_SECONDS` (`config.py:692`) via `create_grant`'s default. The helper is deliberately subject-first so PRD-192 can route policy-plane `ask` verdicts through it (see Sequencing).

### S2 · Consume an authorising grant — the gate finally has a "yes" — S · _tool-runtime J3/C.2, P2-12_

Single consult point covers both the `platform_execute` meta-dispatch and direct `platform_*` calls (both funnel through `PlatformActionExecutor.execute`).

**Files:** `modules/tools/discovery/platform_executor.py` (`:711` — consult `tool_grants.consume_tool_grant(db, …)` before the ask; extend the autonomous-execution audit marking `:928-938` so a grant-authorised execution records `approved_via_grant_id`, distinct from "full-autonomy dial skipped the gate"); `modules/tools/execution/tool_grants.py` (`consume_tool_grant`: `find_active_grant` (`core/services/approval_grants.py:80`) + `is_authorising` (`:163`) + `details.params_hash` equality; **single-use consumption for destructive actions** — retire the grant on use via `revoke_grant(grant, revoked_by="system:consumed")` (`:155` — reuse, no new status, no schema change); write-class grants stay GRANTED for their TTL window *(defaults per the Open-questions box — Gerard's call)*).
**Test:** `test_granted_call_executes` — an active, params-matching grant lets the gated action reach its handler (mock handler; assert no `requires_confirmation` in the result). `test_params_drift_reasks` — same tool, different params ⇒ new ask (the grant authorises *the* call, not the tool). `test_expired_revoked_denied_reask` — each non-authorising status ⇒ ask. `test_destructive_grant_is_single_use` — second identical call after a consumed grant ⇒ new ask. `test_consult_error_fails_closed` — a raising lookup ⇒ the ask, never execution. `test_grant_execution_audited` — the audit marking carries the grant id.
**Notes:** **Fail-closed is the whole point** — this gate exists for deletes/member-removal/system-settings; an error anywhere in the consult must land on the ask, mirroring the gate's existing registry-miss posture (`:724-739`) and the *opposite* of the policy plane's fail-open (`unified_executor.py:271-280`, PRD-192's problem, not this PRD's). The full-autonomy dial keeps its current behaviour (it already skips the gate); grants make the *supervised* path completable — the dial stops being the only yes.

### S4 · Resume the interrupted execution — M · _tool-runtime J3/E.1 + gov B.4 reuse, P2-12_

Approving must complete the work, not just flip a row. Extend the grant API's subject dispatch — today board-only — with the `tool_call` branch: on grant, **re-dispatch the stored call through the spine**; on deny, end it honestly. **Files:** `api/approval_grants.py` (`_requeue_subject` `:142-160` — add the `SUBJECT_TOOL_CALL` branch: rebuild the call from `grant.details` (action, params, caller_context incl. conversation/turn ids and the server-minted agent identity) and execute via `UnifiedToolExecutor.execute_tool` (`modules/tools/execution/unified_executor.py:351`) scoped to `grant.workspace_id` — riding the spine means telemetry (`telemetry.py`), the policy seam, and `capture_tool_outcome` all fire on the resumed execution for free; store the outcome summary on `grant.details["executed_result"]` and return it in the grant response so the card swaps to its executed state; `_fail_subject` `:163-177` — `tool_call` branch is a no-op execution (the grant's DENIED status is the record; the card renders refusal; the model sees the refusal via context on the next turn). **Board linkage:** when `details.board_task_id` is present (the ask fired on a board-task run), the *existing* board branch already re-queues that task on grant (`:150-158`, `notify_task_available`) — the re-run then meets the now-active grant (S2) and completes; wire the issuance (S1) to carry `board_task_id` from the agent lane's caller context so this linkage exists.
**Test:** `test_grant_resumes_tool_call` — granting a `tool_call` grant re-dispatches with the stored params + workspace + caller context (mock `UnifiedToolExecutor` at the boundary; assert args + workspace threading; **no DB side effects beyond the grant row**). `test_deny_does_not_execute` — deny leaves the executor untouched and the grant DENIED. `test_resume_failure_is_honest` — a failing re-dispatch surfaces the failure on the grant/card (never a fake success — this module's signature defect, dossier §C.3, must not be reintroduced on the resume path). `test_board_linked_ask_requeues_task` — a grant whose details carry `board_task_id` re-queues the blocked task (mirror the existing board-branch behaviour).
**Notes:** The chat lane is synchronous (PRD-163 kept it so — the card comes from the tool result); resume therefore executes **server-side on the grant call** and reports through the card + outcome capture — no new streaming/injection machinery invented. The re-dispatch is the *same spine* the original call would have taken, so nothing is exempted from policy/telemetry by being approved. Single-use consumption (S2) means the resume dispatch is the consuming use for destructive grants — consume-then-execute inside one transaction boundary so a crash cannot leave a spent grant with no execution *and* no record.

## Conventions (non-negotiable — see `automatos-ai/CLAUDE.md`)

- **No new tables, no schema growth, no new config keys:** the grant row, its index, its TTL (`APPROVAL_GRANT_TTL_SECONDS`, `config.py:692`), and its API are PRD-181's — reuse them. `subject_id` carries the deterministic call key; `details` JSONB carries the snapshot. No `os.getenv()` outside `config.py` (§4).
- **Reuse the chokepoints:** one consult/issue helper (`tool_grants.py`) called from the *single* gate all platform actions funnel through; resume rides `UnifiedToolExecutor.execute_tool` so telemetry/policy/outcome-capture are never bypassed by an approved call; the card clones `MissionApprovalWidget`; notifications go through `notification_dispatcher` (§2, §11).
- **Fail closed at the gate, fail loud on resume:** every error in issue/consult lands on the ask, never on execution; a failed resume surfaces as a failure on the grant and card — no fake success (`tool-runtime.md` §C.3 is the cautionary tale; no silent `except` swallows).
- **No backward-compat shims:** nothing is superseded here — S15's prose remains the model-facing channel by design; the card is additive for the human. Do not leave a parallel "confirm token" path half-built beside grants (§5).
- **Canonical vocab:** **Playbook**, **Mission**, **Task**, **Command Center**, **Auto**; the human-facing noun on the card is **approval** (matching the mission card), not "confirmation."
- Branch `feat/p2-w2-approve-resume`; commit, push, open a PR; CI is the gate.

## Success metrics (the definition of "the dead end is gone")

- **A supervised workspace can complete a gated action** — ask → pending grant → card → approve → the action executes and the result lands, with the full-autonomy dial untouched (S1–S4). Today this is structurally impossible.
- **The confirmation funnel converts** — the dossier's §G metric (`requires_confirmation` returns vs subsequent grants/executions) moves off its structural 0; approval latency becomes measurable from `requested_at → granted_at` on real rows (pilot signal, not a target).
- **First production `approval_grants` rows** — the table PRD-181 built stops being 0-rows-ever (gov dossier §B.6), and every grant state change is audited via the existing paths.
- **Attribution is honest** — a grant-authorised execution is audit-marked with its grant id, distinct from dial-skipped (S2); a denied ask never executes; a failed resume never reports success (S4).
- **No silent asks** — a non-chat lane hitting the gate emits `approval_requested` (S5); an ask is typed as an ask in memory, not failure spam.
- **Zero schema/route growth** — shipped entirely on PRD-181's table and API (the reuse being the point).
