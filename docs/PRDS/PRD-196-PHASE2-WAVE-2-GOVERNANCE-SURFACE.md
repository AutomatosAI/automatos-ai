## Overview

The governance dossier's core finding is that the best-architected control plane in the platform is **headless**: *"zero frontend callers for approval grants, GDPR, oversight, or policy-plane config. A workspace admin cannot see the audit log, cannot see or action a pending approval, cannot set a budget or a posture, and cannot fire a GDPR export — all of it is API-only"* (`governance-policy.md` §C.8). Re-verified against this worktree: a grep of `frontend/` for `approval-grants` / `gdpr` / `policy_plane` returns **zero** callers. The consequence is stated bluntly in the review: **Art.14 "effective human oversight" is a UI claim, and the durable-grant machinery is unreachable without a front door** (§6 P2-15). PRD-181 built a real approval workflow — durable, scoped, expiring, revocable grants with a grant/deny/revoke API that re-queues blocked board tasks (`api/approval_grants.py`) — and no human can find it. Worse: nothing *notifies* anyone that a grant is pending (no notification fires anywhere in `services/board_approval.py`), and the grant-mutation endpoints carry **no admin gate at all** — any workspace member can approve an agent's destructive action today.

Two compliance floors sit behind the surface gap. **Audit retention:** the Art.12 handler writes one `AuditLog` row per policy verdict (`modules/policy/audit_handler.py:62-115`) and PRD-181's GDPR/grant paths write theirs unconditionally — but nothing ever deletes a row, and nothing reads them (no read API over `audit_logs` exists; the only "audit" surfaces are the unrelated Credential/Skill/Permission logs). The dossier's cost note is explicit: *"grows `audit_logs` unboundedly — needs a retention policy (EU-AI-Act Art.12 mandates ≥6 months, which is a floor, so retention is a compliance requirement, not just housekeeping)"* (§H). **GDPR subject-tags:** PRD-181/183 shipped the export/erase cascade and PRD-187 reworded it for the in-process durable store — and both field memory **and** durable memory carry an explicit, honest `# GDPR-GAP:` marker at the erase site: no data-subject tag exists at write time, so subject-level erasure returns 0 and reports the gap (`vector_field.py:230-246`, `unified_memory_service.py:522-535`, gap ledger `gdpr_service.py:172-191`). *"A subject-erase that mostly returns gaps is not yet a defensible GDPR answer"* (security appendix §2.3). This PRD writes the tag and turns those documented 0s into real filtered deletes.

Judged against the **North Star** — *does this make Auto more autonomously capable and the agents' output higher-quality for clients?* — this is the wave that makes autonomy-with-guardrails **legible**. Wave 2's other PRDs arm the enforcement (192), feed the grants (193), and close the edges (194/195); this PRD is the half that lets a human actually *oversee* it: see what the plane decided, approve or refuse what it paused, set the posture and the budget without hand-writing JSON, and answer a data-subject request without caveats. The dossier ranks it #2 in the whole module's upgrade path: *"Art.14 oversight is a UI claim; without a human surface the durable-grant machinery is unreachable. This is the single biggest client-trust lever and unblocks the whole W11 investment"* (§J.2). **No moat framing; no new capability** — the deliverable is that a client can trust and steer the autonomy the rest of Wave 2 switches on.

**PILOT lens (locked):** `approval_grants` = **0 rows ever** and policy-verdict `audit_logs` = **0** (`governance-policy.md` §B.6) are **not** usage findings to fix by driving traffic — they are the forced output of an OFF flag (PRD-192's job), a cost-blind default gate, and a surface no human can reach (this PRD's job). Do not score the empty tables; build the wiring that lets them fill and be seen. See `feedback-pilot-usage-not-quality-signal`.

**Boundary with the siblings (do not redo):** PRD-192 owns the flag flip, fail-closed-for-destructive, pricing, and the four bypass lanes (dossier J.1/J.3–J.5). PRD-193 owns creating grants from the tool loop and the resume path (tool-runtime J3/E1). PRD-195 (P2-14) owns the platform-wide `@require_permission` sweep — this PRD gates **only its own new/ungated governance endpoints** with the existing PRD-185 S12 dependency and does not start the 85-router sweep. This PRD builds **no new grant producers and flips no flags**: it is the consumer surface, the retention floor, and the subject tag.
