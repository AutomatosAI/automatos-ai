# PRD-278 US-401: everything the API writes to its own disk

**For:** [PRD-278](PRD-278-RUN-ON-MANAGED-CLOUD-SERVICES.md) US-401 (analysis only), and Wave 4 (US-402 to US-405), which build on it.
**Read at:** branch `docs/prd278-us401-disk-writers`, based on `2d90dab0a`, 21 Nov 2026. Nothing was run.
**Labels:** **[T]** read in code at that commit; **[I]** inferred from a library's documented behaviour, not read in its source here; **not determined** says what would settle it.

## 1. What was swept

The API process: every Python file under `orchestrator/`, leaving out `tests/`, and the one-off tools in `scripts/`, `evals/` and `alembic/`, which the API process never starts. The sweep was a text search for each way a program creates, writes, moves, copies or deletes a file or folder (open for write or append, `Path` writes and `mkdir`, `os` and `shutil` calls, every `tempfile` form, uploads, library writers such as `.save(` and `write_pdf`, archives, file-backed stores, child processes with an output path, git clones, library caches, log handlers, lock files). Each hit that reaches the disk was then opened, the path it builds was followed back to the setting or constant it comes from, and the route, job or start-up step that reaches it was found by following callers. The chart's templates and `values.yaml` were read for the volume or scratch mount each path lands on. Section 8 lists every pattern and its count.

[PRD-280 US-103](PRD-280-US-103-WRITE-PATHS.md) lists where each component writes, for the read-only root. This page is finer-grained and covers only the API. Where the two differ, the row says so (section 7).

**What the chart gives the API** (`charts/automatos/templates/api-deployment.yaml`, `values.yaml`, `_helpers.tpl`):

- **Volume `data`**, mounted at `/app/data` (`api-deployment.yaml:96-98`), a 10 Gi claim by default (`values.yaml:196-201`). With `api.data.enabled` on, the chart sets `DOCUMENT_UPLOAD_DIR=/app/data/uploads` and `DOCUMENT_STORAGE_DIR=/app/data/documents` (`api-deployment.yaml:55-60`).
- **Scratch `emptyDir`** at `/tmp`, `/home/automatos` (`HOME` is set to it, `:62-65`), `/app/logs`, and `/app/documents` only with `api.data.enabled=false` (`:105-120`, `:147-157`), while `api.readOnlyRootFilesystem` is on, which is its default (`values.yaml:189`). Emptied when the pod is replaced.
- **`/workspaces`**, the workspace volume, read-only (`api-deployment.yaml:92-94`).
- Under the `local` edition's compose file, `backend_data` is at `/app/data` and `backend_logs` at `/app/logs` (`docker-compose.yml:430-433`), and `envs/api.defaults:85-99` sets `CREDENTIAL_KEY_FILE`, `DOCUMENT_UPLOAD_DIR` and `DOCUMENT_STORAGE_DIR` under `/app/data`. The rest of that container's disk is its own and is lost when it is recreated.

"Object storage configured" below means `is_storage_configured()` (`core/storage/s3.py:90-102`): an endpoint, `AWS_USE_WORKLOAD_IDENTITY`, or a full key pair.

## 7. What this means for US-402 to US-405

Facts, not a design.

**US-402, the upload route.** Writer to cover: A1. Readers that already handle an `s3://` path: download (`documents.py:259`, `services/document_downloads.py:44-77`), reprocess (`documents.py:865-910`, `handlers_documents.py:285-298`), ingest through the manager (`manager.py:622-647`, `:715-717`). Readers that do not: spreadsheet workspace copy (A1), workspace export (it does read `s3://` keys under `workspaces/<ws>/`, `files.py:64-77`), delete (A11: the object is removed too). The new row's local copy is made for ingestion, which opens by path (section 5, item 1). The key repeats on a replace (item 5). The replace branch and the tool in A2 write the same directory.

**US-403, the other writers.** Rows A2, A3, A4, A5, and A6 if the owner puts it in. Row A3 has five write sites that meet in `_output_path` and `_build_result` (`generation_service.py:747-803`). Readers that must find the file with no local copy: `workspace_documents.generated_file` and `docx_renderer._safe_local_image` (section 5, item 3). A3, A4 and A5 already have a copy in object storage when configured, and each keeps the local file when the upload fails (`generation_service.py:842-843`, `store.py:70-72`, `brand_logo.py:206-207`). So for these three, US-403's work is the readers and the failure case, not a new upload.

**US-404, what is already on disk.** Rows to rewrite: `documents.file_path` for A1 and A2, and `doc_metadata["versions"][].file_path`. No rewrite is needed for A3, A4, A5 (item 4). A file missing from disk is a normal case: `_local_source`-style reads already answer "not found" (`documents.py:937`), and the existing mover skips a row whose file is absent (`reingest_documents.py:243-246`).

**US-405, the API without a volume.** After US-402 and US-403 as worded, the volume still holds: A6 (templates, if left out), A7 (skill clones), A8 (host keys), A9 (the shadow log), and A10 in the compose edition. In the chart, A7 to A9 are already on scratch when `api.data.enabled=false`, and A10 is not written. So "the API without a volume" is reachable when the owner decides each of A6 to A9 (section 5): move it, or accept that it is lost on a restart. Two parts of the work stay either way: scratch space for the length of a job (section 5, item 1), and the local file kept when an upload fails. The PRD's functional requirement FR-9, "keep nothing on local disk that has to survive a restart", is met only for rows whose reason in section 2 says the copy in storage is read first or instead.
