## Framing (CLAUDE.md §3)

**Extension + three bug-class fixes.** The stream protocol (`0:` text, `d:` data frames), the tool loop, the watch/report-back machinery (PRD-204/224/205) and the mission card all exist. This PRD adds a reasoning channel to the stream, keeps tool activity visible, gives Auto a bounded wait tool, makes the report-back fire on every ticket ending, and puts a live task card in the chat. Net-new: one data-frame type, one platform action, one card component. **Size:** L across three waves. **Risk:** Medium — S1/S2 touch the LLM client and the stream every reply rides on.

## What the transcript actually shows (grounded)

1. **Reasoning shipped as the answer.** Auto (agent 1) runs `nvidia/nemotron-3.5-lightning-30b-a3b` on the NVIDIA trial lane (PRD-236). It is a reasoning model that writes its deliberation into `content`. `core/llm/clients/openai_compatible_client.py:180-264` reads `message.content` only — no reasoning channel is separated anywhere (only `bedrock_client.py:385-393` knows `reasoningContent`, and it inlines it as "[Reasoning: …]"). The stored assistant text *is* the model's thinking.
2. **Nothing streams until the end.** Every LLM call is non-streaming (`generate_response`); the final text is word-chunked afterwards by `stream_text_aisdk` (`consumers/chatbot/service.py:~2530`). Six calls at 31k–39k input tokens each (`llm.cost_audit` lines) — ~40 s of "Thinking" dots, then the whole text at once.
3. **The perpetual "platform get agent" spinner.** Five tool rounds (activity feed ×2, get agent ×2, one dedup skip). A dedup-skipped call emits **no** `tool-end` frame (`service.py:1566` `if not event.get("skipped")`), and `useChat` never clears running chips at `finish` (`frontend/lib/chat/hooks.ts:273-360` handles no `finish`), so `message.tsx:182-215` shows a running chip forever.
4. **Completed work is invisible.** `renderToolCalls` renders running and error chips only — the trail of what Auto checked disappears the moment it finishes.
5. **The promised report-back never came.** Ticket #92 (Bob, `runtime: cli`, a claude-fable-5 session: 11 assistant messages, 1 permission denial) ended `exit_reason=cancelled` at 19:55:09. The watch armed by the ASSIGN lane ("supervised with auto-report back") is still `status=watching`: `watch_ingest_terminal` is wired only from the `completed` and `failed` dispatches in `api/board_tasks.py:222-290`; the completion writer's `cancelled` branch (`finalize_board_task_run`, `:1250+`) fires a `task_cancelled` board event but never the watch hook, and a ticket parked in `review` reports nothing either, and the watch ticker polls every 300 s anyway (`watches.check_interval_seconds`). The #91 watch's judge failed on a hard-coded `openai/gpt-4o-mini` ("unavailable or removed") — a PRD-223 governance leak.
6. **Capped turns are silent.** `limit_reached` frames (`streaming.py:118`) are not handled by `useChat`.

## Stories

### W1 — make the window honest (S/M, no protocol change)
**S3 · Activity trail.** Every tool call stays visible as a compact line ("Checked the activity feed · 0.2 s", "Looked up Bob") with expand-for-detail; `tool-end` carries a ≤120-char server-side result summary (never raw payloads); dedup-skipped calls emit `tool-end` (`skipped: true`); `finish` marks any still-running chip complete; `limit_reached` renders as a system line. **Files:** `service.py:1560-1576`, `streaming.py:format_aisdk_tool_end`, `hooks.ts`, `message.tsx`. **Test:** stream fixture with a skipped call → no running chip after finish; trail order preserved; summary capped.
**S5 · Report-back that fires on every ending.** `finalize_board_task_run` (the one completion writer, `api/board_tasks.py:1250+`; the CLI result path lands there via `services/cli_host_service.py:575`) calls `watch_ingest_terminal` for `cancelled` too; the terminal event posts into the origin chat through `deliver_background_message` (PRD-205 lane): "Bob's ticket #92 ended — cancelled after 1 permission denial. Last tool: …"; board-task watches poll every 30 s while the ticket is `in_progress` (D3); the watch judge uses the governed default model, never a literal model id. **Test:** cancelled result → watch terminal event + chat message; 300→30 s only for in-progress cli tickets; judge model resolves through governance.

**S9 · A super admin's chat can run super-admin-only tools (edition-neutral bug, found 2026-09-08).** `is_super_admin=True` only widens the *offered* tool set (`service.py:2344` `include_super_admin`); the executor's PRD-143 gate (`platform_executor.py:803-810`) requires a literal `system_role == 'super_admin'` in `caller_context`, and `build_tool_caller_context` (`service.py:105`) never writes `system_role`. Result: the local operator (anonymous lane binds `system_role="super_admin"`, `hybrid.py:944-949`) and a SaaS super admin are offered `platform_get_system_health`, it is denied at execution, and the turn burns a whole LLM round (4 s + 35k tokens on Opus). **Fix:** thread `system_role` from the driving principal into the caller_context at the one call site (`service.py:1625`) — `"super_admin"` only when the chat principal is one; every other caller stays fail-closed exactly as PRD-143 demands. **Test:** su principal → context carries `system_role`, su-only action executes; admin / API-key / member → still denied; `tool_grants.py:52` already lists the key.
**S10 · Durable memory is honestly OFF in the local edition.** `envs/api.defaults:118-126` says Qdrant/mem0 do not ship locally and "the backend degrades gracefully", but sets `QDRANT_URL=http://qdrant:6333`, and `unified_memory_service.py:202` treats a non-empty URL as configured — so every turn attempts L2 writes (6–8 ERROR tracebacks), the heartbeat probes a non-existent host every 30 s, and the workspace/search handlers only say "not configured" when the URL is *empty*. **Fix:** local default `QDRANT_URL=` (empty) so every consumer takes its existing "not configured" branch; guard `durable_store.py:87`, `vector_field.py:82` and the heartbeat probe on an empty URL (log once at boot); ship Qdrant as an opt-in compose profile (`profiles: ["memory"]`) so the operator can light it up with one flag. SaaS keeps its real URL — no behaviour change there. **Test:** empty URL → no writes attempted, no probe scheduled, one boot log line; non-empty → today's behaviour.
**S11 · Tool ranker resilience.** The PRD-232 semantic index embeds the message per turn (Redis-cached, in-flight-deduped, 2.5 s timeout via `SEMANTIC_TOOL_ROUTING_EMBED_TIMEOUT_S`); on a timeout the fallback is the **full 180-action enum** (`tool_router`: "dispatcher enum NOT narrowed"), which costs tokens on top of the lost seconds (2 of 15 calls timed out on 2026-09-08; avg 0.6 s). **Fix:** on timeout fall back to the workspace's last narrowed set (Redis) or a lexical match over action names, never the full enum; keep the background embed so the next turn hits cache. **Test:** timeout → narrowed fallback used, full enum never sent.

### W2 — thinking and the answer as two channels (M)
**S1 · Reasoning channel.** The OpenAI-compatible client separates `reasoning_content` deltas and `<think>…</think>` blocks (per model, from the registry's `reasoning` capability) into `response.reasoning`; the stream gets `d:{"type":"reasoning","delta":…}` frames; `useChat` accumulates `message.reasoning`; `message.tsx` shows a collapsible "Thinking…" block that fills live and **auto-collapses when the answer starts**; persisted as a `{type:'reasoning'}` part or dropped (D1). Bedrock's inline "[Reasoning: …]" goes (same PR). **Test:** client fixtures for both shapes; a Nemotron-style reply yields empty answer text + reasoning → the saved message is the answer only; UI collapses on first `0:` frame.
**S2 · The answer streams.** The final LLM call after the tool loop runs with `stream=True` so the answer types out; tool-loop rounds stay non-streaming. **Test:** frames arrive incrementally (>1 `0:` frame before finish) for a multi-sentence answer.

### W3 — Auto follows through (M)
**S4 · Wait-and-recheck.** New platform action `platform_wait_for_task(task_id, max_wait_s)`: polls the ticket every 5–10 s up to `CHATBOT_WAIT_BUDGET_S` (default 90, D2), emitting `d:{"type":"progress","text":…}` lines built from `board_tasks.runtime_ref` (last tool, files touched, elapsed); returns the terminal state or "still running after N s". Auto then reports, or says "I'll keep watching and report back" — S5 makes that true. Safe because PRD-237 detached the turn from the connection; Stop cancels the wait; a second message queues behind the chat's session lock and the UI says so. Corpus: ~15 utterances for the new action (PRD-232 linter). **Test:** handler polls with a fake clock, respects the budget, emits progress frames, returns each terminal state.
**S6 · Task card in the chat.** When Auto files or checks a ticket, a `task-card.tsx` (sibling of `mission-created-card.tsx`) renders in the message: status, assignee, elapsed, last tool, files touched, link to the board viewer; live via `automatos:board-changed`. **Test:** card renders from a `tool-data.task` payload and updates on the window event.
