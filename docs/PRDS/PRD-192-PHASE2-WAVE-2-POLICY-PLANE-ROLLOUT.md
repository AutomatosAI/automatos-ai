## Overview

The review's security summary is one sentence: **the runtime authorization boundary is off by default, fails open, and is bypassed** (§7 risk 2, CRITICAL-enabler). The best-architected governance layer in the platform — typed `deny > ask > allow` verdicts, errors-as-data, an in-process bus that consciously rejects shell-hook RCE, a per-workspace Balanced posture, model-aware pricing — sits behind `AUTOMATOS_POLICY_PLANE`, which defaults false (`config.py:665`, live-verified) and is set **nowhere**: grep over `envs/`, `docker-compose.yml`, `railway.json`, and the Dockerfiles returns nothing (re-confirmed in this worktree). With the flag off, `_policy_gate_check` returns immediately (`unified_executor.py:228-229`) — so on every real deployment today the rate limiter is a placebo (F040), the admin gate is the workspace-has-an-admin auto-flip (F014), the widget empty-permission god-key stands (F042), `super_admin` is locked out of admin routers (F043), and there is **zero** budget admission. The data corroborates: policy-verdict `audit_logs` ≈ 0 rows ever, `approval_grants` = 0 (`governance-policy.md` §B.6) — the plane has never carried load. Worse, even ON the gate **fails open**: any exception in the plane is logged and treated as "proceed" (`unified_executor.py:276-281`), the board gate has the same posture (`api/board_tasks.py:989-994`), and the budget/posture readers swallow their own faults into allow (`budget.py:111`, `policy_document.py:141`). And even with all of that fixed, **four lanes execute tools around the chokepoint entirely** — the chat per-action Composio shortcut, playbook Composio steps, widget email, and the `/api/tasks` direct-step shell/git lane (§2.2) — none of which fire policy, telemetry, or outcome capture.

The review calls the fix **"the single highest-leverage security action in the review"** (§6 P2-11) and the dossier is blunter still: *"nothing else in this dossier matters while the plane is off"* (`governance-policy.md` §J.1). The fix is deliberately **not** new construction — the dossier's verdict is EXTEND (§E): stage the flag on (**shadow-log → enforce-destructive-only → enforce-all**, each stage one env value, each reversible), land the **fail-closed-for-destructive** branch *before* any enforcement stage (a governance gate whose failure mode is *allow* is a monitoring aid, not a boundary — §C.2), **price the budget gate** so it can refuse the call in front of it instead of only the workspace already over its ceiling (§C.3: `projected_cost` is structurally 0 because no caller threads estimates — `gate.py:163-168`), and **close the four bypass lanes** so "one plane governs everything" becomes true rather than aspirational (§C.4). One genuinely new defect surfaced by this PRD's own grep: **per-action Composio tools misclassify at the gate** — `_is_composio` is prefix-only (`gate.py:245-246`), so a `GMAIL_SEND_EMAIL` routed via the executor's `composio_actions` dict (`unified_executor.py:515-525`) classifies `internal_write` and would **auto-allow under Balanced even with the plane ON**. Arming a gate that waves external sends through would be a false sense of security; the classification fix lands with the dial (S1).

Judged against the **North Star** — *does this make Auto more autonomously capable and the agents' output higher-quality for clients?* — this is the wave that makes autonomy **trustable**: Wave 2's preamble says Auto can't be trusted with client-facing autonomous action until there's an enforced boundary and a scoped principal. Today the honest posture is "careful engineering, wired but not armed" (§7); the widget, channels, and Composio lanes are exactly the surfaces that go hot first with real customers. This PRD converts scaffolding into guardrails *before* that traffic arrives — and because denials are errors-as-data with remediation text (`types.py`, `errors.py`), an armed plane makes Auto *more* capable, not less: a blocked call is something Auto can read, adapt to, and route to a human approval (PRD-193's card) instead of an opaque failure. **No moat framing; no new capability** — the deliverable is that the boundary the platform already designed actually decides what executes.

**PILOT lens (locked):** 0 policy-verdict audit rows, 0 grants, and a 0% priced-call rate are **not cold-start numbers** — the handler is unregistered by flag (`main.py:519-522`), the estimates are unthreaded by construction, and the bypass lanes skip the gate by code path, all grep-proven. These are architecture/wiring findings squarely in scope. What *is* a pilot signal to watch, not chase: shadow-stage verdict volumes and the false-block rate that gates stage advancement (see Gerard's box #3). See `feedback-pilot-usage-not-quality-signal`.

**Boundary with what's already built (do not redo):** PRD-174's gate order (su → admin → budget → act-vs-ask), verdict vocabulary, and bus stay as-is; PRD-181's audit handler stays the single write point (this PRD adds one `mode` key to its details dict); `main.py`'s limiter arming is **already policy-plane-aware** (`swallow_errors=not _policy_plane_on`, `SlowAPIMiddleware` registered only under the flag — `main.py:822-838`) so F040 arms by the flip with no new code; the F014 admin fix and F042 empty=deny (`roles.py:58-77`) are written and arm by the flip. PRD-193 owns the grant surface — this PRD *calls* it, never re-implements it. The governance **UI** (approvals queue, audit view, posture editor) is **P2-15's row in this same wave**, not this PRD's.
