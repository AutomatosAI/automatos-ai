This page details the implementation of trial metering and enforcement, plan tiers, and session modes within the Automatos AI platform. It covers how trial usage is tracked and enforced, how different plan tiers affect feature availability, and the architecture behind the CLI host service for running agents in a local session mode.

## Trial Ledger Metering and Enforcement

The trial ledger system (`orchestrator/services/trial_ledger.py`) manages the onboarding trial credit granted to new users. This system is designed to be lean, avoiding a dedicated database table for trials. Instead, a workspace's trial information is stored within the `workspaces.onboarding.trial` JSONB column, containing `granted_usd`, `spent_usd`, and `state` fields [orchestrator/services/trial_ledger.py:3-5](). Platform-wide daily trial spend is recorded as a single `system_settings` row, keyed by day [orchestrator/services/trial_ledger.py:5-6](). This approach ensures that trial spend is derived from existing usage telemetry, preventing a separate bookkeeping system [orchestrator/services/trial_ledger.py:6-7]().

The trial states are:
*   `active`: Trial is currently in use.
*   `warned`: Trial usage has reached a warning threshold (e.g., >=80% spent) [orchestrator/services/trial_ledger.py:45]().
*   `exhausted`: Trial credit has been fully utilized (e.g., >=100% spent) [orchestrator/services/trial_ledger.py:46]().
*   `converted`: The user has provided a valid payment method, converting their trial to a paid plan [orchestrator/services/trial_ledger.py:47]().

A `None` or absent trial indicates that a trial was never granted or was paused [orchestrator/services/trial_ledger.py:24-25]().

### Daily Spend Tracking

The platform tracks daily trial spend using a `system_settings` entry. The key for this setting is generated by `daily_spend_key()` [orchestrator/services/trial_ledger.py:59-60](), which formats it as `trial_spend_YYYY-MM-DD` (UTC) [orchestrator/services/trial_ledger.py:65](). The `get_daily_trial_spend()` function retrieves this value, returning `0.0` if the setting is unset or unreadable [orchestrator/services/trial_ledger.py:91-92, 97-98]().

### Trial Granting Logic

The `decide_trial_grant()` function determines whether a new user should receive a trial [orchestrator/services/trial_ledger.py:105-112](). This pure function considers several factors:
*   `enabled`: Is the trial feature globally enabled?
*   `already_held`: Has the user already received a trial on any other workspace? `user_has_held_trial()` checks this by looking for any workspace owned by the user that has a `trial` object in its `onboarding` JSONB [orchestrator/services/trial_ledger.py:134-138]().
*   `daily_spend`: The current platform-wide daily trial spend.
*   `daily_cap`: The maximum allowed daily trial spend for the platform.
*   `credit_usd`: The amount of trial credit to grant.

If a trial is granted, a dictionary containing `granted_usd`, `spent_usd`, and `state` (initially `TRIAL_ACTIVE`) is returned [orchestrator/services/trial_ledger.py:126-130](). If not, `None` is returned along with a reason string (e.g., "disabled", "already_held", "daily_cap_reached") [orchestrator/services/trial_ledger.py:121-125]().

The `grant_trial_at_provisioning()` function is called during user provisioning to stamp the trial onto the workspace's `onboarding.trial` JSONB field [orchestrator/services/trial_ledger.py:176-178](). This is done using raw SQL with `jsonb_set` to ensure atomic updates and prevent data loss [orchestrator/services/trial_ledger.py:166-173]().

### Frontend Integration

The frontend component `frontend/components/workspace-provider.tsx` defines the `WorkspaceTrial` type, which mirrors the backend's trial structure [frontend/components/workspace-provider.tsx:32-37](). The `WorkspaceOnboarding` interface includes the `trial` field, which can be `null` if no trial is granted [frontend/components/workspace-provider.tsx:39-43](). This information is fetched via `GET /api/workspaces/current` and used to render trial-related UI elements [frontend/components/workspace-provider.tsx:142-188]().

## Plan Tiers

Plan tiers define the features and limits available to a workspace. These tiers are reflected in the `WorkspaceExposure` interface on the frontend [frontend/components/workspace-provider.tsx:51-61](), which is derived server-side from the workspace's plan tier. This exposure profile drives progressive disclosure in the UI, controlling which navigation items, capability families, and marketplace depth are visible [frontend/components/workspace-provider.tsx:51-61]().

The `Workspace` interface on the frontend includes a `plan` field (e.g., 'basic', 'pro', 'business', 'enterprise') and `planLimits` for agents, workflows, documents, and members [frontend/components/workspace-provider.tsx:63-74]().

System settings can also be influenced by plan tiers, although the `seed_system_settings.py` script primarily focuses on seeding default values and does not directly enforce plan-based overrides [orchestrator/core/seeds/seed_system_settings.py:10-13]().

## Subscription/Session Mode Runtime

The session mode runtime, introduced in PRD-234, allows agents to execute tasks as the user's own Claude Code sessions on their local machine [docs/PRDS/PRD-234-SESSION-MODE-SUBSCRIPTION-RUNTIME.md:1-2](). Automatos acts as a manager, assigning tickets, tracking progress on the board, and integrating with memory and deliverables [docs/PRDS/PRD-234-SESSION-MODE-SUBSCRIPTION-RUNTIME.md:13-15](). This mode is local-only and does not involve SaaS-side session management or credential handling [docs/PRDS/PRD-234-SESSION-MODE-SUBSCRIPTION-RUNTIME.md:35-36]().

### CLI Host Service

The `cli_host_service.py` (`orchestrator/services/cli_host_service.py`) implements the backend contract for CLI hosts. This service handles:
*   **Pairing**: A one-time pairing code is issued by `create_pairing_code()` [orchestrator/services/cli_host_service.py:73-76]() and exchanged for a host token via `pair_host()` [orchestrator/services/cli_host_service.py:98-102](). The pairing code is single-use and expires [orchestrator/tests/test_prd234_s1a_cli_hosts_realdb.py:135](). Only the SHA-256 hash of the code and token are stored [orchestrator/services/cli_host_service.py:10-11]().
*   **Claiming Tasks**: Paired hosts claim `assigned` tickets for `runtime: cli` agents using `claim_for_host()` [orchestrator/services/cli_host_service.py:200-201](). This uses the same `FOR UPDATE SKIP LOCKED` mechanism as the board dispatcher but with a runtime filter [orchestrator/services/cli_host_service.py:3-5]().
*   **Heartbeat and Reconciliation**: `record_heartbeat()` updates the host's presence and capabilities, and reconciles running sessions [orchestrator/services/cli_host_service.py:173-179](). It keeps leases alive for in-progress tasks and re-attaches to assigned tasks that might have been requeued [orchestrator/services/cli_host_service.py:180-184]().
*   **Event Handling and Results**: The host posts idempotent results for task completion, which are indistinguishable from API-run results on the board [orchestrator/services/cli_host_service.py:7-8]().
*   **Revocation**: `revoke_host()` changes the host's status to `REVOKED` and clears its token hash [orchestrator/services/cli_host_service.py:154-157]().

The `CliHost` model (`orchestrator/core/models/cli_hosts.py`) stores host information, including `workspace_id`, `name`, `status`, `pairing_code_hash`, `token_hash`, and `capabilities` [orchestrator/services/cli_host_service.py:79-84]().

### CLI Host Allowlist

The `services/cli-host/automatos_cli_host/allowlist.py` module defines the allowlist for commands that the CLI host is permitted to execute. This is a critical security measure, ensuring that the host only runs trusted commands on the user's machine. The allowlist is designed to prevent arbitrary code execution and maintain the integrity of the user's environment.

### Session Mode Frontend

The `SessionModeTab.tsx` component (`frontend/components/settings/SessionModeTab.tsx`) in the frontend provides the user interface for managing CLI hosts. This includes functionality to create pairing codes, view paired hosts, and potentially revoke them.
