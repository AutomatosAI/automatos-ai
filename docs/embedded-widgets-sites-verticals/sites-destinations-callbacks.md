This page details the implementation of "Sites," which represent external platforms or websites integrated with Automatos AI, and the associated "Destinations" and "Callbacks" features. It covers the backend services for managing sites, dispatching callbacks, and the frontend UI components for configuring these features. The Widget SDK embedding instructions are also provided.

## Sites Management

Sites are a core resource in Automatos AI, representing external platforms (e.g., Shopify, Wix, custom embeds) where the AI widget can be deployed. Each site is associated with a workspace and has its own settings and capabilities.

### Data Model

The `Site` model [core/models/sites.py]() stores information about each integrated site.

### Backend Services (`services/sites.py`)

The `services/sites.py` module provides a thin service layer for CRUD operations on `Site` objects, ensuring workspace-scoped authorization.

- `list_sites(db, workspace_id)`: Retrieves all sites belonging to a given workspace, ordered by creation date [orchestrator/services/sites.py:30-37]().
- `get_default_site(db, workspace_id)`: Resolves the oldest site for a workspace, used as the default for widget endpoints [orchestrator/services/sites.py:40-56]().
- `get_site(db, workspace_id, site_id)`: Fetches a specific site by ID, ensuring it belongs to the workspace [orchestrator/services/sites.py:59-69]().
- `create_site(db, workspace_id, type, display_name, external_id, settings)`: Creates a new site, deriving default capabilities based on its type [orchestrator/services/sites.py:72-98]().
- `update_site_meta(db, workspace_id, site_id, display_name, status)`: Updates surface-level metadata like `display_name` and `status` [orchestrator/services/sites.py:101-131]().
- `update_site_settings(db, workspace_id, site_id, settings_patch)`: Performs a shallow merge of `settings_patch` into the site's `settings` JSONB field [orchestrator/services/sites.py:134-165]().
- `public_site_dict(site)`: Transforms a `Site` ORM object into a dictionary suitable for API responses, excluding sensitive information like `secrets` [orchestrator/services/sites.py:168-185]().
- `ensure_shopify_site_for_workspace(db, workspace)`: A self-healing mechanism that ensures a Shopify-connected workspace has a `type='shopify'` site, creating one if necessary [orchestrator/services/sites.py:207-230]().

### API Endpoints (`api/sites.py`)

The `orchestrator/api/sites.py` module exposes FastAPI endpoints for managing sites.

- `GET /api/sites`: Lists all sites for the current workspace [orchestrator/api/sites.py:86-104](). Includes a self-healing mechanism to ensure Shopify sites are correctly typed.
- `POST /api/sites`: Creates a new site [orchestrator/api/sites.py:107-124](). Requires `workspace:manage` permission.
- `GET /api/sites/{site_id}`: Retrieves a single site by ID [orchestrator/api/sites.py:127-136]().
- `PATCH /api/sites/{site_id}`: Updates a site's `display_name` or `status` [orchestrator/api/sites.py:139-160](). Requires `workspace:manage` permission.
- `PATCH /api/sites/{site_id}/settings`: Updates a site's `settings` JSONB field via a shallow merge [orchestrator/api/sites.py:300-317](). Requires `workspace:manage` permission.

## Destinations Dispatcher

The destination dispatcher is responsible for routing callback requests to various external platforms configured for a site.

### Callback Payload

The `CallbackPayload` [services/destinations/base.py]() dataclass encapsulates the information for a callback request:
- `site_id`: UUID of the site.
- `site_display_name`: Display name of the site.
- `workspace_id`: UUID of the workspace.
- `session_id`: Session ID of the widget interaction.
- `request_id`: Unique ID for the callback request.
- `name`: Customer's name.
- `phone`: Customer's phone number (E.164 format).
- `product_context`: Optional context about the product.
- `urgency`: Optional urgency level.
- `preferred_time`: Optional preferred callback time.

### Dispatch Logic (`services/destinations/dispatcher.py`)

The `services/destinations/dispatcher.py` module orchestrates the delivery of callback requests.

- `_render_callback_text(payload)`: Formats the `CallbackPayload` into a human-readable text message for various channels [orchestrator/services/destinations/dispatcher.py:54-69]().
- `dispatch_via_channel(*, destination, payload, db, workspace_id)`: Dispatches a callback through the unified `channels.sender` service. It handles platform-specific targeting (e.g., `channel_id` for Slack, `webhook_url` for webhooks) [orchestrator/services/destinations/dispatcher.py:72-151]().
- `dispatch_one_destination(*, db, site_id, workspace_id, session_id, request_id, destination, payload)`: Attempts to dispatch a callback to a single destination with retry-with-exponential-backoff logic (up to `MAX_ATTEMPTS` [orchestrator/services/destinations/dispatcher.py:39]()). Each attempt is logged to `widget_event_log` [orchestrator/services/destinations/dispatcher.py:185-197]().
- `dispatch_callback_for_site(*, db, site_id, workspace_id, session_id, request_id, payload, destinations)`: The main entry point for dispatching. It iterates through all configured `destinations` for a site and dispatches them concurrently using `asyncio.create_task` [orchestrator/services/destinations/dispatcher.py:201-229]().

## Callback Service and Endpoints

The callback service handles the business logic for processing callback requests from the widget.

### Backend Service (`services/callback.py`)

The `orchestrator/services/callback.py` module provides core functionalities for callback processing:

- `PHONE_E164_REGEX`: Regular expression for validating E.164 phone numbers [orchestrator/services/callback.py:38]().
- `normalise_phone(raw)`: Cleans a raw phone string to prepare it for E.164 validation [orchestrator/services/callback.py:62-68]().
- `is_valid_phone(phone)`: Checks if a phone number is in E.164 format [orchestrator/services/callback.py:71]().
- `compute_phone_hash(phone, site_id)`: Generates a SHA-256 hash of the phone number, salted with `site_id`, for GDPR-friendly idempotency checks. The plaintext phone is never persisted [orchestrator/services/callback.py:78-89]().
- `find_recent_duplicate(db, site_id, session_id, phone_hash, now)`: Checks for duplicate callback requests within `IDEMPOTENCY_WINDOW` (5 minutes) using the phone hash and session ID [orchestrator/services/callback.py:96-127]().
- `check_rate_limits(db, site_id, session_id, per_site_hourly_cap, now)`: Enforces per-session cooldown (60 seconds) and a per-site hourly cap (default 100 requests). Note that per-IP rate limiting is handled by the `WidgetRateLimitMiddleware` [orchestrator/services/callback.py:141-196]().
- `new_request_id()`: Generates a unique request ID for callback events [orchestrator/services/callback.py:287-289]().

### Widget API Endpoint (`api/widgets/callback.py`)

The `orchestrator/api/widgets/callback.py` module defines the API endpoint for submitting callback requests from the widget. This router is included in the main `Widget API Router` [orchestrator/api/widgets/router.py:63-67]().

- `POST /api/widgets/callback`:
    - Validates the incoming `CallbackRequest` (name, phone, product context, etc.).
    - Resolves the `Site` and its callback settings.
    - Performs idempotency checks using `find_recent_duplicate()`.
    - Enforces rate limits using `check_rate_limits()`.
    - Logs a `callback_requested` event to `widget_event_log`.
    - Dispatches the callback to configured destinations using `dispatch_callback_for_site()` asynchronously.
    - Returns a `CallbackResponse` indicating success or failure.

### Callback Test Endpoint (`api/sites.py`)

- `POST /api/sites/{site_id}/callback/test`: This endpoint is used by the dashboard to send a synthetic callback through the site's configured destinations. It allows merchants to verify their integration without a real customer submission [frontend/lib/sites/api.ts:66-76]().
    - It requires `workspace:manage` permission.
    - It checks if the site exists and belongs to the workspace.
    - It returns a 400 if no destinations are configured [orchestrator/tests/test_prd008a_callback_test_endpoint.py:98-103]().
    - It uses `dispatch_callback_for_site()` to simulate the dispatch and returns the results for each destination [orchestrator/tests/test_prd008a_callback_test_endpoint.py:105-127]().

### Widget Rate Limiting

The `WidgetRateLimitMiddleware` [orchestrator/api/widgets/rate_limit.py:174-178]() is an ASGI middleware that applies per-key and per-IP rate limiting to `/api/widgets/*` routes, including `/api/widgets/callback`.

- It uses a Redis-backed sliding window for shared rate limiting across workers [orchestrator/api/widgets/rate_limit.py:106-168]().
- For money-spending endpoints like `/api/widgets/callback`, it applies an additional per-IP ceiling [orchestrator/api/widgets/rate_limit.py:60-64]().
- If Redis is unreachable, it "fails open" (allows the request) but logs an error and increments a failure counter [orchestrator/api/widgets/rate_limit.py:77-87]().
- It adds `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` headers to responses [orchestrator/api/widgets/rate_limit.py:33-37]().

## UI Components

The frontend provides several panels for configuring site-related features, accessible via the `WidgetSdkTab` [frontend/components/settings/WidgetSdkTab.tsx]() in the settings.

### `WidgetSdkTab`

The `WidgetSdkTab` component [frontend/components/settings/WidgetSdkTab.tsx]() serves as the main interface for managing embedded widget settings.

- It fetches and lists all sites associated with the workspace using `listSites()` [frontend/components/settings/WidgetSdkTab.tsx:38-52]().
- Users can select an active site if multiple exist [frontend/components/settings/WidgetSdkTab.tsx:110-137]().
- It renders different configuration panels based on the selected section: `ApiKeyManager`, `CartIdlePanel`, `CallbackPanel`, `SyncPanel`, and `ShopifyTab` [frontend/components/settings/WidgetSdkTab.tsx:155-177]().
- It handles cases where no sites are found or an error occurs during site loading [frontend/components/settings/WidgetSdkTab.tsx:67-101]().

### `SyncPanel`

The `SyncPanel` component [frontend/components/sites/SyncPanel.tsx]() manages the synchronization of external platform data (e.g., product catalogs) into the workspace's knowledge graph.

- It includes a header card explaining its purpose: pulling product catalogs into the knowledge graph for agents to use [frontend/components/sites/SyncPanel.tsx:35-44]().
- It currently supports Shopify catalog and order synchronization via `ShopifySyncCard` [frontend/components/sites/SyncPanel.tsx:63-170]() and `ShopifyOrdersSyncCard` [frontend/components/sites/SyncPanel.tsx:300-408]().
- It displays the sync status (never synced, running, complete, error) and relevant statistics (e.g., indexed products, relations, duration) [frontend/components/sites/SyncPanel.tsx:131-164]().
- Users can manually trigger a full re-sync using the "Sync now" button [frontend/components/sites/SyncPanel.tsx:112-124]().
- It polls for status updates while a sync is running [frontend/components/sites/SyncPanel.tsx:89-94]().
- It detects "stuck running" syncs (older than 5 minutes) and allows retrying [frontend/components/sites/SyncPanel.tsx:107-111]().

### `CallbackPanel`

The `CallbackPanel` component [frontend/components/sites/CallbackPanel.tsx]() allows configuration of the callback handoff feature.

- It enables/disables the callback feature for the site [frontend/components/sites/CallbackPanel.tsx:191-194]().
- Users can select a destination platform (Telegram, Slack, WhatsApp, Webhook) from a dropdown [frontend/components/sites/CallbackPanel.tsx:198-202]().
- It fetches available channels using `listCallbackChannels()` [frontend/lib/sites/api.ts:14-25]() and filters them to only show platforms relevant for callbacks [frontend/components/sites/CallbackPanel.tsx:86-92]().
- For webhook destinations, it provides an input field for the `webhook_url` [frontend/components/sites/CallbackPanel.tsx:240-244]().
- It includes a "Send test" button that triggers the `sendCallbackTest()` API endpoint [frontend/lib/sites/api.ts:66-76]() to verify the integration [frontend/components/sites/CallbackPanel.tsx:166-178]().
- It displays validation errors and test results [frontend/components/sites/CallbackPanel.tsx:136-143]().
- Changes are saved via `updateSiteSettings()` [frontend/lib/sites/api.ts:38-45]().

### `CartIdlePanel`

The `CartIdlePanel` component [frontend/components/sites/CartIdlePanel.tsx]() configures proactive messages for idle carts.

- It allows enabling/disabling the feature.
- Users can set the `idle_seconds` threshold.
- It configures the `greeting` message.
- It defines `frequency_cap` settings (scope, max pops).
- Changes are saved via `updateSiteSettings()` [frontend/lib/sites/api.ts:38-45]().

## Widget SDK Embedding Instructions

The Automatos AI widget can be embedded into any website. The `WidgetSdkTab` provides instructions for embedding.

The core embedding involves including a JavaScript snippet on the target website. This snippet typically loads the widget SDK and initializes it with a site-specific API key.

```html
<!-- Example embedding snippet (conceptual, actual snippet may vary) -->
<script src="https://your-automatos-domain.com/widget-sdk.js" async></script>
<script>
  window.AutomatosWidget = {
    apiKey: "YOUR_SITE_API_KEY",
    siteId: "YOUR_SITE_ID", // Optional, if multiple sites per API key
    // Other configuration options
  };
</script>
```

The `ApiKeyManager` component [frontend/components/settings/ApiKeyManager.tsx]() within the `WidgetSdkTab` is responsible for managing the API keys required for widget authentication.
