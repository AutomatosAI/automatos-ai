**Tier:** standard · **Status:** partial (discovered unit — no PRD owns it as a capability) · **Reviewed:** 2026-07-04, main @ pinned tree (`77bc9c6d5`)
**Scope:** `orchestrator/evals/`, `orchestrator/scripts/eval/tool_routing/` (~1,625 py LOC), `orchestrator/tests/nl2sql_eval/`, `orchestrator/modules/nl2sql/benchmarks/`, `tools/benchmark_field_memory.py` (+ `compare_benchmarks.py`, committed results), `.github/workflows/test.yml` eval jobs, the decoy packages `orchestrator/modules/learning/` + `orchestrator/modules/evaluation/` + `orchestrator/api/api_playbooks.py`, and — as the "learning loops" half — the online signal→behaviour paths that live in other modules' code (edge builder, RAG feedback penalty, HARNESS, NL2SQL example store, knowledge flywheel, chat votes), reviewed here *as loops* and cross-referenced to their home dossiers.

## A. What it is

This unit is the platform's answer to the question the whole Phase-2 review exists to fix: **is quality a tracked number or a vibe?** It has two halves. The *eval* half is five disconnected offline measurement assets accreted across PRDs 61, 108, 138/139, 160 and 177 — a multi-model tool-routing eval harness, an operating-graph uplift eval, an NL2SQL execution-accuracy regression eval, a per-workspace NL2SQL benchmark endpoint with the platform's only quality UI, and a field-memory A/B benchmark — two of which run in CI as non-required jobs. The *learning* half is the set of loops that are supposed to turn production signal into better behaviour: nightly edge building from tool telemetry, RAG feedback→ranking penalty, the weekly HARNESS org-optimization loop, verified NL2SQL examples, the knowledge flywheel, and chat message votes. Alongside both sits a pair of brand-name decoy packages (`modules/learning`, `modules/evaluation`) that contain none of it. It matters to the North Star doubly: Auto cannot *improve itself* autonomously without loops that are actually fed, and Gerard cannot *know* whether agents deliver client quality without a number that updates.

## B. What it does — real implementation and data path

### B.1 The five eval assets

**1. Tool-routing model-matrix eval** (PRD-138/139, `orchestrator/scripts/eval/tool_routing/`, 11 files). A genuinely engineered offline harness: a hand-curated 47-query eval set (`eval_set.jsonl`, q000–q046, categories agents/analytics/cross/memory/missions/playbooks/workspace_code) validated against the live `ActionRegistry` by `seed_eval_set.py`; a Cartesian runner over (model × full/filtered-prompt mode × query) with resume-from-partial and a disk embedding cache (`run_eval.py`, 562 LOC); a scorer producing top-1 accuracy, "in-set rate" (did the filter even surface a correct action), mean prompt tokens, **$/correct**, and p95 latency (`score.py`, 512 LOC; metric definitions `README.md:109-121`); and a benchmark-promotion convention (`snapshot.py` → `benchmarks/YYYY-MM-DD-<label>/`). It runs only by hand (`README.md:34-59`), never in CI; `results/` and `benchmarks/` are gitignored (`scripts/eval/tool_routing/.gitignore`).

**2. Operating-graph uplift eval** (PRD-177 S6 / W7, `orchestrator/evals/operating_graph_uplift.py`, 456 LOC). Pure-stdlib, no LLM, no network: per-tenant top-1 tool-selection accuracy for three rankers — in-module Okapi BM25 (`:146-175`), a deterministic bag-of-words "embedding proxy" (`:211-224`, with an injection seam for the real `ActionSemanticIndex`, `:297-311`), and a learned-edge ranker that *boosts* the embedding base exactly as production composes them (`:227-271`) — over a deterministic train/test split (`:285-294`), with a hard 5-point mean-uplift gate (`UPLIFT_THRESHOLD_POINTS`, `:49`) and a docstring that pre-commits to honesty: "A sub-threshold number is a valid, honest outcome — it is reported, not massaged, and the caller must not flip the flag on it" (`:23-28`). It always exits 0 — the number is the deliverable, not the pass/fail (`:448-451`). CI runs its self-tests as a gate and the number itself as informational, `continue-on-error: true` (`.github/workflows/test.yml:210-259`).

**3. NL2SQL regression eval** (PRD-160 S5, `orchestrator/tests/nl2sql_eval/`). A self-contained sql-eval-style *execution accuracy* harness: seeds an in-memory SQLite DB from `seed_schema.sql`, runs candidate and golden SQL, compares result sets order-insensitively with float rounding (`harness.py:29-138`); 20 golden questions (`questions.json`); always-on integrity checks (every golden executes, every golden passes the AST validator — `test_eval.py:22-60`); the actual LLM generation eval gated behind `RUN_NL2SQL_EVAL=1` (`test_eval.py:66-67`), which CI never sets (`.github/workflows/test.yml:149-158`). The regression gate compares against `baseline.json` — which still holds the 2026-06-12 placeholder `{"accuracy": 0.0, ... "0.0 until a generation run with a real LLM records a number"}`.

**4. NL2SQL product benchmark** (PRD-61 Phase 8, `orchestrator/modules/nl2sql/benchmarks/runner.py`, 154 LOC). The only eval with a *product* surface: `POST /api/knowledge/sources/database/{id}/benchmark/run` + `GET .../benchmark/history` (`api/database_knowledge.py:974-1056`) test the live generator against a workspace's *verified* training examples and persist to `nl2sql_benchmark_runs`/`nl2sql_benchmark_results` (`core/models/database_knowledge.py:256,274`); the frontend `DatabaseQueryAnalytics.tsx` has a run button and a history card (`frontend/components/context/DatabaseQueryAnalytics.tsx:39,195,208-236`). Two honesty caveats in the code itself: scoring is normalized *exact match* only — `execution_match` is a TODO that mirrors `exact_match` (`runner.py:84-87`), a stricter-than-standard and misleadingly-labelled metric; and the test set is a random subset of the same verified examples the few-shot retriever trains on (`runner.py:119-152`) — train/test contamination by construction.

**5. Field-memory A/B benchmark** (PRD-108, `tools/benchmark_field_memory.py`, 962 LOC + `compare_benchmarks.py` + `modules/context/experiment.py`). A standalone script that runs real missions against the live API, seeds 25 verifiable facts across 6 domains at 3 difficulty tiers (`:52-80`), and scores fact *coverage* of the mission synthesis with an LLM judge (keyword fallback). Its outputs are the only committed eval results in the repo: 9 JSONs in `tools/benchmark_results/` dated 2026-03-30 (e.g. `benchmark_vector_field_parallel_20260330_182000.json`: 5/5 trials, avg coverage 0.88, LLM-judge, ~63k tokens/trial). The companion report generator `modules/context/experiment.py` (`compare_runs`) has **zero callers** anywhere in the orchestrator — orphaned.

Plus golden-output fixtures for Shopify openers (`orchestrator/integrations/shopify/tests/fixtures/`, with `regenerate.py`) — golden-file testing, the right idea, scoped to one integration.

**Maturity: 2 / 5.** The individual artifacts range from good to excellent craftsmanship — but as a *capability*, quality is not a tracked number anywhere in this platform. Every recorded number is synthetic, stale, placeholder, or on one laptop; every learning loop that should be eating production signal is starving; and the packages literally named "learning" and "evaluation" are empty theatre.

- `harness_prescriptions`: **0 rows** — the weekly self-optimization loop has never prescribed anything in prod (its diet is the same starved success/error/cost telemetry, and it needs ≥3 agents + 7 days of data, `harness_service.py:35-36`).

**C.3 The one time an eval gated a decision, it worked — the pattern to keep.** The W7 uplift eval measured −32.9 on the fixture and `TOOL_ROUTING_GRAPH` stayed dark *on evidence, not neglect* (`phase0-residual-map.md:272-276`). The harness's design — train/test split, exit-0-always, "the number is the deliverable", explicit do-not-flip language — is exactly eval-driven development practice, and it prevented shipping a routing mode that the May model-matrix run had already shown underperforming (graph-no-edges 83.0% < filtered 93.6%). This is the platform's single genuine instance of "quality as a tracked number"; the rest of the review is about making it the norm.

**C.4 Eval coverage is inversely correlated with what clients actually touch.** The two CI evals cover NL2SQL (0 audited production queries ever) and graph tool-routing (synthetic-only telemetry). The surfaces doing real daily work — chat (1,278 messages), playbooks (the daily driver, currently failing on OpenRouter 402 with tasks closed "done", per `board-tasks.md`), deliverables (2,242), memory (the seed frustration of this whole review), RAG retrieval quality, context assembly — have **no eval of any kind**. There is no memory eval, no retrieval-quality eval, no deliverable-quality judge, no mission-outcome metric. The eval investment went where PRDs demanded a gate, not where client quality lives.

**C.5 The committed field-benchmark numbers don't evidence what they're labelled as.** In `benchmark_vector_field_parallel_20260330_182000.json`, 4 of 5 trials record `"field": {"backend": null, "pattern_count": 0}` and **all 5 trials record `field_queries: 0, field_injects: 0`** — the run labelled `vector_field` shows no recorded field activity at all. The 0.88 coverage may be real mission-synthesis quality, but the artifact cannot attribute it to the field backend, which was the entire point of the A/B. Nobody noticed because nothing consumes these files (`compare_benchmarks.py` is run-by-hand; `modules/context/experiment.py` has zero callers).

**C.6 One-shot-then-abandon is the house pattern.** Every asset was built, run once (or never), and left: the routing eval ran in May, snapshot convention unused; the field benchmark ran in March, pre-dating PRD-166's field rework — its numbers describe a superseded system; the NL2SQL baseline was placeholdered in June "to bump after a green run" that never came; the product benchmark shipped with a UI and was never clicked. Nothing re-runs on a schedule; nothing trends; nothing alerts. The platform's only *recurring* measurements are CI pass/fail and the HARNESS loop (which measures ops metrics, not output quality, and writes to a table with 0 rows).

**C.7 The decoys actively mislead (F069/F082, both re-confirmed NOT DONE).** A maintainer — or Auto operating on its own codebase — looking for the learning system finds `modules/learning` (hardcoded demo data behind a crashing, still-mounted API) and `modules/evaluation` (empty), while the real loops live unlabelled in `core/services/edge_builder.py`, `services/harness_service.py`, `modules/tools/discovery/`, and `modules/rag/service.py`. The July kill-list PRD (184) that owned their deletion was never authored (`phase0-residual-map.md:734`).

**What's genuinely good:** the uplift eval's honesty architecture (C.3); the routing harness's metric design — in-set rate to separate filter failure from LLM failure, and $/correct as the production-decision metric (`README.md:111-119`) — is better thought through than many commercial eval setups; the NL2SQL harness's always-on golden-integrity tier costs nothing and catches real drift; `seed_eval_set.py` validating goldens against the live registry prevents silent eval rot. The raw material for a serious eval culture exists.

## D. Competitive teardown

The relevant class is the LLM eval/observability layer: **Braintrust, LangSmith, Langfuse, Arize Phoenix** as platforms; **promptfoo, DeepEval, RAGAS** as harness/metric libraries. (These are candidate *adoptions*, not just comparators — see §E.)

**Braintrust** ([braintrust.dev](https://www.braintrust.dev/), [docs](https://www.braintrust.dev/docs/evaluate)) — the eval-first commercial reference. Does better: **online scoring** — LLM-judge scorers run asynchronously over production traces as they're logged, catching regressions on live traffic with no latency impact ([how-to-eval](https://www.braintrust.dev/articles/how-to-eval)); experiments tracked over time with side-by-side prompt/model comparison; GitHub Actions integration that runs evals on every PR and posts per-case regressions as comments ([CI/CD article](https://www.braintrust.dev/articles/best-ai-evals-tools-cicd-2025)). Pricing: free tier (1 GB, 10k scores), Pro $249/mo flat — 5 GB processed data, 50k scores, 30-day retention ([pricing breakdown](https://www.cekura.ai/blogs/braintrust-pricing)). Closed platform; SaaS-first.

**LangSmith** ([langchain.com/langsmith/evaluation](https://www.langchain.com/langsmith/evaluation)) — strongest human-in-the-loop story. Does better: **annotation queues** — flag production runs, assign to subject-matter experts, and use the labels to calibrate automated judges and grow datasets; online evaluators over sampled live traffic; heuristic + LLM-judge + pairwise evaluator types; custom Python/TS evaluators. Pricing: Plus $39/seat/mo + 10k traces included, $0.50/1k overage ([pricing](https://www.langchain.com/pricing), [analysis](https://margindash.com/langsmith-pricing)). Per-seat costs scale; closed; LangChain-ecosystem gravity.

**Langfuse** ([langfuse.com](https://langfuse.com/), [GitHub](https://github.com/langfuse/langfuse)) — the OSS platform benchmark, and the closest shape-fit to this stack. Does better: MIT-licensed core, self-hostable with no license cost; tracing + **LLM-as-a-judge evaluators that run on observations, traces, or dataset experiments** (fully MIT since v3.65.0, [docs](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge)); datasets/experiments with A/B comparison; **Code Evaluators** (May 2026) — deterministic Python/TS checks in-platform with no judge cost; a **GitHub Actions experiment gate** (May 2026, `langfuse/experiment-action`) that fails CI when experiment scores drop below threshold; human annotation queues; scores API for arbitrary online signals; OpenTelemetry ingestion ([overview](https://langfuse.com/docs/evaluation/overview)). Managed cloud (US/EU/JP) if self-hosting is unwanted.

**Arize Phoenix** ([GitHub](https://github.com/arize-ai/phoenix), [docs](https://arize.com/docs/phoenix)) — OSS observability + evals, OpenTelemetry-native with auto-instrumentation for OpenAI/Anthropic/LangChain/LlamaIndex; built-in evaluator catalog (Hallucination, QA, Relevance, Toxicity, Summarization); scores attach back onto traces for filtering/debugging. Elastic License 2.0 (not MIT) and a thinner experiments/dataset story than Langfuse.

**promptfoo** ([GitHub](https://github.com/promptfoo/promptfoo), [docs](https://www.promptfoo.dev/docs/intro/)) — the OSS harness benchmark (22.4k stars, MIT; acquired by OpenAI March 2026 but still MIT). Does better than the in-house harnesses: declarative YAML eval configs with a large assertion library (equality/regex/JSON-schema/semantic-similarity/factuality/LLM-judge/custom JS+Python), model-matrix comparison out of the box, CI/CD integration, plus adversarial test generation across 50+ categories. Everything `run_eval.py`+`score.py` hand-rolls (562+512 LOC) is promptfoo config.

**DeepEval / RAGAS** ([deepeval GitHub](https://github.com/confident-ai/deepeval), [deepeval.com](https://deepeval.com/); [RAGAS metrics docs](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)) — the metric libraries. DeepEval: pytest-native LLM tests with thresholds that pass/fail in CI; 50+ metrics including G-Eval (criteria-based LLM-judge with CoT), agentic metrics (task completion, tool correctness), and RAGAS integration. RAGAS: the standard reference-free RAG quartet — faithfulness, answer relevancy, context precision, context recall ([guide](https://www.leoniemonigatti.com/blog/rag-evaluation-with-ragas.html)). These are exactly the missing RAG/memory/agent-quality metrics from §C.4, available as `pip install`.

**Where Automatos actually stands.** Ahead of nobody on the platform layer — it has no trace store, no score store, no datasets-from-production, no online evaluators, no judges, no annotation flow, no dashboards, no trends. At the harness layer it is *at par with a good promptfoo setup for two narrow domains* (routing, NL2SQL) and has one genuinely distinctive asset: the uplift eval's per-tenant learned-vs-baseline design with an honest business gate — a *decision harness*, which none of the platforms provide off-the-shelf (they provide the substrate it should log to). The five-asset scatter with no persistence is roughly where the industry was pre-2023; the 2026 norm — production traces scored continuously, gold sets curated from real traffic, CI experiment gates ([Braintrust](https://www.braintrust.dev/articles/how-to-eval), [Langfuse](https://langfuse.com/docs/evaluation/overview), [LangSmith](https://www.langchain.com/langsmith/evaluation)) — is entirely absent. One caveat cuts in Automatos's favour: all four platforms assume *you have production traffic to score*. §C.2 shows the binding constraint here is signal capture, not tooling — adopting a platform without fixing the starved loops would produce beautiful empty dashboards.

## E. Build / extend / adopt / replace — the verdict

**ADOPT the substrate (Langfuse, self-hosted OSS) · EXTEND the three domain harnesses onto it · KILL the decoys.** Building an in-house eval platform is not earned: dashboards, score stores, judge orchestration, datasets, annotation queues are commodity, and the in-house track record (§C.6) is five one-shot artifacts and an empty `modules/evaluation` scaffold that has waited "to be built fresh" indefinitely.

- **Adopt: Langfuse self-hosted** as the trace + score + dataset + experiment store. Why Langfuse over the alternatives: MIT core (license-compatible with the open-core direction, unlike Phoenix's Elastic 2.0); self-hostable next to the existing Railway Postgres (no per-seat fees, unlike LangSmith's $39/seat; no $249/mo, unlike Braintrust — though Braintrust is the better product if a managed closed platform is acceptable); LLM-judge + code evaluators + the GH-Actions experiment gate cover the T3 online/offline/CI triad out of the box. Integration shape: (1) OTel/SDK instrumentation at the two chokepoints — `core/llm/` (every model call) and `unified_executor.py` (every tool call — the same finally-block that writes `tool_execution_logs`); (2) push existing online signals as Langfuse *scores* (chat votes, rag_feedback, board task outcomes, playbook step failures); (3) LLM-judge evaluators sampled over production traces for the fuzzy qualities (deliverable quality, mission synthesis faithfulness), calibrated against a small human-labelled set per T3. Rough cost: $0 license + one container and its DB (~$20–60/mo infra) + judge tokens (§H); or Langfuse Cloud free tier to start.
- **Extend (keep building, thin): the domain gold sets and decision harnesses.** The 47-query routing set, the 20-question NL2SQL set, the uplift eval's learned-vs-baseline design, and a new memory/RAG gold set are irreducibly domain-specific — no vendor ships them. Keep them as code; make each run *log a run record + scores to the adopted store* instead of a gitignored CSV, and put the offline runners behind the Langfuse/`promptfoo`-style experiment gate in CI. Rewriting the routing runner onto promptfoo is optional simplification (~1k LOC deleted), not required — the runner works; its problem is persistence, not execution. Use **RAGAS/DeepEval as libraries** for the missing RAG/memory/agent metrics rather than inventing metric math.
- **Kill: `modules/evaluation`, `modules/learning`, `api/api_playbooks.py`** (+ the `modules/__init__.py:24,36-37` re-exports). Zero real function between them, one dead mounted API, and a misleading signpost over the real learning loops. Playbook mining from execution history is a fine future idea — as a PRD against the *real* `run_events`/board data, not this scaffold. This re-raises July's unauthored PRD-184; per §12 the deletion is Gerard's call, but this dossier's evidence says there is nothing to save.
- **Explicitly not adopted: an in-house "EvaluationEngine".** The `modules/evaluation` docstring's plan ("engine/, benchmarks/, assessment/ … Sellable as: automatos-evaluation") is the build-it-in-house path the reuse rule exists to stop.

## G. Quality metric

This module is the meta-module — its quality metric is *whether the platform has quality metrics*. Proposed, trackable:

1. **Eval coverage:** fraction of the 28 capability-map modules with (a) a gold-set/offline eval and (b) an online signal, each having produced a number in the last 30 days. **Today: 0/28 on the 30-day test** (2 modules have offline evals; both numbers stale or fixture-only; 0 modules have a flowing online signal — C.1/C.2).

## H. Cost note (informational)

## I. UX / surface

5. **HARNESS prescriptions already board-route when enabled — keep that pattern** (quality issues become board tasks with evidence attached) rather than inventing a separate review queue.
