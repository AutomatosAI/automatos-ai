## A. What it is

The conversational core is Auto's chat plane: the one execution surface on the platform that runs a genuine, live, model-driven agentic loop. It is the pipeline from `POST /api/chat` through complexity assessment (AutoBrain), agent routing (respond / delegate / mission-suggest), context preparation (SmartChatOrchestrator → ContextService), the converged `ToolLoopExecutor` (iteration caps, dedup, stuck-loop breaking, truncation recovery), Composio per-action injection and error recovery, SSE emission to the AI-SDK frontend, and post-turn memory writes. Three client surfaces ride this one path by construction — dashboard chat (`api/chat.py:147`), voice (`api/chat_voice.py:55`), and the storefront widget (`api/widgets/chat.py:240`, `widget_mode=True`) — so its quality is simultaneously the quality of the product's main UI, its voice leg, and its only live client-facing autonomous leg (INBUILD). The July review called this loop "the load-bearing strength for the entire OS thesis"; after W1's fix (F001) it is also the engine every headless surface (board, Missions, scheduled, webhooks, inter-agent) executes through via `AgentFactory`.

## B. What it does — the real implementation and data path

**1. Ingress and persistence.** `POST /api/chat` (`orchestrator/api/chat.py:134`) authenticates via hybrid auth, then immediately discards the caller's identity for ownership purposes: `get_user_id(db)` returns the row with `id=1` (or the first user) "for MVP" (`api/chat.py:82-89`), and every chat and message is created and access-checked against that constant (`:148`, `:222`, `:498`). Chat + message rows persist per turn (`consumers/chatbot/service.py:260-455`); the full message history is reloaded from the DB every turn (`api/chat.py:236-237`). Concurrent requests for the same chat are serialized through an in-process asyncio lane queue (`core/session_queue.py:1-40`, acquired at `api/chat.py:410-422`).

**2. Complexity assessment (AutoBrain, PRD-68).** A 3-tier assessor (`consumers/chatbot/auto.py:586-640`): Redis cache (24h TTL per workspace+message-hash, `:926-939`), then ~20 ATOM regexes plus a ~450-line hardcoded keyword→platform-tool map (`:96-571`), then an LLM classification call that embeds a 2,000-token planning context pack (`:717-746`, PRD-164 S1) and a few-shot prompt (`:772-823`). Failure falls back to MOLECULE-with-tools rather than ATOM, deliberately, so a broken classifier cannot strip tools (`:868-877`) — a genuinely good failure posture. The result drives: ATOM = lightweight prompt + dispatcher-only tools; MOLECULE+ = full ContextService path; DELEGATE/MISSION = UniversalRouter agent selection (`api/chat.py:346-381`); ORGAN/ORGANISM = a mandatory mission-suggestion directive injected into the system prompt (`service.py:2031-2047`) plus a `mission-suggestion` SSE card (`api/chat.py:424-433`). Platform-hint requests never delegate — Auto keeps platform management for itself (`api/chat.py:318-332`).

**3. Context preparation.** `stream_response_with_agent` (`service.py:1851`) activates the agent concurrently with the first SSE frame (`:1893-1902`), loads tools from the single source `get_tools_for_agent` with semantic dispatcher-enum narrowing when `SEMANTIC_TOOL_ROUTING` is on (`:692-722`, `:1968-2003`), and builds messages via `_prepare_messages` (`:728-848`): the ATOM path is a hand-built light prompt with optional memory (`:850-957`); the full path delegates to `SmartChatOrchestrator.prepare_request` → `ContextService.build_context(mode=CHATBOT)` (`smart_orchestrator.py:150-267`), which owns memory retrieval, identity/persona injection, tool filtering, and the system prompt. A second, older rule-based classifier (`SmartIntentClassifier`, `consumers/chatbot/intent_classifier.py:48+`, 516 lines of regex tables) runs inside this path on every full turn to decide `tool_choice` and memory need (`smart_orchestrator.py:184-207`) — in addition to AutoBrain. Pinned documents are re-injected every turn (`service.py:1036-1059`, PRD-157 S5); the ContextGuard counts tokens and auto-compacts with model-aware thresholds, flushing key facts to memory before discarding (`core/context_guard.py:1-30`; invoked `service.py:833-843`, and again as LLM-failure recovery `:1472-1484`). Plan mode injects a research directive and then sets `use_tools = None` — all tools stripped (`service.py:806-826`).

**4. Composio injection.** For non-ATOM turns, `ComposioToolService.get_tools_for_step` swaps the generic `composio_execute` for per-action tool schemas scoped to the agent's connected apps, plus a scope system message imported from `api.recipe_executor` (`service.py:1065-1115` — a consumer importing from an API module; layering smell). If per-action resolution fails, the keyword-based `ComposioHintService` injects hint lines instead (`:1116-1130`).

**5. The loop.** The first LLM call is non-streaming (`service.py:2092-2094`). If tool calls come back, `_stream_tool_loop` (`:1232-1548`) drives the shared `ToolLoopExecutor` (`modules/tools/execution/tool_loop.py:166-312`): `while has_tool_calls and iteration < max_iterations` (`:242`), per-round stuck-loop breaker persisting the dead-end as a failure memory via `tool_outcome_capture` (`:249-260`, `:51-74` — the July dead-import is fixed), `finish_reason=length` malformed-JSON recovery (`:266-272`, `:477-511`), dedup + per-tool caps via the tracker (`:381`), tool exceptions surfaced to the model as tool content (`:429-433`), and token-budgeted result truncation (`:555-558`). Chat layers its behaviour through hooks: an SSE bridge queue (`service.py:1298-1316`), the Composio direct-action shortcut (`:1321-1335` → `_execute_composio_action:1550-1580`), search-spiral tracking (`:1582-1605`), loop-prevention system messages (`:1791-1845`), Composio action-not-mapped / invalid-parameter recovery with DB-seeded retry budgets (`:1607-1789`), fatal-error short-circuit and force-synthesis on dedup or 8+ attempts (`:1434-1461`). Every platform/registry tool call threads full caller context — `user_query`, `conversation_id`, one `turn_id` per user turn, `prior_action` (`:97-135`, `:1277-1356`, F017 fixed) — into `execute_and_format`, which feeds telemetry and the operating-graph edge builder. Iteration caps are DB policy, not code: `CHATBOT_MAX_TOOL_ITERATIONS` is a required seeded `system_settings` row (chat seeded at 25) that raises loudly if unseeded (`config.py:328-349`). Hitting the cap emits an honest `limit_reached` SSE event naming the setting (`service.py:1531-1546`).

**6. Egress.** The final response uploads inline base64 images to S3 (`:2137-2141`), then is **re-chunked** into 3-8-word "typewriter" chunks with deliberate `asyncio.sleep` pacing (`consumers/chatbot/streaming.py:309-376`) — there is no token streaming anywhere: `core/llm/manager.py` exposes only `generate_response` (`:612`) and a sync variant; the `generate_response_stream` branch in the legacy path (`service.py:2214`) can never be taken. Usage and finish frames are emitted, the assistant message saved, then post-turn work: fire-and-forget memory writes (distilled facts + transcript + daily summary + L1 session, `smart_orchestrator.py:365-434`) with the honest `memory_stored` event emitted only when durable facts actually persisted (`service.py:1156-1174`, PRD-159 S5); a FutureAGI live-traffic eval that is dark unless a worker URL/key is configured (`:1178-1191`; `core/services/futureagi_service.py:63-74`); agent metric counters (`:1193-1225`); and a chat-primitive heartbeat green/red for the turn (`:2172-2183`).

**7. Frontend.** `frontend/app/chat/page.tsx` (classic + Studio shells) with client-side `?chatId=` deep-linking that explicitly works around the dead `/chat/[id]` SSR route (`page.tsx:33-35`); widget→dashboard conversation handoff via sessionStorage (`:69-81`); the PRD-163 mission-approval card renders from `toolData.mission_approval` in `frontend/components/chatbot/chat.tsx:203-217`; composio chips show real running/error state with resolved action names (`message.tsx:264-319`, F037 fixed).

## C. Honest quality — maturity 3/5

**What is genuinely strong (and verified, not self-described):**

- **The loop is real and robust.** The executor matches the Claude-Code loop shape and carries robustness furniture most frameworks don't ship out of the box: exact+semantic dedup, per-tool caps with dispatcher-aware counting (`modules/tools/execution/tool_loop.py:381`, tracker), stuck-loop breaking that *learns* (persists the dead end as a failure memory, `:51-74`), `finish_reason=length` recovery (`:477-511`), errors-as-data to the model (`:429-433`), and force-synthesis fallbacks. The through-the-factory regression test net from W1 (`tests/test_prd171_execution_spine.py:89,141`) plus characterization tests (`tests/test_tool_loop_converged.py`) protect the seam that broke in July.
- **The July fixes actually landed.** Phase-0 verified F001 (kwarg crash) FIXED with seam guard; F017 (caller-context threading) FIXED — intent-conditioned learning edges can now materialize from real chat traffic; F035 (placebo model selector) FIXED — deleted, model resolves server-side; F037 (invisible Composio calls) FIXED with real action names; F038 (fabricated sidebar stats) FIXED (residue: the default `pilot · 11 op` workspace pill, `studio-sidebar.tsx:44,96`).
- **Caps are policy, honesty events exist.** DB-seeded iteration/retry budgets that refuse to boot unseeded (`config.py:328-356`), and a user-visible `limit_reached` message naming the setting (`service.py:1531-1546`) — a small thing that is exactly the right shape.
- **Good failure posture in the classifier.** LLM-classify failure falls back to MOLECULE-with-tools, not ATOM (`auto.py:868-877`), so the worst case adds schemas rather than lobotomizing the agent.

**Concrete defects, each with evidence:**

1. **Every chat belongs to user id=1.** `get_user_id` (`api/chat.py:82-89`) ignores the authenticated principal; chat creation, ownership checks, history, votes, and — worse — PRD-163 Q56 attribution all resolve to that constant: `_driving_clerk` is looked up from the same hardcoded id (`service.py:1268-1275`), so a mission created mid-chat is attributed to user 1's clerk id regardless of who is chatting. The ownership check `chat.user_id != user_id` compares the constant to itself — access control degenerates to workspace scoping. Real data: 22 users exist (census.md), 332 chats all hang off one. In any multi-user workspace this is shared history, misattributed approvals, and unusable per-user memory signal.
2. **There is no real streaming.** The "streaming" chat plane generates the complete response, then replays it as a typewriter with artificial sleeps (`streaming.py:309-376`; sole entry `manager.py:612`). Time-to-first-token for the synthesis equals full completion latency; on a long multi-tool turn the user watches chips, then a fake replay. July's loop-quality item 5 ("true token streaming of the final synthesis") was never picked up by any wave — no commit touches it. This is the single most user-visible quality gap on every surface including the INBUILD widget.
3. **Model-level overclaiming is observed in production and nothing guards it.** The only informative memories in the live DB are chat clippings of the founder catching Auto lying: "auto you are lying again", "You're right. I lied by implication", "That was me overclaiming. I can't edit the live blog/CMS…" (real-data-inventory → memory-short-term.md Q3, 2026-06-07). W10 fixed *UI* fabrications (F035/F037/F038), but there is no mechanism — prompt, post-turn check, or eval — that compares what Auto *claims it did* against `tool_execution_logs`. The claim-vs-executed check is mechanically computable and absent.
4. **Plan mode strips all tools** (`service.py:826`) — the July finding reproduces verbatim: Auto cannot read documents, query the graph, or list agents *while planning*, which is when it needs read access most. Claude Code's plan mode filters to read-only; this one filters to nothing.
5. **The Composio per-action shortcut bypasses the governed path.** `_execute_composio_action` calls `ComposioToolService.execute_action` directly (`service.py:1321-1335,1550-1580`), skipping `execute_and_format` → UnifiedToolExecutor — so no PolicyGate chokepoint (even flag-ON; residual F085/F060), no `tool_execution_logs` telemetry, no caller-context threading. The highest-volume external-action lane in chat is invisible to the W7 learning loop it was supposed to feed, and tool_execution_logs remains 100% synthetic (frozen 2026-05-05, tool-telemetry.md) partly because of this.
6. **Four routing layers with overlapping hardcoded vocabularies.** AutoBrain's ~450-line keyword map (`auto.py:120-571`) + SmartIntentClassifier's regex tables (`intent_classifier.py:59-150+`) + the semantic dispatcher narrowing + ComposioHint/verb maps (F071, NOT DONE) all classify the same utterance per turn. Two of these are rule tables that must be hand-maintained in lockstep with the tool registry; drift is a silent quality bug (a new platform tool is invisible to Tier-2 until someone edits a Python dict).
7. **Conversation state is vestigial.** `SmartChatIntegration` is constructed per request inside `_prepare_messages` (`service.py:755-761`), so `ConversationState` — `MEMORY_REFRESH_INTERVAL=5`, `user_name`, `messages_since_memory_fetch` (`smart_orchestrator.py:83-107,241-248`) — resets every turn. The refresh-interval logic can never trigger; memory is re-decided from scratch each turn.
8. **Dead code sits in the hot file.** `service.py` carries a 115-line duplicate `ToolExecutionTracker` (`:138-253`) that is never instantiated (the loop uses `modules/tools/execution/tool_execution_tracker.py`); the legacy `stream_response` (`:2185-2289`) and `_execute_pretriggered_tools` (`:2291+`) have zero non-test callers (phase0 F017 note). The 2,340-line service file violates the project's own 800-line rule with ~490 lines of it dead.
9. **The `/chat/[id]` zombie is still live-linked** (F036 NOT DONE): the SSR route 401→404s every SaaS request, yet `activity-feed.tsx:236`, `execution-detail.tsx:333`, and `recent-activity-widget.tsx:71` still `router.push` into it. The chat page's `?chatId=` param (`page.tsx:33-35`) is the workaround, not the fix.
10. **Same-session serialization is per-process only.** The session queue is an in-process `asyncio.Lock` (`core/session_queue.py`); with multiple uvicorn workers (the deployment runs several — the F027 evidence documents four), two requests for the same chat on different workers interleave freely: duplicate history loads, racing message saves.
11. **Latency is architecturally high and admitted in-code.** Full tool discovery "takes ~12s" for 45 tools per the code's own comment (`service.py:1961-1963`); the tool surface is rebuilt from DB+registry every turn; the Tier-3 classifier adds an LLM round-trip on cache miss; parallel tool calls don't exist (sequential `for` at `tool_loop.py:367`); and the collision-prone `call_{ms-timestamp}` id fallback survives (`tool_loop.py:529`).
12. **Usage has flatlined.** Real data: 332 chats / 1,278 messages, newest **2026-06-27** (census.md) — a week of zero chat activity at capture while board tasks run daily through 07-03. The founder — the platform's one daily user — has drifted off its flagship surface. Correlate with §C.3 (trust) and §C.2 (latency): the data is consistent with a user who stopped believing the surface.

**Maturity: 3/5.** The loop spine alone would score 4+ — it is correct, tested, robust, and shared. The *conversational core as a product surface* scores lower: fake streaming, single-user attribution, an observed and unguarded honesty failure mode, a bypassed governance/telemetry lane, four overlapping routers, and dead weight in its central file. It is a very good engine in a cab with a painted-on speedometer.

## D. Competitive teardown

**OpenAI Agents SDK / Responses API** (Assistants API sunsetting mid-2026). The SDK gives first-class `Agent` + `Runner` with **sessions** (persistent conversation state), **handoffs** (typed agent-to-agent delegation mid-run), **guardrails** (typed input/output validators that run in parallel with generation), and built-in **tracing** spans for every run — plus true server-side streamed events end-to-end. ([openai.github.io/openai-agents-python](https://openai.github.io/openai-agents-python/), [handoffs](https://openai.github.io/openai-agents-python/handoffs/), [guardrails](https://openai.github.io/openai-agents-python/guardrails/), [platform agents guide](https://developers.openai.com/api/docs/guides/agents), [new tools announcement](https://openai.com/index/new-tools-for-building-agents/)). *Better than Automatos at:* streaming (typed event stream vs re-chunked strings), tracing (spans vs scattered log lines), guardrails as a typed contract (vs the flag-off policy plane). *Automatos parallels or beats it at:* UniversalRouter ≈ handoffs but pre-turn only; dedup/stuck/length-recovery furniture is richer than the SDK's default loop; DB-backed caps beat code constants.

**Claude Agent SDK.** The direct architectural ancestor of this loop, and its clearest teardown mirror: **subagents** with isolated contexts, restricted tools, and *parallel* execution mid-run; **hooks** as deterministic pre/post-tool policy code; **automatic compaction** for indefinitely long sessions (subagent transcripts compact independently); skills with progressive disclosure; MCP as a universal tool source. ([platform.claude.com/docs/en/agent-sdk/subagents](https://platform.claude.com/docs/en/agent-sdk/subagents), [code.claude.com/docs/en/sub-agents](https://code.claude.com/docs/en/sub-agents), [architecture overview](https://www.penligent.ai/hackinglabs/inside-claude-code-the-architecture-behind-tools-memory-hooks-and-mcp/)). *Better at:* mid-loop delegation (Automatos delegation is a pre-turn router decision; there is no child-run with isolated transcript inside a chat turn), parallel tool execution, wired policy hooks (Automatos has the `on_pre_tool` seam, `tool_loop.py:396-419`, but chat never passes it — `service.py:1498-1508`). *Automatos parallels:* ContextGuard ≈ auto-compaction (and flushes facts to memory first, which is a nice touch); skills substrate exists (PRD-22).

**Letta.** The stateful-agents runtime (MemGPT lineage): agents are server-side objects with persistent **memory blocks** editable via API and shareable across agents, and **sleep-time compute** — background agents that reflect on and rewrite the primary agent's memory between turns. Their v1 loop redesign is directly instructive: they *deleted* tool-based control flow (heartbeats, `send_message`) to stay in-distribution with how frontier models are trained. ([letta.com/blog/letta-v1-agent](https://www.letta.com/blog/letta-v1-agent), [sleep-time compute](https://www.letta.com/blog/sleep-time-compute/), [stateful agents docs](https://docs.letta.com/guides/core-concepts/stateful-agents), [github.com/letta-ai/letta](https://github.com/letta-ai/letta)). *Better at:* conversation state as a first-class server object (vs Automatos's per-request vestigial `ConversationState`), memory that improves between turns (vs fire-and-forget writes that produced the 87%-chatter store in memory-short-term.md). *Automatos parallels:* the loop-prevention instincts match Letta's lessons; Automatos's DB-seeded caps are analogous policy.

**Provider primitives Automatos leaves on the table** (adjacent, not a competitor): Anthropic ships **fine-grained tool streaming** (large tool args stream, cutting ~15s waits to ~3s), **interleaved thinking** between tool calls, and **parallel tool use** — none consumable through the current OpenAI-shaped non-streaming envelope. ([fine-grained tool streaming](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/fine-grained-tool-streaming), [streaming](https://docs.anthropic.com/en/docs/build-with-claude/streaming), [tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)).

**Where Automatos actually stands:** the loop robustness layer is genuinely competitive — dedup, spiral detection, length recovery, and stuck-loop *learning* exceed what any of the three give you by default. The delivery and state layers are behind all three: no token streaming (all three have it), no mid-loop subagents (Claude SDK), no typed tracing (OpenAI), no server-side conversation state or background memory refinement (Letta). None of the three, however, ships Automatos's platform coupling — per-workspace agents, board/mission handoff, Composio surface, DB-policy caps — which is the actual reason the verdict below is not "replace."

## E. Build / extend / adopt / replace — verdict: **EXTEND**

**Keep the loop; do not adopt an external orchestration framework.** The reuse-over-build bias was applied and fails here for the core: swapping to OpenAI Agents SDK / LangGraph-class runtimes would (a) forfeit the loop robustness furniture that is demonstrably ahead, (b) strand the three-surface convergence (chat/voice/widget) plus the headless `AgentFactory` path on a second engine — recreating exactly the multi-loop drift the July review condemned, and (c) not fix any of the actual defects (attribution, streaming, honesty, routing sprawl are all Automatos-side integration problems a framework cannot solve). The expensive artifact — a correct, tested, multi-surface loop — already exists; nothing external buys a better one at reasonable migration cost.

**Adopt narrowly, at the provider seam:**
- **True streaming via the provider APIs** (OpenAI/Anthropic/OpenRouter all stream) — an LLM-manager change (`core/llm/manager.py:612`) plus SSE passthrough, replacing the typewriter. No vendor cost beyond what is already paid.
- **Anthropic parallel tool use + fine-grained tool streaming + interleaved thinking** in `anthropic_client.py` normalization — free capability upgrades on models already routed to.
- **Pattern-adopt (not dependency-adopt)** from Claude Agent SDK: subagents as child runs over the (now-revived) delegation path, and hooks via the already-built `on_pre_tool` seam; from Letta: a background memory-refinement job on chat transcripts (this belongs to the memory dossier but the trigger lives here).

**Kill list within the module:** the duplicate `ToolExecutionTracker` (`service.py:138-253`), legacy `stream_response` + `_execute_pretriggered_tools` (`service.py:2185-2340+`), the `/chat/[id]` SSR zombie plus its three live links, and (pending the routing consolidation in J-6) the standalone `SmartIntentClassifier` as a second rule engine.

## G. Quality metric

Nothing about conversation quality is a tracked number today: `rag_feedback` is empty, `memory_access_log` last wrote 2026-03-11, the vote endpoint exists (`api/chat.py:640-663`) but no vote counts surfaced in the census, tool telemetry is 100% synthetic, and the FutureAGI eval hook is dark without a configured worker (`futureagi_service.py:63-74`). The July T3 thesis applies with full force here.

**Proposed metric set (feeds T3), in priority order:**
1. **Overclaim rate** — the metric that catches the observed failure: % of assistant turns whose claimed actions ("I created…", "I published…", "I fixed…") have no matching row in `tool_execution_logs`/`llm_usage` for that turn. Computable offline from existing tables once the Composio shortcut is telemetered (J-3); judge = cheap LLM classifier over (response, executed-tool list). Target: <1%.
2. **Turn outcome signal** — thumbs (`votes` table, already wired end-to-end) + `limit_reached` / forced-synthesis / stuck-break / dedup-skip counters, which are all already logged per turn (`service.py:1453-1460`, `tool_loop.py:253-260,383`) but aggregated nowhere. A daily rollup per workspace is a one-table job.
3. **Latency percentiles** — TTFT (today ≈ full completion time) and turn wall-clock, from the `preparation_time_ms` already computed (`smart_orchestrator.py:253`) plus timestamps already in `llm_usage` (`request_type='chat'`).
4. **Routing accuracy** — AutoBrain tier-2/tier-3 agreement rate and misclassification audit (ATOM-that-needed-tools), measurable by replaying the Redis-cached assessments against a labeled sample; the `x-auto-*` response headers (`api/chat.py:397-403`) already carry the ground truth per turn.
5. **Offline conversational eval** — a golden multi-turn set (incl. the real INBUILD transcripts) scored by LLM-judge for helpfulness/honesty, run in the same non-required CI lane pattern the NL2SQL eval already established.

**The number today:** unmeasured; the only quantified signals are adoption (332 chats, stalled 2026-06-27) and the qualitative honesty failures in the memory store.

## H. Cost note (informational)

Per chat turn: 0-1 AutoBrain Tier-3 classification (~$0.001 and ~200ms by the code's own estimate, `auto.py:14-17`; amortized by the 24h Redis cache and regex tiers) + 1 main completion + 1 completion per loop iteration (cap 25, DB-seeded), each re-sending the full grown transcript plus the tool-schema block; tool results are capped at 2,000 tokens each before re-entry (`service.py:60`, `tool_loop.py:555-558`); ContextGuard compacts near the model window. There is **no prompt caching** on any client (no `cache_control` is ever set; only a passthrough field exists in `bedrock_client.py:371`) — on multi-iteration turns the system prompt + tool schemas are re-billed every round, which for a 25-iteration worst case is the dominant cost. Real attribution exists: `llm_usage` (31,081 rows, current) carries `request_type='chat'` (`manager.py:392-400`), so per-turn dollars are queryable today even though no surface reports them. A real datapoint for scale: one 7-task blog mission consumed 264k tokens (memory-short-term.md); chat turns are typically 1-2 orders below that.

## I. UX / surface

**What exists:** a polished chat surface — classic + Studio three-column shells (`frontend/app/chat/page.tsx:130-189`), history sidebar, widget→dashboard handoff (`:69-81`), `?chatId=` deep links, mission-suggestion and mission-approval cards (`chat.tsx:203-217`), honest tool chips with resolved Composio action names, memory-injected/stored events, the `limit_reached` notice, and routing/complexity metadata already emitted as `x-auto-*` headers (`api/chat.py:397-403`) that the UI never displays.

**Concrete changes, in order of client impact:**
1. **Fix the broken hand-offs into chat**: delete `/chat/[id]` and repoint the three activity-surface links to `/chat?chatId=` (they currently 404 — the Command Center's "open the conversation" affordance is broken, F036).
2. **Perceived-latency honesty**: until real streaming lands (J-2), show generation state truthfully ("thinking… running 3 tools… writing") instead of a fake typewriter; after J-2, stream tokens.
3. **Surface the brain**: a small "why this agent / complexity / what I'm allowed to do" popover fed by the already-present `x-auto-*` headers and the agent-info frame — this is the Jarvis-legibility the OS thesis wants, and it is nearly free.
4. **Plan mode as a first-class mode**: pair J-4 (read-only tools) with a visible plan-mode banner, plan artifact rendering, and the existing plan→mission launch card so the loop from "discuss" to "dispatch" is one surface.
5. **Per-user identity**: once J-1 lands, chat history, votes, and approval cards become per-person; today the sidebar shows one communal history per workspace.
6. **Cost/iteration visibility**: the usage frame already carries tokens per turn — render cumulative turn cost and iteration count in the message footer for admin users; it disciplines both the model and the workspace budget conversation.
