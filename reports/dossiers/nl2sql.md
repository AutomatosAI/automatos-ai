# Module Dossier — NL2SQL Analytics (`nl2sql`)

**Tier:** deep · **Status:** live (advertised) — *effectively unused in production* · **Reviewed:** 2026-07-04, main @ pinned tree
**Scope:** `orchestrator/modules/nl2sql/` (5,810 LOC / 24 files), `orchestrator/api/database_knowledge.py` (1,068 LOC), `orchestrator/modules/tools/execution/exec_research.py`, `orchestrator/tests/nl2sql_eval/`, frontend Databases tab (`frontend/components/knowledge/*`, ~2,980 LOC).
**Security/adversarial lens deliberately excluded** — that runs as the separate Opus hardening pass. Residual security items (F019-half read-only-role gap) are noted only as cross-references to the Phase-0 residual map, not re-analysed here.

## A. What it is

NL2SQL is the platform's "chat with a connected database" capability: a workspace connects an external Postgres/MySQL database as a *knowledge source* (credentials via the credential store), the platform introspects its schema, and then users — or agents, via the `query_database` / `smart_query_database` tools — ask natural-language questions that are converted to SQL by an LLM, validated by a sqlglot AST validator (SELECT-only, table allowlist, LIMIT injection), executed under timeout/EXPLAIN guards, and returned with a confidence score. Around that spine sits a PRD-160 "accuracy stack": a Vanna-style verified-example store with persisted embeddings for few-shot retrieval, an (intended) per-connection semantic layer, per-query audit rows, a benchmark endpoint, and a self-contained execution-accuracy eval harness in CI. It exists to serve the North Star directly: an agent that can accurately answer questions about a client's own operational data (e.g. a Shopify merchant's order database) without a human writing SQL.

## B. What it does — real implementation and data path

**Entry points (4):**
1. **Agent tools** — `query_database` and `smart_query_database` registered at `modules/tools/registry/tool_registry.py:658,699`, dispatched via `modules/tools/execution/unified_executor.py:105-106` to `modules/tools/execution/exec_research.py:135-171`. The shared `_run_nl2sql` (`exec_research.py:41-132`) fail-closes without a workspace (`:55-65`), resolves the source strictly inside the caller's workspace (`:81` → `service.resolve_source_id`, `modules/nl2sql/service.py:976-1020`), and writes an audit row after every call (`:123`).
2. **API** — `POST /api/knowledge/sources/database/{id}/query` (`api/database_knowledge.py:163-203`) → `smart_query` with the authenticated `workspace_id` (`:185`), then audit (`:189`).
3. **Dev SQL runner** — `POST /{id}/query/sql` (`api/database_knowledge.py:467-652`): validator + direct execution + audit rows; labeled "DEV-ONLY" but routed in prod.
4. **Query templates** — `POST /templates/{id}/execute` (`api/database_knowledge.py:437-464`) → `service.execute_template` (`service.py:1040-1107`) with bound `:name` parameters.

**The NL pipeline** (`service.py:372-618`, `query_database`):
- Workspace-scoped source fetch (`_get_source`, `service.py:99-128`; scoping added W3-S9) → credential decrypt (`:412-423`) → stored `schema_metadata` (`:426-439`; introspection required first).
- Few-shot retrieval from the example store (`:441-454`) — `SQLExampleStore.get_similar_examples` defaults to **verified-only**, cosine over embeddings persisted as JSONB float arrays at write time (`modules/nl2sql/training/example_store.py:89-101,129-190`), keyword-overlap fallback.
- NL2SQL-mode system prompt from ContextService (`:456-476`).
- **Value-sampling** (`_augment_schema_with_samples`, `:304-370`): probes low-cardinality char/enum/bool columns (`SELECT DISTINCT … LIMIT 13`, ≤40 columns, 5s timeout) so real literals (`status ∈ {active,churned}`) reach the prompt — a genuinely SOTA-aligned grounding technique.
- Up to 3 generation attempts with **error self-correction**: generate (`query/nl2sql_service.py:47-116`) → AST validate (`query/validator.py:234-298`) → execute under guards (`_run_sql_with_guards`, `service.py:271-302`: per-statement `statement_timeout` + `EXPLAIN` dry-run); failures feed back as `error_context`/`previous_attempts` into the next prompt (`nl2sql_service.py:229-235`).
- On first-try success, **auto-train** stores the pair *unverified* (`:561-573`) — it cannot pollute few-shot until a human verifies (correct Vanna-style gating).
- Confidence scoring (`:576-578` → `query/confidence.py`), heartbeat primitive emit (`primitive_heartbeat.py:30-61` — the Command Center `nl2sql` tile is honestly wired), structured result.

**The validator** (`query/validator.py`, 298 LOC) is the module's strongest artifact: real sqlglot AST walk — single statement (`:249-265`), read-only roots only (`:271-272`), `SELECT … INTO` rejected (`:274-275`), DML/DDL node walk (`:277-279`), a ~40-name side-effecting **function denylist** (`query_to_xml`, `dblink_exec`, `lo_export`, `pg_sleep`, … `:48-66`, enforced `:286-290` — the W2/PRD-172 close of F019's exploit half), table allowlist vs connection schema (`:140-164`), conservative hallucinated-column rejection (`:166-212`), AST-level LIMIT inject/cap (`:214-230`). Covered by two test files (`modules/nl2sql/tests/test_validator.py`, 390 LOC; `tests/security/test_nl2sql_validator.py`).

**Introspection** (`schema/introspection.py`): information_schema walk, per-column `DISTINCT … LIMIT 5` samples on *every* non-JSON column (`:107-121`), `COUNT(*)` row counts (`:129-131`), FK → relationships (`:150-174`). **No table/column descriptions or comments are captured — and there is no surface to add any.**

**Eval harness** (`tests/nl2sql_eval/`): self-contained SQLite execution-accuracy harness (order-insensitive result-set comparison, `harness.py:64-138`), 20 golden questions (`questions.json`), CI job `nl2sql-eval` (`.github/workflows/test.yml:150`) — always-on goldens-integrity checks; the actual LLM generation eval is gated behind `RUN_NL2SQL_EVAL=1`.

## C. Honest quality — inspected against real behaviour and real data

**Maturity: 2 / 5.** The right skeleton with a real validator and real tenancy discipline — but **zero production evidence it works**, its highest-leverage accuracy feature is a placebo end-to-end, several advertised surfaces are dead, and its own quality number is a placeholder.

**C.1 The real-data verdict: the module has effectively never run.**
From the live Railway production DB (2026-07-04, `evidence/data/nl2sql-audit.md`):

| table | rows |
|---|---:|
| `database_query_audit` (per-query choke-point, both entry points wired) | **0** |
| `nl2sql_benchmark_runs` / `nl2sql_benchmark_results` | **0 / 0** |
| `nl2sql_training_examples` | **2** |

Zero audited queries ever, across 21 real workspaces. Either no workspace has ever exercised NL2SQL, or an early call failed before audit. Everything the stack is built around — few-shot learning, auto-train, verification, benchmark trends, audit history — has never processed real traffic. The repo baseline confirms it: `tests/nl2sql_eval/baseline.json` still records `accuracy: 0.0` — the 2026-06-12 placeholder ("0.0 until a generation run with a real LLM records a number"). **The platform has never measured its own NL2SQL accuracy, offline or online.**

**C.2 The semantic layer is a four-layer placebo (worse than F047 recorded).**
The read side is real: the generation prompt renders `semantic_layer['instructions']`/`business_context` as authoritative business definitions (`query/nl2sql_service.py:199-207`) and the layer is injected at generation (`service.py:496-500`). But nothing can ever reach it:
1. **Load is broken:** `SemanticLayerBuilder.tsx:126` GETs `/{id}/semantic`; **no GET route exists** (only `POST`, `api/database_knowledge.py:294`) → 405 on every editor load, swallowed to console.
2. **Save always crashes:** `service.update_semantic_layer` (`service.py:654-678`) calls `self._get_schema_context(source)` (`:666`) and `self._validate_semantic_definitions(…)` (`:667`) — **neither method exists anywhere in the orchestrator** (repo-wide grep: zero definitions). Every save raises AttributeError → route 400s (`api:330-332`); the frontend swallows that too (`SemanticLayerBuilder.tsx:161-164`), so the admin believes it saved.
3. **Even if it ran, it wouldn't persist:** `_get_source` closes its session in `finally` (`service.py:127-128`); `:670-674` assigns onto the detached ORM object with no session/commit.
4. **Even if it persisted, the reader would crash:** the writer stores `metrics` as a **list** of `{name, sql_expression, …}` (`:671`), the reader calls `semantic_layer['metrics'].items()` and `metric.get('sql')` (`nl2sql_service.py:209-212`) — dict protocol, different key. And that AttributeError would escape `generate_sql` uncaught (`_build_prompt` at `:74` sits *outside* the try at `:84`), crashing the whole query.
Plus the previously-banked F047: the `instructions` field — the one competitors prove matters most — has **no write path at all** (residual map `phase0-residual-map.md:296-298`). For the feature every best-in-class player treats as the accuracy foundation (§D), Automatos ships a UI that can neither read nor write, over a service method that cannot execute, in a format the generator couldn't consume.

**C.3 The "schema linker" doesn't exist in the wired path — and isn't what it claims even off-path.**
Production constructs `NaturalLanguageToSQLService(llm_provider=…)` with no linker and no store (`service.py:492`; benchmark route likewise, `api:999`), so linking falls back to keyword scoring (`nl2sql_service.py:137-138` → `_get_relevant_tables:247-320`). The standalone `SchemaLinker` (`query/schema_linker.py`) has **zero callers** (only the module docstring references it) — and despite its docstring's "embedding-based table/column ranking", it assigns `embedding_manager` and **never uses it** (`schema_linker.py:44-45`; the file contains no embedding code). The capability-map's "embedding schema linking" is the code's self-description and is false; the only real embeddings in this module are the example-store question vectors. Since introspection captures no descriptions, the keyword scorer's description factor (`nl2sql_service.py:288-293`) is also dead weight.

**C.4 The `smart_query` analysis lane is permanently broken — and it's the default API path.**
`smart_query` keyword-routes any question containing *plot/chart/graph/trend/correlation/visualize/compare/forecast* to `analyze_database` → PandasAI (`service.py:963-969`). **`pandasai` is not in `requirements.txt`** (grep: no hit) → `get_pandasai_service()` returns None (`modules/tools/services/pandas_ai_service.py:13-25`) → every such query returns "PandasAI service is not enabled or configured." (`service.py:918-922`). The chat API route calls `smart_query` (`api:178`), so a user typing "show me revenue **trend** by month" into the product's own Query Explorer hard-fails, while "revenue by month" works. The `smart_query_database` tool card's own examples — "Show me sales trends", "Compare performance" (`tool_registry.py:745-746`) — route straight into the dead lane.

**C.5 Tool cards actively mislead the agent LLM.**
- `smart_query_database` advertises "AI-powered clarification, rephrasing, explanation, and visualization" with parameters `skip_clarification`, `clarification_answers`, `include_visualization` (`tool_registry.py:701-741`); the executor reads **only** `query` and `database_name` (`exec_research.py:67-71`). Those features live in the 0-caller `intelligence/` decoy (F080) — the dead package's capabilities are still *advertised to every agent on every turn*.
- `query_database` claims it queries "knowledge sources **or the main Automatos database**" with examples like "Show failed workflows in the last 14 days" (`tool_registry.py:660-692`) — the main-DB path was deliberately deleted by PRD-156 S3 (`exec_research.py:3-12`). An agent picking this tool for a platform question gets "No database source is configured for this workspace." The Explorer's suggested queries reference `workflow_executions`/`system_metrics` platform tables too (`DatabaseQueryExplorer.tsx:258-260`) — stale pre-156 framing.
- `analysis_prompt` (query_database param) is likewise read by nothing.

**C.6 Confidence can structurally never be "high".**
Production builds `ScoringContext` without `linked_schema` (max 25 pts) or `metrics_matched` (max 15) (`service.py:637-642`) → ceiling 60/100 < the 70 "high"/auto_execute threshold (`query/confidence.py:87-89`). With the empty example store, realistic scores are ≤30 → permanently "low / manual_review". The number shown in the Explorer is a deflated artifact of unwired factors, not a signal.

**C.7 The product benchmark measures the wrong thing; the good harness is disconnected.**
`POST /{id}/benchmark/run` uses normalized **exact string match** and copies it into `execution_match` with a TODO (`benchmarks/runner.py:83-87`) — the metric the field abandoned years ago (semantically-equivalent SQL differs textually). Meanwhile the *correct* execution-accuracy harness exists 30cm away in `tests/nl2sql_eval/harness.py` and isn't used by the product endpoint. The one UI consumer, `DatabaseQueryAnalytics`, hardcodes `sources[0]` (`frontend/components/context/DatabaseQueryAnalytics.tsx:37-39,193-195`) and lives on the Context-Engineering page, not the Databases tab. And the eval set itself is toy-tier: 20 single/two-table questions (`questions.json`) — nothing like BIRD's dirty-value, external-knowledge difficulty.

**C.8 Placebo surfaces and dead limbs (kill-list inputs).**
- **Query Templates:** `DatabaseQueryTemplate` has **zero creation sites** (model only; no API create, no seeds) — `QueryTemplatesGrid` + the PRD-160-"fixed" execute button operate over an unpopulatable table.
- **`total_queries_executed` / `avg_query_time_ms`** on the sources list are never written anywhere (defined `core/models/database_knowledge.py:69`, only read `api:98,359-360`) — permanent fake zeros in the UI.
- **`intelligence/` decoy:** 1,687 LOC, zero external callers, still exported (`modules/nl2sql/__init__.py:61-68`) — F080 confirmed again, grew since July.
- **Legacy PRD-21 limb inside `service.py`** (`:680-883`): `_execute_query:762` calls `self._build_connection_string` which **does not exist** (AttributeError if ever reached); `_validate_sql`'s regex-era checks and `_build_sql_generation_prompt` are shadow duplicates of the real pipeline.
- **`add_ddl`/`add_documentation`** (`example_store.py:307-339`): Vanna's training triad imitated, zero callers — and their shape (stuffing DDL/doc text into the `sql` field of *verified examples*) would pollute few-shot prompts if ever called.
- **UX honesty:** on `success:false` (HTTP 200) the Explorer still fires `toast.success("Query executed successfully! … rows returned")` unconditionally (`DatabaseQueryExplorer.tsx:164`).
- Residual (banked, for the Opus pass): execution still runs on the source's stored write-capable credentials with no read-only-role/`SET TRANSACTION READ ONLY` backstop — F019's open half (`phase0-residual-map.md:221-222`).

**C.9 What is genuinely good.**
The workspace-scoping discipline is exemplary post-PRD-160/172 (fail-closed tool path, scoped source resolution, scoped audit reads `api:674-702`); the AST validator is real engineering with real tests; the self-correction loop, EXPLAIN dry-run, value sampling, verified-only few-shot with persisted embeddings, and the dual-entry audit choke-point are all the *correct* modern shapes; the eval harness design (execution accuracy, seeded, no-regression gate, non-required CI) is the best eval artifact on the platform and the natural template for the T3 unified harness. The human-verification loop is wired end-to-end in the UI (thumbs-up → verified example → few-shot; `DatabaseQueryExplorer.tsx:236-253,475`). This is why the score is 2 and not 1: the skeleton is competitive; the productization and the proof are absent.

## D. Competitive teardown

**1. Snowflake Cortex Analyst** — the reference for *semantic-model-first* NL2SQL. A YAML/semantic-view model (logical tables, dimensions, metrics, relationships) plus a **Verified Query Repository** and **custom instructions** drive generation; Snowflake reports **~20% accuracy uplift from the semantic model alone** across four test datasets, and runs an agentic multi-model selection pipeline with multi-turn follow-ups, priced per message over a REST API ([docs](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst), [VQR docs](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst/verified-query-repository), [engineering blog](https://www.snowflake.com/en/blog/engineering/agentic-semantic-model-text-to-sql/)). A GitLab production deployment on this pattern went 60% → 85–95% (simple) / ~75% (complex) accuracy ([ZenML LLMOps case study](https://www.zenml.io/llmops-database/natural-language-analytics-with-snowflake-cortex-for-self-service-bi)). **Beats Automatos on:** a semantic layer that actually works (Automatos' is a placebo, C.2); verified-query optimization loops; measured accuracy. **Not adoptable:** Snowflake-only.

**2. Databricks AI/BI Genie** — Genie Spaces package datasets + **text instructions + example queries + trusted/certified assets**, with **built-in benchmarks** (question sets with reference SQL, scored inside the product) and a **good/bad feedback loop** that curates SME-approved queries back into examples ([docs](https://docs.databricks.com/aws/en/genie/), [best-practices guide](https://www.databricks.com/blog/data-dialogue-best-practices-guide-building-high-performing-genie-spaces), [GA blog](https://www.databricks.com/blog/aibi-genie-now-generally-available)). **Beats Automatos on:** the operationalized measure-and-improve loop as a product surface (Automatos has benchmark tables with 0 rows and an exact-match metric); instruction authoring. **Not adoptable:** Databricks-only.

**3. Vanna.AI (MIT, OSS)** — the RAG-for-SQL library Automatos' example store explicitly imitates ("Vanna-inspired", `example_store.py:2`): the training triad of **DDL + documentation + question-SQL pairs** in a pluggable vector store, LLM-agnostic, self-hostable ([GitHub/docs](https://github.com/vanna-ai/vanna), [Qdrant integration docs](https://qdrant.tech/documentation/frameworks/vanna-ai/)). **Beats Automatos on:** the training loop actually being fed (its whole UX funnels users into training), community-hardened prompting, chart generation. **Honest negative for Vanna:** its dynamic Plotly-code path produced a CVSS-critical prompt-injection→RCE (CVE-2024-5565, fixed ≥0.5.6) — its execution-side guarding is *weaker* than Automatos' AST validator + no-exec design ([JFrog analysis](https://jfrog.com/blog/prompt-injection-attack-code-execution-in-vanna-ai-cve-2024-5565/), [Hacker News writeup](https://thehackernews.com/2024/06/prompt-injection-flaw-in-vanna-ai.html)). Automatos' validator/tenancy layer is genuinely ahead here.

**4. WrenAI (Canner, OSS)** — GenBI agent with **MDL**, a JSON semantic layer encoding models/joins/metrics/definitions compiled into LLM context, SQL validated against the semantic model and transpiled per dialect (DataFusion), 20+ sources, charts/reports ([GitHub](https://github.com/Canner/WrenAI), [OSS page](https://www.getwren.ai/oss), [DataFusion post](https://www.getwren.ai/post/powering-semantic-sql-for-ai-agents-with-apache-datafusion)). **Beats Automatos on:** a real, open semantic-layer implementation — the closest OSS analog to Cortex's model — and join-disambiguation by construction. It is, however, a whole separate BI product (own UI/services), heavy to embed as a library.

**The external accuracy bar (for T3 calibration):** BIRD execution accuracy — human 92.96%; top pipelines ~80–82% (Gemini-SQL2 80.04% EX, June 2026; AskData+GPT-4o 81.95%); best open model Arctic-Text2SQL-R1-32B 71.8% ([leaderboard mirror](https://llm-stats.com/benchmarks/bird-sql-(dev)), [Snowflake Arctic blog](https://www.snowflake.com/en/engineering-blog/arctic-text2sql-r1-sql-generation-benchmark/), [BIRD gap analysis](https://beancount.io/bean-labs/research-logs/2026/06/06/bird-benchmark-text-to-sql-real-database-gap)). Notably, the field's consensus is that the remaining gap closes through **semantic layers and verified examples**, not raw models ([MotherDuck: "your data model is the semantic layer"](https://motherduck.com/blog/bird-bench-and-data-models/)) — exactly the two legs that are broken (C.2) and unfed (C.1) here.

**Where Automatos actually stands:** behind all four on accuracy infrastructure (no working semantic layer, no measured accuracy, no operating feedback loop); ahead of Vanna on execution guarding and true multi-tenant scoping; roughly at Vanna-parity on pipeline shape. Its unique asset — deep integration into an agent platform (workspace-scoped tool, audit plane, heartbeat, chat) — is precisely what none of the four have, and it is the reason to fix rather than abandon.

## E. Build / extend / adopt / replace — verdict

**EXTEND (narrowed), with two targeted adoptions of *patterns* — plus a hard kill-list. Do not adopt a whole external engine; do not keep building new surface.**

- **Why not adopt wholesale:** the two best-in-class systems (Cortex Analyst, Genie) are locked to their platforms — useless for querying an arbitrary client Postgres/MySQL. WrenAI is a full parallel product (own services/UI; AGPL-3.0 licensing to check) — integration cost exceeds fixing what's here. Vanna (MIT) is adoptable as a library, but what it would replace — example store + prompt assembly — is the part Automatos already has working and workspace-scoped; Vanna would *not* fix the three actual gaps (placebo semantic layer, zero usage, unmeasured accuracy), and its execution side is weaker than the in-house validator (CVE-2024-5565 history). Nothing external wins where this module is actually losing.
- **What to adopt as patterns (not dependencies):**
  1. **Cortex/Wren-style semantic model** — replace the broken metrics/dimensions editor + dataclass path with one per-source *semantic document* (instructions + definitions + metric SQL, YAML/JSON on `DatabaseKnowledgeSource.semantic_layer`), one working GET/PUT route, rendered exactly where `nl2sql_service.py:199-218` already reads. Snowflake's ~20% uplift claim makes this the highest single accuracy lever available at S-effort.
  2. **Genie-style benchmark-in-product** — retire the exact-match runner and re-point the benchmark endpoint at the existing execution-accuracy harness pattern (compare result sets against the source, or a sampled snapshot).
- **What stays in-house:** validator, workspace scoping, audit choke-point, example store, eval harness — all correct and already integrated with the policy/audit/heartbeat planes.
- **Rough cost:** all extension work is S–M items (see J); no new vendor spend. Optional: adopt BIRD-mini (public dev subset) as an external yardstick — free.

## G. Quality metric

**Primary (offline): execution accuracy** — % of eval questions whose generated SQL returns the golden result set. The harness exists (`tests/nl2sql_eval/harness.py`); the discipline doesn't. Targets: honest baseline first, then the PRD-160 goal (≥ baseline +15pts on a 30-question set).
**Secondary (offline): BIRD-mini EX** on a fixed public subset for external comparability (top pipelines ~80%, human ~93% — §D).
**Online (from the audit choke-point, once fed):** success rate (`success=true` / total), correction rate (attempts>1 / total), human-verify rate (verified examples / distinct questions), and per-source verified-example count (the Vanna/Genie leading indicator of accuracy).
**Today's numbers:** offline **0.0 (placeholder — never run)**; online **n/a (0 audited queries ever)**. That is the honest state: *unmeasured*. This module should be the first CI-gated lane of the T3 unified harness — its harness is the platform's best eval artifact and the template.

## H. Cost note (informational)

Per NL query: 1–3 generation calls (schema prompt = up to 10 tables × columns + samples + few-shot ≈ 1.5–5k input / 100–300 output tokens per attempt) + 1 embedding call (few-shot lookup) + up to 40 `SELECT DISTINCT … LIMIT 13` probes on the client DB (5s cap; mostly skipped when introspection already sampled) + EXPLAIN + execute. Order of magnitude **$0.002–0.02 per question** on a mid-tier model at current prices — dominated by schema tokens, so the semantic-model/linking work in J also *cuts* cost. Introspection is the heavy one-off: `COUNT(*)` + per-column DISTINCT over every table (`introspection.py:107-131`) — full scans on big client DBs; fine at SMB scale, needs sampling/estimates (`pg_class.reltuples`) beyond it.

## I. UX / surface

**Where it lives:** Knowledge page → Databases tab (`frontend/components/documents/document-management.tsx:1130-1163`): Query Explorer, Semantic Layer, Templates, Training Examples; plus `DatabaseQueryAnalytics` stranded on the Context-Engineering page (`context-engineering.tsx:540`); plus a real Command Center heartbeat tile (green/down per query, honest-unknown when unscoped — `primitive_heartbeat.py`).

**Concrete changes (all grounded in C):**
1. **Stop lying to the user.** Explorer must branch on `data.success` — no success toast + no "Saved" silence on failed semantic saves (`DatabaseQueryExplorer.tsx:164`, `SemanticLayerBuilder.tsx:161-164`). Surface `result.error`, `attempts`, and the corrections trace (the backend already returns them, `service.py:585-596`) — showing the self-correction is a trust feature.
2. **Semantic tab → one "Business definitions" document** (instructions textarea + optional metric rows) replacing the 846-line metrics/dimensions builder that can't load or save. This is the tab that makes accuracy user-tunable — today it's décor.
3. **Remove or feed the Templates tab** — currently a grid over a table nothing can populate (C.8). Cheapest honest fix: "Save as template" from a successful Explorer query (producer + the existing executor).
4. **Move analytics under each source** (benchmark history, success rate, verified-example count, last-introspected) and kill the `sources[0]` hardcode; the source card's fake `total_queries_executed` either gets written (from audit counts) or removed.
5. **Regenerate suggested queries from the connected schema** (table names are in `schema_metadata`), not stale platform tables (`DatabaseQueryExplorer.tsx:258-260`).
6. **Agent-side surface is part of UX:** rewrite both tool cards to describe only what executes (C.5) — for an agent platform, the tool card *is* the UI.
