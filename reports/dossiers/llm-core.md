## A. What it is

`llm-core` is the layer every single LLM token in the platform rides through: eight hand-written provider clients (OpenAI, Anthropic, Google, Azure, HuggingFace, Bedrock, Grok, OpenRouter) behind one `LLMManager`, a PRD-136 three-tier role map (Auto / System / Embeddings) that decides which configured model a given internal service gets, a per-agent `model_config` path with BYOK key resolution, a PRD-15 model registry (`llm_models`) holding pricing and capability metadata, an OpenRouter catalog sync + model marketplace, per-call usage/cost tracking into `llm_usage` (31,081 rows, current through 2026-07-03), and two adjacent services — the PRD-58 prompt registry and the FutureAGI prompt-optimization worker seam. It is the platform's engine room — and the review window caught it mid-failure: its default provider ran out of credits in mid-June and every autonomous playbook LLM step failed daily for ~2.5 weeks without the module noticing, failing over, or telling anyone.

## B. What it does — real implementation and data path

### B.1 The manager and the three-tier role map

`SERVICE_CATEGORY_MAP` (`orchestrator/core/llm/manager.py:33-53`) maps ~14 internal service names onto exactly three settings tiers: `orchestrator_llm` (Auto's brain: `orchestrator`, `heartbeat`), `system_llm` (12 background services: chatbot, codegraph, rag, nl2sql, planner, graph_extraction, …), and `embeddings`. Provider+model come from DB `system_settings` rows with **no hardcoded fallback** — unset config raises with an actionable message (`manager.py:114-127`). Temperature and max_tokens are the only other tier settings actually read (`manager.py:488-489`). The manager lazily instantiates one of 8 provider clients (`manager.py:580-600`), all subclasses of `BaseLLMProvider` (`core/llm/clients/base.py:101-163`) which contributes shared tool-schema sanitisation (wrap bare functions, strip OpenAI-only `strict` for other providers, `base.py:131-163`).

Platform default (used to seed agents and as last-resort): **OpenRouter + `google/gemini-2.5-flash`** (`core/llm/defaults.py:13-14`).

### B.2 Two model-resolution paths

**(a) Service-tier path** — `create_llm_manager(service_name=…)` (`manager.py:787-826`), used by ~20 call sites: chat (`consumers/chatbot/service.py:2202`), heartbeats (`services/heartbeat_service.py:687`), the complexity assessor (`consumers/chatbot/auto.py:828`), planner (`modules/coordination/planner.py:382`), board task planning (`api/board_tasks.py:1188,1268`), graph extraction, NL2SQL, RAG query enhancement, blog handlers, Composio action classification. Workspace id falls back to the auth-middleware ContextVar so usage is always attributed (`manager.py:812-817`).

**(b) Per-agent path** — `AgentFactory` resolves precedence `force_llm_tier` → `use_orchestrator_llm` → agent's own `model_config` → orchestrator-tier default (`modules/agents/factory/agent_factory.py:700-755`), then repairs provider/model mismatches: unknown providers with slash-format models are rerouted through OpenRouter, bare model ids get vendor prefixes inferred from a rules table (`agent_factory.py:343-383`), and a provider whose credential is missing falls back to OpenRouter with a rewritten model id (`agent_factory.py:778-795`). Key resolution is BYOK-first: workspace `settings.byok_overrides[provider]` → decrypted `user_api_keys` row → platform credential store (4 name guesses) → env var (`agent_factory.py:418-453` + `:780-795`), returning a `ResolvedKey` whose `is_byok` flag flows into usage rows.

### B.3 The call itself

`generate_response()` (`manager.py:612-633`) is async but every client wraps a **synchronous** SDK call in `run_in_executor` (`openrouter_client.py:61-116`, `anthropic_client.py:159-178`). There is **no streaming interface anywhere in the module** — zero `stream` hits across `core/llm/` (grep-verified). There are **no retries and no failover at call time**, by explicit design ("No default fallback models — fail clearly", `manager.py:573`; "No fallback helpers — errors surface directly to the user", `manager.py:610`); the one grace is rewriting dead-model errors (404 / "no endpoints found") into an actionable ValueError (`manager.py:602-608, 627-631`). Provider-specific behaviors worth knowing:

- **OpenRouter client:** sets `tool_choice="required"` by grepping the system message for the literal string "You MUST call" (`openrouter_client.py:88-93`) — a brittle string coupling to prompt copy; retries once without tools if the model rejects tool use (`:99-106`); raises on empty `choices` (`:118-122`); extracts Gemini-style generated images from the nonstandard `images` field into markdown + `additional_blocks` (`:127-172`). The sync variant silently **drops tools entirely** (`:206-229`).
- **Anthropic client:** converts OpenAI-format messages/tools to Anthropic format (`anthropic_client.py:50-149`), but multiple system messages collapse to the **last one** (plain overwrite at `:74-75`), and a user message whose content happens to be a JSON array string is reinterpreted as tool-result content blocks (`:79-90`) — a latent misparse for legitimate JSON-looking user content. **No `cache_control` anywhere** — prompt caching is unused (see C.8). No extended-thinking / reasoning-effort support.

### B.4 Tracking: every call writes a row

`_track_usage` (`manager.py:654-696`) fires on success *and* exception (`status="error"`, `manager.py:625`) → `UsageTracker.track` opens its own session, prices tokens from the `llm_models` registry (unknown model → **cost 0.0**, `core/llm/usage_tracker.py:49-58`), writes an `llm_usage` row, and folds cumulative stats into `Agent.model_usage_stats` (`usage_tracker.py:85-107`). In parallel a grep-able cost-audit log line is emitted using a **separate hardcoded in-memory price map** (`manager.py:713-736` — deliberately kept per the in-code F059 note to avoid a DB round-trip per call). Real data: 31,081 `llm_usage` rows, newest 2026-07-03 ([census.md](evidence/data/census.md)) — the tracking plane genuinely runs.

### B.5 Catalog, registry, marketplace

`OpenRouterSyncService` pulls the full OpenRouter public catalog into `openrouter_models_cache` with per-model pricing incl. cache-read/write rates, modalities, tool/vision/reasoning support flags, and derived category/tier/tags (`core/services/openrouter_sync_service.py:128-233`). The marketplace API (`api/llm_marketplace.py`) browses that cache and, on install, **copies a price/capability snapshot** into `llm_models` and links it to the workspace via `workspace_models` (`llm_marketplace.py:101-143, 334-371`). Nothing ever refreshes those copied prices afterwards (grep: the only assignment to `input_cost_per_1k_tokens` outside seeds is that copy). The PRD-15 `ModelRegistry` adds `find_best_model()` scoring and task recommendations (`core/llm/model_registry.py:219-333`) — **called only by API endpoints that nothing calls**: not one internal agent path invokes it, and the frontend never hits `/api/models/recommend`, `/by-task`, or `/estimate-cost` (grep of `frontend/` — zero hits; the agent model-selector uses `/api/marketplace/llm/installed` via `hooks/use-model-api.ts:98`).

### B.6 BYOK

`api/user_api_keys.py` — add/list/delete/test keys per workspace (7 providers, `user_api_keys.py:28`), encrypted at rest via the platform `EncryptionService` (`:107-113`), masked on read, plus super-admin platform-key management (`:231-406`). Agent-side resolution honors the workspace's `byok_overrides` toggle (B.2). `is_byok` is carried through to `llm_usage` for platform-vs-BYOK cost splits in the admin analytics (`api/llm_analytics.py:768+`).

### B.7 Analytics

`/api/analytics/llm/*` — usage/costs/summary grouped by model/provider/agent/tier, daily-by-model, model comparison, cost projections (`api/llm_analytics.py:99-677`), plus three OpenRouter passthroughs: activity sync into `llm_usage`, **credits balance**, and key-info (`:680-751`). The credits endpoint is pull-only — no scheduled job or alert consumes it (grep: `get_credits` has exactly one caller, the API route).

### B.8 Prompt registry + FutureAGI seam

`PromptRegistry` (`core/services/prompt_registry.py`) — DB-backed prompts (`system_prompts` + versions) with a 60s TTL cache and 7 hardcoded bootstrap fallbacks (`:149-199`), managed via `api/admin_prompts.py`. `FutureAGIService` (`core/services/futureagi_service.py`) routes prompt assess/optimize/live-eval to an isolated worker over HTTP; note `AGENT_OPT_WORKER_URL` defaults to `http://localhost:8080` (`config.py:809`), which makes `is_available` **always true** (`futureagi_service.py:64-67`) — the chat live-eval hook (`consumers/chatbot/service.py:1181-1184`) fires HTTP calls at a dead localhost port on any deployment that hasn't stood the worker up (fire-and-forget, so wasted work + log noise rather than user breakage).

## C. Honest quality — maturity **2.5 / 5**

The plumbing — provider abstraction, BYOK, catalog, per-call telemetry — is real and solid. The *operational* half — reliability, routing intelligence, cost integrity — failed a live test during the review window. Concrete findings:

1. **The June outage is the module's verdict, and it's damning.** Playbook LLM steps have failed **daily since ~mid-June** with OpenRouter 402 "Insufficient credits" ([memory-short-term.md](evidence/data/memory-short-term.md) — the exact error text, memorised twice per run); deliverables — the client-visible output — **stopped 2026-06-16** ([deliverables.md](evidence/data/deliverables.md)); board tasks kept closing `done` (194 done-with-error, [board-tasks.md](evidence/data/board-tasks.md) — that mis-close is the board's defect, but the *outage* is this module's). What makes it an llm-core indictment: the module **recorded its own failure and had its own fuel gauge, and nothing read either.** Every 402 wrote an `llm_usage` row with `status="error"` (`manager.py:624-625` fires `_track_usage(None, start, status="error")` on the exception path), and a working credits-balance endpoint existed the whole time (`api/llm_analytics.py:703-726`). No scheduled probe, no error-streak alarm, no failover to a funded provider — for a platform whose North Star is *autonomous operation*, the engine room ran dry and the machine idled for 2.5 weeks. Auto cannot check its own fuel gauge.
2. **No resilience primitives in the core — and callers are hand-rolling them one incident at a time.** The deliberate "no silent fallbacks" stance (`manager.py:573,610`) is right for *misconfiguration* but has been over-applied to *transient provider failure*: no retry, no backoff, no failover exists in `LLMManager` or any client. The scar tissue proves the need: `recipe_executor` grew its own empty-completion retry loop + fallback-model swap after a Gemini 2.5 Pro degradation incident (`api/recipe_executor.py:474-523`, config knobs `RECIPE_EMPTY_COMPLETION_*` at `config.py:366-374`) — caller-side, playbook-lane-only, and blind to the 402 class that actually took production down. The per-agent `fallback_model_id` field exists but is consulted **only during activation verification** (`agent_factory.py:631-645`), never at call time.
3. **No streaming, anywhere.** Zero streaming support in the provider layer (grep across `core/llm/`); all 8 clients block until completion, sync SDKs on executor threads. Chat tokens cannot stream to the UI from this layer, long generations hold worker threads, and heartbeat/mission loops can't observe partial progress. Every comparable layer (LiteLLM, Portkey, OpenRouter native, all first-party SDKs) treats streaming as table stakes (§D).
4. **Model choice is static; the routing "intelligence" is decorative.** What ships: a 3-tier role map + per-agent config. `ModelRegistry.find_best_model`/`get_recommended_models` have **zero callers** outside their own unused API endpoints (§B.5); the capability data they'd score on is hand-written adjectives ("excellent"/"good" → 0-1 map, `model_registry.py:72-82`) from an October-2025 seed (`core/seeds/seed_models.py` — GPT-4-Turbo-era models, `ON CONFLICT DO NOTHING`). The AutoBrain complexity assessor classifies every message atom→organism (`consumers/chatbot/auto.py:790-880`) and then **never varies the model** — it gates tools and delegation only. Meanwhile the platform's *only* recorded cross-model eval shows routing headroom is real and large: on tool-routing, gpt-4.1-mini scored **93.6% @ ~$0.0007/call**, claude-opus-4.7 95.7%, and **gemini-2.5-pro 46.8%** — a 2× accuracy spread ([repo-eval-artifacts.md](evidence/data/repo-eval-artifacts.md)) — while the platform default sits in that same Gemini family for everything. PRD-68 progressive-complexity routing exists only as the capability-map blurb says: a role tag.
5. **Pricing is fragmented and silently drifts** (F059 residual, confirmed PARTIAL — the count of price sources went *up*). Four+ parallel sources: the `llm_models` registry (authoritative for `llm_usage` rows), the hardcoded `_MODEL_COST_MAP` audit-log estimates (`manager.py:713-727`), stale-2024 `TOKEN_COSTS` in `core/utils/logging_utils.py:469-484`, and the model-blind flat `COORDINATOR_COST_PER_1K_TOKENS=0.003` that still prices Mission auto-approval and Playbook ceilings (residual map F059). Worse, registry prices **freeze at install time** — the marketplace copies the OpenRouter cache price once (`llm_marketplace.py:127-128`) and the nightly-able catalog sync never back-propagates — and any model absent from `llm_models` books **$0.00** per call (`usage_tracker.py:54-56`), so cost analytics silently understate. Cached-token pricing isn't representable at all (no `cached_tokens` capture in `LLMResponse.usage`, `base.py:90-98`).
6. **The analytics table double-counts if you use a documented feature.** The OpenRouter activity sync inserts **daily aggregate** rows into the same `llm_usage` table as per-call tracking (`core/llm/openrouter_analytics.py:118-140`, `request_type="activity_sync"`), deduped only against other sync rows; `/usage`, `/costs`, `/summary` aggregate with **no `request_type` exclusion** (`api/llm_analytics.py:123-139`). A workspace that triggers `/openrouter/sync` sees its OpenRouter spend roughly doubled in every dashboard sum.
7. **Placebo settings fields — the F035 pattern, still alive server-side.** The PRD-136 tier settings seed `max_retries` and `timeout_seconds` rows (`alembic/versions/prd136_collapse_llm_tiers.py:53-55`) and the Settings UI renders them as live controls (`frontend/components/settings/LLMTierCard.tsx:40-44`), but the tier config loader reads **only temperature and max_tokens** (`manager.py:488-489`) — no code consumes either knob on the tier path (grep: zero hits in `core/llm/`). W10 deleted the chat model-selector placebo (F035 FIXED); these two survived.
8. **Prompt caching unused — real money on a high-volume plane.** The Anthropic client sends no `cache_control`, and the OpenRouter path neither passes breakpoints nor records cached-token usage. Heartbeats alone have produced 148,362 results ([census.md](evidence/data/census.md)), each run re-sending a large stable system prompt at full price; Anthropic cache reads are 0.1×, Gemini 2.5 caches implicitly at 0.25× *only if usage is recorded to see it* ([OpenRouter caching docs](https://openrouter.ai/docs/guides/best-practices/prompt-caching)). The module can neither request nor even *observe* caching.
9. **Credential resolution is a guessing cascade.** `get_credential_data` tries an explicit settings mapping, then **7+ name variations** ("production_openai_api", "openai", "Openai", …), then type-based lookup, then a **production→development environment fallback**, then env vars (`manager.py:135-363`), all TTL-cached 300s (`manager.py:131-134`, so key rotation takes up to 5 minutes to be seen). It works, but failure diagnosis is miserable and the resolution order is effectively undocumented behavior.
10. **Dead weight inside the module:** `function_executor.py` (437 lines), `function_registry.py` (407), `response_parser.py` (360), `semantic_skill_matcher.py` (203) are exported from `core/llm/__init__.py:40-44` with **zero external callers** (grep-verified) — ~1,400 lines of dead scaffolding predating the real tool loop. Plus the misfiled `api/anthropic_client.py` zombie with a broken import (F083 leg 2, confirmed NOT fixed in the residual map) and the orphaned `frontend/lib/ai/models.ts` gpt-4 catalog (F035 notes). The FutureAGI seam is dormant-but-armed (localhost default → always "available", §B.8).
11. **What is genuinely good — say it plainly:** the provider abstraction is clean and battle-tested (correct OpenAI↔Anthropic message/tool format conversion both directions, shared `strict`-field sanitisation, image-output extraction others get wrong); provider/model mismatch **auto-repair** and OpenRouter rerouting prevent the LLM-config dead-ends that plague multi-provider setups (`agent_factory.py:343-415`); BYOK is properly encrypted, workspace-scoped, toggleable, and cost-attributed; the OpenRouter catalog sync with real capability flags + cache-price columns is fresher data than most platforms hold; usage tracking actually fires on every call including errors and is current to the day; the 3-tier collapse (PRD-136) was the right simplification; and the no-hardcoded-model bootstrap stance means config drift fails loudly instead of silently running the wrong model.

**Why 2.5:** the abstraction/telemetry/BYOK substrate alone would rate 3.5 — it is real, current, and unusually complete for an agent platform. But judged by the North Star, the module let the platform's entire autonomous output lane die silently for 2.5 weeks on its watch (with the failure data in its own table), streams nothing, retries nothing, prices inconsistently, and carries its routing intelligence as an unused ornament. The engine is sound; the gauges, governor, and spare tank are missing.

## D. Competitive teardown

The relevant class is LLM gateways/routers. Four players, verified current:

**1. LiteLLM (OSS gateway — BerriAI)** — the direct like-for-like. One OpenAI-format interface over **100+ providers** with: automatic **retries + configurable fallback chains with backoff** ([reliability docs](https://docs.litellm.ai/docs/proxy/reliability)), routing strategies (latency-based, cost-based, weighted, round-robin) configurable **per key/team** ([routing docs](https://docs.litellm.ai/docs/routing-load-balancing)), **budgets per key/user/team with durations and hard blocking**, virtual keys, RPM/TPM rate limits, caching, streaming everywhere, and a continuously **maintained price/context map** (`model_prices_and_context_window.json`) used for exact per-call USD costing ([GitHub](https://github.com/BerriAI/litellm)). *What it does better:* essentially the entire reliability + budget + price-freshness layer Automatos lacks, as maintained OSS. *What it lacks vs Automatos:* no workspace/agent product semantics — BYOK-per-workspace, per-agent model configs, marketplace install UX are above its pay grade.

**2. OpenRouter (the aggregator Automatos already pays)** — the embarrassing comparison, because most of what the June outage needed is a request-body away: automatic **provider-level failover** within a model (`allow_fallbacks` default-on), **model-level fallback** via a `models: [...]` array triggered on rate limits, downtime, context-length and moderation errors, load-balancing across providers by price×uptime, `:nitro`/`:floor` sort shortcuts, and **failed requests not billed** ([provider routing docs](https://openrouter.ai/docs/guides/routing/provider-selection), [model routing blog](https://openrouter.ai/blog/insights/model-routing/), [nitro/floor announcement](https://openrouter.ai/announcements/introducing-nitro-and-floor-price-shortcuts)). Plus **prompt caching** with per-provider multipliers (Anthropic 0.1× reads; Gemini 2.5 implicit 0.25×) and `cached_tokens` reported in the usage object ([caching docs](https://openrouter.ai/docs/guides/best-practices/prompt-caching)), and credits/activity/generation APIs for exact billed cost. *Where Automatos stands:* it uses OpenRouter as a dumb pipe — no `models` fallback array, no provider preferences, no cache breakpoints, no cached-token accounting, credits API wired but never polled.

**3. Portkey (commercial gateway)** — the governance ceiling to aim at: fallbacks on configurable error codes, weighted load-balancing, **automatic retries up to 5 with exponential backoff**, granular request timeouts, virtual keys with budgets/rate-limits/RBAC, 50+ guardrails, full request/trace observability, 1,600+ models ([gateway docs](https://portkey.ai/docs/product/ai-gateway), [GitHub](https://github.com/Portkey-AI/gateway)); Developer free tier / $49-mo Production / enterprise SSO-VPC tiers ([pricing](https://portkey.ai/pricing)). *What it does better:* config-as-code routing policies + org-grade governance in one place. *Honest negative for adopting it here:* it would be a second aggregator hop in front of OpenRouter — duplicated routing semantics, added latency, a second bill — for capabilities W4's policy plane + OpenRouter features already cover in kind.

**4. Not Diamond (learned per-query router)** — what PRD-68 imagined: a router model that picks the best LLM *per query*, trainable on your own eval data, with claims of **39% average accuracy improvement** on SRE benchmarks and joint prompt-adaptation gains of 5-60% ([docs](https://docs.notdiamond.ai/docs/what-is-model-routing), [VentureBeat](https://venturebeat.com/ai/not-diamond-automatically-routes-your-query-to-the-best-llm), [supported models](https://docs.notdiamond.ai/docs/llm-models)); pricing undisclosed (fixed fee per Mtok, enterprise plans) ([third-party analysis](https://www.morphllm.com/notdiamond-alternative)). OSS analog: LMSYS **RouteLLM** ([GitHub](https://github.com/lm-sys/RouteLLM)). *What it does better:* the actual learned quality-per-dollar routing Automatos has zero of. *Honest caveat:* Automatos's own W7 lesson applies — a learned layer without eval data measured *negative* (tool-selection dossier). Until T3 gives per-task gold sets, a learned router here would be another unfed learning plane.

**Net position:** Automatos's differentiated ground — workspace BYOK, per-agent model configs, marketplace install UX, is_byok cost attribution woven into an agent platform — none of the gateways offer as product. Its gaps are precisely the commoditized parts: reliability, streaming, caching, price freshness, budget enforcement. Building those by hand in 2026 is re-implementing LiteLLM slowly.

## E. Build / extend / adopt / replace — the verdict

**Extend the manager; adopt the reliability layer you already pay for (OpenRouter's), adopt LiteLLM's price map as data, and spike LiteLLM-as-SDK for the client layer. Do not add a second gateway hop. Defer learned routing until T3 exists.**

Specifically:

1. **Keep (extend) `LLMManager` + the tier map + AgentFactory resolution** — this is the platform-semantics layer (BYOK, per-agent config, tiering, usage attribution) that no external product replaces, and it's woven through ~30 call sites. Nothing external wins here.
2. **Adopt OpenRouter's routing surface — integration is request-body-shaped, cost ≈ $0.** Send `models: [primary, fallback…]` on OpenRouter calls (kills the single-model-outage class *except* account-level 402), add provider preferences where latency matters, add `cache_control` breakpoints on stable system prompts, and read `cached_tokens`/generation cost back into `llm_usage`. This is days of work for the largest reliability/cost win available.
3. **Adopt LiteLLM's `model_prices_and_context_window.json` as the price feed** (MIT-licensed data, [repo](https://github.com/BerriAI/litellm)) — or equivalently back-propagate the already-synced OpenRouter cache prices into `llm_models` on every sync. Either kills the frozen-snapshot problem; the OpenRouter-cache route needs zero new dependencies and is the better fit (verdict: do that, use LiteLLM's map only for non-OpenRouter direct providers).
4. **Spike (2-3 days): LiteLLM SDK as the client layer inside `LLMManager`** — one dependency could replace ~2,200 lines of hand-written clients and deliver streaming, retries, and provider quirks maintenance for free, while the manager keeps owning tiering/BYOK/tracking. Counter-arguments to respect: the existing clients' tool-format conversions and image-extraction are battle-tested against this platform's exact traffic, and a bad abstraction swap on the hottest path is high blast-radius. Hence spike, not commit. If the spike fails, **build** streaming + a small retry/failover policy into the existing clients (bounded: ~1 PRD).
5. **Reject for now:** Portkey (second hop duplicating OpenRouter + W4 policy plane), Not Diamond/RouteLLM (no eval substrate yet — the W7 negative-uplift lesson), and any in-house "smart model picker" revival of `find_best_model` on adjective data (delete it instead; see J).

## G. Quality metric

The module's quality is measurable today from its own table — it just isn't measured:

- **Reliability (primary): daily LLM call success rate per lane** = `1 − error_rows/total_rows` from `llm_usage.status` grouped by `request_type` — plus **time-to-detection of a provider failure streak** (alert when a (provider, request_type) pair logs ≥N consecutive errors). *Today's number:* unmeasured; the data shows the worst case — playbook-lane success ≈ 0% for ~2.5 weeks with detection time = ∞ (found by this review, not the platform).
- **Recovery rate:** % of failed primary calls rescued by a fallback (model or provider). *Today: 0%* — no call-time fallback exists (C.2).
- **Cost integrity:** % of `llm_usage` rows with non-zero computed cost (unknown-model rows book $0, C.5) + price-staleness (max age of `llm_models` prices vs the OpenRouter cache). *Today: both unknown, neither tracked.*
- **Routing quality (feeds T3):** per-task accuracy×cost frontier across candidate models, reusing the existing tool-routing eval harness pattern (`scripts/eval/tool_routing/` — the one artifact that already did this: 22 model×mode pairs, gpt-4.1-mini 93.6% @ $0.0007). Re-run per platform task family (routing, distill, NL2SQL, summarise) quarterly; the metric is "regret vs best-known model per task."
- **Latency:** p50/p95 `latency_ms` per tier (column exists on every row; no dashboard reads percentiles).

First concrete step: a nightly job computing success-rate + $0-cost-share + error-streaks from `llm_usage`, surfaced as one Command Center tile and a notification rule. That single metric would have caught the June outage on day one.

## H. Cost note (informational)

- Volume driver is the System tier + heartbeats: 31,081 tracked calls to 2026-07-03, alongside 148,362 heartbeat results — each heartbeat run is a multi-iteration tool loop re-sending a full uncached system prompt (B.3, C.8).
- The only precisely measured per-op cost in the repo: **~$0.0007/call** for tool-routing on gpt-4.1-mini ([repo-eval-artifacts.md](evidence/data/repo-eval-artifacts.md)). Default-tier chat turns on `google/gemini-2.5-flash` land in the same order of magnitude at typical context sizes; Auto-tier turns with full context assembly are 10-50× that.
- Unpriced-and-invisible: cache savings (Anthropic 0.1× reads / Gemini 0.25× implicit — neither requested nor recorded), and every call on a model absent from `llm_models` books $0.00, so true spend is *understated* by an unknown margin while activity-sync double-counting *overstates* OpenRouter workspaces that use the sync (C.6). Net: current dashboards are directionally useful, not accounting-grade.

## I. UX / surface

**Exists today:** Settings → 3 tier cards (`LLMTierCard.tsx`) + API-keys tab (BYOK + platform status) + `SystemLLMSettingsTab`; Marketplace → LLMs tab browsing the OpenRouter cache with install/uninstall (`marketplace-llms-tab.tsx`, `llm-model-card.tsx`); Agents → model-selector grouped by tier with inline cost/context (`components/agents/model-selector.tsx`); Analytics → cost dashboards (`analytics-costs.tsx`).
