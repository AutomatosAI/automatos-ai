## A. What it is

Context assembly is the platform's single prompt-building path: `ContextService` composes every LLM call's system prompt, message list, and tool set from ~19 registered, priority-ordered sections (identity, skills, memory, knowledge-graph excerpt, platform-action catalog, task/playbook/mission context, field digest, …) under per-mode token budgets, across 10 declared `ContextMode`s — plus the PRD-164 planning pack that every planner consumes. It is the layer the July review called the single highest-leverage quality lever ("one context assembler", `PLATFORM_OS_REVIEW_2026-07-01.md` §2), because it decides *what Auto and every agent actually knows on every turn*. The honest one-line verdict of this dossier: **the assembly machine is genuinely good and genuinely singular, but on real production data most of its intelligence sections inject noise or nothing, and no one can see or measure what was assembled.**

## B. What it does — implementation + data path

**The one entry point.** `ContextService.build_context` (`orchestrator/modules/context/service.py:71-211`) runs a 10-step pipeline: mode-config lookup (`:95-100`), `SectionContext` bag construction (`:107-119`), section instantiation from the mode's declared list (`:122`, `:371-384`), **parallel** section rendering with per-section exception swallowing (`:125`, `:386-415`), token-budget allocation (`:128-129`), prompt concatenation (`:132`, `:439-451`), tool loading by strategy (`:136`, `:453-484`), message formatting/trimming (`:139`, `:486-513`), PRD-127 attachment injection (`:151-179`), and an immutable `ContextResult` (`result.py:10-27`). A section that raises is logged and contributes "" — a prompt build never crashes on one feed (`service.py:393-408`).

**Modes.** `ContextMode` declares 10 modes (`modes.py:13-23`); `MODE_CONFIGS` (`modes.py:36-153`) maps each to a section list, tool-loading strategy (`full` / `filtered` / `dispatcher_only` / `none`), personality flag, and optional max_tokens. Live callers, verified by grep:

**Sections.** 19 classes registered in `SECTION_REGISTRY` (`sections/__init__.py:31-51`), each `BaseSection` with `name/priority/max_tokens` and an async `render()` (`sections/base.py:45-82`). The load-bearing ones:

- **identity** (priority 1, never dropped): non-chat modes get name/role/persona (`sections/identity.py:87-120`); CHATBOT gets the full `AutomatosPersonality` stack — base prompt + platform skill + tool guidance + action response style + anti-patterns + self-learning + execution policy — explicitly uncapped ("the full chatbot personality is essential", `identity.py:190-191`). The personality source is ~14.8k chars of static template (`consumers/chatbot/personality.py`, measured) ≈ 3.7k tokens per turn.
- **skills** (priority 4): renders the agent's SKILL.md bodies; primary skill uncapped, auxiliaries share 5k (`sections/skills.py:31-34,70-86`). Auto's platform-management skill seed is 44 KB (`evidence/data/repo-eval-artifacts.md`) ≈ 11k tokens, uncapped, every turn. The "highest-priority active skill" sort is a phantom — no `priority` column exists on Skill, so `getattr(s,"priority",0)` makes the sort a no-op and "primary" is load-order (`skills.py:63-67`; July F054, residual map: NOT DONE — owned by `agents-skills` dossier, but the defect lives in this module's file).
- **platform_actions** (priority 5, cap 4,000 — `config.py:753`): the `platform_execute` catalog. With `SEMANTIC_TOOL_ROUTING` (default **true**, `config.py:751`) and a query present it renders the embedding-ranked top-15 (`sections/platform_actions.py:103-115,230-282`); graph chain-hints exist behind `TOOL_ROUTING_GRAPH` (default **false**, `config.py:757`; `platform_actions.py:118-182`), workspace-scoped per W7 (`:142-147`).
- **memory** (priority 6, cap 1,500 — `config.py:755`): tries the PRD-79 Context Router (`UnifiedMemoryService.retrieve_context`, `sections/memory.py:110-132`), falls back to `SmartMemoryManager` top-8 + Redis session hydration + daily logs (`:209-311`; daily logs on by default, `config.py:929`), renders "## What You Know About This User". Any failure silently degrades (`:134-139`). The chatbot can skip it entirely per turn when the complexity classifier says so (`skip_memory`, `smart_orchestrator.py:203-208,236`).
- **business_graph** (priority **45**, cap 800): loads the workspace Knowledge Graph (LRU-cached, `modules/knowledge/graph_service.py:344-385`), scores nodes by **lexical term overlap** with the last message (threshold 0.3), BFS depth-2 from the top 3 (`sections/graph_context.py:22-25,113-135`).
- **field_memory** (priority 7, cap 1,200 — `config.py:874`): W9/F021's read-half — the workspace-persistent Qdrant field digest for HEARTBEAT_AGENT and PLANNING (`sections/field_memory.py:64-110`; `modes.py:80-88,144-152`; residual map: F021 FIXED).
- **task_context / playbook_context / mission_context** (priority 2, never dropped): the work order (`sections/task_context.py:26-88`, `playbook_context.py:26-135`, `mission_context.py:30-104` — the last only in the dead COORDINATOR mode).
- **tools / conversation** are pseudo-sections: they render "" and instead populate `ContextResult.tools` (4 strategies incl. SmartToolRouter intent filtering, `sections/tools.py:61-231`) and the trimmed message list (oldest-first drop, `sections/conversation.py:110-136`).

**Budgeting.** `TokenBudgetManager.allocate` (`budget.py:66-145`): per-section cap by **character slice** (`content[:max_tokens*4]`, `:83`), then whole-section drops lowest-priority-first; priority ≤2 never dropped even if the result still exceeds budget (`:121-122,137-143`). `DEFAULT_BUDGETS` hardcodes `total=128_000` (131,072 for the dead COORDINATOR) for every mode (`budget.py:152-211`). Token counting on this path is the char/4 heuristic (`estimator.py:16-20`); the tiktoken `precise()` exists but nothing in the build path calls it.

**The planning pack** (PRD-164 S1/Q61). `build_planning_context` (`service.py:217-314`) assembles PLANNING-mode sections — RAG-on-goal through the PRD-157 choke point (`sections/planning_knowledge.py:50-62`), typed mission-history recall (`sections/planning_history.py:61-88`), KG subgraph, field digest, roster + performance — under a real tokenizer budget (`core.context_guard.count_tokens`, `service.py:271-288`) with the PRD-157 whole-chunk budgeter (`planning.py:83-178`). All three planners consume it and nothing else: MissionPlanner (`modules/coordination/planner.py:142`, roster off), board `plan_task` (`api/board_tasks.py:1157`, 4k cap), AutoBrain Tier-3 (`consumers/chatbot/auto.py:728`, 2k cap). Default pack budget 12k (`budget.py:206-210`).

**Adjacent but separate:** `core/context_guard.py` is the *runtime* window guard — tiktoken counting (`:49-56`), model-aware thresholds from the `LLMModel.context_window` DB column (`:101-127,150-175`), mid-conversation compaction with a Mem0 fact-flush — used only on the chat path (`consumers/chatbot/service.py:830-833,1474-1475`). So the platform has assembly-time budgeting (char/4, fixed 128k) and run-time guarding (tiktoken, model-aware) that don't share a definition of "how big is this."

## C. Honest quality — inspected against real data

**What could and could not be inspected.** Assembled prompts are not persisted anywhere (see B), so no literal production prompt could be read — itself a finding. What *can* be established precisely is what each section's substrate contained on 2026-07-04 production Postgres, and therefore what the code at these lines would have injected.

**The machine (good, with defects).** The single-assembler claim is real and verified across every live execution path, including the previously amnesiac heartbeat lane (W9). Fail-soft rendering, parallel section fan-out, one planning pack for three planners, and real test coverage put this module's *engineering* above most of the platform. That deserves saying plainly.

**What actually enters the prompt (the real-data verdict):**

1. **The memory section injects spam or nothing.** The durable arm is dead: `MEM0_API_URL` answers Railway-edge 404 on every path (`evidence/data/mem0.md`) and `memory.py:134-139` swallows the failure silently. The fallback store, `memory_short_term`, is 2,211 rows of which **~87% is duplicated operational chatter** — the same OpenRouter-402 playbook failure memorised twice per run, daily, plus heartbeat summaries stored twice (`evidence/data/memory-short-term.md`). The only informative rows (`exchange`, ended 2026-06-07) are raw chat clippings *including the user telling Auto it is lying* ("auto you are lying again…"). MemorySection applies **no relevance floor and no content-type filter** (`memory.py:261-267` — top-8, whatever comes back), so for a matching query the platform's "What You Know About This User" block is 402-error spam or Auto's own recorded lies. The write-side root cause belongs to the `memory` dossier; the **assembly-side failure is real and independent: this module gives its worst feed an uncritical, always-on slot in every chat/task/recipe prompt.**
2. **The field digest may never have rendered a byte.** Qdrant was unreachable/unconfigured from the audited env (`evidence/data/qdrant.md`); `field_memory.py:98-110` degrades to "" with only a debug-level trace. Since nothing persists section outcomes, there is no way to know whether HEARTBEAT_AGENT/PLANNING prompts have *ever* contained a field digest in production. A feature can be silently dark for months in this design.
3. **The knowledge-graph section is the one live intelligence feed** — 155 workspace graph blobs rebuilt 2026-07-01 (`evidence/data/workspace-graphs.md`) — but it is matched by naive lexical term overlap (`graph_context.py:127-135`) against node labels, capped at 800 tokens. Real graph, weak retrieval.
4. **The learned tool-routing garnish has no real diet.** Graph chain-hints are flag-off (`config.py:757`) and the edges are 100% synthetic seed data anyway — 21 real workspaces have zero learned edges (`evidence/data/operating-graph-edges.md`). The embedding top-15 action filter is the only live narrowing.
5. **The planning pack reads a nearly empty history.** `planning_history` recalls 12 `mission_summary` + 7 `task_failure` rows, newest 2026-06-07 (`evidence/data/memory-short-term.md` Q2), and its L3 arm is the dead mem0. The "learning demo" section works as code and starves as data.

**Assembly-machine defects (independent of feed quality):**

6. **Two definitions of "how many tokens is this".** The live build path budgets with char/4 (`estimator.py:16-20` via `service.py:57`, `budget.py:22`) and truncates by char slice (`budget.py:83`, `base.py:72-82` — mid-word, mid-JSON); the planning pack and RAG use tiktoken `count_tokens`. char/4 materially under-counts JSON/markdown-heavy content, so "capped" sections can overshoot their caps by tens of percent, and the fixed budgets are enforced against a wrong number.
7. **Budgets are not model-aware.** Every mode assumes `total=128_000` (`budget.py:152-211`) while the platform's own `ContextGuard` resolves real windows from the `LLMModel` table (`core/context_guard.py:101-127`). A small-window model overruns at assembly and gets emergency-compacted later (chat only); a 200k-window model leaves capacity unused. The model-aware plumbing exists one import away.
8. **Incoherent priority scheme.** Documented scale is 1 (never dropped) → 10 (`base.py:51-53`); `business_graph` is priority **45** with a docstring placing tools at "50-ish" (`graph_context.py:4,36`) when `tools` is actually 3 — two authors, two scales. Budget pressure does whole-section drops only; and priority-≤2 sections are never dropped *even when the result still exceeds the budget* (`budget.py:137-143`) — the assembler can knowingly emit an over-budget prompt.
9. **Dead weight inside and beside the module.** Two of ten modes have no caller (COORDINATOR, ORCHESTRATOR_STAGE); `tone.py` and `experiment.py` are dead; TASK_EXECUTION declares a `conversation` section but its factory caller never passes messages (`agent_factory.py:924-929`); and the three F079 rival stacks (~2,300 lines incl. the mounted `api/context_policy.py`) still offer competing answers to "context budget" — July's coherence complaint, verbatim open.
10. **Zero persisted observability** (B above). For the layer that decides what every agent knows, nothing records what was assembled, trimmed, or skipped per turn. This blocks debugging ("what did Auto know when it said that?"), makes regressions invisible, and leaves G's metrics unmeasurable today.
11. **Turn-silent memory gating.** The complexity classifier can zero the memory section per turn (`smart_orchestrator.py:203-208`) with no record — a misclassification makes Auto amnesiac invisibly.

**Maturity score: 3 / 5.** The convergence, fail-soft design, planning pack, and test coverage are a solid 4 as *machinery*; judged by the North Star — what actually reaches the model each turn — the intelligence sections deliver noise (memory), silence (field), or lexical-grade relevance (graph), there is no measurement, budgets are enforced with the wrong tokenizer against the wrong window, and rival stacks remain mounted. That is a 3: strong spine, unproven and unobserved payload.

## D. Competitive teardown

**1. Anthropic — context-engineering practice + platform context management.** The published playbook ([Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)) frames a finite "attention budget"/context-rot and prescribes just-in-time retrieval over pre-loading, compaction, structured note-taking, and sub-agents returning 1–2k-token summaries. The platform now ships this server-side: **context editing** (automatic clearing of stale tool results, cache-preserving) and the **memory tool**, with published evals of +39% over baseline combined, and an 84% token reduction on a 100-turn task ([context management announcement](https://claude.com/blog/context-management), [context-editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing), [memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). Automatos compares: assembly-time sectioning is arguably *ahead* of "one big prompt" practice, but there is **no runtime context editing on any tool loop** (ContextGuard compacts chat only), no note-taking primitive, and **no prompt caching at all** — and the cache hierarchy (tools → system → messages; any tool-definition change invalidates everything, reads cost 0.1×, [prompt-caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)) means Automatos' per-query FILTERED tool lists and per-query action catalog would bust the cache every turn as currently ordered.

**2. Letta (MemGPT) — memory blocks.** Context is compiled per request from DB-persisted, labeled, size-limited **blocks** that the agent itself edits via tools (`rethink_memory`), that can be shared across agents, and that developers can read/write directly via API/ADE ([Letta memory blocks](https://www.letta.com/blog/memory-blocks/), [docs](https://docs.letta.com/guides/core-concepts/memory/memory-blocks)). This is the observable, durable, *agent-editable* analog of Automatos' sections — and it is exactly what Automatos' sections are not: Automatos sections are code classes with env-var budgets, invisible to operators, not editable by agents, not shareable. Letta's honest weakness: adopting it means adopting its entire agent server/runtime, which would displace the platform's own loop, tenancy, and tool plane — a non-starter as a wholesale replacement.

**3. LangChain / LangGraph — context-engineering middleware.** Ships `SummarizationMiddleware`, `trim_messages`, `@dynamic_prompt`, `@wrap_model_call` transient message rewriting, and state-schema isolation of tool outputs until needed ([LangChain context-engineering docs](https://docs.langchain.com/oss/python/langchain/context-engineering), [blog](https://www.langchain.com/blog/context-engineering-for-agents)). Stronger than Automatos on *runtime* history management primitives; weaker as a product: it is a toolkit — no multi-tenant, per-workspace-personality, DB-driven assembler exists out of the box. Automatos' mode/section model is genuinely more structured than what most LangGraph apps hand-roll. Honest negative for the field: none of these vendors ships a drop-in replacement for what this module does.

**4. 12-factor agents — Factor 3 "own your context window."** The production-agents playbook argues for owning serialization (custom, token-dense formats) and warns of degraded recall in the middle of large windows ([factor-03](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-03-own-your-context-window.md)). Automatos owns its window (good) but does not manage *placement*: volatile, low-trust content (memory excerpts, graph snippets) lands mid-prompt between stable blocks, and the biggest block (an 11k-token skill) is uncapped by design with no evidence it earns its slot.

**Where Automatos actually stands:** ahead of the OSS toolkits on multi-tenant assembly structure; behind Anthropic's platform on runtime context lifecycle (editing/compaction/caching/notes); far behind Letta on context observability and operator/agent editability; and behind everyone on measurement, because nothing is recorded.

## E. Build / extend / adopt / replace — verdict

**EXTEND** (keep the in-house assembler as the spine; adopt three narrow externals; delete the rivals).

- **Why not adopt a replacement:** the two credible candidates fail the swap test. Letta replaces the whole runtime, not just assembly; LangChain middleware requires adopting the LangGraph execution model the platform deliberately doesn't use. Nothing external provides multi-tenant, DB-driven, mode-aware prompt assembly for an existing FastAPI/SQLAlchemy agent OS. The module is also one of the platform's few genuinely converged spines — replacing it would re-fragment eight execution paths for zero capability gain.
- **What to adopt (specific):** (a) **Anthropic context editing + memory tool** on Anthropic-routed loops — request-parameter-level integration (`context_management`/`memory_20250818`), the cheapest 30-80% context-lifecycle win available ([docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)); (b) **tiktoken everywhere** — already a dependency via `core/context_guard.py`, adopt as the single counting definition; (c) **prompt caching** — pure API adoption, requires the cache-aware section ordering in J6. Rough cost: all three are integration work measured in days, no new vendors, no new infra.
- **What to replace/delete (in-repo):** the F079 rival stacks (`api/context_policy.py` + `ContextAssembler` + `ContextRetrievalEngine` + `ContextOptimizer`, ~2,300 lines), `tone.py`, `experiment.py`, and the two caller-less modes. One budgeter, one assembler — finish July's sentence.
- **Why keep building:** the remaining gaps (persisted traces, injection-time quality floors, model-aware budgets, sections-as-data) are platform-shaped product work no vendor sells at this seam, and each is directly North-Star-loaded: they determine whether agents act on knowledge or on noise.

## G. Quality metric

**Today's number: none exists.** `sections_included/trimmed/token_estimate/preparation_time_ms` are computed every build (`service.py:184-196`) and thrown away; the only related telemetry (`memory_access_log`) recorded 6 reads ever, last 2026-03-11 (`evidence/data/memory-short-term.md`).

Proposed, feeding the T3 harness — all derivable from one persisted assembly trace (J1):

1. **Context precision (per mode, primary metric):** on sampled turns, LLM-judge fraction of injected section content that was relevant to the turn's outcome, calibrated against a small human-labelled set. Sub-metric that matters most now: **memory-injection precision** — by inspection of the substrate it would score ≈0 today (87% operational spam), which is exactly why it must become a tracked number.
2. **Section liveness:** % of builds per mode in which each section rendered non-empty (catches the silent-dark field/mem0 class instantly).
3. **Budget honesty:** estimator error (char/4 vs tiktoken on the same content — measurable offline immediately), trim/drop rate per section, % of builds emitted over budget.
4. **Assembly latency:** `preparation_time_ms` p50/p95 per mode (already computed, just persist it).
5. **Cache-hit rate** on the stable prefix, once J6 lands.
6. **End-to-end lift (the North-Star check):** A/B task success / human-accept with a section on vs off (the machinery for on/off already exists — `skip_memory`, flags) — proves which sections *earn their tokens*, incl. the uncapped 11k-token skill.

## H. Cost note (informational)

- **Per CHATBOT turn (Auto):** system prompt ≈ **15–22k tokens** — identity/personality ~3.7k (measured, uncapped) + Auto's platform skill ~11k (uncapped) + actions ≤4k + memory ≤1.5k + composio ≤1k + plugins ≤2k + graph ≤0.8k — plus up to 60k conversation reservation and tool schemas. At Sonnet-class $3/MTok input that is roughly **$0.05–0.25 input per turn** before output; `llm_usage` (31,081 rows, current through 07-03) confirms sustained real volume.
- **No prompt caching:** the ~15k stable prefix is re-paid every turn. Cached reads price at 0.1× ([pricing](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)), so cache-aware ordering (J6) is a ~85-90% saving on the static prefix within TTL windows — the single largest cost lever in this module, but note the trade: per-query tool filtering (token saving) and caching (prefix stability) currently fight each other.
- **Assembly compute:** each build fans out DB queries + a vector recall + graph scoring + embedding ranking in parallel; worst case is first-load of a workspace graph blob (up to 42 MB JSON → networkx, LRU-cached thereafter, `graph_service.py:344-385`). Planning pack adds one RAG retrieve + typed recall + KG BFS per plan, capped 2-12k tokens.

## I. UX / surface

**Today:** context assembly has *no* operator surface. The `api/context.py` stats endpoints (fixed by W2) serve RAG metrics; the one frontend component built for them (`context-engineering.tsx`, 773 lines) is mounted nowhere; section budgets are env vars (`config.py:751-757`); and neither Command Center nor chat offers any way to see what an agent knew.

**Concrete changes (in order of client value):**
1. **Command Center → "Context Inspector":** per-run/per-turn view of the persisted assembly trace — mode, sections included/trimmed with token counts, the memory/graph items injected (with source links), which action-catalog variant rendered. This is the trust surface for "why did Auto say/do that?", and it makes the silent-dark-section class visible to operators, not just engineers.
2. **"What Auto knows" affordance in chat:** one action on any Auto reply that reveals the (read-only) assembled context for that turn — the direct answer to the founder's recorded frustration (the "you are lying" exchanges) because grounding becomes checkable.
3. **Planning-pack preview on the PRD-163 approval card:** show the pack the planner saw next to the plan it produced; approvers judge plans against the evidence the planner had.
4. **Workspace settings → Context panel:** move section budgets/toggles from env to per-workspace settings (memory on/off per mode, section caps), with the safe defaults current values.
5. **Disposition of the orphan:** either wire `context-engineering.tsx` to the new trace API as the Inspector's seed, or delete it with the F079 cluster. Not "keep unmounted."

## J. Upgrade path (impact × effort, North-Star ordered)

1. **Persist the assembly trace** — one narrow table (or JSONB on `llm_usage`): turn/run id, mode, sections+tokens, trims, memory item ids, prep_ms. **(S; unlocks G, I1-3, and every debugging conversation about agent quality.)**
2. **One tokenizer, token-aware truncation** — estimator delegates to `context_guard.count_tokens`; replace `content[:max_tokens*4]` with `truncate_to_token_budget` (exists at `modules/rag/budget.py`). **(S; makes every cap and budget honest.)**
3. **Model-aware budgets** — resolve `TokenBudget.total` via `get_context_window(model)` at build time; agent `llm_config` already carries the model. **(S; stops over/under-provisioning per model.)**
4. **Injection-time quality floor for memory** — relevance threshold + content-type exclusion (operational types `playbook_summary`/`heartbeat_log` never enter the user-memory block) at `memory.py:261-267`. The write side is the `memory` dossier's fix; this is the assembly-side guarantee that noise cannot reach prompts even when the store is dirty. **(M; the fastest visible quality win for clients — it removes recorded-lie/402-spam injection now.)**
