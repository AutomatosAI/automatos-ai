## A. What it is

The capability that decides whether a stranger — or the owner on a fresh laptop — can turn this repository into a running platform, and whether the CI that guards `main` actually blocks bad merges. It is the sum of the W6 (PRD-176) and W12 (PRD-182) hardening plus the platform-hygiene relics folded in: a one-command `docker compose up` stack (9 services), a fail-loud router mount manifest with an `ALLOW_DEGRADED_BOOT` escape hatch, a single-alembic-head invariant with a from-zero CI replay, a fail-closed wait→migrate→seed container entrypoint, `pg_dump`/`pg_restore` DR tooling with a tested runbook, a frontend CI lane with a route-contract gate, and a coverage ratchet. Read against the North Star, this module is **infrastructure, not intelligence** — it makes Auto and the agents *neither* more autonomous *nor* higher-quality directly. Its North-Star value is entirely second-order and conditional: a platform that cannot be stood up cannot be adopted, evaluated, or self-hosted by anyone but the owner on the one machine that already works; and CI that cannot block a bad merge is the mechanism by which every *other* module's quality silently regresses (the July review's own root-cause for "four alembic heads shipped undetected"). The honest headline: **W6/W12 moved real ground and the CI scaffolding is genuinely well-designed, but a fresh clone still cannot boot, and the gates that should protect the other 27 modules do not bite.** The good work is one-line-fixes and one repo-admin action away from being real; today it is instrumented-but-inert.

## B. What it does (real implementation + data path)

**The one-command stack.** `docker-compose.yml` defines nine services (`postgres`, `redis`, `minio`, `minio-init`, `backend`, `frontend`, `workspace-worker`, `adminer`, `gotenberg`) with named volumes and healthchecks. Postgres seeds its schema from a bind-mount at `docker-compose.yml:35` — `./orchestrator/core/database/init_complete_schema.sql` (1,964 lines, present) into `/docker-entrypoint-initdb.d/`. MinIO gives the deploy a local object store so the knowledge flywheel can persist (F089): the backend is wired `S3_ENDPOINT_URL` default `http://minio:9000` with creds and a `depends_on: minio` (`docker-compose.yml:140,161-168`), a one-shot `minio-init` creates the bucket (`:106-124`), and `DocumentManager` threads the endpoint + path-style addressing into the boto client (`modules/rag/ingestion/manager.py:424-445`). In production `S3_ENDPOINT_URL` is unset → real AWS S3, unchanged.

**The container lifecycle (F051).** The backend runs through a hand-written `docker-entrypoint.sh` (repo root) whose functions are `wait_for_postgres` (`:22`) → `check_database` (`:101`) → `run_migrations` (`:51`) → `load_seed_data` (`:66`) → `exec "$@"` (`:147`), under `set -e` (`:13`). Migrations are **fail-closed**: `run_migrations` executes `alembic upgrade heads` and aborts startup on failure (`:53-61`). The compose backend bind-mounts this script over the image copy at `docker-compose.yml:188` — `./docker-entrypoint.sh:/usr/local/bin/docker-entrypoint.sh:ro`.

**The fail-loud router manifest (F034 boot half / PRD-155 S3).** `orchestrator/router_manifest.py` (138 lines) exists because the July code silently dropped routers whose import failed — `api.auth` and `api.evaluation` failed on *every* boot and nobody noticed (`router_manifest.py:3-5`). `mount_manifest_routers` raises `RouterMountError` (a `RuntimeError`, `:44-45`) if any `optional=False` spec fails to import, unless `ALLOW_DEGRADED_BOOT=true` downgrades it to a logged skip (`:109-124`). Scope is deliberately narrow: only the *previously-silent* routers live in the manifest; the ~100 routers mounted as plain `app.include_router(...)` at `orchestrator/main.py:944-1000+` already fail loud on a bad import by nature of a Python `import` (`:16-17`). This is the fix that made the July "starlette silently no-ops `include_router`" class survivable — paired with the pin below.

**The dependency pin that holds the API together (F092 cold-boot).** `orchestrator/requirements.txt:2,8`: `fastapi>=0.115.0,<0.116.0` and `starlette>=0.40.0,<0.42.0`. The `<0.42.0` ceiling is load-bearing: starlette ≥0.42 silently no-ops FastAPI `include_router`, collapsing the whole API to ~12 routes on a fresh CI install (documented in project memory as the F092 diagnostic). The pin is present and correct on live main.

**Schema truth (F010 / F051).** Alembic is a single head: `e773c09189a9_merge_prd176_prd181_heads.py` merges the post-wave pair on top of `prd176_merge_heads.py` which merged the four July heads; AST parse of all 137 revision files confirms exactly one head, and CI hard-asserts it (`test.yml:335-343`). But schema is written by **four** mechanisms that mutate overlapping tables: (1) the initdb SQL (compose only); (2) alembic (`upgrade heads`); (3) `create_tables()` = `Base.metadata.create_all` at `orchestrator/main.py:181`, run on *every* boot; (4) inline `ALTER TABLE … ADD COLUMN IF NOT EXISTS` at `main.py:186-193` (verified live: `system_prompts` at :188, `skills` at :192), plus the seeders. Critically, `init_complete_schema.sql` carries **no `alembic_version` stamp** (verified: `grep -i alembic_version` returns empty) — so on a fresh volume the fail-closed `alembic upgrade heads` must replay the entire 137-revision forest.

**DR (F050).** `scripts/dr/backup.sh` (pg_dump -Fc of `DATABASE_URL` + optional first-class `MEM0_DATABASE_URL`) and `scripts/dr/restore.sh` (pg_restore into a fresh DB, `CREATE EXTENSION vector` first) are executable, env-driven, no hardcoded creds. `docs/runbooks/DR-postgres.md` states RPO ≤24h / RTO ≤30min covering primary + mem0 in parallel (`:21-25`); restore is round-trip tested (`orchestrator/tests/test_dr_restore.py:138`, dump→restore→row-parity, skips without Postgres).

**The CI bar (F034/F044/F056/F092).** `.github/workflows/test.yml` runs: the **required** `orchestrator-tests` job (pytest + `--cov`, but schema via `create_all` in `scripts/init_test_db.py`, `:109-110`); a `frontend-ci` job (vitest hard gate, `tsc --noEmit` baselined to a measured floor of 554 via `frontend/scripts/tsc-baseline-check.js`, eslint report-only, `:383-421`); a route-contract step (`frontend/scripts/check-route-contract.js` reads `orchestrator/reports/route-manifest.json`, fails on new api-client calls to unlisted paths, `:420-421`); an `orchestrator-module-tests` job that finally collects the two formerly-orphaned test trees (`pytest.ini:22-25` widened to `tests, modules, integrations`); and an `alembic-from-zero` job. Supply-chain: CodeQL python+js (`codeql.yml`) and gitleaks full-history (`gitleaks.yml`, fetch-depth:0) are live and green; `ioc-scan` is a required context. `.github/workflows/smoke-fresh-clone.yml` does `docker compose up` and curls `/health`.

**Config localisation (F068).** All nine `railway.internal` config defaults flipped to localhost and `LOG_RELAY_ENABLED` → false (`config.py:442,443,543,544,557-561,578,809,833,1000`), guarded by a no-`railway.internal`-in-any-default test assertion (`test_config_env_centralization.py:194-212`). SaaS behaviour preserved via env override.

**The hygiene relics this unit owns.** `orchestrator/api/anthropic_client.py` still `from .base import …` while `api/base.py` does not exist (F083 leg 2 — latent broken dead file, zero importers). Frontend ships **three tracked lockfiles** (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml` all in git — verified) → nondeterministic builds. `frontend/app/api-control/page.jsx` is a live routed placebo panel driving toggles for the PRD-168-deleted mock system; `usePageAPI` is imported by 17 pages but forwards to `apiClient.setCurrentPage`, a no-op (`frontend/lib/api-client.ts:131-133`, verified). `frontend/app/styleguide/page.tsx` is 442 lines routed in prod. (F084 cluster.)

## C. Honest quality — inspected against real behaviour and CI evidence

**Maturity score: 2 / 5** (early — real, well-designed scaffolding; the load-bearing paths do not yet work end-to-end and the gates do not enforce).

The paradox of this module is that the *engineering judgment* on display is a 4 and the *delivered behaviour* is a 1-to-2, and honesty forces me to grade the behaviour. Every design choice here is the right one — fail-closed migrations, fail-loud router mounts, baselined-not-aspirational tsc gate, a route-contract choke point backed by an eslint ban on raw `fetch('/api…')`, DR that is actually round-trip tested. But the two things this module exists to guarantee — *a fresh clone boots* and *CI blocks bad merges* — are both false on live main, and the CI is instrumented in a way that reports green while failing.

**Defect 1 — a fresh clone still cannot boot; the smoke lane lies about it (F009, from-zero blocker).** The July-cited defect (wrong initdb mount path) is fixed. But the headline behaviour is still true, via a *second* blocker the July review never cited: `docker-entrypoint.sh` sits at the repo root with git mode **100644 (non-executable)** — verified live: `git ls-files -s docker-entrypoint.sh` → `100644`. Compose bind-mounts it over the image's `chmod +x` stub (`orchestrator/Dockerfile:103-104,130`). The kernel cannot exec a non-executable file, so the backend container dies at start with `exec: "docker-entrypoint.sh": executable file not found in $PATH` *before the lifecycle ever runs*. The wave's own `smoke-fresh-clone.yml` reproduces exactly this — latest run 2026-07-03 (job 85061322908) printed `FAIL: docker compose up failed` — but `continue-on-error` masks it and the job concluded **"success"**. This is the single most important fact in the dossier: the acceptance criterion "fresh-clone `docker compose up` returns 200 on `/health`" is **unmet**, and the CI that is supposed to prove it is green-while-broken.

**Defect 2 — from-zero migration replay crashes; also masked green (F010, from-zero half).** The single-head invariant is real and hard-asserted. But the *ADJUSTED core* of F010 — replay from an empty DB — still fails: the pinned-main run (28684977751, job 85075865428) exited 1 on the "Replay all migrations from an empty database" step with psycopg2 `relation "marketplace_installs" does not exist`, again masked by `continue-on-error` (`test.yml:355`), job conclusion "success". The Step-2 single-baseline squash that would reconcile ALTERed-but-never-CREATEd tables never landed.

**Defect 3 — the fix for Defect 1 will *cause* a new boot abort unless Defect 2 is also fixed first (F051, the compounding trap).** This is the subtle one. Because the initdb SQL carries no `alembic_version` stamp, once the entrypoint *does* execute (i.e. after the exec bug is fixed), its fail-closed `alembic upgrade heads` on a fresh volume must replay the full 137-revision forest — the exact replay the from-zero CI lane proves currently crashes on `marketplace_installs`. So fixing the exec permission alone converts July's *silent schema drift* into a *hard boot abort on the fresh-clone path the wave was meant to open*. The two residuals are coupled: the entrypoint fix is inert (or harmful) without either an `alembic_version` stamp in the initdb SQL or the Step-2 squash. This is a genuine quality flag, not a nitpick — fail-closed is the right posture, but it was bolted onto an unstamped schema.

**Defect 4 — the gates don't bite; the other 27 modules are unprotected (F057, live-verified).** Re-read live via `gh api` on 2026-07-04: branch protection on `main` is `strict:false`, required contexts only `["orchestrator-tests","ioc-scan"]`, `enforce_admins:false`, `required_approving_review_count:0`. So **none** of the new W12 lanes — `frontend-ci`, `route-contract`, `orchestrator-module-tests`, `alembic-from-zero` — can block a merge, and the stale-merge window (`strict:false`) that the July review named as the cause of the red-main incidents is unchanged. This is a 30-second repo-admin action (the ready command sits in `docs/runbooks/W12-BRANCH-PROTECTION.md`), deliberately not applied by the wave. Until it flips, the entire W12 CI-bar investment protects nothing.

**Defect 5 — the coverage ratchet is unarmed (F092 leg b).** `pytest-cov` is wired into the required job with `--cov` and a `.coveragerc`, but `orchestrator/.coverage-baseline` still holds the SEED token, so `scripts/check_coverage_baseline.py` prints the number and exits 0 every run. The 80% doctrine is measured, never enforced — one human commit (the measured floor over SEED) away from real.

**Defect 6 — schema truth still has four writers (F051).** `create_all` at boot + inline ALTERs + initdb SQL + alembic all mutate overlapping tables (verified live at `main.py:181,186-193`). This is the mechanism by which drift ships undetected; consolidating to one lifecycle is unfinished.

**The hygiene tail (F084, F083 leg 2) — real but low-stakes.** Three tracked lockfiles are a genuine nondeterministic-build risk and the cheapest possible fix (delete two). The dead `api/anthropic_client.py`, the `/api-control` placebo panel, the 17 `usePageAPI` no-ops, and `/styleguide` in prod are hygiene debt that erodes trust in the codebase but does not break a deploy. None of these were claimed by any wave — PRD-184 (the dead-code kill list) was never authored.

**What is genuinely done and good (honest positives).** F050 DR is complete and *tested* — the literal asks are fully met. F068 config localisation is thorough and test-guarded. F044's route-contract net is a well-architected gate (single choke point enforced by an eslint ban). F056 collected two entire orphaned test trees at root cause (raw-DDL for migration-only tables in `init_test_db.py`, honest environment-probe skips). F089's MinIO seam is complete and default-on for compose. The supply-chain leg of F092 (CodeQL + gitleaks + live automated-security-fixes, verified `{"enabled":true,"paused":false}` 2026-07-04) is done. The starlette pin holds. The *code* is not the problem; the *last mile* (six one-line/one-command arming actions) is.

**Real-data note.** There is nothing to inspect in prod Postgres for this module — deployability is a build-and-boot property, not a stored-data property. The relevant "real behaviour" evidence is the CI run logs (read via `gh` in the residual map), which is what grounds Defects 1, 2, 4 and 5 above. The one adjacent real-data signal: the prod DB agrees it is migratable (152 tables including wave tables `approval_grants`, `error_events`, `unrouted_events` — [census](evidence/data/census.md)), which tells us the *incremental* alembic path works against a long-lived DB; it is only the *from-zero* path that is broken. That distinction matters: the running Railway prod is fine; the open-core promise (anyone else stands it up fresh) is not.

## D. Competitive teardown

The comparators are OSS-core products whose *whole business* depends on strangers self-hosting them cleanly. Automatos is measured against the deploy hygiene those products treat as table stakes.

**Dify (langgenius/dify).** The reference for a frictionless self-host of an LLM-app platform. Deploy is `cd dify/docker && cp .env.example .env && docker compose up -d`; the compose bundle ships web + API + worker + DB + vector store, and the self-hosted edition has no meaningful feature gates. Where it beats Automatos: **the fresh-clone path actually works out of the box** and is the primary documented install, not an aspiration behind a masked-green smoke lane. Dify also pins a minimum Docker Compose version (2.24.0) as an explicit prerequisite rather than discovering incompatibility at runtime. Automatos's compose is comparably complete (9 services, MinIO, Gotenberg) — it is strictly the boot-correctness (exec bit, schema stamp) that separates them. Source: [Dify docs — Deploy with Docker Compose](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose), [GitHub langgenius/dify](https://github.com/langgenius/dify).

**Cal.com (open-core, Prisma).** The closest parallel on the *migration-on-boot* axis, and instructive precisely because it shares Automatos's danger. Cal.com "runs Prisma migrations automatically on container startup when schema changes are present," and its own docs warn that Prisma "can drop entire columns of data if it can't figure out what to do" and "always take a database backup before any update." Where it beats Automatos: it separates `db-deploy` (production, apply-only, migration-history-tracked) from `db-migrate` (dev, generate), so production never silently regenerates schema — versus Automatos running `create_all` + inline ALTERs on *every* boot alongside alembic (four writers). Where Automatos is ahead: it *has* the DR backup tooling Cal.com only tells you to run manually. The shared lesson is that migration-on-boot is only safe with a single apply-only path and a stamped baseline — the exact two things Automatos is missing. Source: [Cal.com — Database migrations](https://cal.com/docs/self-hosting/database-migrations), [Cal.com Docker self-host](https://cal.com/docs/self-hosting/docker).

**n8n (self-host).** The bar for *low-ceremony* boot: `docker compose up` with Postgres, tables auto-created on startup, a single documented gotcha (`DB_TYPE=postgresdb`, host = compose service name). n8n beats Automatos on *simplicity of the guarantee* — there is one schema mechanism (the ORM creates tables), not four, so there is no from-zero-replay forest to crash on. Automatos's schema surface is far larger and genuinely harder (152 tables, pgvector, raw-DDL tables with no ORM model), so a straight ORM-create is not open to it — but n8n shows that "one writer of schema truth" is the property to converge on. Source: [n8n Docker docs](https://docs.n8n.io/hosting/installation/docker/), [n8n-hosting withPostgres](https://github.com/n8n-io/n8n-hosting/blob/main/docker-compose/withPostgres/README.md).

**Supabase (declarative schema + migration tooling).** The most directly *adoptable pattern* for Automatos's specific problem. Supabase lets you declare the desired schema in SQL files (`supabase/schemas/`) and runs `supabase db diff` (via `djrobstep/migra` against a shadow DB built by applying migrations) to *generate* the migration that reconciles them, with a migration-history table (`supabase_migrations.schema_migrations`) as the single source of truth; subsequent pushes skip already-applied migrations. Where it beats Automatos decisively: **one declared schema is the source of truth, and drift between it and the migration forest is a CI-checkable diff** — exactly the check Automatos lacks (`route-manifest.json` gets a determinism test but the schema does not; and the from-zero replay is the thing that would catch drift, but it runs `continue-on-error`). The shadow-DB diff is the discipline that would have caught "ALTERed but never CREATEd" tables before they shipped. Source: [Supabase — Declarative database schemas](https://supabase.com/docs/guides/local-development/declarative-database-schemas), [Supabase CLI — db diff](https://supabase.com/docs/reference/cli/supabase-migration).

**Where Automatos actually stands.** On *breadth* of the deploy (multi-service compose, DR tooling, supply-chain CI, config localisation) it is competitive with or ahead of several of these — Automatos ships tested `pg_dump`/restore that Cal.com and n8n leave to the operator. On the *one thing that matters most* — a stranger cloning the repo and getting a running platform — it is behind all four, because the fresh-clone path is broken (exec bit + unstamped schema) and the CI that should prove it works is masked green. This is not a capability gap; it is a **last-mile correctness gap**, which is both the good news (small) and the indictment (it is exactly the mile an open-core deploy exists to cover).

## E. Build / extend / adopt / replace — the verdict

**EXTEND — finish the last mile in place; adopt one external *pattern* (Supabase-style declarative schema + shadow-DB diff), replace nothing.**

There is no product to "adopt" here that would replace a bespoke multi-service compose + alembic stack for a 152-table pgvector platform — the deploy is intrinsic to this codebase and the W6/W12 scaffolding is already the right shape. Building anything new would be waste; the work is almost entirely *arming what exists*. Concretely:

1. **Extend (owner, ~1 line each):** make `docker-entrypoint.sh` executable in git (`git update-index --chmod=+x`, or change the ENTRYPOINT to `exec bash docker-entrypoint.sh "$@"`); then drop `continue-on-error` on the smoke lane so it can never again report green while broken. Closes the F009 second blocker.
2. **Extend (owner, small):** stamp `alembic_version` into `init_complete_schema.sql` **or** author the Step-2 single-baseline squash, so a fresh volume does not replay (and crash on) the 137-revision forest; then drop `continue-on-error` on the from-zero replay. Closes F010/F051 residuals **and** must land *with or before* action 1, or action 1 turns silent drift into a hard boot abort.
3. **Adopt (pattern, not vendor):** borrow Supabase's discipline — treat `init_complete_schema.sql` as a *declared* schema and add a CI step that diffs it (or a fresh `create_all` dump) against the applied-migrations shadow DB, failing on drift. This is the structural fix for "four writers of schema truth": it makes drift a red check instead of a production surprise, and it is the check that would have caught `marketplace_installs`. Cost: one CI job + a `migra`/`alembic check`-style diff (both exist off-the-shelf). No new runtime dependency.
4. **Extend (owner, 30 seconds):** flip branch protection `strict:true` and add `frontend-ci`, `orchestrator-module-tests`, `alembic-from-zero` (once green) as required contexts — the ready command is in-tree. This is what gives every other module's CI teeth (F057). Highest leverage-per-effort action in the entire Phase-2 program.
5. **Extend (owner, 1 commit):** commit the measured coverage floor over the SEED token to arm the ratchet (F092 leg b).
6. **Replace-by-deletion (small):** delete two of the three lockfiles, the dead `api/anthropic_client.py`, the `/api-control` placebo page, and `/styleguide` from prod; keep or no-op-collapse `usePageAPI`. This is PRD-184 territory — author it (owner call, §12).

Why extend and not build/replace: the delta to enterprise-grade here is measured in one-line fixes and one repo-admin toggle, not in new systems. Justifying a new deploy tool or a migration framework swap against that is impossible — nothing external wins when the in-house thing is six small arming actions from done.

## G. Quality metric

The right metric for this module is **binary boot-and-block correctness, tracked as CI truth** — and the first job is to make the existing lanes *tell the truth* so the number is trustworthy:

- **Primary: fresh-clone boot success** = does `smoke-fresh-clone` reach `/health` 200 *without* `continue-on-error` masking? **Today: 0 (FAIL, masked green).** Target: 1 (hard-gated pass). This is the single number that says "an outsider can run this."
- **From-zero migration replay success** = does `alembic upgrade heads` from an empty DB exit 0 as a *required* check? **Today: 0 (crashes on `marketplace_installs`, `continue-on-error`).** Target: 1 (required).
- **Required-check coverage** = fraction of the CI lanes that are actually required by branch protection. **Today: 2 of ~6 meaningful lanes** (`orchestrator-tests`, `ioc-scan`); `strict:false`. Target: all green lanes required, `strict:true`.
- **Schema-writer count** = number of mechanisms that mutate schema on a normal boot. **Today: 4** (initdb SQL, alembic, `create_all`, inline ALTERs). Target: 1 (alembic, with a stamped baseline).
- **Coverage ratchet armed?** boolean. **Today: false** (SEED token). **tsc baseline: 554, frozen** (measured, not reduced).

The pattern to institutionalise (feeds T3): every deploy-correctness lane must be *hard* (no `continue-on-error`) and *required* — an instrumented-but-inert lane is worse than none because it reads as a passing check. The T3 eval harness should surface these five booleans on a dashboard as the module's health, because unlike the intelligence modules there is no fuzzy judge needed here — the answers are yes/no and CI already computes them; they are just masked.

## H. Cost note

Effectively zero per-operation LLM/compute cost — this module invokes no model. The relevant costs are (a) CI minutes: the from-zero replay + smoke-fresh-clone + module-tests jobs add real wall-clock to every push (the smoke lane spins a full compose stack), currently spent producing masked-green results — negative ROI until de-masked; (b) the **operational cost of the missing fixes**: a broken fresh-clone path costs every prospective self-hoster's first hour and every onboarding of a new contributor; an unarmed gate costs the debugging time of every red-main incident it fails to prevent (the July review attributes real incidents to exactly this). The DR runbook's nightly dump is unscheduled (runbook §3.2 assigns it to cron/Railway) — an operator action, not a code cost. Net: the cheapest module to *fix* in the entire review (six one-line/one-command actions) and one of the higher-cost to *leave broken*.

## I. UX / surface

Deployability's "UX" is the operator/contributor experience and the honesty of the status surfaces:

- **The README / quick-start is the primary surface** and it currently over-promises: `docker compose up` does not yield a running platform. Fix the two boot blockers first, then the one-command story becomes true and can be documented as Dify does (single copy-env + up).
- **CI status is a UX surface for the owner and any contributor**, and it is actively lying (two lanes green-while-broken). De-masking is a UX fix as much as a correctness one — a red check that means "broken" is more usable than a green one that means "maybe broken."
- **Command Center tie-in:** there is a genuine opportunity to surface *deploy/boot health* as a first-class tile in the "is-it-working" strip (`frontend/components/command-center/is-it-working-strip.tsx`, owned by `observability-slos`) — e.g. "last fresh-clone smoke: PASS/FAIL", "migration head: single", "schema drift: none" — reusing the SLO tile pattern. This would make the module's own quality visible to the owner instead of buried in Actions logs.
- **`/api-control` and `/styleguide`** are routed prod pages that should not be in a shipped product; removing them tightens the surface an evaluator sees.
- No new IA is warranted beyond deleting the relic pages and (optionally) the boot-health tile — this is not a user-facing feature module.

## J. Upgrade path (prioritised by North-Star impact × effort)

Ranked by leverage. Note the North-Star framing: this module's impact is second-order (it *unblocks* adoption and *protects* every other module's quality), so the ranking weights "unblocks the most" and "cheapest."
