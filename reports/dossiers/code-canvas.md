## A. What it is

Code Canvas (PRD-170, wave W14, PR #501, merged 2026-07-04) is a Claude-Code-quality coding surface embedded in the platform: a **headless Claude Agent SDK session runs per workspace inside the workspace-worker container**, and the UI renders it — file tree + Monaco editor on the left, a streamed agent-session panel (turns, diff-approval cards, commit/push) on the right. It sits on top of the pre-existing **workspace-worker** (PRD-56/66): a Redis-queue task consumer plus an aiohttp HTTP server that owns the persistent `/workspaces` volume and exposes file-browse, command-exec, grep, git and html-to-png endpoints that the platform proxies. The module therefore has two halves: a **compute substrate** (worker + `workspace_*` agent tools + the `/api/tasks` direct-step lane) that is live and lightly used, and the **canvas SDK-session layer** on top of it that is the headline W14 feature and — as shipped — cannot yet perform its core function.

## B. What it does — real implementation and data path

### B.1 The worker (compute substrate, PRD-56/66)
`services/workspace-worker/main.py` runs one `WorkspaceWorker` process (`main.py:62`, concurrency default 3, `:75`) that (a) consumes tasks from four Redis priority queues and executes their steps (`_execute_task:229`, `executor.execute_step`), and (b) runs an aiohttp health server (`_health_server:463`) on port 8081 exposing `/workspaces/{id}/files`, `/files/content`, `/exec`, `/files/write`, `/files/grep`, `/files/download`, `/git`, `/html-to-png`. All paths go through `WorkspaceManager.resolve_safe_path` (`workspace_manager.py:242`, rejects absolute/`..`/null-byte) and `WorkspaceToolExecutor`, which enforces a binary allowlist (`executor.py:35-73`), a blocked-pattern list (`:76-98`) and a stripped sandbox env. One shared volume `workspace_data:/workspaces` backs every workspace (`docker-compose.yml:264`); the worker drops to a non-root `worker` uid (`Dockerfile`, entrypoint).

### B.2 Agent + browser access to the substrate
The platform reaches the worker through `core/workspace_client.py` (`WorkspaceClient`, one httpx singleton, `X-Internal-Token` auth `:33`, single `WORKER_INTERNAL_URL` for all workspaces `:44`). Two callers:
- **Auto's own agents** via the `workspace_read_file/write_file/list_dir/grep/exec/git/html_to_png/get_public_url` tools (`modules/tools/discovery/workspace_actions.py:15-341`, executed in `modules/tools/execution/exec_workspace.py:183`). This is the model-agnostic, autonomy-facing lane.
- **The browser** via `api/workspace_files.py` (proxy, tenancy-checked `ctx.workspace_id != workspace_id → 403` on every route, e.g. `:74-75`).

### B.3 The canvas SDK session (S1)
`services/workspace-worker/canvas_session_service.py` — `CanvasSessionManager` holds one `_LiveSession` per workspace (`:97`, process-singleton `get_canvas_manager:536`). `start_session(workspace_id)` (`:289`, note: **only** a workspace id — no prompt argument) enforces one-active-session-per-workspace (`:295-304`), provisions the dir tree (`ensure_workspace_exists:311`), reads prior volume state for resume (`_load_state:513`), builds `ClaudeAgentOptions(cwd, env{CLAUDE_CONFIG_DIR}, permission_mode="default", can_use_tool, resume?)` (`:336-346`), lazily imports and connects a real `ClaudeSDKClient` (`_default_sdk_client_factory:125`, `client.connect():350`), then spawns a message pump (`_pump:452`). State + the CLI transcript persist under `<workspace>/.canvas/` on the volume (atomic write `_persist:505`), so sessions survive worker/orchestrator restarts and resume via the persisted `sdk_session_id`.

### B.4 Confinement + approvals (S1/S4)
`canvas_confinement.py` is the hard tenancy gate the SDK `can_use_tool` callback runs first (`canvas_session_service.py:187`): `confine_path` re-binds relative paths under the workspace root and rejects `..`/symlink/null-byte/out-of-root absolutes (`:59-82`); `_command_escape_reason` rejects bash strings that reference the volume outside this workspace or contain a `..` component (`:85-126`). Then `canvas_approvals.py` gates mutation: `requires_approval` returns True for every `Bash` and (unless session auto-accept is on) every `Write/Edit/MultiEdit/NotebookEdit` (`:55-67` — bash can never be auto-accepted); `PendingApprovals` is an asyncio registry that registers a request, emits a `permission.request` event with a diff payload (`build_permission_payload:96`), and **awaits the human decision indefinitely** (`_await_decision:221`), resolved out-of-band by the decision endpoint (`decide:253`). `fail_all` denies every waiter on teardown (`:178`).

### B.5 Event stream → UI (S3)
`canvas_events.py` maps SDK messages to a **closed, versioned** event vocabulary (`CANVAS_EVENT_SCHEMA_VERSION = 1`, `:34`; seven types `:45-55`) — assistant text, tool call, tool result, file edit, permission request, turn complete. `serialize_sdk_message` (`:177`) duck-types the SDK surface and never emits secrets. The worker publishes each event to a per-workspace Redis channel (`main.py:923` `_canvas_event_sink` → `CANVAS_EVENTS_CHANNEL`); `api/workspace_files.py` subscribes and re-emits over SSE with tenancy enforced (`_canvas_event_stream:332`, `stream_canvas_events:372`). The frontend validator `frontend/components/widgets/CodingCanvasWidget/canvasEvents.ts` mirrors the vocabulary and a vitest fails on drift.

### B.6 Git integration (S5)
`modules/tools/discovery/canvas_git.py` — branch-per-session `canvas/<slug>` (`canvas_branch_name:37`), a deterministic (no-LLM) editable commit-message generator (`generate_commit_message:117`), `plan_commit_push` emitting checkout/add/commit/push steps with every value shlex-quoted and the remote allowlist-validated (`_validate_remote:158`, two injection gates), and `redact_token` (`:48`, three-pass secret scrub re-running the PRD-154 S12 test class). The proxy routes are `GET /canvas/commit-preview` and `POST /canvas/commit` (`workspace_files.py:420,459`), push auth from a GitHub-App token (`resolve_github_token`), redacted before any output leaves the process (`:503-507`).

### B.7 Codegraph-over-clone (S6) — glue only
`modules/codegraph/workspace_clone_index.py` defines the pure binding for pointing the PRD-165 codegraph family at the local workspace clone — project name (`:54`), tenancy-fenced clone path (`:65`), and an on-start/on-commit reindex trigger (`should_reindex:105`). Its own docstring (`:19-37`) states the DB-backed indexing and the SDK MCP bridge are **not wired**, and names the two missing infra pieces. Grep confirms **no production caller** of any symbol in this file.

### B.8 Frontend + entry
`CodingCanvasWidget/index.tsx` composes `WorkspaceExplorer` (tree/editor/terminal) + `CanvasSessionPanel`; `useCanvasSession.ts` starts/stops the session, opens the SSE stream (reusing the W10 board-stream transport), folds events through the tested reducers, and POSTs approve/deny + auto-accept decisions. Opened from chat via a "Code Canvas" button (`components/chatbot/chat.tsx:95-124`) or the standalone `/workspace` page. The `/api/tasks` **direct-step lane** (`api/tasks.py:62`) is a separate ingress: POST concrete shell/git/file steps → Redis → worker `execute_step`, bypassing any LLM.

## C. Honest quality — maturity **2 / 5**

The split is stark: the substrate (worker + `workspace_*` tools) is real, careful and works but is barely used; the canvas SDK-session layer is well-engineered scaffolding that, as merged, **cannot perform its one job** and rides a lane with almost no production history. Grounded findings:

1. **The canvas has no prompt-ingress path — the agent can never be instructed.** This is decisive. `CanvasSessionManager` connects the SDK client (`canvas_session_service.py:350`) and pumps *received* messages (`_pump:452`), but **nothing ever calls `client.query(...)`** — `grep` for `.query(`/`send`/`user_message`/`prompt` across `services/workspace-worker/*.py` returns nothing but comments. `start_session` takes only a workspace id (`:289`); there is no worker endpoint, no `WorkspaceClient` method, and no proxy route to send a turn (the canvas routes are start/status/stop/decision/auto-accept/events/commit — `workspace_files.py:208-517`). The frontend confirms it: `useCanvasSession` exposes `start/stop/decide/setAutoAccept` and no `send` (`useCanvasSession.ts:109-120`); the only `Textarea` in the widget is the **commit-message** editor (`CanvasCommitControl.tsx:19`); the session panel's empty state literally reads *"Ask Auto to change this workspace"* (`CanvasSessionPanel.tsx`) beside a UI that has no box to ask in. A `ClaudeSDKClient` in streaming mode does nothing until it receives a query, so a started session connects and idles. **The PRD's headline demo — "add input validation to X and push" → streamed work (§Success Metrics) — is unreachable through the shipped surface.** Every downstream piece (events, diff approvals, commit) is wired to fire, but the first turn can never be sent.

2. **Real behaviour: the substrate is nearly unused and the canvas has zero production runs.** `task_executions` holds **9 rows total** ([census.md](evidence/data/census.md):57) — nine lifetime direct-task/worker executions across the platform's history. `codegraph_projects = 1` / `codegraph_symbols = 7,702` (census :60-61) is a single indexed project (the platform's own tree, not a canvas clone — S6 is unwired, #6 below). Client-facing `deliverables` stopped 2026-06-16 ([deliverables.md](evidence/data/deliverables.md)). The canvas itself merged on the review baseline date, so **no canvas session has ever run in production** — the maturity call rests on code inspection plus the substrate's thin usage record, and the substrate's record says the workspace-compute lane is, in practice, dormant.

3. **The worker has no model credentials in the committed config.** The Dockerfile installs `@anthropic-ai/claude-code` + `claude-agent-sdk` (`Dockerfile`), but the worker's compose env block (`docker-compose.yml:251-263`) sets DB/Redis/volume/quota vars and **no `ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN`** — only the *api* service gets an Anthropic key (`:158`). `start_session` builds `ClaudeAgentOptions` with cwd/env/permission_mode/resume but no key or model (`canvas_session_service.py:336-346`). So even after #1 is fixed, the SDK subprocess in the worker has no committed auth path — a second end-to-end gap. (A deploy could inject it into the image env, but the reviewed config does not.)

4. **Isolation is shared-process path-confinement, not per-session sandboxing.** All workspaces share one worker process (`main.py:62`, concurrency 3) on one volume (`docker-compose.yml:264`); each canvas session is a `claude` subprocess of that shared worker, fenced to its subdir only by `canvas_confinement`'s path re-binding and a command-string regex (`canvas_confinement.py:85-126`), all running as the same `worker` uid on the same kernel. There is no per-workspace container/VM. This is a legitimate pilot choice and the confinement code is pure-stdlib and unit-tested, but it is materially weaker than the per-task VM isolation the enterprise coding-agent peers ship (§D) and it caps how safely Auto can run agentic code unattended. (Adversarial depth handed to the security pass.)

5. **Provisioning (S2) is a `mkdir`, not a container.** "Provision-on-demand" resolves to `WorkspaceManager.ensure_workspace_exists()` creating the default subdir tree on the shared volume and returning a `provisioned` boolean (`workspace_manager.py:72-91`, called `canvas_session_service.py:311`). There is no container lifecycle for wizard-created workspaces; the PRD's "cold provisioning < 2 min with honest progress" (S2 / Success Metrics) has nothing to provision beyond directories. `provisioningState.ts` exists to render a cold-start state that the backend never really enters.

6. **Codegraph-over-clone (S6) is unwired — the seed symptom, confirmed.** `workspace_clone_index.py` is pure glue with zero production callers (grep-verified); its docstring honestly records the two missing builds (`:19-32`): a local-directory index entrypoint on `CodeGraphService` (only `index_github_project` exists, which clones from a URL) and an **SDK MCP server** so the headless CLI session can call codegraph at all (no MCP surface exists in the codebase). So S6's acceptance ("agent answers 'what calls X?' inside a canvas session") cannot be met. Credit where due: the author flagged the gap in-code per CLAUDE.md §12 rather than silently deferring — but the story is not done.

7. **The direct-step lane is ungoverned (F060 residue).** `/api/tasks/submit` enqueues raw shell/git/file steps straight to the worker with auth + workspace-ownership checks only — no PolicyGate, no budget ceiling, no approval ([phase0-residual-map.md](evidence/phase0-residual-map.md) F060 pt 5; `tasks.py:62-124`, still mounted `main.py:1000`). This is the lane that *can* run unattended (automation/agents POST steps), and it sits entirely outside the merged W11 policy plane. For the North Star (agents acting autonomously and safely) this is the governance gap that matters most on this module.

8. **No approval/audit persistence — the PRD's own success metric is unmeasurable.** PRD-170 sets "zero unapproved writes in audit across the pilot" (§Success Metrics). But approvals live only in an in-memory `PendingApprovals` registry (`canvas_approvals.py:148`); nothing writes an approval/decision record to the DB. There is no audit store to count unapproved writes against, and a worker restart loses all in-flight approval state (`fail_all` denies them, `:178`). The guarantee is enforced at runtime but not auditable after the fact.

9. **No live-session integration test.** The pure modules are well-covered (approvals 365 / events 327 / session-manager 438 / git 252 test lines), but the session-manager tests inject a *fake* SDK factory — **no real `claude` subprocess ever runs in CI**, and every S1/S3/S4/S5/S6 acceptance criterion that says "integration test / e2e / dev-browser" shipped verified only by unit tests. The behaviours most likely to break in production (SDK connect, the query loop that doesn't exist, real confinement against a live tool call) are the untested ones.

10. **What is genuinely good.** The event schema is closed, versioned and drift-guarded across the FE/BE boundary (`canvas_events.py:34` ↔ `canvasEvents.ts` vitest). The approval registry is a clean asyncio bridge with deny-by-default on cancel/teardown. Confinement and git-token redaction are pure, tested, and re-use the platform's proven S12 redaction discipline; the git remote gets two injection gates. State persistence is atomic (`tmp`+`os.replace`) with real resume semantics, and `.canvas` is in the worker's `_SENSITIVE_NAMES` so the file browser cannot leak session state/transcript (`main.py:476`). The substrate's exec sandbox (allowlist + blocked patterns + stripped env) is careful. **This is well-built scaffolding** — the deduction is not for sloppiness, it is because the assembled system cannot yet do the thing it exists to do.

**Why 2:** the canvas SDK-session layer alone rates ~1.5 (inert — no prompt loop, no worker model auth, no codegraph, no live test, zero prod runs); the underlying compute substrate rates ~3 (real, careful, works — but 9 lifetime executions and an ungoverned direct-step lane). Weighted across the broadened scope, **2/5**. The bones are good; the loop is open.

## D. Competitive teardown

**1. Anthropic Claude Agent SDK / Claude Code** (the embedded engine itself — [code.claude.com/docs/en/agent-sdk/permissions](https://code.claude.com/docs/en/agent-sdk/permissions)). The SDK's permission pipeline is *PreToolUse hook → deny rules → allow rules → ask rules → permission mode → `can_use_tool` → PostToolUse*; for headless runs Anthropic's guidance is `allowedTools` + a non-blocking permission mode plus a programmatic `can_use_tool` for anything that slips through. **Where it beats Automatos:** Automatos wired only the `can_use_tool` leg (plus a hard confinement pre-check) and streaming — but not the **turn ingress** (`client.query`) that makes Claude Code a loop, nor allow/deny/ask rules, subagents, or PostToolUse hooks. The reference harness is complete; Automatos's is missing the first mile. **Where Automatos stands:** its server-side confinement pre-gate (re-binding agent paths before the tool runs) is a sound addition the base SDK leaves to the integrator, and its diff-card approval UX is a genuine product surface over the raw callback.

**2. OpenAI Codex, cloud agent** ([developers.openai.com/codex/concepts/sandboxing](https://developers.openai.com/codex/concepts/sandboxing), [openai.com/index/introducing-codex](https://openai.com/index/introducing-codex/)). Each task runs in its **own isolated container**; a two-phase runtime (setup with network to install deps, then agent phase offline by default) with per-environment network allowlists; **3–5 parallel tasks each in a separate sandbox with separate git state**, results delivered as separate PRs; secrets are removed before the agent phase. **Where it beats Automatos:** per-task isolation, parallelism, egress controls, and a mature "work → diff + logs → PR" trace. Automatos matches only the git-output leg (branch-per-session push) and runs one shared worker, one session per workspace, no network isolation. **Where Automatos stands:** its branch-per-session + editable-message + token-redaction commit flow is a close, clean analogue of Codex's PR output.

**3. Devin 2.0 / Devin Desktop** ([devin.ai/pricing](https://devin.ai/pricing), [docs.devin.ai/release-notes/2026](https://docs.devin.ai/release-notes/2026)). A full cloud IDE (terminal, browser, filesystem); a **team of parallel "managed Devins," each its own isolated VM**, coordinated by a lead session; session management (child sessions, playbooks, structured output), and full **search/replay across shell/file/browser/git/MCP activity**; VPC deploy; ACU pricing ≈ $2.00–2.25 per ~15 min of work. **Where it beats Automatos:** per-session VM isolation, fan-out parallelism, and session search/replay — Automatos has one session per workspace, no parallelism, and no replay/search (approvals aren't even persisted, §C.8). **Where Automatos stands:** Devin is a standalone coding product; Automatos's canvas lives *inside* an ops platform beside Auto's own agents and the same workspace — a genuinely different position, currently unrealized because the canvas doesn't connect to Auto (§E).

**4. Sandbox runtimes — the isolation layer Automatos lacks** (Modal [modal.com/resources/best-microvm-sandboxes-ai-code-execution](https://modal.com/resources/best-microvm-sandboxes-ai-code-execution), Northflank [northflank.com/blog/how-to-sandbox-ai-agents](https://northflank.com/blog/how-to-sandbox-ai-agents), plus E2B / Firecracker). Firecracker microVMs boot in ~125 ms with <5 MiB overhead and give each workload its **own kernel** under KVM — hardware isolation the shared-process model cannot offer. **Where they beat Automatos:** these are the drop-in substrate for per-session isolation that Codex/Devin build on; Automatos runs everything in one worker process on one volume (§C.4). **Read:** this is an *adopt* candidate, not a competitor to beat — if the canvas is to run agentic code unattended, the isolation belongs to a runtime like these, not to hand-rolled path-confinement.

**Where Automatos actually stands:** the git-audit-trail and diff-approval UX are competitive and tasteful; the confinement/redaction engineering is careful. But on the three things that make a coding agent *work* — a live prompt→work loop, per-session isolation, and parallelism — it is behind all three named peers, and its one structural differentiator (a coding surface fused to an autonomous ops platform) is not yet wired to that platform.

## E. Build / extend / adopt / replace — verdict

**Extend the harness to close the loop; adopt an isolation runtime and the SDK MCP bridge rather than build them; and put the North-Star scope question to Gerard before investing further.** The scaffolding is worth finishing, but not blindly.

- **Extend (finish the loop — cheap, unblocks everything):** wire the missing turn ingress — a worker `POST /canvas/session/message`, a `WorkspaceClient.canvas_session_send`, a proxy route, and a prompt box in `CanvasSessionPanel` that calls `client.query(...)` on the live `_LiveSession`. Then wire worker model auth (an `ANTHROPIC_API_KEY`/OAuth path in the worker env, §C.3). These two changes are small and turn an inert harness into a working agent surface. Building the harness in-house was justified (it's a thin, tested layer over the SDK); it just wasn't completed.
- **Adopt (isolation):** if this lane will run agentic code unattended, adopt a sandbox runtime (E2B / Modal / a Firecracker-based service) for per-session isolation instead of extending shared-process path-confinement (§C.4, §D.4). Integration shape: the worker launches each session inside a per-workspace sandbox rather than a subdir; rough cost = per-session compute metered by the runtime. Do **not** build microVM isolation in-house.
- **Adopt (S6 codegraph):** the missing pieces are a local-directory index entrypoint on `CodeGraphService` (small build) and an **SDK MCP server** exposing the PRD-165 codegraph tools to the headless session — adopt the Agent SDK's MCP-server pattern rather than invent a bridge. Gate this behind the base loop working; codegraph-over-clone is worthless while the session can't be prompted.
- **Govern (substrate):** bring the `/api/tasks` direct-step lane under the merged W11 policy plane (§C.7, F060) — it is the unattended-execution ingress and the cheapest safety win on this module.
- **Reconsider scope — Gerard's call, not a descope (§12):** the canvas is a **human**, Claude-only coding panel. The North Star is Auto's autonomy and agent output quality. The autonomy value lives in the `workspace_*` tool lane that the platform's *own* model-agnostic agents already use — which is under-built (9 lifetime executions, ungoverned direct-step, no codegraph tools on the platform agents). Finishing a human coding panel and hardening/using the agent-driven workspace lane are different bets. Both are legitimate; surface the trade and let Gerard choose which the pilot funds first.

## G. Quality metric

**No number exists today** — 0 canvas sessions in production, 9 lifetime `task_executions` (census.md:57), and the primary funnel is unreachable past step 1 (§C.1). Proposed metrics (feed T3):
- **Session-completion funnel:** `start → first turn sent → ≥1 approved edit → commit+push` (the PRD demo path). Today measurable only to "start"; instrumenting the funnel is what would have surfaced the missing prompt loop immediately.
- **Unapproved-write count** (the PRD's own success metric): requires an approval/decision **audit store** that does not yet exist (§C.8) — build it before the metric can read anything but zero-by-absence.
- **Session start latency** vs the PRD targets (warm <10 s, cold <2 min): no telemetry emitted today; add a timing event on `start_session`.
- **Test-reality gap:** 0 live-session integration tests (§C.9) — track container-backed AC coverage as a first-class number, since the pure-unit suite is green while the assembled system is inert.

## H. Cost note (informational)

- **Per canvas session:** one persistent `claude` CLI subprocess (Sonnet/Opus-class) held open per workspace inside a worker capped at 2 vCPU / 2 GB (`docker-compose.yml:266-270`) with concurrency 3 — so ~3 concurrent sessions saturate the worker, and an idle session still pins a subprocess + file handles + the SSE channel. Token cost, once the loop is wired, is a full Claude-Code agentic loop (tens of K to hundreds of K tokens/task, model-priced). **Today: $0** — no turns are ever sent.
- **Direct-step task lane:** compute-only (no LLM) — cheap; bounded by the exec timeout (≤300 s) and 100 KB stdout cap.
- **Codegraph indexing (if wired):** one embedding pass over the clone per session-start/commit — small per repo, per-commit on the reindex trigger.

## I. UX / surface

**Exists today:** opened from chat via a "Code Canvas" button (`chat.tsx:95`) as a widget — `WorkspaceExplorer` (tree + Monaco + interactive terminal) left, `CanvasSessionPanel` right (start/stop, an auto-accept toggle, streamed turns, `DiffCard` approvals, `CanvasCommitControl`); also a standalone `/workspace` page. Session state is per-widget-instance and client-side.

**Concrete changes, in order of value:**
1. **Add the prompt input** — the panel invites "Ask Auto to change this workspace" with no box to ask in (§C.1). A message composer wired to a new send path is the single change that makes the whole surface functional; everything else is polish until it lands.
2. **Session-scoped token budget** — PRD-170's D11 binding amendment ("session token budgets surfaced in UI") was never built; surface it in the panel header once turns flow.
3. **Honest provisioning state** — `provisioningState.ts` renders a cold-start path the backend never really enters (§C.5); make it reflect the actual `provisioned` mkdir vs a future sandbox spin-up, not a fictional container boot.
4. **Command Center canvas panel** — approvals and live sessions are visible only inside the one open widget; a long-running or agent-driven session's pending approval is invisible if the widget is closed. A Command Center view of live sessions + cross-session pending approvals makes unattended/parallel use possible and is where the "zero unapproved writes" story becomes observable.
5. **Unify the terminal with the session shell** (PRD S7): `WorkspaceExplorer`'s `InteractiveTerminal` and the SDK bash tool are two shell surfaces on the same workspace; per S7 the terminal should be the session shell (approval-gated), not a parallel path.
