## A. What it is

The storefront widget is Automatos's **live autonomous leg**: an embeddable chat widget a merchant drops onto their storefront (Shopify theme, blog, generic site) that talks to shoppers as a full platform agent, not a siloed support bot. A server-type SDK key is exchanged for a short-lived JWT; the browser widget then streams SSE chat that reuses the *same* `ChatService`/`StreamingChatService` as the main dashboard chat — so a shopper conversation carries the workspace's agent, memory, RAG, Composio tools and platform tools. On top of that it layers a commerce-aware **proactive engine**: product-page openers and cart-idle nudges grounded in the workspace Knowledge Graph's frequently-bought-together / collection / vendor edges, and a GDPR-conscious **callback-capture** flow that hashes the shopper's phone and fans the lead out to the merchant's Slack/Telegram/WhatsApp/webhook. Around the shopper-facing embed sits a dashboard surface: a per-workspace **Sites hub**, an SDK **API-key** manager, a **Widget SDK settings tab** (Callback / Cart-idle / Sync panels), plus companion operator panels (email/memory/workflow) and a dashboard "widget marketplace." The shopper client itself lives in a separate monorepo (`automatos-widget-sdk`): a CDN loader + core client + chat/blog widgets + a React wrapper.

One scoping note up front, because the codebase overloads the word: **"widget" means three different things here** and only the first is this module. (1) the **storefront embed / SDK** — the autonomous leg reviewed here; (2) **dashboard workspace widgets** (`components/widgets/` Terminal/Workflow/Image panels) and their install marketplace (`/api/widget-marketplace`, `MarketplaceWidget`/`WidgetInstallation`); (3) **Command Center activity widgets** (`components/activity/widgets/`). (2) and (3) are internal operator UI and are orthogonal to the storefront autonomous leg; the capability-map folded the "widget marketplace" and "companion panels" in, but they are a distinct concern and are treated as adjacent surface, not core, below.

## B. What it does (implementation + data path)

**Mount + middleware.** The plane is registered fail-loud via the router manifest: `api.sites`, `api.widget_email` (optional), `api.api_keys`, `api.widgets.router` (the SSE aggregator), `api.widget_marketplace` (`router_manifest.py:54-62`), plus `widget_workflows`/`widget_memory` mounted directly (`main.py:946,961`). Two pure-ASGI middlewares wrap every `/api/widgets/*` (and `/api/sites/*`) request so SSE is never buffered: `WidgetCORSMiddleware` and `WidgetRateLimitMiddleware` (`main.py:797-801`).

**Auth: server-key → JWT → origin-checked fallback.**
- **Token exchange** (`api/widgets/session.py:77-164`): `POST /api/widgets/auth` takes a raw API key, requires `key_type=="server"` (`:100-104`), resolves effective permissions as a *subset* of the key's grants (empty key grant = unrestricted, `:107-121`), signs an HS256 JWT carrying `workspace_id`/`api_key_id`/`permissions`/optional `default_agent_id`/`team` with a clamped 60s–24h expiry (`:56-59,124-150`), and returns it with a projected `widget_config` (`:155`). The browser never holds the secret key.
- **Request auth** (`api/widgets/auth.py:100-213`): `widget_auth` tries the Bearer token as a JWT first (`:136-166`), else validates it as a raw key via `ApiKeyService.validate_api_key` (`:169`, SHA-256 lookup, active + not-expired, bumps `last_used_at` — `api_key_service.py:110-138`). Public keys (`ak_pub_*`) are then origin-checked against `allowed_domains` (`auth.py:182-183` → `ApiKeyService.check_domain`, fnmatch host wildcards, empty list = all origins — `api_key_service.py:212-228`). An optional `X-Workspace-ID` header must agree with the token/key workspace (`auth.py:149-153,194-200`).
- **Permission guard** (`auth.py:220-266`): `require_permission("chat")` etc. With the policy plane OFF (default — see §C), an empty permission list is the historical **allow-all** god-key (`:255-257`); ON, it unifies on the board plane's empty=deny via `modules/policy/roles.has_permission` (`:253-254`). Valid scopes are declared in `api/api_keys.py:27-41` (chat, blog, documents:*, data:query, data:execute, agents:*, workflows:*, tasks:read).

**Chat: SSE reusing the main agent loop, dispatched through a vertical plugin.** `POST /api/widgets/chat` (`api/widgets/chat.py:127-556`):
- Reads `workspace.settings.vertical` (`:107-120`) and dispatches the message through `PLUGIN_REGISTRY[vertical]` (`:196-217`, registry `integrations/__init__.py:87-101`). The generic plugin prepends an opaque `(Context: …)` block only for non-proactive turns (`integrations/generic/widget_proactive.py:38-56`); the Shopify plugin does richer grounding (below). **`chat.py` holds zero Shopify identifiers** — the PRD-141 vertical-agnostic refactor is real.
- Resolves/creates a workspace-scoped conversation on the shared `chats`/`messages` tables (`:243-297`), owned by a **well-known user id 1** for FK satisfaction (`_get_widget_user_id`, `:89-104`) — widget conversations carry no per-shopper identity.
- Resolves the agent: a key-locked `default_agent_id` overrides any client-supplied `agent_id` (`:338-359`); else the workspace Auto agent.
- Streams via `StreamingChatService.stream_response_with_agent(..., widget_mode=True)` and re-frames AI-SDK chunks as browser SSE events (`message`/`tool-start`/`tool-end`/`open-callback-form`/`done`, `:373-546`). A `system_preamble` from the plugin is injected into the LLM history for the current turn only and **never persisted** (`:313-336`) — the stored transcript keeps the shopper's verbatim words.
- `GET /api/widgets/chat/{conversation_id}` returns workspace-scoped history (`:563-610`).

**Proactive engine (the differentiated bit).** `integrations/shopify/widget_proactive.py`:
- **Product-page opener** (`:50-135,239-313`): given `productHandle`/`productTitle` in page context, `_resolve_graph_related_products` loads the workspace graph (`GraphifyService.load_graph(workspace_id)` → `workspace_graphs` blob), finds the seed product node, walks 1-hop edges grouped by relation — `frequently_bought_with` (sorted by raw `co_count`), `in_collection`, `by_vendor` — and returns the top per relation. `_build_proactive_opener_message` renders them as provenance-cited facts ("bought together in 12 of 57 orders") inside a hard directive: `≤140 chars, plain text only, no tool calls, use these facts as source of truth, do NOT invent specs/compatibility/pricing`.
- **Cart-idle nudge** (`:138-236,316-379`): multi-seed FBT aggregation across every cart line-item, scored by cross-cart pairing count then aggregate `co_count`, excluding items already in cart; same never-fabricate directive.
- **Deictic grounding for normal turns** (`:382-414`): a `[PAGE_CONTEXT]` preamble resolving "this"/"it" to the viewed product, carrying facts only (no output directives), so a typed question is grounded identically to an opener.
- Openers run `force_text_only=True, skip_composio=True` (`chat.py:429-430`) to hold the sub-2s latency budget — the agent's ~45 skill tools are cleared so the LLM can only emit text.

**Callback capture (lead → any channel).** `POST /api/widgets/callback` (`api/widgets/callback.py:73-215`) + service (`services/callback.py`): resolves the Site, validates E.164 phone (`:98-104`), gates on `callback.enabled` (`:108-113`), computes a **SHA-256 salted-per-Site phone hash** (`services/callback.py:76-86`) — the plaintext phone is *never persisted*, only forwarded to merchant destinations — checks a 5-minute idempotency window (`:118-134`), enforces per-session 60s cooldown + per-Site hourly cap (`:136-155`, `services/callback.py:138-192`), writes a `callback_requested` row to `widget_event_log`, synthesises a locale-aware SLA phrase honouring working-hours/team-capacity (`services/callback.py:224-276`), and fires destination delivery. `enqueue_callback_dispatch` (`services/destinations/dispatcher.py:294-316`) → `dispatch_callback_for_site` fans out to all destinations in parallel with retry+backoff (`:154-248`), routing through the *unified* `channels.sender.send_to_channel` (the same path heartbeats use — no parallel destination zoo), logging `callback_delivered`/`callback_failed` per attempt and recording terminal failures to the ERRORS-by-subsystem tile.

**Sites hub + config.** `api/sites.py:85-368` is per-workspace CRUD over the universal `Site` (self-heals a Shopify-connected workspace to `type=shopify` on list, `:90-100`), with strict destination validation requiring a matching `ChannelConnection` (`:162-245`) and a "Send test callback" endpoint (`:306-368`). Public widget config is a *whitelist projection* of `Site.settings` (Site-first, workspace-fallback) — only `widget_proactive`, `cart_idle`, `callback` keys reach the browser (`api/widgets/config.py:48-108`).

**The shopper client** (`automatos-widget-sdk`, read-only): the CDN **loader** (`@automatos/loader` 0.4.1) bootstraps two independent engines — `bootstrapProactive` and `bootstrapCartIdle` (`packages/loader/src/index.ts:4-5,65-92`) — that fetch `GET /api/widgets/config`, gate on merchant+theme config (OR semantics, `proactive/resolve-config.ts:50-51`), and `POST /api/widgets/chat` with `trigger_reason: proactive_opener|cart_idle` (`proactive/fetch-opener.ts:43-47`). The **core client** (`@automatos/core` 0.4.0) sends `page_context` on *every* message for deictic grounding and handles the `open-callback-form` SSE event (`packages/core/src/client.ts:80-84,299-305`); page context is harvested from `data-*` attributes (`page-context.ts:20-38`: product handle/title/vendor/price/availability, collection, shop currency/locale, cart count/total). The **React wrapper** (`@automatos/widget-sdk` 0.1.0) mounts `ChatWidget` directly (`packages/react/src/react.tsx:19-44`).

**What the real data says.** The proactive engine's data source is *live and fresh*: `workspace_graphs` = 155 blobs rebuilt 2026-07-01 (workspace-graphs.md), which is where FBT/co_count/total_orders edges live. Widget conversations land in the shared tables: `chats` = 332, `messages` = 1,278, **newest 2026-06-27** (census.md) — consistent with the platform-wide tapering after mid-June, though widget-origin chats can't be isolated without a query (see §C audit gap). `knowledge_nodes`/`knowledge_edges` = 0 (the commerce graph persists as blobs, not in those tables, so that zero is expected, not a widget defect).

## C. Honest quality — maturity **3 / 5**

**What is genuinely good:**
- **Best-structured module in the ingress/egress half.** The PRD-141 vertical-plugin split is clean and load-bearing: `chat.py` is vertical-agnostic, verticals self-register, and the `system_preamble` mechanism grounds each turn without polluting the persisted transcript (`chat.py:313-336`). Adding a "barbershop" vertical is a new plugin file, not a fork.
- **The shopper agent *is* a platform agent.** Reusing `ChatService`/`StreamingChatService` means widget chat inherits workspace memory, RAG, Composio and platform tools — not a bolt-on FAQ bot. This is the single biggest North-Star asset here: the autonomous leg shares the same brain as Auto.
- **Graph-grounded openers are a real capability, not a template.** Single-seed FBT/collection/vendor traversal and multi-seed cart aggregation, ranked by real co-purchase signal, cited with provenance, wrapped in strict never-fabricate directives with graceful fallback to a Layer-1 opener when the graph is cold (`widget_proactive.py:50-236`). That is meaningfully better than a generic "Hi, need help?" opener.
- **Production scar tissue.** `force_text_only`/`skip_composio` for the opener latency budget (`chat.py:423-430`); Site-first-then-workspace config resolution for backfill-safety (`config.py:79-103`); callback GDPR posture (phone never stored, salted per-Site hash, plaintext only forwarded — `services/callback.py:76-86`); callback delivery reusing the unified `channels.sender` with retry/backoff and per-attempt `widget_event_log` telemetry (`dispatcher.py:154-248`); dedicated per-attempt logging into the ERRORS tile.

**Concrete defects, with evidence:**

1. **The module has no measurement of its own effectiveness — none.** The one thing every competitor below leads with (resolution/containment rate, assisted conversion, AOV lift, opener-acceptance) is entirely absent. The *raw substrate exists* — `widget_event_log` records `callback_requested/delivered/failed`, the proactive engine logs opener latency + `related_count`, `chat.py` logs stream counts (`:531-545`) — but nothing aggregates any of it into a tracked number, and none of it surfaces in Command Center. For a module judged by "can Auto do this job well for clients," having zero read-out of whether the autonomous opener converts, whether callbacks get delivered, or whether widget chats resolve, is the defining weakness. It is flying blind. (Feeds §G, §J-1.)

2. **The headline autonomous feature rides an untested extraction pipeline (F091).** Every opener that says "bought together in X of Y orders" is citing `co_count`/`total_orders` produced by `map_shopify_orders`/`map_shopify_catalog` (`modules/knowledge/graph_extraction.py:503,693`), which have **zero behavioral tests**, and both headline commerce golden journeys are **skipped** (J3 widget-plugin, J9 sync→FBT-opener — `tests/test_golden_journeys.py:101,221`). The phase-0 map records this exposure as having *widened*, because catalog webhooks now auto-run the untested mapper (F032+F091). So the autonomous opener's factual grounding is only as trustworthy as an unverified mapper — a silent regression corrupts every opener and cross-sell with a confident, provenance-styled sentence, and no test catches it. This is the most North-Star-relevant defect in the module: autonomy that fabricates-with-citations is worse than a canned opener.

3. **Distribution is asymmetric and unpublished (F052).** The React wrapper (`react.tsx:19-44`) instantiates `ChatWidget` with a config carrying no page-context/proactive/cart-idle keys, and the proactive + cart-idle engines live *only* in the CDN loader package (`loader/src/index.ts:4-5`), never imported by the React path. So a React-embedding merchant silently gets the degraded widget: chat + deictic grounding, but no proactive openers, no cart-idle. Compounding it, `@automatos/widget-sdk` is unpublished on npm (`registry.npmjs.org/@automatos%2Fwidget-sdk` → Not found, real-data-inventory.md) and the packages are version-skewed (react 0.1.0 vs core 0.4.0 vs loader 0.4.1). The "React channel" is effectively a second, worse product.

4. **I could not confirm the plane carries real live traffic.** `sdk_api_keys`, `sites`, and `widget_event_log` were **not** in the W1 real-data census, and a scoped read-only query for their row counts was blocked this session (production-read guard). So the honest position is: the *code* is comprehensive and the *graph data it reads* is fresh, but there is **no banked evidence that any shopper openers fired, any callbacks were captured, or any keys are in active use** in production. The adjacent signal (widget chats share the `chats` table, newest 2026-06-27) suggests low and declining live activity, consistent with the platform-wide mid-June tapering, but widget-origin can't be isolated. This gap should be closed first in any Phase-2 work (§J-1) — a module you can't prove is used is a module you can't prioritise honestly.

5. **Every widget conversation is owned by user id 1.** `_get_widget_user_id` returns a well-known user row purely for FK satisfaction (`chat.py:89-104`). Fine for referential integrity, but it means widget chats have no per-visitor identity — per-shopper memory, attribution, and any "this returning shopper" personalisation are impossible without a real session-identity model.

6. **Callback dispatch shares one DB Session across parallel tasks + fire-and-forget.** `dispatch_callback_for_site` opens one `SessionLocal()` and passes the *same* session into N parallel `dispatch_one_destination` coroutines under `asyncio.gather` (`dispatcher.py:265-279`), each of which writes `widget_event_log`. A SQLAlchemy Session is not safe for concurrent use across tasks — a merchant with 2+ destinations races on one session. And `enqueue_callback_dispatch` uses a bare unreferenced `asyncio.create_task` on the request loop (`:307`) — GC-eligible, no worker, no durability (the code openly marks this "v1, swap for Redis"). A destination fan-out is exactly where this bites.

7. **The widget rate limiter is per-process and mostly inert by its own admission.** `WidgetRateLimitMiddleware` uses an in-memory sliding-window dict (`rate_limit.py:46-78`) that resets on every deploy and is not shared across replicas; worse, its own docstring notes the check only really applies once `api_key_id` is known, which happens *inside* the handler, not in the middleware — so on the first request per connection it "injects headers but the sliding window check is only active when the key ID is already known" (`:90-98`). The callback endpoint's own DB-backed per-session/per-Site limits are real, but per-IP is explicitly deferred "until Redis" (`services/callback.py:44-46,128-129`). Effective abuse-throttling of the widget plane is thinner than it looks.

8. **Default CORS is open, and the widget-email lane skips the tool chokepoint.** `WidgetCORSMiddleware` allows *all* origins when `WIDGET_ORIGIN_ALLOWLIST` is unset ("development default," `cors.py:41-51`) — the default posture is permissive. Separately, the email companion panel (`api/widget_email.py:286,340,388,437`) calls Composio `client.execute_action` directly rather than through the unified executor's policy chokepoint (F085 residue) — a governance-parity gap, informational here.

9. **Carried-over open finding, handed to the security pass (F053).** A public `ak_pub_` key skips the domain check when the Origin/Referer header is absent (`auth.py:182-183`), still present at the pinned tree (phase0: NOT DONE). Named for completeness; the fix and analysis belong to the dedicated Opus security pass, not this dossier.

**Score justification.** The engineering is a genuine 3.5–4 in isolation: clean vertical abstraction, real agent substrate, a differentiated graph-grounded proactive layer, careful GDPR/callback plumbing. But the North Star asks whether it makes Auto autonomously *good for clients*, and on that axis it is held back hard by (a) **zero effectiveness instrumentation** — it cannot show it works; (b) a **headline feature grounded on an untested pipeline** (F091) — its autonomy can silently fabricate; (c) **no proof of live use** from the banked data; and (d) a **degraded/unpublished distribution channel**. It is not on fire (unlike Playbooks at 2.5), and it is the best-built ingress module — but "well-architected, unproven, uninstrumented" is a **3/5**, not higher. The path to 4 is short and is mostly measurement + one pipeline test, not a rebuild (§J).

## D. Competitive teardown

The storefront widget competes with two families: **Shopify-vertical AI concierges** (Rep AI, Gorgias AI Agent, and — critically — Shopify's own native assistants) and **channel-agnostic AI support agents** (Intercom/Fin). On per-turn intelligence *in its own platform context* Automatos is competitive-to-ahead (a real workspace agent with memory/RAG/tools/commerce-KG openers). On the axes that define the category — **proven outcomes, behavioral proactivity, and measurement** — every one of them is ahead today.

**Rep AI** — the closest analog to Automatos's proactive ambition. Rep AI's behavioral AI detects when a shopper is losing interest and *steps in proactively* (not click-to-open), with product recommendations, upsell, abandoned-cart rescue and sales analytics, packaged as Sales/Support/Concierge modules; it publishes hard revenue attribution — Proof Wallets at "$84 for every $1" and 12.7% of store revenue, FASS Motorsports at 20× ROI / 11% of revenue / +9% AOV across 200k+ SKUs ([Rep AI on the Shopify App Store](https://apps.shopify.com/rep-ai-sales-associate), [Rep.ai review](https://www.salesrobot.co/blogs/rep-ai-review)). **Better than Automatos at:** behavioral-intent triggering (Automatos fires openers on page-type + delay + config, not on inferred disengagement), and — decisively — it *measures and reports* assisted revenue/AOV, which Automatos does not compute at all. **Behind Automatos at:** the widget agent being a full cross-workspace platform agent wired to the same board/Auto substrate; Automatos's openers cite the workspace's *own* order-graph FBT edges rather than a generic recommender.

**Intercom Fin** (renamed "Fin," ~$3.6B Salesforce acquisition June 2026) — the outcome-measurement and resolution bar. Fin prices at **$0.99 per outcome** (resolution / procedure-handoff / disqualification), with published real-world resolution rates of **42–50%**, deployable standalone on any helpdesk ([Fin AI Agent outcomes](https://www.intercom.com/help/en/articles/8205718-fin-ai-agent-outcomes), [Fin pricing 2026](https://www.gleap.io/blog/intercom-fin-ai-pricing-2026)). The lesson isn't the product — it's that Fin's entire commercial and product model is *built on a measured resolution outcome per conversation*. Automatos has no equivalent number for a widget conversation. **Better than Automatos at:** outcome definition + measurement, mature multi-channel handoff. **Behind Automatos at:** ecommerce/commerce-graph grounding and being an autonomous agent rather than a support-resolution engine.

**Shopify Sidekick + Shopify Inbox AI sales associate** — the honest existential comparison for the Shopify slice. Shopify now ships a native AI sales associate *in Shopify Inbox* that "answers buyer questions, suggests products, and handles order inquiries using catalog, inventory and policy data already in the admin, with merchants controlling tone and escalation," included free with the plan, plus Sidekick on the merchant side; weekly-active shops grew 4× YoY in Q1 2026 ([Shopify Sidekick](https://www.shopify.com/sidekick), [Shopify Spring '26](https://www.digitalapplied.com/blog/shopify-spring-2026-edition-sidekick-campaign-autopilot-ai)). **Better than Automatos at:** zero integration (it's already in the admin), free, native catalog/inventory/policy access, and Shopify's distribution. **Behind Automatos at:** it's Inbox-scoped and Shopify-locked, not a cross-workspace agent, and it does not embed a proactive on-page opener grounded in the merchant's own order graph the way Automatos does. This is the competitor Automatos most has to *justify its existence against* for Shopify merchants — and today it can't, because it doesn't measure whether it out-converts the free native option.

**Gorgias AI Agent** — the ecommerce-helpdesk incumbent. Same storefront chat-bubble embed, automates ~60% of support (order tracking/returns/shipping), ~$0.90–1.00 per resolved conversation, Shopify-only ([Gorgias AI Agent](https://www.gorgias.com/ai-agent), [Gorgias 2026 guide](https://www.eesel.ai/blog/gorgias-for-shopify)). **Better at:** deep post-purchase workflows (returns/order edits) wired to Shopify, and a measured automation rate. **Behind at:** proactive pre-purchase selling and the platform-agent substrate.

**Where Automatos actually stands.** It has a genuine, defensible-on-its-own-terms edge that none of the four replicate: the shopper-facing agent is the *same* platform agent as the operator's, its openers are grounded in the merchant's *own* order-graph co-purchase signal with provenance, callbacks capture leads to *any* channel (not locked to an inbox), and the whole thing is one tenant-scoped surface wired into Auto and the board. But it is behind Rep AI on behavioral triggering, behind Fin/Gorgias on outcome measurement, and behind all of them on the one number that matters — *does it work?* — because it computes no such number. And for Shopify specifically it now competes with a free native assistant. The engineering is competitive; the evidence base is not.

## E. Build / extend / adopt / replace — verdict: **EXTEND**

**Extend the in-house widget; adopt no external concierge; adopt measurement *patterns* (not products) from Fin/Rep.** Reasoning per §2's reuse-bias:

- **Adopt Rep AI / Intercom Fin / Gorgias (embed or replace the widget)?** No. All three are siloed support/sales bots that would re-silo the channel and sever the one thing that makes this module worth having — the shopper agent being a full Automatos platform agent (workspace memory, RAG, Composio, platform tools, commerce KG) on the same board/Auto substrate. Replacing the widget with a SaaS concierge turns the autonomous leg back into an integration. The features Automatos lacks versus them — outcome measurement, behavioral-intent triggering, published conversion attribution — are **days-to-weeks of in-house work** (aggregating an event log that already exists, an intent heuristic, an attribution join), not an engine swap.
- **Adopt the measurement model from Fin, the behavioral trigger from Rep — as patterns.** Fin's "outcome per conversation" and Rep's "assisted-revenue attribution" are the right *designs* to copy into the in-house telemetry (§J-1), calibrated to `widget_event_log` + order data. This is adopt-the-idea, not adopt-the-vendor.
- **Honest threat to weigh, not bury: Shopify Sidekick/Inbox.** For the Shopify vertical the widget competes with a *free, native, zero-integration* AI sales associate. The widget only earns its place if it demonstrably out-converts or out-contains the native option — which is unmeasured today. This is not a moat argument; it is a "prove it beats free" argument, and it routes straight back to §J-1. If, once instrumented, the widget does *not* beat Sidekick-in-Inbox for a Shopify merchant, the honest call may be to lean the Shopify slice on Sidekick and focus the widget where it's genuinely differentiated (proactive order-graph openers, callback-to-any-channel, non-Shopify verticals).
- **One internal REPLACE:** the in-memory rate limiter (`rate_limit.py`) and the fire-and-forget single-session callback dispatch (`dispatcher.py:265-316`) should be replaced by the Redis-backed shared-store + worker path the code already anticipates — not extended in-process.
- **Keep building only:** the effectiveness telemetry, the F091 pipeline tests, the distribution fix (F052), and a Command Center surface. Everything else is extension of a sound engine.

## G. Quality metric

**The module has no effectiveness metric today; the substrate to build one already exists and is write-only.** Proposed tracked numbers, in North-Star priority:

- **Opener-acceptance rate** (proactive opener shown → shopper replies within N turns / openers fired). Directly measures whether the autonomous, graph-grounded opener actually earns engagement. Raw signal: proactive-opener sends are already tagged (`trigger_reason`, `related_count`, latency logged in `chat.py:220-229` + the loader). **Today: unmeasured.**
- **Callback funnel** (`callback_requested → callback_delivered` from `widget_event_log`, then merchant-side outcome). The event rows already exist per attempt (`dispatcher.py:185-216`); nothing aggregates them. **Today: unmeasured** (and the plane's real callback volume is unknown — §C audit gap).
- **Widget-assisted conversion / AOV** (widget-touched sessions → orders, vs baseline) — the Rep AI/Fin headline. Needs a session→order attribution join (the user-id-1 model, §C defect 5, blocks per-shopper attribution today). Highest business value, highest effort.
- **Containment / resolution rate** (widget chats closed without human handoff) — the Fin/Gorgias bar; requires defining a widget "resolution outcome."
- **Opener latency p95** (budget < 2s; already logged per-request, `chat.py:466-472`) and **time-to-first-token** — the only metrics with data flowing today, but not aggregated or alerted.

**Number today:** effectively unmeasurable from banked evidence. This is the metric story for T3: the widget is the *easiest* commerce module to instrument (binary events — opener shown/accepted, callback requested/delivered — already land in `widget_event_log`), and the *most important* to instrument, because it is the only surface talking to real end customers.

## H. Cost note (informational)

- **Proactive opener:** one short **text-only** LLM call (`force_text_only`, `skip_composio`, ≤140 chars) — sub-cent at the eval-recorded gpt-4.1-mini rate (~$0.0007/call, repo-eval-artifacts.md); the FBT graph traversal is pure in-process over the loaded blob (no LLM).
- **Regular widget chat turn:** a full agent tool-loop — same cost profile as main dashboard chat (multiple iterations × model rate); the dominant driver, and priced identically to §llm-core.
- **Cart-idle nudge:** one text-only call + in-process multi-seed aggregation.
- **Callback:** **$0 LLM** — pure validation + hashed write + channel send.
- **Hidden cost worth flagging:** `GraphifyService.load_graph(workspace_id)` runs on *every* proactive fire, and workspace-graph blobs reach **42 MB JSON in a TEXT column** (workspace-graphs.md storage smell). Re-loading a multi-MB blob per opener is the real per-opener cost and an obvious cache target (§J-8) — ties into the vector-substrate/graph work.

## I. UX / surface

**Merchant dashboard (present, reasonable):** Settings → **Widget SDK tab** (`WidgetSdkTab.tsx`) with a Site selector and Callback / Cart-idle / Sync / Shopify panels (`:31-176`); **API-key manager** (`ApiKeyManager.tsx`, `ApiKeysSettingsTab.tsx`); the **Sites hub** backed by `api/sites.py`; the dashboard **widget marketplace** (`/marketplace/widgets`) — which, per the §A scoping note, is the *internal dashboard-widget* marketplace and is unrelated to storefront-SDK distribution.

**Shopper-facing (present):** the embedded chat bubble (CDN loader + `chat-widget`) with proactive openers, cart-idle popups, deictic grounding, and the inline callback form.

**The biggest IA gap: the live autonomous leg is invisible to Command Center.** Nothing about the widget — openers fired/accepted, callbacks captured and their delivery state, live shopper conversations, per-Site funnel — surfaces in the operator cockpit. The one surface talking to real customers has zero presence in the place the operator watches autonomy. **Recommend a Command Center "Storefront" tile** reading `widget_event_log` + the opener/chat logs: openers fired vs accepted, callbacks captured → delivered (with failed-delivery alerting), active widget conversations, and a per-Site conversion funnel once §J-1 lands. This is the same "instrument the autonomous leg" move as §G/§J-1, surfaced.

**Naming/IA cleanup:** the tri-fold "widget" overload (storefront embed / dashboard workspace widgets + their marketplace / Command Center activity widgets) muddies navigation and this very review. At minimum, rename the storefront surface consistently (e.g. "Storefront" / "Sites") and stop sharing the word "widget marketplace" between the SDK and the internal dashboard-panel store.

**Distribution UX:** publish `@automatos/widget-sdk`, align package versions, and route the React wrapper through the loader so a React merchant gets the *same* proactive engine as a script-tag merchant (§J-3).

## J. Upgrade path (prioritised by North-Star impact × effort)

1. **Instrument effectiveness — the funnel (highest impact, medium effort).** Aggregate `widget_event_log` + opener/chat logs into tracked numbers: opener-acceptance, callback funnel, containment, and (with an order join) widget-assisted conversion/AOV. Ship them to a Command Center Storefront tile (§I) and into the T3 harness. Rationale: the module cannot be prioritised, defended against free-native Sidekick, or improved while it computes no measure of whether it works. The substrate is already written and write-only — this is aggregation, not new capture. *Also closes the §C-4 audit gap: makes real widget usage visible.*
2. **Verify the opener data pipeline — F091 (very high impact, low-medium effort).** Add behavioral tests for `map_shopify_catalog`/`map_shopify_orders` and un-skip the two golden journeys (J3 widget-plugin, J9 sync→FBT-opener). Rationale: the autonomous opener cites `co_count`/`total_orders` straight from these untested mappers; a silent regression makes the widget confidently fabricate to real shoppers. Disproportionate North-Star value — this protects the module's one differentiated autonomous feature.
3. **Close the distribution gap — F052 (medium impact, low effort).** Publish the npm package, align versions (core/loader/react), and make the React wrapper mount through the loader so it inherits proactive/cart-idle/page-context. Removes a silent-degradation footgun for React merchants.
4. **Harden callback dispatch (medium impact, medium effort).** Per-task DB sessions inside `dispatch_callback_for_site` (stop sharing one Session across `gather`), hold the `create_task` reference or move to the anticipated Redis queue+worker, and add per-IP callback rate limiting. Rationale: destination fan-out is exactly where the shared-session race and fire-and-forget durability gap bite a paying merchant's leads.
5. **Replace the in-memory rate limiter (medium impact, medium effort).** Shared store (Redis) + resolve `api_key_id` in the middleware so the sliding window is actually enforced across replicas — today it is per-process and, by its own docstring, largely inert.
6. **Command Center Storefront tile (medium impact, medium effort).** Surface openers/callbacks/live conversations/funnel to the operator cockpit (detailed in §I). Pairs with J-1.
7. **Cache the workspace-graph load per opener (medium impact, low-medium effort).** Avoid re-reading a multi-MB blob on every proactive fire; coordinate with the vector-substrate/graph consolidation work.
8. **Per-shopper session identity (medium impact, medium effort).** Replace the user-id-1 owner model with a real widget-visitor identity so per-shopper memory, attribution, and returning-visitor personalisation become possible — a prerequisite for the assisted-conversion metric in J-1.
9. **Route widget-email through the tool chokepoint (low impact, low effort).** Governance parity with the unified executor (F085 residue).
10. **Hand F053 to the security pass (tracked, not scored here).** The origin-absent public-key handling is a security matter for the dedicated Opus pass, not a §J build item.
