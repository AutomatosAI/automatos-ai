## A. What it is

The tool runtime is the machinery that actually **runs** a tool call once a model has decided to make one — every lane (chat, board, Missions, heartbeats, playbook LLM-steps, widget) funnels through one dispatch spine: `ToolLoopExecutor` (the converged LLM↔tool loop with dedup, stuck-loop breaking and truncation recovery) → `UnifiedToolExecutor` (the single router across platform actions, workspace-worker ops, Composio, research/DB/document tools) → per-domain executors and, for the platform's own surface, `PlatformActionExecutor` with its gate stack (super-admin → admin → confirmation → hierarchy → rate-limit). Alongside the spine sits the **platform-action surface**: 174 `ActionDefinition`s across 34 files (166 `platform_*` + 8 `workspace_*`) that let Auto operate Automatos itself — agents, playbooks, missions, documents, members, channels, graphs, Shopify sync — which is the substance of "Auto runs the platform." Universal telemetry, typed outcome-capture into memory, and a three-audience result formatter (LLM / frontend widgets / raw) complete the runtime. It is the single most load-bearing module for the North Star: if this layer is dishonest or gated wrong, every agent is.

## B. What it does — real implementation and data path

### B.1 The dispatch spine
`UnifiedToolExecutor.execute_tool` (`modules/tools/execution/unified_executor.py:350-615`) is the one entry point. Routing precedence: policy-plane chokepoint (`:395-400`, see B.7) → `platform_execute` meta-dispatcher with registry validation, required-param checking with self-correction hints, and LLM param-shape tolerance (`:403-491`) → direct `platform_*` (`:494-500`) → `workspace_*` worker proxy (`:503-509`) → per-action Composio names installed by the agent factory (`:514-524`, `self.composio_actions` dict `:93`) → registry-known tools incl. the `composio_execute` meta-tool (`:527-557`) → a 40-entry static route table for research/DB/file/shell/document/planning tools (`:96-160`, dispatched `:560-576`). Every exit path funnels through a `finally` that fires universal telemetry and typed memory outcome-capture (`:593-615`). Three factories instantiate it per request: `tool_router.py:60`, `agent_factory.py:45`, `modules/tools/service.py:55`.

### B.2 The loop
`ToolLoopExecutor` (`modules/tools/execution/tool_loop.py:166-511`) is the converged chat+agent loop (PRD-142 W3-S4): iteration cap, exact+semantic dedup and per-tool retry limits via `ToolExecutionTracker` (`tool_execution_tracker.py:49-150` — `platform_execute` counted per inner action `:94-98`, prefix-aware caps `:64-77`), an OpenHands-style stuck-loop breaker that persists a `tool_outcome` failure memory when it trips (`tool_loop.py:249-260`, `:51-74`), and `finish_reason=length` recovery that re-prompts for shorter args instead of executing malformed JSON (`:477-511`). Caller hooks: `on_event` (SSE), `on_tool_result` (chat's Composio recovery / fatal short-circuit), `on_round_end` (force-synthesis), and the PRD-174 `on_pre_tool` policy seam whose `PreToolResult` can block-with-reason or rewrite args (`:104-127`, applied `:401-419`). Tool calls in a round execute **strictly sequentially** (`:367` — a plain `for` loop; see C.8). Oversized results are token-budget truncated, not char-sliced (`:542-559`).

### B.3 The platform-action surface and its gate stack
- **Registry:** `ActionRegistry` (`modules/tools/discovery/action_registry.py`) holds 174 `ActionDefinition`s (dataclass `:27-56`: permission_level read/write/destructive, requires_confirmation, admin_only, super_admin_only, promoted, tags, examples). Composition measured from source: **101 read / 65 write / 8 destructive; 12 requires_confirmation; 7 admin_only; 7 super_admin_only; 42 promoted**. It renders three surfaces: the single `platform_execute` dispatcher schema with an optionally-narrowed action enum and fail-open fallbacks (`:163-262`), first-class schemas for promoted actions (`:138-161`), and the markdown prompt catalog (`:264-400`).
- **Executor:** `PlatformActionExecutor` (`modules/tools/discovery/platform_executor.py:306-946`) maps **176 handler entries** (incl. legacy `recipe`/`playbook` alias pairs) onto standalone async handlers in 33 `handlers_*.py` files, every one with the uniform `(db, workspace_id, params)` signature. Gate order in `execute()` (`:615-946`): JSON-string param tolerance (`:632-636`) → super-admin gate, literal `system_role == 'super_admin'` only, fail-closed on missing context (`:652-668`) → full-autonomy dial resolve (`:673`, fail-safe to supervised `:595-613`) → admin gate (caller roles; identity-less callers fall to `_agent_inherits_admin`, which with the policy plane OFF is the July workspace-has-an-admin auto-flip — `:675-709`, `:563-593`; residual F014-PARTIAL) → confirmation gate (`:711-722`) → registry-lookup failure ⇒ fail-closed to confirmation (`:723-739`) → PRD-140 hierarchy check for 20 mapped mutating actions, fail-closed on error (`_HIERARCHY_TARGETS` `:277-303`, check `:745-816`) → per-(workspace,agent) write rate limit, **fail-open when the limiter is unavailable** (`:820-843`) → destructive-without-confirmation misconfiguration backstop (`:846-862`) → server-side param injection (agent team for graph/doc tools `:867-888`; field binding from threaded caller context only, the F020 fix `:897-904`; mission attribution `:906-923`) → handler (`:926`), with autonomous-execution marking for the audit trail (`:932-938`).
- **Actor identity is server-minted:** `exec_platform.execute_platform_action` strips any caller-supplied `_agent_id`/`_agent_name` and injects the trusted runtime identity (`modules/tools/execution/exec_platform.py:59-81`) — the impersonation door is closed at the dispatch layer, not per-handler.
- **Sampled handlers** (probe): `list_agents` filters `Agent.workspace_id == workspace_id` with batched count sub-queries (`handlers_agents.py:13-24`); documents handlers filter workspace on every query (`handlers_documents.py:88,124,188,307`); the W13/F088 Shopify pair threads `workspace_id` from the authenticated executor context, never params (`handlers_shopify.py:34-80`), registered at `platform_actions.py:36,73` and `platform_executor.py:514-515` with codegraph index/reindex parity at `:517-526` — **F088 closure verified in live source**.

### B.4 The second registry
`ToolRegistry` (`modules/tools/registry/tool_registry.py`, 65 KB) is a *separate* registry of `ToolSpec`s for the non-platform tools (search_knowledge, composio_execute, file/shell ops, DB tools…) with its own permission vocabulary (`SecurityLevel` enum `:53`) and `validate_tool_access` (`:1314-1494`): tier policy (system/platform bypass, marketplace needs assignment), a hard Composio gate requiring assigned∩connected apps with workspace auto-inheritance (`:1401-1447`), site-config gating for widget UI tools (`:1368-1394`), and a **hard-coded** per-agent context→category map (`CONTEXT_MAP` `:1464-1470`). `get_tools_for_agent` (`modules/tools/tool_router.py:220-489`) assembles the final schema list: registry tools + enriched `composio_execute` description (alphabetical top-50 cache rows, `:322-358` — F074) + dispatcher schema with semantic enum narrowing + promoted schemas, with the unconditional workspace-membership `is_admin` exposure flip at `:368-388` (residual F014 note).

### B.5 Results — three audiences
`ToolResultFormatter` (`modules/tools/formatting/result_formatter.py`): `standardize_result` normalizes shape variance incl. Composio's `data` envelope (`:465-536`); `format_for_frontend` builds widget payloads — grouped document cards with full-content DB reassembly, NL2SQL tables, terminal output, schema-driven Composio widget detection via `ResponseTypeDetector` (works for any email provider, `:692-746`), the PRD-163 mission-approval card with AI-Act oversight fields (`:770-793`); `format_for_llm` gives platform/workspace tools a JSON dump capped at 20k chars and search tools a synthesis-oriented digest (`:797-866`). The frontend maps tool names to widgets via `TOOL_WIDGET_MAP` (`frontend/components/widgets/router.ts:35+`). `ToolRouter.execute_and_format` (`modules/tools/tool_router.py:620-768`) is the chat-side wrapper: Composio validation lane, PRD-157 S5 out-of-scope document-widget suppression (`:570-618`), signal recording, S15 confirmation-message passthrough (`:717-722`), and the flag-gated errors-as-data `policy_error` envelope (`:771-796`).

### B.6 Telemetry and outcome capture
Every spine execution fires `fire_telemetry` (fire-and-forget task, `telemetry.py:140-172`) → `write_telemetry` (`:47-112`) into `tool_execution_logs`: per-action Composio resolution (F016 fix `:20-44`), keys-only param capture (`:92`), selection outcome / turn / conversation ids in `router_decision` (`:115-137`). `capture_tool_outcome` (PRD-159 S2) writes typed failure/success memories in the same `finally`. Chat threads full caller context — user_query, conversation_id, turn_id, clerk user, prior_action (`consumers/chatbot/service.py:97-135, 1340-1356`).

### B.7 The policy seam
`_policy_gate_check` (`unified_executor.py:204-280`) evaluates every call through W4's `PolicyGate` (su → admin → budget → act-vs-ask, `modules/policy/gate.py:83-118`) and fires the Art.12 audit bus on every verdict (`:262-266`, `:282-335`). Two structural facts (Phase-0 §2, F085): the whole plane is behind `AUTOMATOS_POLICY_PLANE` **default OFF** and nothing in the deploy surfaces sets it, and even ON the gate **fails open** on any internal error (`:275-280` — an explicit design choice, "a fault in the plane must not wedge tool execution").

### B.8 The lanes — who actually rides the spine
- **Chat:** `ToolLoopExecutor` (`service.py:1491`) → `_tool_callback` → `ToolRouter.execute_and_format` → `execute_tool` (fresh `SessionLocal` per call, `tool_router.py:497-553`) → spine. Fullest treatment: formatting, scope-filtering, telemetry context, signal recording.
- **Agents (board / Missions / heartbeats / scheduled):** `agent_factory.execute_with_prompt` → `ToolLoopExecutor` (`agent_factory.py:1075`) → `_agent_tool_cb` → `tool_executor.execute_tool` **directly** (`:1046-1073`) — no `ToolRouter`, no formatter, no truncation (`content_truncate_tokens=0`, `:1079`), `caller_context` carries only field-binding (`:1041-1044`).
- **Around the spine** (verified live, restating F085 with this module's consequence): the chat **per-action Composio shortcut** executes via `ComposioToolService.execute_action` before the router is ever reached (`service.py:1321-1335`, `:1550-1580`); **playbook LLM-steps** call the Composio service directly (`api/recipe_executor.py:655`); **widget email** calls the client at 4 sites (`api/widget_email.py:286,340,388,437`); **`/api/tasks` direct steps** go straight to the worker queue (`api/tasks.py:62-124`). None of these four lanes passes the policy chokepoint, **and none fires telemetry or outcome-capture** — they are invisible to the learning plane by construction.

## C. Honest quality — maturity **3 / 5**

The spine is the best-engineered seam in the platform — genuinely converged, traced, gated, with real tests (`test_prd174_executor_chokepoint.py`, `test_tool_loop_converged.py` ×5, `test_tool_loop_characterization.py` ×11, `test_prd171_execution_spine.py` ×10). But inspected against real behaviour, three of its four promises — honest results, universal telemetry, a workable approval moment — do not hold today. Findings, each grounded:

1. **NEW ROOT CAUSE — the universal telemetry write is type-poisoned for every logged-in chat user.** `ToolExecutionLog.user_id` is `Column(Integer)` (`core/models/composio_cache.py:215`). The chat lane threads `caller_context["user_id"] = driving_clerk` — the **Clerk id string** (`service.py:1268-1275` reads `User.clerk_user_id`, a `String(255)` per `core/models/core.py:1010`; packed at `service.py:131-132`) — and `write_telemetry` binds it straight into the Integer column (`telemetry.py:91`). Postgres rejects the insert (`invalid input syntax for type integer`), the broad `except` swallows it at **DEBUG** (`telemetry.py:107-112`), and the rollback erases the row. Net: **every chat tool call by a logged-in user writes zero telemetry, invisibly.** Combined with F001 (all non-chat execution dead until the 2026-07-02 fix merged) and the four bypass lanes (B.8), this fully explains the W1 finding that all 2,341 `tool_execution_logs` rows are synthetic and two months of live chat produced none ([tool-telemetry.md](evidence/data/tool-telemetry.md)). grep confirms `telemetry.py` is the **only** production writer of `ToolExecutionLog`. Everything downstream — edges, affinities, intent clusters, selection-health, uplift evals — starves on this one line. (Code-confirmed; not live-reproduced per the no-runs rule.)
2. **The confirmation gate is a dead end — there is no way to say yes.** `requires_confirmation` returns errors-as-data (`platform_executor.py:711-722`) and S15 makes the ask legible to the model (`tool_router.py:717-722`) — but nothing can ever *satisfy* it: the executor consults no confirmation token, no grant, no caller field (grep: no `user_confirmed`/`confirm` param anywhere in `modules/tools/` or `consumers/chatbot/`); the W11 `ApprovalGrant` surface is consumed **only** by the board-task subject (`api/approval_grants.py:22`, `SUBJECT_BOARD_TASK`); and the frontend has **zero** components handling `requires_confirmation` (grep over `frontend/` returns nothing). So when the user replies "yes, delete it," the retried call hits the same gate again — or worse, the dedup tracker skips it as "already executed with identical parameters" (`tool_execution_tracker.py:126-127`). The **only** route through for all 12 gated actions (8 destructive + `platform_update_system_setting`, `platform_update_auto_reporting_prefs`, `platform_cancel_scheduled_task`, and — absurdly for a read — `platform_get_system_health`, which is also su-only, `actions_workspace.py:191-205`) is the workspace-wide full-autonomy dial (`:673-679`), an all-or-nothing knob that simultaneously grants admin. Judged by the North Star this is the single sharpest autonomy ceiling in the module: supervised workspaces structurally cannot let Auto complete any destructive action, ever. (Context: a durable tool-agnostic approval-grant surface was explicitly deferred by the owner as its own slice — this dossier's finding is that the cost of that gap lands here.)
3. **Result honesty is broken on exactly the lanes that need it most.** (a) The chat Composio shortcut returns `{"success": True, …, "raw_result": {}}` **unconditionally** — failures come back as an error *string* in `llm_context` while the loop, the SSE `tool-end` frame, and the round state all see success (`service.py:1328-1335`); (b) the agent lane's callback returns `success: True` whenever the executor doesn't *raise* (`agent_factory.py:1063-1067`), so a `{"success": false}` platform result still counts as a successful round and `fatal_error` short-circuits can never fire on autonomy lanes; (c) `execute_and_format`'s success heuristic `or bool(result.get("results"))` (`tool_router.py:685-689`) can promote a failed result carrying a non-empty `results` key. The board data's "done-with-error" pathology (194 tasks; [board-tasks.md](evidence/data/board-tasks.md)) is this module's signature written into the product.
4. **The autonomy lanes get raw, unbounded, unformatted results.** The agent callback dumps `json.dumps(raw)` with truncation explicitly disabled (`content_truncate_tokens=0`, `agent_factory.py:1079` — "agent path historically did not truncate") and never touches `format_for_llm`. A single `platform_list_documents` or graph query can flood a mission agent's context with the full JSON payload while chat gets a 2,000-token-budgeted, synthesis-oriented digest (`service.py:60`, `:1367-1369`). Same runtime, opposite treatment — inverted relative to where quality matters for clients.
5. **A `TypeError` fallback can double-execute side-effecting tools without tenant context.** The route-table dispatch retries any `TypeError` with the bare 3-arg signature (`unified_executor.py:564-574`). The except cannot distinguish "callback doesn't accept kwargs" from "a TypeError raised *inside* the tool" — in the latter case a document generation or file write re-runs, now stripped of `workspace_id`/`caller_context`. Low frequency, high blast radius.
6. **Dead scaffolding advertises capabilities the runtime doesn't have.** (a) `concurrency.py` ("input-aware batching", partition read-safe vs mutating) has **zero callers** (grep) — and if wired it still wouldn't work: its `_READ_SAFE_PLATFORM_ACTIONS` uses unprefixed names (`"list_agents"`) that can never match real `platform_list_agents` actions (`concurrency.py:69-109`), so every `platform_execute` classifies mutating. All tool rounds run serially (B.2). (b) `ToolService` (`modules/tools/service.py`) is a near-dead wrapper whose `execute` reads `.success` attributes off dicts (always false → reports success unconditionally, `:110-118`) and whose `get_openai_tools_schema` calls a registry method that doesn't exist (`:121` → AttributeError). (c) The Composio Tool-Router delegate would crash if ever reached — it reads `executor.db_session`, an attribute `UnifiedToolExecutor` doesn't have (`exec_composio.py:254` vs `unified_executor.py:80`), further confirming the tool-selection dossier's finding that this lane has been unrouted dead code since May. (d) `exec_file_ops` consults a `_current_workspace_id` executor attribute that is never set anywhere (`exec_file_ops.py:49`).
7. **F055 confirmed intact — the skill `tools_schema` column still holds three mutually-blind formats.** The materializer writes dict form `{"tools": [...]}` (`services/skill_materializer.py:124-127`); the prompt section reads **only** dict form (`modules/context/sections/skills.py:103-114`); the agent registry reads **only** list-of-OpenAI-specs plus a JSON-string branch (`modules/agents/registry/agent_registry.py:103-118`). Which tools an agent is *told* it has and which the registry *reports* diverge per row era. No normalizer exists (Phase-0: NOT DONE).
8. **No parallelism, no timeout, no cancellation at the spine.** Sequential rounds (B.2) plus: `execute_tool` has no per-call timeout — a hung handler holds the whole turn (the W13 Shopify sync is a deliberately synchronous minutes-long Bulk Op inside a tool call, Phase-0 F088 note); there is no cancellation propagation; and the sole global `workspace_dir` default is a shared `/tmp/automatos_workspace` (`unified_executor.py:69`) though real file ops proxy to the per-workspace worker (`exec_file_ops.py:1-13` — the July-era container-local trap is genuinely closed).
9. **Two registries, two permission vocabularies, one hard-coded policy table.** `ToolSpec.SecurityLevel` (safe/restricted/dangerous) and `ActionDefinition.permission_level` (read/write/destructive) never reconcile; `CONTEXT_MAP` category policy is source-baked (`tool_registry.py:1464-1470`); the 176-entry handler map carries dual `recipe`/`playbook` aliases the canonical-terms rule says shouldn't exist. Registration is import-heavy but boring — the 3-file pattern is consistently followed across all 34 action files (`platform_actions.py:49-87`).
10. **What is genuinely good** — and better than the July picture: the chokepoint is real (all four non-spine lanes are *known* and enumerated, everything else demonstrably funnels); the gate stack fails closed at the right places (su gate, registry-miss ⇒ confirmation, hierarchy-check error ⇒ deny with escalation target, destructive-misconfig backstop); actor identity is server-minted with param-smuggling stripped (`exec_platform.py:59-71`); the missing-param error teaches the model to self-correct with per-param hints (`unified_executor.py:458-477`); length-recovery and stuck-loop learning are the kind of unglamorous machinery most frameworks lack; the mission-approval card with floored oversight tier is honest UX (`result_formatter.py:539-562`); F088/F087 landed genuine agent-side parity (Shopify sync + codegraph reindex as authenticated tools); and trace-id logging is threaded end-to-end. The dispatcher's enum-fallback design (never leave the model with zero actions, `action_registry.py:207-225`) is a defensible availability-over-strictness call, made consciously and logged.

**Why 3.0:** a real, live, well-shaped spine (alone ~4) pulled down hard by the broken telemetry write (the module's own instrumentation has never recorded a real event), two dishonest-success lanes, the confirmation dead-end that caps supervised autonomy, and a periphery of dead or drifted scaffolding. The bones are excellent; the nervous system is severed in three places.

## D. Competitive teardown

**1. OpenAI Agents SDK** ([openai.github.io/openai-agents-python](https://openai.github.io/openai-agents-python/), [approvals guide](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)). The reference design for the exact thing Automatos lacks: tools marked `needs_approval` **pause the run and record an approval interruption**; the result returns `interruptions` + a resumable `state`; the application approves/rejects and **resumes the same run** via `state.approve(interruption)` — surviving streaming, delayed review, and nested handoffs. Tool guardrails run per-invocation on input and output, "next to the tool that creates the side effect," and built-in tracing records every generation, tool call, guardrail and handoff ([tracing](https://openai.github.io/openai-agents-python/tracing/), [guardrails](https://openai.github.io/openai-agents-python/guardrails/)). **Where it beats Automatos:** the pause→approve→resume loop (vs. the dead-end gate, C.2); per-tool output validation (vs. none); tracing as a first-class artifact (vs. log lines + a broken telemetry table). **Where Automatos stands:** the SDK gives you *no* equivalent of the 174-action self-operation surface, the hierarchy/rate/confirmation gate stack, or workspace-scoped multi-tenant dispatch — those are platform assets the SDK expects you to build.

**2. Claude Agent SDK** ([permissions](https://code.claude.com/docs/en/agent-sdk/permissions), [hooks](https://platform.claude.com/docs/en/agent-sdk/hooks)). Its tool pipeline has a **fixed, documented evaluation order** — PreToolUse hooks → deny rules → permission mode → allow rules → `canUseTool` callback — and a hook deny holds **even in `bypassPermissions` mode**; permission modes (`dontAsk`, allowlists, bypass) are orthogonal to hooks. **Where it beats Automatos:** the precedence contract is explicit and mode-proof, whereas Automatos's equivalent (policy plane → per-router gates → full-autonomy dial) is flag-dark by default, fails open on plane error (`unified_executor.py:275-280`), and the autonomy dial *silently elevates to admin* as a side effect (`platform_executor.py:677-679`). **Where Automatos stands:** its `on_pre_tool`/`PreToolResult` seam (`tool_loop.py:104-127`) is the same shape as SDK hooks — the design is already right, it's the default wiring that isn't; and Automatos's gate stack is multi-tenant and role-aware, which the single-user SDK is not.

**3. LangGraph ToolNode + interrupts** ([ToolNode reference](https://reference.langchain.com/python/langgraph.prebuilt/tool_node/ToolNode), [HITL docs](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)). ToolNode executes a round's tool calls **in parallel** with configurable `handle_tool_errors` (template / string / callable / exception-class); `interrupt()` + checkpointer persists the *entire* graph state so a human can approve / **edit** / reject a pending tool call and resume later with `Command(resume=…)` on the same thread — durable across process restarts. **Where it beats Automatos:** parallel read execution (Automatos built the classifier for this and never wired it, C.6a); durable approve-with-edit resume (vs. none); error-handling policy as a typed parameter (vs. ad-hoc per lane). Honest counter-note: LangGraph itself shipped a default regression here — tool error handling silently flipped to off in `langgraph-prebuilt` 1.0.1 ([issue #6486](https://github.com/langchain-ai/langgraph/issues/6486)) — default-drift is not unique to Automatos. **Where Automatos stands:** dedup/stuck/length-recovery are ahead of stock ToolNode, and LangGraph brings no tenancy, no action registry, no permission taxonomy.

**4. E2B** ([e2b.dev](https://e2b.dev/), [pricing](https://e2b.dev/pricing)). Firecracker microVM sandboxes purpose-built for agent code execution: kernel-level isolation per sandbox, ~150 ms cold starts, per-second billing (~$0.05/hr per vCPU), free tier with 20 concurrent sandboxes; used by Perplexity, Hugging Face, Manus. **Where it beats Automatos:** real isolation for arbitrary code — Automatos's `execute_command` is a read-only allowlist in the API container (`agent_action_executor.py:45-64`) and everything heavier proxies to a single shared workspace-worker service, which is workspace-scoped but not kernel-isolated. **Where Automatos stands:** for the current tool mix (DB-backed platform actions + SaaS calls via Composio + worker file ops) a microVM per call would be cost and latency for nothing; E2B becomes relevant exactly when the W14 code-canvas / arbitrary-code lane becomes a client-facing product surface.

**Forward pattern worth tracking — Anthropic programmatic tool calling** ([advanced-tool-use](https://www.anthropic.com/engineering/advanced-tool-use)): tool results processed in a code environment instead of entering context (43,588 → 27,297 avg tokens, −37% on complex workflows; Tool Use Examples lifted complex-parameter accuracy 72%→90%). Directly relevant to C.4: Automatos's agent lane currently does the *opposite* (raw JSON dumps, no truncation).

## E. Build / extend / adopt / replace — verdict

**EXTEND.** No external runtime replaces this module at acceptable cost: the value is not the loop (commodity) but the 174-action self-operation surface, the multi-tenant gate stack, and the platform coupling — none of which OpenAI Agents SDK, Claude Agent SDK, or LangGraph provide. Swapping the spine for a framework would mean re-implementing every gate and handler *inside* someone else's loop for zero capability gain. The extend program is specific:

1. **Adopt the pattern, not the product, for approvals:** implement interrupt→grant→resume on the existing W11 `ApprovalGrant` table (new subject type `tool_call` beside `SUBJECT_BOARD_TASK`), mirroring OpenAI's `interruptions`/`state.approve` semantics — an in-chat approval card (the PRD-163 mission card is the template, `result_formatter.py:770-793`) whose grant the executor consults before the `requires_confirmation` return. This is the deferred "approval-grant surface for non-chat ask" slice; the evidence here says it is the highest-value extension in the module. *(Owner's call on scheduling — flagged, not descoped.)*
2. **Keep the in-house loop** — with the honesty and telemetry fixes of §J it is competitive with ToolNode and SDK loops for this platform's shape.
3. **Optional edge adopt, deferred:** E2B (or equivalent microVM) only if/when the code-canvas lane (W14) executes untrusted client code as a product feature; the current worker-proxy + allowlist is adequate for today's tool mix. Rough cost if adopted: ~$0.05/vCPU-hr, free tier covers a pilot.
4. **Kill list:** `modules/tools/execution/concurrency.py` (wire it correctly or delete — currently a false capability), `modules/tools/service.py` `ToolService` (two latent crashes, no callers), `composio_tool_router.py` + its executor delegate (unrouted since May, would crash on the `db_session` attr), the `_current_workspace_id` phantom fallback, and the duplicate `recipe`/`playbook` handler aliases.

## G. Quality metric

The runtime's quality is measurable and currently isn't measured — its own instrument is the broken part:

- **Sentinel: organic telemetry rows/day per lane** (chat / agent / playbook / widget). Today: **0 on every lane** ([tool-telemetry.md](evidence/data/tool-telemetry.md)) — after the C.1 fix this single number proves the nervous system is connected. A CI canary (execute one tool per lane against a test DB, assert a `tool_execution_logs` row with `telemetry_source='production'`) makes "no lane writes telemetry" a failing build instead of a two-month-invisible outage.
- **Tool-call success rate + error taxonomy per action** from `tool_execution_logs` (the synthetic seed shows the shape: 1,911/2,341 = 81.6% success). Track p50/p95 `execution_time_ms` per action (seed p50 ≈ 800 ms; real `platform_list_agents` row: 41 ms).

- **Confirmation funnel:** count of `requires_confirmation` returns vs. subsequent grants/executions — today the conversion is structurally 0 in supervised workspaces; after the grant surface it becomes the approval-latency metric.
- **Loop health:** dedup-skip rate, stuck-loop trips (already persisted as `tool_outcome` memories), `max_iterations_reached` rate, length-recovery invocations — all derivable from existing signals once telemetry writes.

## H. Cost note (informational)

Platform actions are DB queries executed in-process — compute cost is negligible (tens of ms; the outliers are deliberate, e.g. the synchronous Shopify Bulk-Op sync). The real cost is **tokens around the runtime**: the dispatcher schema + prompt catalog (covered in the context-assembly dossier) on every tool-bearing turn; tool results at up to 2,000 tokens/call in chat (`_TOOL_RESULT_TOKEN_BUDGET`, `service.py:60`) but **unbounded on agent lanes** (C.4) — the single biggest cost lever in the module is giving agents the formatter+budget chat already has; loop iterations capped at a DB-backed setting for chat and 10 for agents (`agent_factory.py:863`). Telemetry adds one INSERT per call (~free). The May routing eval's cost point (~$0.0007/call, gpt-4.1-mini filtered_schema — [repo-eval-artifacts.md](evidence/data/repo-eval-artifacts.md)) prices the selection turn, not execution.
