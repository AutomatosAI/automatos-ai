## A. What it is

Tool selection is the machinery that decides, per turn or per task, **which of the platform's ~174 registered platform actions (`modules/tools/discovery/actions_*.py`, 174 `ActionDefinition`s) and ~856 Composio apps' actions an agent is actually shown and allowed to call**. It is a four-layer stack: (0) a regex intent gate that decides whether tools are offered at all, (1) an embedding-cosine index over platform actions (`ActionSemanticIndex`) that narrows the dispatcher enum and feeds ranking, (2) a learned per-tenant "operating graph" (`GraphRouter` over `tool_routing_edges`/`_affinities`/`_intent_clusters`, fed by tool-execution telemetry via a nightly edge builder), and (3) a Composio-lane hint pipeline (`ComposioHintService` three-tier keyword/ILIKE matching plus an alphabetical enum enrichment) with a capability/destructive-action gate. W7 (PRD-177) hardened the data side of the learning loop in July; the seed symptom this review probes is that W7's own uplift eval came back **negative** — and the W1 data shows the learning plane has, to date, never eaten a single real datum.

## B. What it does — real implementation and data path

### B.1 The gate: tools or no tools
Every chat turn is first classified by a **pure-regex** intent classifier — `consumers/chatbot/intent_classifier.py:198` (`classify`), pattern tables at `:59-188` (GREETINGS set, MEMORY/DATA/SEARCH/EXTERNAL/CREATION pattern lists). `requires_tools=False` → the turn gets **zero tools** (`smart_tool_router.py:208-215`), softened only by a platform-tools fallback in the FILTERED loader (`modules/context/sections/tools.py:210-219`). There is no LLM or embedding involvement in this binary gate.

### B.2 Strategy per lane (who gets which selection intelligence)
`modules/context/modes.py:36-101` declares tool loading per context mode:

| Mode | strategy | selection intelligence applied |
|---|---|---|
| CHATBOT (`:41-51`) | `filtered` | full stack: intent gate → GraphRouter keep-set → category fallback |
| TASK_EXECUTION (`:55-64`) | `full` | none except dispatcher-enum embedding narrowing (query-dependent) |
| HEARTBEAT_AGENT (`:80-89`) | `full` | same |
| RECIPE (`:91-101`) | `full` | same + recipe-mode hint service |
| HEARTBEAT_ORCHESTRATOR (`:66-75`) | `dispatcher_only` | embedding-narrowed enum only |

`ToolsSection.load_tools` dispatches the strategy (`modules/context/sections/tools.py:61-106`); FILTERED loads everything then calls `SmartToolRouter.route` (`tools.py:196-208`).

### B.3 Layer 1 — embedding narrowing (the layer that demonstrably works)
`ActionSemanticIndex` (`modules/tools/discovery/action_semantic_index.py`) embeds `name: description | tags | examples | category` per action (`:42-49`) via the provider-agnostic `EmbeddingManager` with per-text Redis caching (`:99-113`) and a hardened provider-qualified cache key (`:51-68` — the comment records a real incident: a broken cache key mixed vector families and dropped in-set rate 97.9%→57.4%). `rank_actions` (`:122-162`) is a full-scan cosine over the eligible set. Consumers:
- **Dispatcher-enum narrowing** — `_rank_actions_for_dispatcher` (`modules/tools/tool_router.py:125-169`), applied when building `platform_execute`'s action enum (`tool_router.py:404-419`; `tools.py:112-142` for DISPATCHER_ONLY), top-K default 15 (`config.py:752`), behind `SEMANTIC_TOOL_ROUTING` **default true** (`config.py:751`). Sync callers cross the async boundary via a **fresh ThreadPoolExecutor + new event loop per call** (`tool_router.py:106-122`).
- **GraphRouter entry nodes** (below).

### B.4 Layer 2 — the learned operating graph
`GraphRouter.rank_chains` (`modules/tools/discovery/graph_router.py:125-190`): top-5 embedding entry nodes (`:28,158-165`) → one-hop expansion over `used_after` + `meta_sibling` edges with `confidence ≥ 0.6` (`:307-341`), workspace-scoped exactly (`ToolRoutingEdge.workspace_id == workspace_id`, else IS NULL only — `:318-320`, the W7/F015-S5 fix, confirmed) → affinity boosts/penalties (`:354-416`) → super-admin chain drop (`:429-446`) → dedupe, sort, 5-minute Redis cache keyed on (query, agent, k, su, **ws**) (`:62-85`).

**Live consumers:** (1) `SmartToolRouter.route` under `SEMANTIC_TOOL_ROUTING` (`consumers/chatbot/smart_tool_router.py:224-246`) — chat/FILTERED only; the ranked chains are flattened into an **unordered keep-set** (`:232-234`) unioned with CORE_TOOLS + pins + promoted actions. (2) `PlatformActionsSection._build_graph_filtered` chain hints in the prompt catalog (`modules/context/sections/platform_actions.py:124-182`) — **dark** behind `TOOL_ROUTING_GRAPH` default false (`config.py:757`), held on eval evidence (below).

**Writers:** (a) universal telemetry — every `UnifiedToolExecutor.execute_tool` fires `fire_telemetry` in a finally block (`modules/tools/execution/unified_executor.py:593-605`) → `tool_execution_logs`, with per-action composio resolution (`modules/tools/execution/telemetry.py:20-44`, F016 fix) and turn/conversation ids in `router_decision` (`telemetry.py:133-136`, F017 fix); chat mints a per-turn id and threads full caller context (`consumers/chatbot/service.py:97-135, 1277-1281, 1340-1355`). (b) The **nightly edge builder** at 03:00 UTC (`services/edge_builder_scheduler.py:44-52`, wired `main.py:408-412`) recomputes edges/affinities/intent-clusters from a 30-day window (`core/services/edge_builder.py:67-124`): `used_after` co-occurrence per (turn|conversation|5-min window) session (`:174-215`), `failed_after` (write-only by design, `:218-276`), k-means intent clusters with centroid embeddings (`:393-482`), Wilson-bound affinities (`:521-619`). (c) An **intra-day batched signal recorder** (`modules/tools/discovery/signal_recorder.py`) — well-engineered (single drain task, one session per flush, NULL-safe upserts) but gated by `TOOL_SIGNAL_RECORDER_ENABLED` **default false** (`config.py:774`; silent no-op at `signal_recorder.py:173-174`), and set by nothing in `envs/`, `docker-compose.yml`, `railway.json`, or `Dockerfile` (grep-verified).

### B.5 Layer 3 — the Composio lane
- `composio_execute`'s schema description is enriched with the **alphabetical** top-50 cached actions (max 10/app) — `modules/tools/tool_router.py:322-350` (`.order_by(app_name, display_name).limit(50)` at `:328`) — F074, unchanged.
- `ComposioHintService.build_hints` (`modules/tools/services/composio_hint_service.py:103-219`) injects a system message: Tier 1 capability overlap on `ComposioActionMetadata` (`:323-399`), Tier 2 ILIKE with a mandatory capability-term gate (`:511-607`), Tier 3 top-N fallback (`:612-644`), plus a taxonomy-free recipe mode (`:404-506`) and live SDK param enrichment (`:685-756`). Its inputs are hand-maintained keyword tables: `STOP_WORDS`/`DANGEROUS_TOKENS`/messaging regex (`:44-56`), `INTENT_TO_CAPABILITIES` (`modules/tools/capabilities/taxonomy.py:288`), `_HINT_TO_APPS` (`modules/tools/services/composio_tool_service.py:80-96`).
- Execution safety: chat composio calls with an intent route through `execute_tool_with_validation` (`tool_router.py:664-674` → `:1059-1123`) → capability/destructive check that **fails closed** on empty metadata for destructive-reading intents (`modules/tools/services/action_capability_filter.py:274-296`; `_destructive_fail_closed` `tool_router.py:955-977`; keyword list `taxonomy.py:263-267`), with the daily metadata sync (`services/composio_sync_scheduler.py`, `main.py:414-423`, default ON `config.py:769`) — the W7/F018 fix, confirmed live.
- **Dead in-tree alternative:** `modules/tools/composio_tool_router.py` (205 lines) wraps Composio's own `COMPOSIO_SEARCH_TOOLS`/`COMPOSIO_EXECUTE_TOOL` meta-tools, with an executor delegate at `unified_executor.py:667-668` — but **no entry in `tool_routes` dispatches to it and no flag references it** (grep-verified); it has sat unrouted since pre-#303 (May).

### B.6 Observability
Per-dispatch selection outcome (narrowed/hit/fallback) persists into `router_decision->'selection'` (`telemetry.py:124-131`; stash in `signal_recorder.py:202-247`), aggregated by the super-admin `GET /api/analytics/selection-health` (`api/analytics_real.py:223-275`). Recorder counters surface via `/api/harness/self-learning` (`api/harness.py:123-124`) into the Command Center **Self-Learning tile** (`frontend/components/activity/widgets/self-learning-health-widget.tsx:36-55`).

## C. Honest quality — maturity **2.5 / 5**

The embedding layer is genuinely good and measured; the learned layer is genuinely unproven and currently value-negative; the lanes that matter most for autonomy get the least of either. Concrete findings, each grounded:

1. **The learning loop has never eaten a real datum.** All 2,341 `tool_execution_logs` rows are `telemetry_source='synthetic'`, frozen 2026-05-05 ([tool-telemetry.md](evidence/data/tool-telemetry.md)); all 29 learned edges, 232 affinities and 20 intent clusters belong to the all-zeros seed workspace; **none of the 21 real workspaces has a single edge** ([operating-graph-edges.md](evidence/data/operating-graph-edges.md)). Two months of live operation produced zero organic telemetry rows. Contributing causes visible in code/history: (a) F001 killed **all non-chat agent execution** until its fix merged 2026-07-02, so board/mission/heartbeat/scheduled lanes could not generate telemetry for the entire period; (b) playbook LLM steps have 402-failed daily since mid-June *before* any tool call (W1 inventory §3); (c) chat traffic was a single developer; and (d) the write path is **undiagnosable by design** — `write_telemetry` swallows every failure at `logger.debug` (`telemetry.py:107-112`) and `fire_telemetry` silently skips without a loop (`:170-172`), so "no rows" and "failing writes" are indistinguishable in production logs. Whatever the mix, the consequence is hard: every downstream artifact (edges, affinities, clusters, uplift claims, the selection-health metric) is untested against reality.
2. **The learned layer measured *negative* where it was tested.** The W7 S6 offline uplift eval (`orchestrator/evals/operating_graph_uplift.py`, +5-point gate at `:49`) reported **−32.9 points mean uplift**, so `TOOL_ROUTING_GRAPH` stays dark (residual map F015; `config.py:757`). The May routing eval recorded `graph (no-edges)` mode at **83.0% vs 93.6%** for plain `filtered_schema` ([repo-eval-artifacts.md](evidence/data/repo-eval-artifacts.md)). Holding the flag on this evidence is exemplary discipline — but the honest summary is: *on every measurement so far, the graph shape underperforms the plain embedding baseline.* The layer is complexity not yet earning its keep.
3. **Even where edges exist, their live influence is structurally minimal.** On the only live path (chat FILTERED), chain scores are discarded — `keep = {name for _,_,chain in chains}` (`smart_tool_router.py:232`) turns the ranking into unordered membership, then unions pins; the LLM receives an unordered tools array. Learned ranking today can only add/remove candidates at the margin of a top-30 chain cut. The two consumers that would actually *use* order (prompt chain hints; dispatcher enum re-rank) are respectively dark (`TOOL_ROUTING_GRAPH=false`) and never built (F074, `tool_router.py:328` still alphabetical).
4. **Intent-conditioning is write-only.** The edge builder computes k-means clusters and stores `centroid_embedding` (`edge_builder.py:463-474`), and affinities are keyed `succeeds/fails_for_intent` per cluster — but **no live read ever matches the query embedding against centroids** (grep: `centroid` appears only in `edge_builder.py`, `intent_clustering.py`, the model — never in `graph_router.py` or any consumer). `_query_affinities` filters only on action/workspace/agent (`graph_router.py:379-399`), so a "fails for intent X" penalty is applied to *every* intent. Additionally, boosts/penalties attach only to 2-hop chains — single-action chains keep raw cosine (`:215` vs `:247-265`) — so negative affinities cannot demote the most common (single-action) candidates at all.
5. **`used_after` "confidence" is not a confidence.** `wilson_lower_bound(sample_count, sample_count)` (`edge_builder.py:353`) is the Wilson bound of a 100% rate — a pure monotone rescaling of the count. Pair counting also ignores whether the *second* action succeeded (`:174-215` has no status filter), so an A→B pair that reliably errors still forms a high-"confidence" recommended edge (the separate `failed_after` signal is never consumed in ranking — `:100-103`, by design). The synthetic rows confirm the shape: conf 0.90 at n=34, 0.70 at n=9 — exactly Wilson(n,n).
6. **The composio lane drops the intent thread W7 built.** `execute_tool_with_validation` has **no `caller_context` parameter** and calls `execute_tool` without one (`tool_router.py:1059-1123`, final call `:1119`). Chat routes every composio call with an intent through precisely this wrapper (`:664-674`), so composio telemetry rows lose `user_query`/`turn_id`/`conversation_id` — no intent clustering and only weak 5-min-window `used_after` pairing for exactly the cross-app lane F016/F017 were built to serve. (The batched recorder path does keep `prior_action` — `:693-697` — but it is dark, see #7.) *New finding beyond the residual map.*
7. **A second dark flag the Phase-0 ledger missed:** `TOOL_SIGNAL_RECORDER_ENABLED` default false (`config.py:774`) — the intra-day learning path is a silent no-op, and the Command Center Self-Learning tile therefore reports `recorded: 0` forever while looking operational (`self-learning-health-widget.tsx:53`, reading `api/harness.py:123-124`). The tile cannot distinguish "healthy but quiet" from "disabled".
8. **The autonomy lanes get the least selection intelligence.** Missions, heartbeat agents and playbooks run `tool_loading="full"` (`modes.py:55-101`): no intent gate, no GraphRouter, no category filter — only the query-dependent enum narrowing plus the alphabetical composio enrichment. Judged by the North Star (autonomous agents doing client work), the smartest selection today protects the human-supervised lane and leaves the unsupervised ones with the dumbest surface.
9. **The tools-or-no-tools gate is English-only regex** (`intent_classifier.py:59-188`). The synthetic corpus itself shows the failure ("wie viele Agenten habe ich?" → error row in [tool-telemetry.md](evidence/data/tool-telemetry.md)); a paraphrase or non-English request classifies as chitchat and strips every tool — an autonomy ceiling in one function.
10. **Policy is source-baked** (F071/F072 residuals, confirmed): `DESTRUCTIVE_CAPABILITIES`/`REQUIRES_CONFIRMATION`/`INTENT_TO_CAPABILITIES` (`taxonomy.py:230-288`), hint keyword tables (`composio_hint_service.py:44-56`), `_HINT_TO_APPS` (`composio_tool_service.py:80-96`). Changing which actions need confirmation is a deploy. `DANGEROUS_TOKENS` also blanket-drops tokens like "archive"/"close" from recipe hints regardless of intent (`:469-470`).
11. **Staleness and hygiene defects:** (a) edges are upsert-only — when the 30-day window empties the nightly build writes nothing and *deletes* nothing (`edge_builder.py:92-94`), so the May-2026 synthetic edges are still served to the seed workspace today, and stale learned edges would persist indefinitely for real tenants too; (b) a **workspace-scoped** `build_edges(workspace_id=X)` run deletes *all* intent clusters for the embedding-model key plus every affinity referencing them, then rebuilds from X's logs alone (`edge_builder.py:440-458`) — a latent cross-tenant learning wipe (today only the PRD-143 S12 backfill passes the param); (c) duplicate (from,to) edge rows per scope are expected (agent-scoped vs global) but the seed data shows 3× duplicates the reader must dedupe; (d) dead code: `modules/tools/composio_tool_router.py` (§B.5), `get_composio_action_hint` and `should_skip_tools_for_message` (`smart_tool_router.py:368-408`, zero callers — grep-verified); (e) comment drift: "≤ ~110 actions" (`action_semantic_index.py:142`) vs 174 registered.
12. **What is genuinely good:** per-tenant scoping done properly end-to-end (required kwarg, no global fallback, ws-keyed cache — `graph_router.py:129-156`); the destructive gate fails closed by default with an honest cold-start caveat (`action_capability_filter.py:274-296`); per-action telemetry resolution is correct and privacy-preserving (`telemetry.py:20-44,92`); the batched recorder is the right design for its job; the S6 eval is a model of honest gating (its docstring explicitly forbids flag-flipping on a bad number); embedding-index engineering (cache-key incident writeup, no-truncation-before-scoring fix) shows real care. The bones are good; the diet is missing.

**Why 2.5:** a proven, well-built baseline layer (would be 3.5 alone) dragged down by a learning superstructure that is unfed, unread where it matters, measured-negative where tested, and invisible when it fails — plus the inversion that autonomy lanes get the weakest selection.

## D. Competitive teardown

**1. Anthropic Tool Search Tool** (launched 2025-11-20; [anthropic.com/engineering/advanced-tool-use](https://www.anthropic.com/engineering/advanced-tool-use)). Tools ship `defer_loading: true`; the model *searches* (regex or BM25 server-side implementations; custom embedding search pluggable) and only matched definitions expand into context. Measured: **85% token reduction** (~77K → ~8.7K tokens with 50+ MCP tools) and MCP-eval accuracy **49%→74% (Opus 4)**, **79.5%→88.1% (Opus 4.5)**. Recommended when >10 tools / >10K tokens of definitions — Automatos is far past both. **Where it beats Automatos:** the model is *in the loop* — it can reformulate a failed search and try again, where Automatos's one-shot pre-turn narrowing silently falls back to the full enum (`tool_router.py:404-419`); and the numbers are measured on real multi-server workloads. **Where Automatos stands:** its pre-turn narrowing is provider-agnostic (Automatos runs multi-model via OpenRouter; Anthropic's feature is Claude-only) and costs zero extra round-trips. The two compose rather than conflict.

**2. RAG-MCP** (Gan & Sun, 2025-05, [arXiv:2505.03275](https://arxiv.org/abs/2505.03275)). Semantic retrieval over an external tool index before the LLM sees anything; on an MCP stress test, **>50% prompt-token cut and 3.1× tool-selection accuracy (43.13% vs 13.62% baseline)** as the tool pool scales into the thousands. **Read:** this *validates* Automatos's `ActionSemanticIndex` approach as the right primitive — and shows the gains come from retrieval-vs-all-tools, not from learned graphs. Automatos's 93.6% on its own 47-query set is not comparable (tiny, synthetic, in-distribution); RAG-MCP's stress methodology (accuracy as a function of pool size) is the test Automatos hasn't run.

**3. LangGraph `bigtool`** ([github.com/langchain-ai/langgraph-bigtool](https://github.com/langchain-ai/langgraph-bigtool)). OSS pattern: a `retrieve_tools` tool over a Store with embedding search; the agent iteratively pulls tools into context; retrieval function fully customizable; Postgres or in-memory backends. **Where it beats Automatos:** search-as-a-tool works on *every* lane of any agent built on it, uniformly, in ~zero code — versus Automatos's per-mode strategy matrix where FULL lanes get nothing. It is also the cheapest reference implementation to port for a provider-agnostic search meta-tool. **Where Automatos stands:** bigtool has no notion of per-tenant learned success/failure, no destructive-action gating, no telemetry loop — Automatos's *scaffolding* is richer than what bigtool offers.

**4. Composio Tool Router (beta)** ([composio.dev/blog/introducing-tool-router-(beta)](https://composio.dev/blog/introducing-tool-router-(beta)), [docs.composio.dev/tool-router/overview](https://docs.composio.dev/tool-router/overview)). Session-scoped MCP endpoint over Composio's 1,000+ toolkits (~10k+ tools); toolkits discoverable by default via a search meta-tool (`COMPOSIO_SEARCH_TOOLS`); per-user sessions handle auth and toolkit restriction. **Where it beats Automatos:** it replaces the entire home-grown Composio-lane discovery stack (hint tiers, ILIKE scoring, stale `ComposioActionCache`, SDK param enrichment) with the vendor's own maintained search over live schemas — on the lane Automatos already pays Composio for. **Sharp local fact:** Automatos already wrote this integration (`modules/tools/composio_tool_router.py`, `COMPOSIO_SEARCH_TOOLS`/`COMPOSIO_EXECUTE_TOOL`) and never routed it (§B.5) — the adopt decision was half-made in May and abandoned without a recorded reason.

**5. Research frontier (context, not a vendor):** history-aware tool routing — learning from execution history which tool serves which intent — is an active research topic (e.g. ACE-Router, 2026, [arXiv:2601.08276](https://arxiv.org/pdf/2601.08276), embedding-based tool-graph construction + trajectory-trained routers). **Honest negative for the field:** none of the shipping products above does per-tenant, success-weighted learned routing; Automatos's operating-graph design is genuinely ahead of what Anthropic/LangChain/Composio sell today. That lead is currently worth nothing — the substrate has no real data and its only eval reads negative — but the *design bet* is not disproven either: the eval failed on synthetic seed data in a regime (47 queries, one fake workspace) where learning had nothing real to learn. The correct posture is "unproven, cheaply held", not "refuted".

## E. Build / extend / adopt / replace — verdict

**Extend the embedding layer into the one selection spine; adopt the search-as-a-tool pattern (Anthropic-style meta-tool, and Composio's Tool Router for the Composio lane); replace the regex gate; hold the learned-edge layer dark until it has a real diet and a passing eval.**

- **Extend (core spine):** `ActionSemanticIndex` + dispatcher narrowing is the proven asset (93.6% offline; mirrors RAG-MCP's validated mechanism). Extend it into a provider-agnostic **`search_tools` meta-tool** (bigtool pattern, ~2-3 days by porting the existing index behind a registered action) offered on **every** lane — this single move gives Missions/heartbeats/playbooks the selection intelligence they currently lack and cuts FULL-lane prompt cost, which is where Anthropic measured 85% savings. When running on Claude models, additionally emit `defer_loading` + native Tool Search (free accuracy per Anthropic's published numbers). Building this in-house is justified because Automatos is multi-provider and the index already exists — nothing external is better *for the platform-action surface*.
- **Adopt (Composio lane):** finish the already-written Composio Tool Router integration (route `COMPOSIO_SEARCH_TOOLS`/`COMPOSIO_EXECUTE_TOOL`, or its current sessions/MCP form) and retire the three-tier `ComposioHintService` + alphabetical enrichment + `_HINT_TO_APPS` keyword maps on that lane. It replaces ~1,000 lines of hand-tuned keyword plumbing with the vendor's maintained search; integration shape = session per (workspace,user) + meta-tools in the agent surface; cost = inside the existing Composio relationship (Tool Router is beta — verify SLA before making it the only path, and keep `composio_execute` as fallback during transition). The destructive/capability gate (`action_capability_filter`) **stays** — it wraps execution regardless of how the action was discovered.
- **Replace:** the regex tools-or-no-tools gate. Cheapest honest option: stop gating (always include the `search_tools` meta-tool — a few hundred tokens) and let the model decide; alternately a small-LLM classifier. An English-only regex deciding whether an autonomous agent may act is not defensible at this maturity.
- **Hold, don't kill (learned edges):** keep the schema, nightly builder, and eval gate; keep `TOOL_ROUTING_GRAPH` and chain hints dark; build **no further read-side consumers** until (a) organic telemetry actually flows and (b) the S6 uplift eval re-run on ≥30 days of real multi-workspace traffic clears its +5 gate. Rationale for holding rather than deleting: the marginal carry cost is near zero (a nightly job over an empty window no-ops), no vendor sells per-tenant learned routing, and the negative eval was measured on synthetic data the learner had never really "learned" from. Rationale for not investing more now: two independent measurements read negative, and the North Star is better served by the two proven moves above. **This staging is a recommendation for Gerard's decision, not a descope.**

## G. Quality metric

**Primary offline metric: top-1 / top-K selection accuracy + in-set rate** on a held-out query→correct-action set, per lane and per strategy — exactly what `scripts/eval/tool_routing/` already computes. Today's numbers (all synthetic-fixture, 2026-05-05/08, gitignored on one laptop — [repo-eval-artifacts.md](evidence/data/repo-eval-artifacts.md)): `filtered_schema` **93.6%** top-1 (gpt-4.1-mini, 47 queries), `graph (no-edges)` **83.0%**, best model (claude-opus-4.7 full) 95.7%. **Uplift metric:** learned-ranker uplift vs best baseline, gate ≥ +5 points (`operating_graph_uplift.py:49`) — today **−32.9**. **Online metrics (built, starved):** `selection-health` hit-rate / fallback-rate from `router_decision->'selection'` (`api/analytics_real.py:223-275`) — currently 0 rows; recorder counters (`signal_recorder.py:104-110`) — 0 by dark flag.
**Gaps to close for T3:** (1) the single most diagnostic number is the **organic telemetry row rate** (rows/day where `telemetry_source='production'`) — it is 0 today and would have flagged this module's blindness in May; alert on it. (2) Grow the eval set from 47 to a few hundred with abstain cases, multi-turn, paraphrase/non-English variants, and score AST-style on action+params like BFCL ([gorilla.cs.berkeley.edu/leaderboard.html](https://gorilla.cs.berkeley.edu/leaderboard.html)) rather than name-only. (3) Commit eval outputs to the repo/CI, not a laptop. (4) Re-run the uplift eval on organic telemetry quarterly; the flag decision stays chained to it.

## H. Cost note (informational)

- **Selection decision:** one query embedding per turn (qwen3-embedding-8b, 2048-dim via OpenRouter — model key visible in the intent clusters) ≈ 20–40 tokens ≈ negligible ($<10⁻⁵); GraphRouter DB reads are two indexed queries + 5-min cache; the May eval measured the full routing decision at **~$0.0007/call** (gpt-4.1-mini `filtered_schema`, 93.6%). The real money is **tool schemas in the prompt**: FULL-lane surfaces (dispatcher enum of 174 actions + core tools + per-action composio schemas + hint blocks) plausibly run tens of K tokens/turn — the regime where Anthropic measured ~77K tokens and an 85% cut from search-based loading, i.e. roughly cents/turn on mid-tier models, compounding across every heartbeat tick and mission step.
- **Latency:** dispatcher narrowing pays one embedding RTT (~100–300 ms) *plus* a fresh thread + event loop per call (`tool_router.py:106-122`) on context assembly; hint-service SDK enrichment adds one Composio API call per matched app (`composio_hint_service.py:714-753`).
- **Learning plane:** nightly edge build over an empty window is ~free; at real volume it is one batch-embedding pass over distinct user queries/night (thousands of queries ≈ dollars/month).
