## A. What it is

The layer that answers *who is calling, for which tenant, and what may they do* on every one of the ~92 routers that take the shared hybrid dependency. It is really two layers welded together. The **identity + tenant-resolution spine** — `get_request_context_hybrid` (`core/auth/hybrid.py`) — turns a Clerk JWT (SaaS edition) or no credential at all (local edition) into a request-scoped `(workspace_id, UserContext)`, auto-provisioning a personal workspace for brand-new users; this half is genuinely good, careful, and heavily exercised. Bolted on top is the **authorization + collaboration layer**: workspace CRUD/settings, PRD-37 invitations and member roles, PRD-158 Teams (a knowledge-ACL primitive, distinct from members), the PRD-18 encrypted credential store, three deliberately-distinct key systems (SDK keys, BYOK keys, integration credentials), and an `api/permissions.py` "agent-tool RBAC" surface. The seed symptom from the capability map — role/permission semantics fork across planes — is confirmed and is worse than the two findings it names: **the platform runs four-to-five disconnected role vocabularies**, and the flagship per-tenant RBAC (editor/viewer) is decorative on 85 of 92 routers. Authentication is solved (Clerk, correctly adopted); **authorization is the module's unfinished work**, and most of the fix is already written but parked behind a default-OFF flag.

## B. What it does (real implementation + data path)

**The tenant-resolution spine.** `get_request_context_hybrid` (`core/auth/hybrid.py:653-828`) resolves identity in three ordered lanes: (1) **Clerk JWT** (`:684-776`) — verify via JWKS, extract user info, then a real cross-tenant access check: if the client sent an `X-Workspace-ID` the user cannot reach, it is *not* honoured (`_user_has_workspace_access`, `:146-165`); otherwise resolve from org → owned/member workspace → auto-provision (`_resolve_workspace_for_clerk_user`, `:390-468`). (2) **Env API key** (`:778-800`) — `hmac.compare_digest` against `ORCHESTRATOR_API_KEY`, minted as `system_role="admin"`. (3) **Anonymous dev-fallback** (`:805-826`), reachable only when `REQUIRE_AUTH=false`. New-user provisioning is transactionally careful: an `INSERT … ON CONFLICT` upsert (`:273-280`) plus a transaction-scoped advisory lock (`pg_advisory_xact_lock`, `:298-301`) that serialises concurrent first-requests so a new Clerk user cannot get N duplicate workspaces — a real race fix, not boilerplate. This is the load-bearing path: **21 workspaces / 237 agents** ([census](evidence/data/census.md)) resolve through it on every request.

**Clerk seam.** `ClerkAuth` (`core/auth/clerk.py`) verifies RS256 against cached JWKS (`:63-107`), enforces audience when `CLERK_AUDIENCE` is set to block cross-app JWT reuse (`:83-95`), and normalises claims (`extract_user_info`, `:109-230`). A defence-in-depth gate refuses to honour an `admin` role in Clerk `publicMetadata` unless the email is on the configured staff domain (`:203-213`) — the F075 fix that turned a hardcoded `@automatos.app` literal into `config.PLATFORM_STAFF_EMAIL_DOMAIN` (`config.py:172-173`). It also wraps the Clerk management API for invitations, org membership, and user deletion (`:282-439`).

**Editions (F008).** `AUTH_EDITION` (`config.py:157-166`) is one flag with two values: `saas` (Clerk is the boundary; the default) and `local` (single auto-authenticated user, no Clerk env), which forces `REQUIRE_AUTH=false`. A boot guard `validate_auth_edition` (`config.py:1064-1104`) is meant to fail-closed: `saas` requires the Clerk env, `local` requires `DEFAULT_WORKSPACE_ID`. Frontend mirrors this in a single `AuthBoundary` (`frontend/components/providers.tsx:29-75`) — `local` renders `LocalAuthProvider` (a no-op token getter over the same `apiClient.setClerkTokenGetter` seam, `local-auth-provider.tsx:19-29`) with no Clerk symbol imported; `saas` renders `ClerkProvider`.

**The role/permission surfaces (this is where it forks).** Five separate vocabularies coexist:
1. **`system_role`** — `super_admin` / `admin` / `user` / `service`, carried on `UserContext` (`core/auth/dependencies.py:8-27`). Gated by `require_super_admin` (`core/auth/super_admin.py:17-29`, obs tier) and `caller_is_admin` (`core/auth/roles.py:28-45`, the F043 shared helper).
2. **Workspace role** — `owner` / `admin` / `editor` / `viewer` with a wildcard permission matrix (`core/workspaces/permissions.py:12-36`), enforced by the `@require_permission` decorator (`:60-137`).
3. **Frontend `SystemRole`** — `admin` / `user` / `customer_manager` (`frontend/contexts/role-context.tsx:13`) — note `customer_manager` exists in **no** backend role set.
4. **SDK-key scopes** — `chat` / `documents:read` / `agents:execute` / `tasks:read` … (`api/api_keys.py:27-41`), checked by `ApiKeyService.check_permissions` (`core/services/api_key_service.py:234-243`).
5. **Agent-tool RBAC** — a hardcoded `agent_type → tool-name` matrix (`api/permissions.py:97-122`).

**Collaboration + secrets.** `api/workspaces.py` serves `/current` and workspace settings (integrations, BYOK prefs, the Auto "soul"). `api/team.py` does members CRUD + invitations, all four write endpoints behind `@require_permission("members:*")` (`:76-256`), plus a public `accept-invitation` that verifies the Clerk JWT directly (`:337-449`); the shared invite flow lives in `core/workspaces/invitations.py:137-231`. `api/teams.py` (PRD-158) is a clean, properly workspace-scoped teams surface via `core/team_access` (`teams.py:38-59`). `api/credentials.py` (PRD-18) is the encrypted credential store with per-row workspace checks (`_check_credential_workspace`, `:65-68`) and admin-gated decrypt/resolve (`:358-359,588-589`). `AuditService` (`core/workspaces/audit.py:49-98`) writes `audit_logs`, extended by PRD-181 to log non-human (agent/system) actors with a nullable `user_id`.

## C. Honest quality — inspected against real behaviour and data

**The real-data backdrop that reframes everything.** Prod holds **21 workspaces against 22 users** ([census](evidence/data/census.md)) — ≈1.05 users per workspace. The deployment is almost entirely *solo* workspaces. `approval_grants` = 0, `skill_audit_log` = 6, `memory_access_log` = 6. So the entire multi-seat apparatus this module is built around — invitations, teams, member roles, the editor/viewer hierarchy, the audit plane — is **essentially unexercised in production**. That is not a criticism of the code; it is the lens: the tenant-*resolution* spine is hammered on every request, while the authorization/collaboration layer is a near-dormant B2B future. Judge the two halves separately.

**What is genuinely good.** `get_request_context_hybrid` is the strongest single file in the module: real cross-tenant guards (`_user_has_workspace_access`, `:146-165`; SDK-key workspace-header-may-only-match, `:597-606`), the advisory-lock provisioning race fix (`:298-301`), audience-pinned JWT verification, existence-hiding 404s, and a proper W2 tenant-isolation test suite behind it. The F008 open-core edition split is clean and the F075 staff-domain fix is correct. The credential store is real: Fernet encryption, BOLA checks on every by-id path, admin-gated resolution, audit rows. Clerk is the right authN choice and is correctly adopted. None of the July *tenancy* criticals reproduce.

**The defects, with evidence:**

1. **Authorization is a five-way fork with no single authority (the seed symptom, confirmed and enlarged).** The five vocabularies in B do not map onto each other: a workspace `owner`/`editor`/`viewer` is invisible to `system_role`; the frontend's `customer_manager` (`role-context.tsx:13`) resolves to nothing on the backend; SDK scopes and the agent-tool matrix are islands. There is no function that answers "can principal P do action A on resource R" once — there are five, and they disagree. This is the root cause of the F042/F043-class bugs, not an incidental detail.

2. **Editor/viewer workspace roles are decorative on 85 of 92 routers.** `@require_permission` — the *only* thing that reads the `owner/admin/editor/viewer` matrix — appears in exactly **6 places**: the four `api/team.py` member endpoints and the widget plane (`grep` count, `api/team.py` + `api/widgets/*`). The other **92 routers** take the bare hybrid dependency, which resolves a workspace and a `system_role` but **never consults the workspace role**. Concrete consequence: a workspace `viewer` can create agents, launch Missions, edit documents, and delete deliverables — every mutating router accepts any authenticated *member* regardless of role. The `ROLE_PERMISSIONS` matrix (`permissions.py:12-36`) governs member-management and the widget plane and nothing else. The UI will happily render a "viewer" who is functionally an editor.

3. **The empty-permission fork (F042) is the live behaviour on a default deployment.** The unifying fix exists — `modules/policy/roles.has_permission` makes empty = deny everywhere — but only fires when `AUTOMATOS_POLICY_PLANE` is ON, and it is **OFF by default** (`config.py:645`; nothing in `envs/`, compose, or `railway.json` sets it). So the July divergence is what actually runs: widget plane `require_permission` keeps "empty list = unrestricted" (`api/widgets/auth.py:257-262`) while the board plane keeps "empty = deny" (`core/auth/hybrid.py:527-539`). One minted no-permission key is a god-key on widgets and a null-key on the board. Verified live: both branches present, flag defaults OFF.

4. **super_admin is locked out of every admin router on a default deployment (F043).** The shared helper is adopted across all 8 formerly-forked routers (`caller_is_admin`, `core/auth/roles.py:28-45`; callers `admin_workspaces.py:49`, `marketplace.py:41`, `skills.py:526`, etc. — verified), but plane-OFF it returns `role == 'admin'` (`roles.py:45`), i.e. the platform `super_admin` still gets 403 from all of them, by documented design (`roles.py:8-14`). The hierarchy fix (`super_admin ⊇ admin`) only exists behind the OFF flag. So on the running product, the highest-privilege principal cannot reach the admin surfaces the fix was written to open.

5. **The agent-tool RBAC plane (`api/permissions.py`) is a workspace-blind fossil.** `AgentToolPermission`, `Tool`, and `PermissionAuditLog` carry **no `workspace_id`** (`core/models/tools.py:103-140`) — so this "RBAC" *cannot* be tenant-scoped even in principle; `get_permission_matrix`/`list_assignments`/`assign_tool_to_agent` (`permissions.py:214-452`) query `Agent`/`Tool`/`AgentToolPermission` globally, taking `ctx` and never using it. Worse, the matrix it enforces is a hardcoded `agent_type → vendor-name` map (`code_architect → [GitHub, Jira, Docker…]`, `permissions.py:97-122`) that is disconnected from how tools are *actually* gated on this platform (the Composio registry + `tool_router`'s `is_admin` schema exposure + per-agent scoping). It is a marketplace-era artifact, untouched since PR #303, mounted at `main.py:977`. It reads as a real RBAC pillar in the capability map; in practice it governs nothing the runtime respects.

6. **Credential isolation has a NULL-workspace hole.** `_check_credential_workspace` (`credentials.py:65-68`) rejects only a *mismatching, non-null* `workspace_id`: `if cred.workspace_id and str(cred.workspace_id) != str(ctx.workspace_id)`. A credential row with `workspace_id IS NULL` (legacy or globally-seeded) therefore passes for **every** tenant, and `resolve_credential` by *name* (`:599-608`) calls `get_credential_by_name` with no workspace filter, then relies on that same null-permissive post-check. The by-id paths are sound; the name path and null rows are the gap. (Flagged here as an isolation-model correctness gap; the dedicated hardening pass owns the exploit framing.)

7. **F012: the committed Clerk artifact is still tracked on live main.** `git ls-files tests/e2e/.auth/user.json` returns the path and `git cat-file -t HEAD:…` returns `blob` on the live tree; `.gitignore:129-130` lists it but a gitignore is a no-op for an already-tracked file (no `git rm --cached` was done). The gitleaks lane stays red pending a human history purge. JWTs were 60-second, so live-credential risk is low, but the re-commit hazard is open.

8. **Auth degrades toward resolution, not refusal, in one spot.** When a Clerk user presents a `workspace_id` they cannot access, the spine does **not** 403 — it logs and silently falls through to the resolver, binding them to their *own* workspace instead (`hybrid.py:726-730`, "user may have a stale localStorage value"). Defensible as UX for a known client bug, but it means a cross-workspace header attempt returns a 200 for the caller's own tenant rather than an error, which masks both client bugs and probing.

9. **The "fail-closed boot" is really fail-closed-per-request.** `validate_auth_edition` raises `RuntimeError` (`config.py:1064`), but `run_stage` catches boot-stage exceptions and only records "failed" without re-raising (residual map, F004 note) — the same swallow that affects the Shopify and F005 boot guards. A `saas` deploy that lost its Clerk env does **not** hard-abort; only the per-request 401 in lane 1 protects it. The guard's advertised protection is weaker than its docstring claims.

**Maturity score: 3 / 5.** Split honestly: the identity + tenant-resolution spine is a **4** (careful, race-safe, cross-tenant-guarded, well-tested, and the July tenancy criticals are all closed), and Clerk adoption is the right call. But authorization is a **2**: five disjoint role vocabularies, editor/viewer decorative platform-wide, the two written fixes (F042/F043) dark behind a default-OFF flag, the flagship agent-tool RBAC a workspace-blind fossil, and a credential null-workspace gap. North-Star framing: agents cannot be trusted to act autonomously *on behalf of a scoped principal* when the platform has no single, enforced answer to "what may this principal do" — the resolution layer knows *which tenant*, but the authorization layer cannot reliably say *what within it*. Net **3**.

## D. Competitive teardown

The instructive split: for **authentication** the incumbents are ahead only where Automatos already buys in (Clerk); for **authorization** — the actual gap — the relevant field is the policy/FGA engines, and Automatos is behind all of them because it has no centralized model at all.

- **Clerk (already adopted — the authN benchmark).** Clerk embeds roles/permissions directly in the session token, so authorization checks need no extra network hop, and ships Organizations with `admin`/`member` defaults plus custom roles/permissions and "role sets" via the B2B add-on ([clerk.com/docs — roles & permissions](https://clerk.com/docs/guides/organizations/control-access/roles-and-permissions), [clerk.com/organizations](https://clerk.com/organizations)). Pricing is MAU-based: free to 10k, then $0.02/MAU, plus $1 per Monthly Active Organization beyond the first 100 ([clerk.com/pricing](https://clerk.com/pricing)). Automatos uses Clerk for identity but **re-implements** org-membership resolution, invitations, and roles in Postgres (`hybrid.py`, `team.py`) rather than leaning on Clerk Organizations — a reasonable choice (the workspace IS the tenant, and Clerk-org coupling was the F008 problem), but it means the role model Clerk offers for free is duplicated and then diverges.
- **WorkOS / AuthKit (the enterprise-SSO and agent-authz benchmark).** AuthKit is free to **1M MAU** with email/social/MFA; enterprise SSO and SCIM Directory Sync are $125/connection; and WorkOS ships **Fine-Grained Authorization free to 10M checks/month** ([workos.com/pricing](https://workos.com/pricing)). Directly North-Star-relevant: WorkOS's 2026 positioning is *authorization for AI agents* — scoped, revocable permissions for non-human principals ([workos.com/blog — authorization platforms for AI agent permissions](https://workos.com/blog/best-authorization-platforms-ai-agent-permissions-2026)). That is exactly the principal type Automatos has (`system_role="service"` SDK keys, agent actors in `audit_logs`) and exactly the scoping it lacks.
- **Keycloak (the open-core/self-host benchmark).** Apache-2.0, no per-user fees, ~$200-700/mo self-hosted regardless of user count; realms *and* the newer Organizations feature (26.0) for in-realm multi-tenancy; and — the pointed part — a **policy-based authorization engine** (resource/scope/role policies) that is strictly more expressive than Auth0's role/permission RBAC ([skycloak.io — Keycloak vs Auth0](https://skycloak.io/blog/keycloak-vs-auth0-comparison-guide/), [skycloak.io — multitenancy via Organizations](https://skycloak.io/blog/multitenancy-in-keycloak-using-the-organizations-feature/)). Relevant because the open-core `local` edition currently ships with *no* real authorization model at all (single god-user); Keycloak is what a self-hoster would expect.
- **The authZ engines (the real comparison set): OpenFGA / Oso / Cerbos.** These are what the module is missing, not another authN vendor. **OpenFGA** is Zanzibar-style ReBAC — model access as relationships (`agent → member_of → team → can_read → doc`), self-hostable, stateless, horizontally scalable, the hosted form is Auth0 FGA ([openfga.dev](https://openfga.dev/)). **Cerbos** is the lightest adopt: YAML policies evaluated by a stateless sidecar/SDK, ABAC+RBAC out of the box, self-host/serverless/air-gapped, **no data-sync required** ([cerbos.dev — Cerbos vs OPA](https://www.cerbos.dev/blog/cerbos-vs-opa)). **Oso** keeps logic in app code and answers from your own DB, good for custom patterns ([osohq.com — OpenFGA alternatives](https://www.osohq.com/learn/openfga-alternatives)). The selection rule from the field: simple roles+attributes → a policy engine (Cerbos/OPA); per-object sharing, nested groups, list-filtering → a Zanzibar system (OpenFGA) ([authzed.com — OpenFGA alternatives](https://authzed.com/learn/openfga-alternatives)).

**Where Automatos actually stands:** authentication is competitive (Clerk, correctly chosen; local edition a genuine open-core win). Tenant resolution is solid and, for a single-tenant-per-workspace model, arguably simpler and safer than a general org graph. **Authorization is behind every player named** — there is no single policy model, roles fork five ways, editor/viewer don't enforce, and there is no FGA for the agent-as-principal scoping that WorkOS now treats as table stakes.

## E. Build / extend / adopt / replace — the verdict

**KEEP Clerk for authN (adopt — already done). CONSOLIDATE authorization onto the ONE model that already exists in-tree — EXTEND `modules/policy/roles.py` into the single authority and turn the plane ON. KILL the agent-tool RBAC fossil and the frontend `customer_manager` ghost. ADOPT an external FGA engine (Cerbos first) ONLY IF an eval shows per-object/agent-scoped sharing is needed — otherwise the in-house hierarchy plus a real `@require_permission` sweep is enough.** The reuse bias points *inward* here: the expensive fix (a coherent role model) is ~80% written and dark behind a flag; buying a vendor before flipping that flag would add a sixth vocabulary, not remove five.

1. **Authentication — KEEP Clerk + the local edition.** Clerk wins on React DX and session-embedded roles; the F008 split is clean; churn buys nothing. Revisit **WorkOS** *only* if a pilot demands enterprise SSO/SCIM at scale (WorkOS is the SSO specialist and free to 1M MAU) — not now, at 22 users.
2. **Authorization — EXTEND `modules/policy/roles.py` to be the single authority, and flip the plane ON.** The `super_admin ⊇ admin ⊇ user` hierarchy and the "empty = deny" rule already exist and are tested (`modules/policy/roles.py`); they resolve F042 and F043 the moment `AUTOMATOS_POLICY_PLANE` defaults ON. Then do the `@require_permission` sweep (defect 2) so editor/viewer actually gate the ~85 unguarded mutating routers, collapse the frontend `SystemRole` onto the backend set (delete `customer_manager`), and make SDK scopes reference the same permission strings. One model, enforced. ~1-2 weeks; almost entirely wiring and deletion.
3. **Agent-tool RBAC (`api/permissions.py`) — REPLACE with nothing (KILL).** It is workspace-blind by schema, disconnected from the real tool-gating path, and untouched since pre-waves. Delete the router, the `AGENT_TOOL_PERMISSIONS` matrix, and (after a migration audit) the `AgentToolPermission`/`PermissionAuditLog` tables if no live writer remains. Tool authorization already lives correctly in the Composio/tool-runtime lane; this is subtraction.
4. **Credential store — EXTEND (keep, fix the hole).** Fernet + audit + BOLA is sound; close the NULL-`workspace_id` gap (defect 6) by treating null as deny for non-admin callers and scoping `get_credential_by_name` to the workspace. Small, high-value.
5. **FGA (Cerbos/OpenFGA) — ADOPT only behind an eval.** If the North Star needs "agent A may read doc X but not doc Y" or team-nested resource sharing, **Cerbos** is the lightest adopt (YAML policies, stateless sidecar, no data-sync, self-hostable for the open-core edition) — reach for **OpenFGA** only if the relationship graph (agent→team→workspace→resource) genuinely needs Zanzibar. Do *not* adopt before step 2; an FGA engine on top of five forked vocabularies inherits the mess. Defer behind the T3 eval that measures whether per-object scoping changes agent output quality.
6. **Explicitly not doing:** replacing Clerk; adopting Keycloak for the SaaS product (relevant only as the open-core self-host story, and only once local-edition authZ is more than a god-user); building a sixth bespoke role system.

## G. Quality metric

Authorization is measurable; today none of it is measured. Feeding T3:

1. **AuthZ enforcement coverage (SLI):** share of mutating routers behind an *enforced* permission check. **Today ≈ 7% (6 of ~92).** Target: every mutating router either enforces a workspace-role permission or is explicitly, auditably public. This is the number that would have flagged defect 2.
2. **Role-vocabulary count (CI gate, integer):** distinct role/permission systems the codebase resolves against. **Today: 5** (system_role, workspace-role, frontend SystemRole, SDK scopes, agent-tool matrix). Target: **1** authority (`modules/policy/roles.py`) with typed adapters.
3. **Policy-plane-on (boolean):** is `AUTOMATOS_POLICY_PLANE` ON in the default/prod config? **Today: NO** — so F042/F043 are live. This single boolean is the difference between the written fixes mattering and not.
4. **super_admin reachability (boolean):** can a `super_admin` reach the 8 admin routers on the running config? **Today: NO** (defect 4).
5. **Tenant-isolation test coverage of the authZ paths:** the W2 suite covers the resolution spine; the by-name credential path (defect 6) and the widget/board empty-permission fork have no isolation test asserting the *unified* semantic. Target: one test per plane asserting empty = deny.

## H. Cost note (informational)

- **Authentication:** Clerk at $0.02/MAU beyond 10k free ([clerk.com/pricing](https://clerk.com/pricing)) — at **22 users**, effectively $0; the free tier covers the pilot with four orders of magnitude of headroom. No token/compute cost on the hot path beyond one cached-JWKS RS256 verify per request (the JWKS set is cached 5 min, `clerk.py:56-60`).
- **Authorization (in-house):** the `modules/policy/roles.py` path is stdlib-only, no DB, no config read beyond the flag — ~0 marginal cost. The `@require_permission` decorator adds one indexed `workspace_members` lookup per gated call (`permissions.py:102-114`).
- **FGA (if adopted):** Cerbos self-host is OSS ($0 licence) + a small always-on sidecar pod; WorkOS FGA is free to 10M checks/mo ([workos.com/pricing](https://workos.com/pricing)) — check volume at 22 users is negligible either way.
- **The real cost is the fragmentation tax:** five role vocabularies × routers that don't enforce them = recurring F042/F043-class bugs and engineer-hours, not dollars. Consolidation (E.2) is a cost *reduction*.

## I. UX / surface

The module has no single "who can do what" surface, and the UI actively lies about roles (a viewer sees full controls the backend never blocks):

1. **One Access panel (Settings → Access).** Fold the scattered surfaces — members + roles (`team.py`), teams (`teams.py`), API keys (`api_keys.py`), credentials (`credentials.py`) — into one page with a real permission matrix. Today they are separate tabs with no shared mental model.
2. **Make roles mean something in the UI.** After the E.2 `@require_permission` sweep, a `viewer` should see read-only controls, not full editors that 403 (or worse, silently succeed) on click. The current gap (defect 2) is a UX integrity problem before it is a backend one.
3. **Surface the super_admin/obs tier honestly.** `require_super_admin` gates the observability tier; the frontend `RoleProvider` (`role-context.tsx`) should reflect the *real* backend role set — delete the `customer_manager` ghost that resolves to nothing.
4. **Audit-log viewer.** `audit_logs` is written (member actions + PRD-181 agent/system verdicts) but there is no reader surface in Command Center. For a platform whose North Star is autonomous agents acting as principals, "show me every action an agent took in this workspace" is a high-value, near-free panel once the plane is on and writing.
5. **Kill the agent-tool permission-matrix UI** (if any renders `permissions.py`) alongside the router (E.3).
