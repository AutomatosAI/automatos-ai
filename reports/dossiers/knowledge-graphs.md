## A. What it is

Automatos runs three distinct graph substrates under one banner. The **workspace Knowledge Graph** is a per-tenant NetworkX property graph built by `GraphifyService` from LLM entity/relation extraction over documents and agent reports plus deterministic mappers (agent roster, DB schemas, Shopify catalog/orders), clustered into communities with cheap-LLM titles, persisted as JSON blobs in Postgres, and consumed by five `platform_graph_*` agent tools, a cluster-first REST drill-in UI, and — the one genuinely autonomous consumer — the Shopify widget's proactive opener/cross-sell engine reading `frequently_bought_with` edges. The **code graph** is a separate pipeline: tree-sitter parses a cloned GitHub repo (15 extensions / 14 languages) into symbols + call/import/extends relationships stored in Postgres with pgvector embeddings, searched fuzzily/semantically and exposed through nine `platform_codegraph_*` tools plus a push-webhook auto-reindex. The **operating-graph edge substrate** is a nightly batch (`edge_builder.py`) that turns tool-execution telemetry into `used_after`/`failed_after` edges, intent clusters, and affinities with Wilson-bound confidence — construction lives here; consumption (GraphRouter) is the tool-selection dossier's territory. The **knowledge flywheel** closes the loop by routing mission syntheses, generated documents, and reports back through RAG ingestion and into the KG's incremental build.

## B. What it does (implementation + data path)

### B1. Workspace Knowledge Graph (documents/reports → graph)

**Build pipeline** — `orchestrator/modules/knowledge/graph_service.py`:
- `build_graph` (`:232-342`): per-workspace `asyncio.Lock` (`:206-210`), configurable timeout (default 1800s, `:239`), then: collect sources → extract → merge → `graphify.build_from_json` → `cluster` → `god_nodes` → `surprising_connections` → community reports → export → meta → cache → snapshot+diff → build report → prune history. Success/failure emits an honest `graph` primitive heartbeat (`modules/knowledge/primitive_heartbeat.py:36-67`).
- **Sources** (`_collect_sources`, `:820-930`): documents with status completed/processed, text reassembled from `document_chunks` ordered by index, **hard-capped at 8,000 chars** (`:842`, `:876-883`); agent roster rows on full rebuilds (`:893-913`).
- **Extraction** (`modules/knowledge/graph_extraction.py`): one LLM call per document/report (`extract_from_document` `:265-316`, `extract_from_report` `:319-371`), parallel with semaphore 5 (`graph_service.py:984-985`), model = `GRAPHIFY_MODEL` → falls back to the system-LLM setting (`config.py:266-272`). The prompt asks for concepts/entities/processes/metrics/rules with `EXTRACTED|INFERRED|AMBIGUOUS` confidence enums, per-edge confidence scores, and up to 3 hyperedges per doc (`:101-145`). Deterministic mappers for roster/blueprints/db-schemas/connected-apps (`:385-481`). All failures degrade to an empty graph, never crash the build.
- **Merge** (`_merge_extractions`, `graph_service.py:1047-1064`): dedup **by node id only, last-write-wins** (`:1060-1061`); edges concatenated. This is the entity-resolution story in its entirety.
- **Incremental** (`schedule_incremental_update` `:497-533` + `_debounced_rebuild` `:1354-1382` + `_incremental_build` `:1384-1484`): 60s debounce (`:85`), pending sources partitioned into changed doc-ids + report texts (`partition_pending_sources` `:96-140` — the PRD-164 fix that stopped dropping agent-output types). Add-only: `add_node`/`add_edge` into the existing graph (`:1431-1440`); edges whose endpoints aren't both present are silently dropped (`:1439`).
- **Storage** (`core/graph_storage.py:41-183`): `DbWorkspaceClient` upserts artifacts into the `workspace_graphs` table (`(workspace_id, path)` key, TEXT content, `:94-117`) — graph.json, meta.json, communities.json, graph.html, `history/{date}_graph.json` (max 30), `latest_diff.json`, `reports/{date}_build.md`.
- **Community reports** (`modules/knowledge/community_reports.py:74-143`): GraphRAG-style cheap-LLM titles+one-line summaries for the top-25 communities by size (configurable), concurrency-capped, never fails the build; user label edits set an `edited` flag the next build respects (`graph_service.py:781-814`).
- **Query surface**: five promoted agent tools — `platform_query_graph` (term-scored BFS/DFS + text serialization), `platform_graph_neighbors`, `platform_graph_communities`, `platform_graph_impact`, `platform_graph_stats`, `platform_graph_path` (`modules/tools/discovery/actions_graph.py:63-219`, handlers `handlers_graph.py:98-546`); REST cluster-first drill-in for the UI — communities list → community subgraph (capped, degree-ranked, honest `truncated` flag) → node expand → path → search (`api/knowledge_graph.py:157-246`; server-side subgraph extraction `graph_service.py:663-779`, explicitly the LightRAG pattern per `:626-629`). PRD-124 team ACL filters every read (`graph_service.py:148-181`).
- **Triggers**: document ingestion (`modules/rag/ingestion/manager.py:1211-1213`), report submission (`api/agent_endpoints.py:94-95,598-599`), DB-schema mapping (`api/database_knowledge.py:142-143`), wizard first-build (`api/wizard.py:692-694`), manual `/api/knowledge/graph/build` (`api/knowledge_graph.py:101-118`), flywheel pendings. **No scheduled rebuild exists** — freshness is purely event-driven.

### B2. Commerce KG (Shopify)

- `map_shopify_catalog` (`graph_extraction.py:503-670`): pure, deterministic JSONL→graph mapper — product/variant/collection/vendor/metafield nodes with rich attrs, `variant_of`/`in_collection`/`by_vendor`/`has_metafield` edges. `map_shopify_orders` (`:693-799`): privacy-by-design FBT mapper — only aggregated product↔product `frequently_bought_with` edges (co-count, support≥2, cancelled orders excluded), no customer/order nodes.
- Sync: `_product_sync_impl` runs Bulk Op → mapper → `import_graph(workspace_id, graph, merge=False)` (`api/shopify.py:568`). Orders sync strips stale FBT edges first, then `import_graph(..., merge=True)` (`:808-844`). W13 (F032) made catalog webhooks fire `_sync_catalog_for_workspace` end-to-end from the sibling Remix app (`api/shopify.py:315-396`), and F088 promoted sync/status to platform tools (`actions_shopify.py:15-54`).
- **Consumption — the live autonomous leg**: `integrations/shopify/widget_proactive.py` loads the workspace graph (`:74-77`) and ranks `frequently_bought_with` > `in_collection` > `by_vendor` (`:101-129`) to ground widget openers and cross-sells; golden opener fixtures exist (`integrations/shopify/tests/fixtures/`).

### B3. Code graph

- `modules/codegraph/codegraph_service.py`: clone (`:435+`, URL/branch sanitized via `core/security/git_sanitizer`) → discover → parse → store. Tree-sitter parser covers 15 extensions/14 languages with per-language symbol/call/import/extends node-type maps (`parsers/treesitter_parser.py:75-125`); AST fallback for python/TS/JS (`codegraph_service.py:615-838`). Incremental re-index by SHA-256 file hash with changed-file symbol deletion and deleted-file cleanup (`:244-266`, `:318-339`).
- Embeddings: batches of 100 through the centralized embedding manager into pgvector `codegraph_symbols.embedding` (`:916-1011`), with a dimension-check ALTER guard (`:840+`). Relationships resolved exact-then-fuzzy by simple name (unambiguous single candidate only), unresolved targets stored as `external_reference` rows instead of dropped (`:1033-1146`).
- Query: `search_symbols` ILIKE fuzzy (`:1152-1275`), `semantic_search` pgvector cosine with prompt-block formatting for LLM consumption (`:1277-1367`), call-graph / architecture / dependencies (`:1538+`), PageRank repo-map ranking explicitly modelled on Aider (`ranking/pagerank_ranker.py:1-60`), regex-classified NL code search (`search/nl_code_search.py:20-70`). Query telemetry now actually writes (`_log_query` `:1369-1407`).
- Agent surface: nine tools incl. W13's write-parity trio `platform_codegraph_index`/`reindex`/`set_auto_reindex` (`actions_codegraph.py:15-240`); GitHub push webhook filters projects on the now-settable `auto_reindex` and fires background reindex (`api/codegraph.py:667-741`).

### B4. Operating-graph edge substrate (construction)

- `core/services/edge_builder.py`: nightly 03:00 UTC (`services/edge_builder_scheduler.py:28-58`; runs regardless of the read-side flag). From `tool_execution_logs`: session grouping by turn_id > conversation_id > agent+5-min window (`:161-171`), `used_after` sequential-pair edges (`:174-215`), `failed_after` 2-step-lookahead edges with Wilson-bound **failure-rate** confidence (`:218-276`), K-means intent clusters (deterministic seed) with model-keyed centroids and FK-safe idempotent rebuild (`:393-482`), succeeds/fails_for_intent + agent_prefers affinities (`:521-619`). Per-workspace and per-agent scoping columns throughout; sample floor 3.

### B5. Knowledge flywheel

- `services/knowledge_flywheel.py:124-229`: ONE choke point `ingest_agent_output` for mission syntheses / generated documents / reports → per-workspace opt-out (ON by default, `:60-79`) → `DocumentManager.upload_document` (chunk+embed, tagged `agent_output`) → typed KG pending scheduled (`:114-121`). W9 fixed starvation (SQL-side terminal markers + DESC ordering, `coordinator_service.py:1150-1181`); W6 gave it a local object store seam (F089).

## C. Honest quality — maturity **2.5 / 5**

Per-leg: document/report KG **2**, commerce KG **3**, code graph **3**, edge substrate **2**. The engineering *around* the graphs (locks, debounce, honest degradation, team ACL, server-side drill-in, incremental doc builds, W13 autonomy tools) is genuinely good; the graphs' *content quality machinery* is a generation behind, and the real data says most of the learning surface has never been fed.

### What the real data shows

- **The blob store is the freshest learning-adjacent surface in the DB**: 155 `workspace_graphs` rows rebuilt 2026-07-01 across multiple workspaces (`evidence/data/workspace-graphs.md`) — the KG is real and maintained, unlike `memory_items` (0 rows) or `rag_feedback` (0 rows).
- **But one workspace's graph.json is 42.4 MB in a TEXT column**, another 19.6 MB, with same-size history snapshots doubling the footprint per rebuild (`workspace-graphs.md`). `load_graph` JSON-parses the whole blob on every cold read (`graph_service.py:357-376`) and the LRU caches up to 20 full NetworkX graphs **per uvicorn worker** (`:84,199`). At 4 workers that is potentially >3 GB of duplicated graph RAM for the two big tenants alone.
- **The dedicated persistence tables are dead**: `knowledge_nodes` / `knowledge_edges` = 0 rows ever (`evidence/data/census.md`), yet `analytics_engine.py:285-342` still counts them and `api/system.py:642` surfaces the count — a stats tile that structurally reads 0 forever. The graph actually lives in blobs; the tables and their analytics are zombies.
- **The edge substrate has never eaten organic food**: all 29 edges / 232 affinities / 20 clusters belong to the all-zeros synthetic workspace, frozen 2026-05-05; **none of the 21 real workspaces has a single learned edge** because `tool_execution_logs` gets no organic writes (`evidence/data/operating-graph-edges.md`). Even the synthetic clusters are noisy ("show me my knowledge base" → hot action `platform_create_agent`). Duplicate (from,to) rows appear up to 3× (per-agent scoping rows), so any naive read must aggregate. The only recorded routing eval had `graph (no-edges)` mode at **83.0% — below the 93.6% filtered_schema baseline** (`evidence/data/repo-eval-artifacts.md`), which is why the read side is honestly held dark.
- **Codegraph is a single-project deployment**: 1 project, 7,702 symbols (`census.md`). Real multi-repo, multi-tenant behaviour is untested in production.
- **Extraction quality on real workspace data remains unverified** — the recon captured blob sizes, not contents; nothing in-repo or in the DB measures extraction precision/recall, duplication rate, or hallucination rate. The July-review discipline ("read the actual memories") has never been applied to the graph. Given the memory module's confirmed low quality from the same LLM-write-side pattern, assuming extraction quality is fine would be unjustified.

### Concrete defects (verified in code at HEAD)

1. **Catalog sync clobbers the whole workspace graph.** `_product_sync_impl` ends in `import_graph(..., merge=False)` (`api/shopify.py:568`) — full replacement. Since F032, catalog webhooks fire this automatically on every product/collection/inventory change. Any knowledge the flywheel or document extraction merged in since the last catalog sync — mission syntheses, report entities, roster — is **silently wiped on the next product edit**. The orders path proves the team knows the right pattern (strip only stale `frequently_bought_with` edges, then `merge=True`, `api/shopify.py:808-844`); the catalog path never got it. On a commerce workspace, "knowledge accumulates" is currently false by construction.
2. **No entity resolution.** Merge is exact-snake_case-id last-write-wins (`graph_service.py:1060-1061`). "Acme Corp" / "Acme" / "acme_corporation" are three nodes; re-extraction of the same doc under a slightly different label duplicates rather than converges. No alias sets, no embedding-similarity merge, no LLM disambiguation. This is where graph quality lives or dies (the T1 brief's own warning), and it is absent.
3. **No temporal model.** Nodes/edges carry no valid-from/valid-to, no invalidation; the incremental path is add-only (`:1431-1440`). A contradicted fact ("pricing is $49" → "$99") coexists with its successor indefinitely; nothing prunes deleted documents' nodes until someone manually triggers a full rebuild — and **no scheduled full rebuild exists**.
4. **Paid-for output is discarded.** The extraction prompt requests hyperedges (max 3/doc, `graph_extraction.py:120-136`) and `_normalise_extraction` parses them (`:247-256`) — then `_merge_extractions` drops them on the floor (`graph_service.py:1053-1064`: nodes+edges only). Likewise `surprising_connections` (`:306-308`) and `score_all` (`:300-302`, `:471`) are computed on every build and never exported or used. `graph.html` is written on every build (`:1092-1112`) and has **zero consumers** (repo-wide grep: only the delete endpoint references it) — a potentially multi-MB dead artifact per build.
5. **Multi-worker build races.** Debounce handles, pending buffers, and build locks are all in-process dicts (`graph_service.py:199-210`); prod runs 4 uvicorn workers. Two workers can debounce/rebuild the same workspace concurrently — the per-workspace `asyncio.Lock` doesn't span processes — and the artifact set (graph.json from build A, communities.json from build B) can interleave. Same defect family as F027.
6. **F064 still open (codegraph).** The embedding-failure fallback INSERT omits NOT-NULL `workspace_id` and binds `str(dict)` into JSONB (`codegraph_service.py:1016-1031`) — every fallback row fails, so an embedding outage loses the whole symbol batch instead of degrading to non-semantic search. Two-line fix, confirmed NOT DONE in Phase 0.
7. **F091 widened (commerce).** `map_shopify_catalog`/`map_shopify_orders` still have zero behavioral tests, and both golden journeys (J3, J9) remain skipped — while F032 now runs the catalog mapper automatically on every webhook. A silent mapper regression corrupts every opener/cross-sell with no human in the loop (`evidence/phase0-residual-map.md` F091).
8. **Cross-Mission agent-identity bleed on graph reads.** The `_agent_id` injection for graph/document tools still resolves via `.first()` on *any* running Mission in the workspace (`platform_executor.py:864-888`) — the identical defect family F020 fixed for field tools. Concurrent Missions can read the graph under each other's team scope (too-wide or too-narrow).
9. **Weak NL query.** `platform_query_graph` = whitespace term overlap scoring → BFS from the single top node → token-budgeted text dump (`handlers_graph.py:113-172`). No embedding-seeded matching, no multi-start, no answer synthesis, no community-level (global) query mode despite community reports existing. Agents get a neighborhood dump, not an answer.
10. **8,000-char doc cap** silently discards everything past ~2 pages of every document (`graph_service.py:876-883`) — no chunked multi-pass extraction, no map-reduce. Long PRDs/contracts contribute only their opening.
11. **Miscalibrated confidence on used_after edges**: `wilson_lower_bound(sample_count, sample_count)` (`edge_builder.py:353`) is a monotone function of count (successes≡total), so "confidence" is a dressed-up frequency, not a success-rate bound — only `failed_after` uses Wilson meaningfully (`:382`). And FBT "confidence" = co-count/total-orders is *support*, not confidence in the association-rule sense (`graph_extraction.py:787`).
12. **Webhook edges**: codegraph webhook accepts unsigned payloads when `GITHUB_WEBHOOK_SECRET` is unset (`api/codegraph.py:679-684`); catalog re-sync has no debounce/coalescing or already-running guard, so a bulk edit fires N concurrent full Bulk-Op syncs (`api/shopify.py:346-350,517`). *(Flagged here for completeness; hardening detail belongs to the separate security pass.)*

### What is genuinely good (credit where due)

The cluster-first server-side drill-in (communities → subgraph → expand → path) is the correct large-graph UX pattern and is cleanly implemented with honest truncation flags. Community reports are a real GraphRAG-lite. The deterministic commerce/roster/schema mappers are the right tool (no LLM where none is needed) and the FBT mapper's privacy-by-design is exemplary. The flywheel's single-choke-point design with a provable opt-out is textbook. W13's agent write-parity (index/reindex/sync/status as tools) is a straight autonomy win no OSS graph library ships. Failure handling almost everywhere degrades honestly instead of crashing builds.

## D. Competitive teardown

### Graphiti (Zep) — the direct rival for the document/agent-output leg

Apache-2.0, ~28.3k stars, backends Neo4j/FalkorDB/Neptune/Kuzu ([github.com/getzep/graphiti](https://github.com/getzep/graphiti)). What it does better, specifically:
- **Bi-temporal model with fact invalidation**: every edge carries valid-time and ingestion-time; new knowledge that conflicts is detected via hybrid search and *invalidates* (not deletes) superseded facts ([help.getzep.com/graphiti overview](https://help.getzep.com/graphiti/getting-started/overview)). Automatos has no temporal axis at all (defect C.3).
- **Entity resolution built-in**: extraction dedupes/resolves entities against the existing graph per episode; custom Pydantic entity/edge types constrain the ontology ([github.com/getzep/graphiti](https://github.com/getzep/graphiti)). Automatos resolves by exact string id (C.2).
- **Hybrid retrieval in one call** — semantic + BM25 + graph traversal with rerankers; sub-second query targets. Automatos' graph query is term-overlap + BFS (C.9).
- **Tenant partitioning via `group_id`** on every node/edge, filterable in all queries ([deepwiki.com/getzep/graphiti multi-tenancy](https://deepwiki.com/getzep/graphiti/7.3-multi-database-and-multi-tenancy)) — maps 1:1 onto workspace_id, and could also express Automatos' *scope partitions* (personal/agent/vertical) that today only exist as team_access lists.
- Zep's hosted layer on the same tech reports DMR 94.8% (vs MemGPT 93.4%) and up-to-18.5% accuracy gains with 90% latency reduction on LongMemEval ([arxiv.org/abs/2501.13956](https://arxiv.org/abs/2501.13956)) — evidence the temporal-graph approach pays off on *agent memory* tasks specifically.
- **Where Automatos is ahead**: Graphiti has no deterministic commerce mappers, no FBT co-occurrence, no community reports/titling out of the box, no per-team read ACL semantics (group_id is partition, not row-level team lists), and its LLM-heavy ingestion is costlier per document than one-call-per-doc extraction. It also adds an operational dependency (a graph DB) Automatos doesn't currently run.

### Microsoft GraphRAG / LazyGraphRAG — the query-quality benchmark

- Hierarchical Leiden communities with **multi-level community reports** powering *global search* (map-reduce over community summaries) — answers dataset-wide "what are the themes" questions Automatos' single-level, top-25-titled communities cannot ([microsoft.github.io/graphrag](https://microsoft.github.io/graphrag/)); dynamic community selection cuts global-search token cost 77% ([MS Research blog](https://www.microsoft.com/en-us/research/blog/graphrag-improving-global-search-via-dynamic-community-selection/)).
- **LazyGraphRAG** inverts the economics: NLP-graph indexing at ~0.1% of GraphRAG's original indexing cost, deferring all LLM work to query time; comparable-or-better answer quality at 4% of global-search query cost ([MS Research blog](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)). Automatos pays LLM extraction up-front on every document *and* gets no global-query capability for it — the worst quadrant.
- Where Automatos is ahead: GraphRAG is a batch indexing pipeline, not a live multi-tenant service — no incremental updates (historically), no tenancy, no ACL, no agent tools. Automatos' debounced incremental build is operationally further along than stock GraphRAG.

### Neo4j GraphRAG (neo4j-graphrag-python) — the production-pipeline yardstick

- First-party, supported package: `SimpleKGPipeline` = chunk → schema-guided extraction → **entity resolution (on by default)** → storage, plus a retriever family (vector, vector+Cypher graph traversal, hybrid, text2cypher) ([neo4j.com KG-builder guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html), [package overview](https://neo4j.com/developer/genai-ecosystem/graphrag-python/)). It demonstrates the *shape* a mature extraction pipeline takes: pluggable resolver, schema enforcement, lexical-graph provenance (chunk→entity links). Automatos has provenance (`source_file`) but no resolver and no schema enforcement beyond prompt text.
- Where Automatos is ahead: Neo4j's package assumes you run Neo4j; it has no multi-tenant story, no communities/titling by default, no commerce specifics.

### LightRAG — the pattern Automatos already half-adopted

- EMNLP-2025; dual-level retrieval (low-level entity + high-level theme keys) over a graph+vector index; **incremental set-merge updates without global rebuild**; ~60% indexing-token reduction and roughly half the query latency vs GraphRAG ([github.com/hkuds/lightrag](https://github.com/hkuds/lightrag), [arxiv.org/abs/2410.05779](https://arxiv.org/abs/2410.05779)). Automatos cites LightRAG for its drill-in (`graph_service.py:626-629`) but did not adopt the part that matters for answer quality: retrieval keyed on both specific entities and abstract themes, fused with vectors. Its incremental merge is also *cleaner* than Automatos' (no clobbering import path).

### Sourcegraph / SCIP — the code-graph ceiling

- **Precise, compiler-grade indexing** via SCIP (protobuf, language-indexer-emitted) vs Automatos' tree-sitter heuristics + unambiguous-single-candidate fuzzy call resolution (`codegraph_service.py:1074-1084`) ([sourcegraph.com/blog/announcing-scip](https://sourcegraph.com/blog/announcing-scip)). Cross-repository go-to-def/find-refs with version-aware symbol resolution ([cross-repo navigation](https://sourcegraph.com/blog/cross-repository-code-navigation)); a continuously updated, org-shared code graph feeding AI context ([context comparison](https://sourcegraph.com/resources/context-compare)). Automatos' single-project, name-collision-prone resolution will produce wrong call graphs in any codebase with overloaded names — fine for repo-map context, unreliable for "what breaks if I change X" answers.
- Where Automatos is ahead: Sourcegraph is a product, not an embeddable library; Automatos' codegraph is workspace-tenanted, agent-tool-native, and pgvector-searchable inside its own stack, with PageRank repo-maps (the Aider trick) that Sourcegraph doesn't frame for LLM token budgets.

**Net position:** Automatos is competitive on *operational shape* (tenancy, ACL, tools, incremental, drill-in UX) and genuinely differentiated on the commerce leg; it is one-to-two generations behind on *graph content quality machinery* (entity resolution, temporal validity, hybrid retrieval, global/theme-level query) and pays LLM indexing costs the field has learned to defer.

## E. Build / extend / adopt / replace — verdict

**Split verdict by leg** (one verdict would be wrong — these are different problems):

1. **Commerce KG: KEEP + EXTEND in-house.** Nothing external does Shopify-catalog→typed-graph + privacy-safe FBT as a library; the deterministic mappers are correct engineering and they feed the platform's one live autonomous consumer. The work is repair, not replacement: scoped catalog re-sync (kill the `merge=False` clobber), mapper behavioral tests, webhook debounce.
2. **Code graph: EXTEND in-house.** Tree-sitter + pgvector + PageRank repo-maps is a sound Aider-class midpoint, already agent-tool-native. Sourcegraph is a product (and an operational dependency) that would replace far more than needed; SCIP-precise indexing is the eventual upgrade path *if* agents start making correctness-critical refactoring decisions from call graphs — adopt SCIP indexers then, not now. Fix F064 immediately.
3. **Document/agent-output KG (the extraction+temporal core): ADOPT-TRIAL Graphiti — gated on thesis T1.** The missing capabilities (entity resolution, bi-temporal invalidation, hybrid graph retrieval, scope partitions) are exactly Graphiti's core, Apache-2.0, with `group_id`→workspace mapping and Pydantic ontology types that could encode Automatos' node taxonomy. Integration shape: run Graphiti+FalkorDB (or Neo4j) as a service; route `ingest_agent_output` and document-ingest pendings to Graphiti episodes per workspace; keep `DbWorkspaceClient` exports (or a projection job) feeding the existing drill-in UI and `platform_graph_*` tools during transition. Rough cost: one graph-DB container + the same order of LLM extraction spend (Graphiti's per-episode calls ≈ today's per-doc call + resolution overhead); engineering ≈ 2–4 weeks for a faithful trial. **Do not run two permanent substrates** — the trial's exit criterion is T1's verdict (converge memory+knowledge on one temporal graph, or stay hybrid). If T1 says stay hybrid, the fallback is building resolution+invalidation in-house — justified only then, because a proven Apache-2.0 implementation exists and building it is not differentiating work.
4. **Operating-graph edge substrate: KEEP as-is.** Construction is sound (Wilson on failure rates, idempotent rebuilds, tenant scoping); its problem is *diet* (no organic telemetry) and *read-side consumption*, both owned by the tool-selection dossier. Do not add machinery here until real edges exist.
5. **Kill list (this module):** `graph.html` export (zero consumers); `surprising_connections`/`score_all` dead computation (or export them and give them a UI); hyperedge prompting (or actually build hypergraph support); `knowledge_nodes`/`knowledge_edges` tables + their analytics tiles (`analytics_engine.py:285-342`, `api/system.py:642`) — wire them or drop them.

## G. Quality metric

**Today's numbers:** 155 graph artifacts fresh to 2026-07-01; 0 organic learned edges across 21 real workspaces; 1 codegraph project / 7,702 symbols; extraction quality **unmeasured** (no gold set, no eval, no recorded inspection of real graph contents); `graph (no-edges)` routing mode 83.0% vs 93.6% baseline (synthetic, 2026-05-05).

**Proposed metric set (feeds T3):**
- **Extraction quality (the headline):** a ~20-document per-vertical gold set with labeled entities/relations → precision/recall per build; plus two cheap always-on proxies computable from every build artifact: *duplicate-node rate* (near-identical labels per 100 nodes, embedding-sim > 0.9) and *dangling-edge drop rate* (edges discarded at `graph_service.py:1439`).
- **Freshness SLO:** `max(documents.updated_at, catalog change) − workspace_graphs.updated_at` per workspace — measurable today with one SQL view.
- **Retrieval usefulness:** `platform_graph_*` call volume + success/empty-answer rate from `tool_execution_logs` (currently ~0 organic — the number itself is the finding); widget opener acceptance (click/convert) as the FBT-edge quality proxy.
- **Codegraph correctness:** zero-result rate from `codegraph_query_logs`; a 50-symbol spot set asserting call-graph edges against ground truth per indexed repo.
- **Community report quality:** LLM-judge rating of title/summary faithfulness on a sampled 20 communities per month, calibrated against a small human-labeled batch.

## H. Cost note (informational)

- **KG full build:** 1 LLM call per document (≤8k chars in, ~1–2k tokens out) + ≤25 community-title calls. A 644-doc workspace ≈ ~670 calls; at the gpt-4.1-mini-class rate recorded in the routing eval (~$0.0007/call) ≈ **$0.50–2 per full rebuild**; premium-model config multiplies this 10–50×. Incremental builds cost 1 call per changed doc — cheap. Note the hyperedge portion of every one of those calls is currently discarded (C.4).
- **Commerce sync:** no LLM; cost is Shopify Bulk-Op latency (minutes) + one full-graph re-cluster + a 2×blob write (graph + history) — the 42 MB tenant writes ~85 MB of TEXT per catalog webhook burst.
- **Codegraph:** ~1 embedding per symbol (7.7k symbols ≈ cents), re-paid only for changed files thanks to hash-skip.
- **Edge builder:** nightly embeddings for distinct user queries in the 30-day window; trivially cheap at current volume (zero organic).
- **Storage:** history snapshots ×30 per workspace of multi-MB blobs in Postgres TEXT — the dominant marginal cost at scale, and it ages badly (C, real-data).

## I. UX / surface

**Exists:** `KnowledgeGraphExplorer` (cluster-first drill-in, 354 lines) on the shared `GraphView` shell (PRD-165; also hosts codegraph + field viz), editable community labels, node provenance (`source_file`) in payloads, `graph` primitive heartbeat wired to the health surface.

**Concrete changes, by value:**
1. **Graph freshness chip + last-build status** on the KG panel and Command Center (data already exists: `meta.last_built`, primitive heartbeat, `workspace_graphs.updated_at`). Today a user cannot tell a 3-month-stale graph from a fresh one.
2. **Surface `latest_diff.json` as a "what your graph learned" feed** in Command Center — the diff artifact is computed and stored on every build (`graph_service.py:1191-1232`) and has no UI consumer. This is the cheapest possible "the platform is learning" moment, and it is honest (real diffs).
3. **Provenance facets in the explorer** — filter nodes by source (`shopify://catalog`, `platform://agent_roster`, document, report). The data is on every node; the UI doesn't expose it. On commerce workspaces this also makes the catalog-vs-knowledge split (and the C.1 clobber, until fixed) visible instead of mysterious.
4. **Extraction review queue (lightweight):** the community-label editing pattern (`edited` flag survives rebuilds) generalizes — let users merge/rename/delete nodes with the same survive-rebuild semantics. This is the human-in-the-loop lever for extraction quality and costs one JSON overlay.
5. **Kill the forever-zero "knowledge nodes" stat tile** (`api/system.py:642`) — replace with real blob-store stats (nodes/edges/communities from meta.json).
