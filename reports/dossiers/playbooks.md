## A. What it is

Playbooks are Automatos's repeatable, multi-step agent pipelines — the "cron jobs with brains": an ordered list of steps, each step an agent + prompt template (optionally a deterministic `pre_exec` shell command or a `generate_document` step), launched from seven surfaces (manual HTTP, playbook webhook, cron, Composio trigger, workspace webhook, auto-retry, and Auto's own platform tools) through one consolidated `PlaybookEngine` seam. It is the platform's **only currently-live autonomous production line** — the daily social-content playbooks that generated most of the 2,242 client-visible deliverables — and simultaneously the module whose failure story is the worst on the platform: it has been failing silently every day since ~2026-06-16 while marking its own board tasks "done."

## C. Honest quality — maturity **2.5 / 5**

**What is genuinely good (and proven by data):**
- **It runs, daily, from real triggers.** This is the only intelligence/execution module whose production activity is current and real rather than synthetic: 735 executions, cron firing through 07-03, five trigger types in the data (`cron_scheduler`, `webhook`, `composio_trigger`, manual, `auto_retry` lineage columns). Nearly all 2,242 client-visible deliverables came off this line.
- **The consolidation is real.** All seven launch sites verifiably import the engine seam (B, above) — the July "scattered launch sites" defect was actually fixed, with a parity test (`tests/test_playbook_launch_parity.py`, cited in the seam docstring `playbook_engine.py:77-79`).
- **The step executor is the platform's best-integrated runtime.** Chatbot-parity components (ContextService RECIPE mode, Composio per-action SDK search with hint fallback, tool router), plus defenses that show scar tissue from real production: empty-completion retry with model fallback (`recipe_executor.py:482-522`), Composio call dedup (`:599-605`), ms/s timeout normalization (`:1132-1156`), workspace-disabled gates, cancel that actually aborts the in-flight HTTP call.
- **Execution rows are honest.** `_fail_execution` records `failed` + `error_message` on `RecipeExecution` correctly — the memory spam text itself proves the failure path executes (`"The playbook execution cron-… failed. … Error code: 402"`).
- **Auto can author playbooks.** The 11 platform tools make playbook creation/scheduling/execution fully agent-drivable — a real autonomy asset most competitors lack.

**Concrete defects, with evidence:**

1. **Failed-marked-done is systemic and current — the module's failure plane lies.** `complete_recipe_board_task` unconditionally sets `done` (`board_task_bridge.py:110-113`); the reconciler closes orphaned board tasks as `done` too (`task_reconciler.py:145-152`); there is no `playbook_failed` notification type (`notification_dispatcher.py:54-55`) and `_fail_execution` dispatches nothing. Real-world consequence, verbatim from the data: playbook LLM steps have failed with OpenRouter 402 **every day since ~2026-06-16**; deliverables and `playbook_complete` notifications both stop that date; board_tasks closes those runs `done` daily (194 done-with-error, 484 done-without-result); only 2 tasks in the table's entire history are `failed` — both from a *different* lane (board-tasks.md, notifications.md, deliverables.md). **The platform's one live autonomous production line has been down ~2.5 weeks and nothing surfaced it.** For a module judged by "can Auto operate autonomously for clients," this is disqualifying behavior: autonomy without honest failure signaling is worse than no autonomy.

2. **The learning loop has been silently severed at the read end for ~3.5 months.** Commit `eb7bf8930` (2026-03-17, "rename recipes to playbooks across platform") renamed `core/services/recipe_memory_service.py` → `playbook_memory_service.py` and `recipe_learning_service.py` → `playbook_learning_service.py` (git `R075`/`R091`), but **three import sites still reference the deleted module names**: pre-run memory retrieval `recipe_executor.py:1118` (`from core.services.recipe_memory_service import RecipeMemoryService`), post-run auto-learning `:1742` (`recipe_learning_service`), and the `/learn` endpoint `workflow_recipes.py:1231`. The first two are inside `except Exception` blocks that log at info/warning and continue — so **playbooks write memories every run but have never read one back since March; `auto_learning` does nothing; `POST /{id}/learn` 500s on every call.** This is confirmed independently by the data: `memory_access_log` shows recall last exercised 2026-03-11 (memory-short-term.md) — days before the rename landed.

3. **Playbook memory writes are the platform's #1 memory polluter.** Per failing run the service stores the same failure twice (playbook-level + step-level, both `content_type='playbook_summary'`, `playbook_memory_service.py:104-124,165-189`) with no dedup or repeat-error suppression — 1,255 rows, 57% of all platform memory, mostly identical daily 402 text, `promoted_to_l3=false` on every one (memory-short-term.md). Combined with defect 2, the loop is write-only spam: never read, never promoted, never deduplicated.

4. **No failure classification or circuit breaker.** A permanent billing error (402) is treated identically to a transient blip: the cron refires daily into the same wall, step retries are immediate with no backoff (`recipe_executor.py:1492-1569`), the reconciler only retries *stalls* (not classified errors, `task_reconciler.py:170-207`), and nothing ever pauses a playbook that has failed N days running. 17+ consecutive identical daily failures produced zero escalation.

5. **Step token accounting undercounts.** `_execute_step` records only the **final** LLM response's `total_tokens` (`recipe_executor.py:720-724`), not the sum across tool-loop iterations — so a 10-iteration step reports ~1 call's tokens. This directly feeds the dollar-ceiling's `used_usd` (`:1188-1199`), making the (already opt-in, flat-rate — phase0 F059/F060) budget line vacuous in practice. The auto-*report* is more honest because it rolls up server-side `llm_usage` (`:113-126`).

6. **Linear-only pipelines.** No conditional branching, no parallel steps, no joins; the FE collects `pass_to` but the executor ignores it (B). Fine for today's 1–6-step content pipelines; a real gap against every competitor below.

7. **Naming split-brain and squatters.** Canonical term is Playbook (CLAUDE.md §10) but the API is `/api/workflow-recipes`, the model is `WorkflowTemplate` aliased `WorkflowRecipe`, the table is `workflow_recipes`, board tasks say "Recipe:", `created_by_type='recipe'` — while the canonical `/api/playbooks` prefix is squatted by a dead-on-arrival miner router (F069) and a 1,424-line legacy fifth engine stays mounted with one live execute endpoint (F078). Both flagged in July; neither retired.

**Score justification:** the machinery is a solid 3.5 — consolidated seam, production-hardened step executor, real daily usage, honest per-run records, agent-authorability. But judged by the North Star, the module's *systemic* behavior failed its one real client-facing job for 17+ days without telling anyone, its self-improvement story (memory/learning/miner) is severed or fake, and its budget line doesn't price reality. Strong engine, no instrument panel, no learning: **2.5/5**.

## D. Competitive teardown

The honest frame: Playbooks compete with two families — workflow-automation products (n8n, Zapier) and agent-orchestration frameworks (LangGraph, CrewAI Flows), with Temporal as the durability ceiling. Automatos's per-step *context quality* (a full platform agent with workspace memory, RAG, Composio per-action search, platform tools) is richer than an n8n/Zapier step; on the axis that defines this category — **reliability and failure observability** — it is currently behind all of them.

**n8n** — the OSS automation bar. Failure is a *first-class routed event*: every workflow can designate an **error workflow** fired by a dedicated **Error Trigger node** that receives the failed execution's details ([docs.n8n.io/flow-logic/error-handling](https://docs.n8n.io/flow-logic/error-handling/), [Error Trigger node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.errortrigger)); per-node **Retry On Fail** with configurable attempts/wait, and per-node **On Error** modes — stop / continue / **continue-using-error-output**, which gives each node a second output lane so failures branch into handling paths. Plus visual DAG branching and merge nodes, and 2026 guardrail patterns (manual approval gates, memory/context scoping) in its AI-agent workflows ([n8n AI features guide](https://chronexa.io/blog/n8n-ai-agents-features-2026-complete-guide), [error-handling best practices](https://n8nlab.io/blog/n8n-error-handling-best-practices)). **Better than Automatos at:** failure routing, per-node error semantics, branching. **Behind Automatos at:** agents-as-steps with platform-native memory/tools/marketplace; n8n's AI Agent node carries no equivalent of the workspace context substrate.

**LangGraph** — the durability/state bar for agent pipelines. **Durable execution**: checkpointers (e.g. PostgresSaver) snapshot graph state at every step so a crashed or interrupted run **resumes exactly where it left off**, not from step 1 ([LangGraph durable execution docs](https://docs.langchain.com/oss/python/langgraph/durable-execution)); per-node **retry policies** (backoff, max attempts, exception filters); human-in-the-loop **interrupts** that pause without holding threads and resume on human input hours later; **time-travel** to rewind to any checkpoint, edit state, re-execute ([HITL time-travel writeup](https://christianmendieta.ca/human-in-the-loop-ai-time-travel-workflows-with-langgraph/), [ZenML on the durable runtime](https://www.zenml.io/blog/langgraph-durable-runtime)). Worth noting the counter-critique that checkpoint-replay alone still falls short of true durable execution for external side effects ([Diagrid](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows)). **Better at:** mid-run resume (Automatos's reaper *kills* orphans and the reconciler re-runs from scratch), pause-for-approval inside a run, per-node retry policy. **Behind at:** it's a framework, not a product — no marketplace, no cron/webhook/trigger surface, no agent-authorable tools out of the box.

**CrewAI Flows** — the closest OSS analog to "playbook as typed pipeline." Event-driven `@start/@listen/@router` methods; `or_()`/`and_()` join conditions; typed **Pydantic state** vs Automatos's string scratchpad; **`@persist`** state snapshots (SQLite default) with **resume and fork by run UUID**; `@human_feedback` pause-for-approval; built-in `flow.usage_metrics` token rollup ([CrewAI Flows docs](https://docs.crewai.com/en/concepts/flows)). **Better at:** conditional routing, joins, typed state, resumable runs. **Behind at:** persistence/HITL are code-level constructs for developers; no hosted trigger surface, no marketplace, no per-workspace concurrency/plan governance.

**Zapier** — the mainstream ceiling for "my automation failed" UX, which is the exact axis Playbooks failed: multi-path decision trees (Paths), **custom retry rules that classify transient errors** into wait-and-retry, error alerting to Slack/email as table stakes, conditional human-approval steps, and **cost-cap alerts that halt AI calls at a spend threshold** ([Zapier AI orchestration guide](https://zapier.com/blog/ai-orchestration-workflows/), [Zapier error handling & paths guide](https://techelix.co/blogs/zapier-error-handling-paths-sub-zaps-2026/)). Zapier Agents/Canvas/Copilot moved it into goal-directed agent territory over 2025-26 ([Hatchworks n8n-vs-Zapier](https://hatchworks.com/blog/ai-agents/n8n-vs-zapier/)). **Better at:** failure UX, error classification, spend caps, NL workflow authoring for non-developers. **Behind at:** depth per step — no real agent runtime, no workspace substrate.

**Temporal** (calibration point, one line): the industrial answer to everything in defect-class 1/4 — every step an Activity with automatic retries, state persistence, crash recovery and full per-step visibility; its OpenAI Agents SDK integration went GA 2026-03-23, and OpenAI/Replit/Lovable run agents on it ([Temporal + OpenAI Agents SDK](https://temporal.io/blog/announcing-openai-agents-sdk-integration), [InfoQ](https://www.infoq.com/news/2025/09/temporal-aiagent/)).

**Where Automatos actually stands:** ahead of all four on *step intelligence in its own platform context* (agents with memory/RAG/tools/marketplace, agent-authorable pipelines) and on trigger breadth as a product (cron + three webhook flavors + chat + board + marketplace in one tenant-scoped surface). Behind n8n/Zapier on failure routing and alerting (the current outage is the proof), behind LangGraph/CrewAI on resume/checkpointing and conditional flow, behind everyone on error classification. None of the four could replace Playbooks without losing the platform substrate — but every one of them would have surfaced the 402 outage on day one.

## E. Build / extend / adopt / replace — verdict: **EXTEND**

**Extend the in-house engine; do not adopt an external workflow engine now.** Reasoning against each alternative, per §2's adopt-bias:

- **Adopt n8n / Zapier (embed or replace)?** No. The differentiator of Playbooks is that a step *is* a platform agent — ContextService RECIPE mode, workspace memory, Composio per-action tools, platform tools, marketplace cloning of agent dependencies. Embedding n8n would sever that substrate (steps become HTTP calls into the platform) and duplicate trigger/tenancy/governance surfaces. The features Playbooks actually lacks from n8n/Zapier — failure routing, alerting, error classification — are **days of in-house work** (a notification event type, a status write, an error classifier), not an engine.
- **Adopt LangGraph as the executor?** Not yet. The current library of real playbooks is 1–6 **linear** steps; a checkpoint-resume graph runtime would rewrite the executor and abandon the chatbot-parity component path (PRD-50) for capabilities (branching, mid-run resume) no current playbook uses. Revisit if/when client playbooks need conditional flow or >30-min multi-step runs where full re-run is too costly; the step-level `step_results` persistence (`recipe_executor.py:1636`) already gives 80% of the resume substrate in-house (J-6).
- **Adopt Temporal for durability?** Overkill at today's scale (hundreds of runs/month, single leader-locked scheduler). The honest durability posture — crash-marked-failed + reconciler retry with lineage — is adequate *once failures are visible*. Keep Temporal as the known ceiling if Playbooks becomes the client-facing automation product at volume.
- **Keep building (net-new features)?** Only the failure plane, learning-loop repair, and retirement list (J-1..5). Explicitly **not** a DAG engine ahead of demand (honest negative: branching is a competitor gap that currently has no North-Star pull — zero real playbooks need it).

One **replace** verdict inside the module: the PlaybookMiner vertical (`api/api_playbooks.py` + `modules/learning/playbooks/miner.py` + the stubbed `PlaybooksPanel` miner UI) is dead-on-arrival demo code squatting the canonical route — **delete it** (kill-list), don't fix it. Mining "which step sequences recur" is better served later by the eval/telemetry harness (T3) with real `recipe_executions` data.

## G. Quality metric

**Primary metric — Playbook run success rate** (`completed / (completed+failed)` over trailing 7d, per workspace and platform-wide), straight off `recipe_executions.status` — the rows are honest today. The UI already computes a per-playbook `success_pct` (`playbook-metrics-widget.tsx:63-65`); it needs to become a *tracked, alerting* number, not a widget. **Number today:** not precisely computable from the sampled data, but bounded by it — the four daily content playbooks in the sampled workspace have failed every run since ~2026-06-16 (memory-short-term.md, board-tasks.md), i.e. ~0% for the platform's only active playbook workspace over the last 2.5 weeks.

**Secondary metrics:**
- **MTTD of playbook failure** (failure → first human-visible signal). Today: **infinite** (17+ days, no signal). Target after J-1: < 1 tick.
- **Deliverable throughput** (deliverables/day from playbook-sourced runs) — today 0 since 06-16, vs a steady daily rate before (deliverables.md).
- **Retry recovery rate** (`retry_of` chains ending in `completed` / all chains) — measures whether the reconciler's retries ever rescue anything or just re-fail.
- **Memory hygiene ratio** (unique failure signatures / playbook_summary rows written) — today ≈ 1 : many hundreds; target ~1:1 after J-2 dedup.
- **Step token-accounting error** (report-rollup tokens vs sum of step `tokens_used`) — today large by construction (defect 5); target <5% after J-4.

These feed T3 directly: playbooks is the easiest module to put on the harness first because its ground truth (run status, deliverable produced or not) is binary and already stored.

## H. Cost note (informational)

- **Per successful run:** steps × tool-loop iterations × LLM calls. The auto-report already computes true per-run cost from `llm_usage` (`recipe_executor.py:113-126,146-155`) — e.g. the sampled mission-scale analog burned 264k tokens across 7 tasks (memory-short-term.md); typical 1-3-step content playbooks are far smaller. At the eval-recorded gpt-4.1-mini rate (~$0.0007/call, repo-eval-artifacts.md) a 3-step × 5-iteration playbook is on the order of a cent; agent models priced higher scale linearly.
- **Per failed run (the current reality):** ~$0 LLM (402 rejects the first call) but non-zero platform cost: 2 memory rows + 1 agent_report + 1 board task + heartbeat writes per run, daily, forever — pure noise mass that actively degrades the memory module (57% pollution).
- **Ceiling math is currently fictional** (defect 5 + flat `COORDINATOR_COST_PER_1K_TOKENS` rate, phase0 F059): treat any `cost_ceiling` on a playbook as advisory until J-4.

## I. UX / surface

**Today:** `/playbooks` (Studio → Assignments hub tab), a good grid with run-dots + latest-run link into the Execution Kitchen, create/view modals with step builder (incl. `pre_exec` and schedule config), marketplace tab, and a Command Center metrics widget with per-playbook success%. Solid bones; three structural problems: (1) failure is invisible end-to-end — the board shows green "done" cards for failing runs, notifications are silent, and the success% widget is passive; (2) the naming split (Playbooks UI over `workflow-recipes` API and "Recipe:" board cards) leaks legacy vocabulary to users; (3) a dead classic `PlaybooksPanel` with a stubbed miner button ships in the bundle.

**Concrete changes (IA/UX):**
1. **Failure-first Command Center strip.** "Playbooks needing attention": any playbook whose last run failed or success% < threshold, with the error class ("Provider billing — OpenRouter 402"), days-failing counter, and pause/retry/open-run actions. The metrics widget's data source already exists; this is wiring + alert routing.
2. **Honest board cards.** Recipe-mirror tasks show `failed` (red) when the execution failed; keep the "wrapper task vs actionable tickets" distinction the bridge comment intends by *linking* the run detail, not by lying about status.
3. **Run detail = step timeline.** `step_results` + S3 `log_url` + `retry_of` lineage are all persisted; render attempts, per-step duration/tokens/tool summaries, and the retry chain. Today the Execution Kitchen link exists but retry lineage has no UI.
4. **Playbook health on the playbook card:** last-N run dots already exist — color them by *error class*, and add a "paused (failing since …)" badge once J-3 lands.
5. **Route/term consolidation:** retire `/api/workflow-recipes` in favor of `/api/playbooks` (after evicting the miner squatter), rename `Recipe:` task titles and `created_by_type='recipe'` stamps at write-time to `playbook` (data migration optional), delete the classic `PlaybooksPanel` stub.
6. **Auto as operator:** give Auto a `get_playbook_health` platform tool (12th) so the agent that *authors* playbooks can also *notice* they're failing and raise/act on it — closing the loop the heartbeat-review tasks (`"Review FIXER heartbeat — {'status':'error'}"`, board-tasks.md) already gesture at.

## J. Upgrade path (prioritised, impact × effort, judged by North-Star impact)

1. **Make failure visible — the outage-class fix.** *(Impact: highest on the platform; Effort: S — ~1 day.)* Add `playbook_failed` to `NotificationDispatcher`'s event types (`notification_dispatcher.py:54-55`) and dispatch it in `_fail_execution` (`recipe_executor.py:1929-2014`, `action_required` semantics); change `complete_recipe_board_task` to set `failed` when `success=False` (`board_task_bridge.py:110-113` — the board's `failed` lane already exists, proven by the 2 heartbeat-lane rows on 07-03); same for the reconciler's orphan close (`task_reconciler.py:145-152`). This single change converts the 17-day silent-outage class into same-hour signals. Nothing else in this dossier matters until this lands.
2. **Reconnect the severed learning loop.** *(Impact: high; Effort: S — 3 import lines + class names.)* Fix `recipe_executor.py:1118,1742` and `workflow_recipes.py:1231` to import `playbook_memory_service.PlaybookMemoryService` / `playbook_learning_service.PlaybookLearningService`. Then fix write quality: dedup by error-signature hash (same playbook + same error class within N days → increment a counter instead of new rows) and stop double-writing playbook+step memories for single-step playbooks (`playbook_memory_service.py:104-189`). Add a regression test that imports every `core.services.*` module referenced anywhere (this bug class — rename + swallowed ImportError — survived 3.5 months and would again).
3. **Failure classification + circuit breaker.** *(Impact: high; Effort: M.)* Classify step errors (billing/auth/quota = permanent; 5xx/timeout/empty = transient). Transient → backoff between step attempts (today immediate, `recipe_executor.py:1492-1569`). Permanent → fail fast, **pause the playbook** (`schedule_config.enabled=false` equivalent) after K consecutive failures, emit `action_required`. A paused-not-refiring playbook would have saved 17 days of daily 402s and ~2,000 junk memory rows.
4. **Fix token accounting.** *(Impact: medium; Effort: S.)* Accumulate `response.usage` across all tool-loop iterations in `_execute_step` (`:720-724`); when the W4 registry-backed pricing (`modules/policy/pricing.py`) is adopted platform-wide (F059), price playbook ceilings with it instead of the flat rate (`:999-1002`).
5. **Retirement slice (human-gated per §12.6).** *(Impact: medium — cuts confusion + a mounted fifth engine; Effort: M.)* (a) Unmount `api_playbooks` + delete the miner vertical and `PlaybooksPanel` stub (F069 kill-list); (b) migrate `jira_bug_triage` to a seeded Playbook (its 6 steps map cleanly onto step schema + `pre_exec`) or a Mission, then unmount `workflows.py` + `workflow_templates` (F078); (c) route rename `workflow-recipes` → `playbooks` with FE repoint (~13 hooks in `use-playbook-api.ts` → api-client methods).
6. **Step-level resume.** *(Impact: medium; Effort: M.)* The executor already persists `step_results` after every step (`recipe_executor.py:1636`); teach the reconciler's retry to seed the scratchpad from completed steps and start at the first incomplete one instead of re-running everything. This is the pragmatic 80% of LangGraph-style durability with zero framework adoption.
7. **Conditional steps — demand-gated, not now.** *(Impact: low today; Effort: L.)* Branching/joins/`pass_to` execution only when a real client playbook needs it (honest negative: every current playbook is linear; building a DAG engine now is polish, not North-Star capability). If demand arrives, *that* is the moment to re-run the LangGraph/CrewAI adopt-vs-build question (E) rather than extending in-house.
8. **Cross-module flags (owned elsewhere, recorded here):** playbook runs still have no ask/approval gate (`SUBJECT_PLAYBOOK_RUN` defined but unused — governance module scope, phase0 F060 gaps) and playbook Composio steps execute outside the W4 policy chokepoint (`recipe_executor.py:655`, phase0 F085) — both belong to the governance dossier's backlog but land in this module's files.

---

**Bottom line.** Playbooks is the platform's most *real* execution module — genuinely consolidated, production-scarred, agent-authorable, and the only line that ever shipped daily client-visible output. It is also the module whose data tells the most damning story: for 2.5 weeks it failed every day, marked itself done, told no one, and spammed the memory system with the evidence. Two of the three fixes that would have prevented that are one-day changes (J-1, J-2). Fix the instrument panel before touching anything else; the engine underneath deserves it.
