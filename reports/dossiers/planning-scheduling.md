## A. What it is

This module is the platform's **temporal plane**: everything that makes Auto and the agents act *on their own clock* instead of waiting for a user message. Concretely it is (1) a single fcntl-elected APScheduler leader hosting roughly ten background job families — orchestrator/agent **heartbeats**, cron **playbook** firing, agent-created **scheduled tasks**, the Mission coordinator tick, memory/field/edge/Composio maintenance jobs, and the weekly **HARNESS** self-optimization sweep; (2) the **planning intelligence** read/write halves — the PRD-164 planning context pack consumed by every planner, and the mission-memory writes that feed it; and (3) the **PRD-162 unified schedule truth** — one stateless, DB-first answer to "what runs next?" shared by the calendar, the scheduler, and the `platform_get_schedule` tool. Judged by the North Star, this module *is* the autonomy substrate: if it fires reliably and produces signal instead of noise, Auto runs the workspace; if it doesn't, the platform is a chat app.

## B. What it does (real implementation + data path)

### B1. One leader, one scheduler, ~10 job families

Boot-time leader election is an exclusive non-blocking flock on `/tmp/automatos_scheduler.lock` (`orchestrator/main.py:354-366`); the winning uvicorn worker starts the `UnifiedScheduler` singleton — an `AsyncIOScheduler` with a Memory job store, Redis job store only if `REDIS_URL` is set (`orchestrator/services/scheduler.py:39-52`). Losing workers skip silently (`main.py:458-461`). The leader then mounts, in order: HeartbeatService, PlaybookScheduler, TaskReconciler, MemoryJobScheduler, FieldPromotionJob, EdgeBuilderScheduler, ComposioSyncScheduler, agent ScheduledTasks, CoordinatorService, HarnessService (`main.py:368-454`). Every family is fail-soft (`except: logger.warning`) — a family that fails to mount is logged and skipped, never fatal, never surfaced to a UI.

Flag reality of a default deploy (probe question 1): `HEARTBEAT_ENABLED`, `RECIPE_SCHEDULER_ENABLED`, `COORDINATOR_ENABLED`, `HARNESS_ENABLED` all default **true** (`orchestrator/config.py:620-623`), so the whole loop plane runs out of the box. The one dark surface is HARNESS *actuation*: `HARNESS_SELF_MANAGEMENT_ENABLED` defaults **false** (`config.py:627`), so `/api/harness/prescriptions/{rx}/approve` answers HTTP 409 on out-of-the-box config (`api/harness_commands.py:133-135` → `api/harness.py:72-75`).

### B2. Heartbeats (the platform's pulse)

Config lives as JSON blobs on `workspace.settings.orchestrator.heartbeat` and `agent.configuration.heartbeat`, loaded and scheduled at boot (`orchestrator/services/heartbeat_service.py:264-301`). Intervals become fixed-time cron triggers through the shared `schedule_util.interval_to_cron` (`heartbeat_service.py:307-321`; `services/schedule_util.py:34-61`), so calendar and firing agree (PRD-162).

- **Orchestrator tick** (`_orchestrator_tick`, `heartbeat_service.py:519-607`): active-hours guard with fail-open on config error (`:387-454`), DB-backed cooldown dedup so restarts don't double-fire (`:460-513`), then an LLM tool-loop tick: ContextService builds the prompt in `HEARTBEAT_ORCHESTRATOR` mode, `PlatformActionExecutor` executes tool calls up to `AGENT_HEARTBEAT_MAX_TOOL_ITERATIONS` (`:609-783`), with idle-in-transaction hygiene per turn (`:704`). Shallow no-LLM fallback counts agents (`:785-827`).
- **Agent tick** (`_agent_tick`, `:829-988`): executes through `AgentFactory.execute_with_prompt` with `ContextMode.HEARTBEAT_AGENT` (`:924-929`) — which since W9 includes the workspace field-memory digest (**F021 fixed**: `modules/context/modes.py:80-88`, section at `modules/context/sections/field_memory.py:32-126`), so recurring agents are no longer amnesiac by config.
- **Every tick fans out**: a `heartbeat_results` row (`:1101-1143`) with a best-effort `objective_met` classifier (`:1145-1169`), a notification through `NotificationDispatcher` (`:1175-1299`), and an auto-created report (`:1514-1733`). Per-agent `report_to` overrides: `auto` creates a BoardTask assigned to Auto (`:1305-1384`), `webhook` POSTs directly (`:1386-1424`).
- **Daily summary** at 01:00 UTC (`:176-184`, `:994-1095`): counts the last 24 h of `heartbeat_results` and stores the roll-up into memory **twice** — once via `smart_memory.store_conversation` wrapped as a fake `User:/Assistant:` transcript (`:1049-1062`) and once via `unified.store_short_term` as `heartbeat_log` (`:1064-1089`).
- **Mem0 health probe** every 30 s (`:186-210`, `:221-258`): pings mem0 and, per workspace with an active orchestrator heartbeat, writes one `primitive_check` row into `heartbeat_results` via `emit_primitive_finding` (`:53-123`, `tokens_used` hardcoded 0 at `:105`).

### B3. HARNESS (PRD-121 weekly self-optimizing loop)

One sweep job, Sundays 02:00 UTC (`orchestrator/services/harness_service.py:34,91-105`), iterating opted-in workspaces (on by default, `:352-364`). Per workspace, a 5-phase pipeline (`_harness_tick`, `:255-346`): **COLLECT** — 10 platform analytics tools concurrently (`:468-518`); **DIAGNOSE** — pure rule-based deltas vs the previous baseline, ±10 % thresholds classify REGRESSION/IMPROVEMENT (`:524-630`), plus sustained tool failures from the tool-routing graph (W4-S10, `:646-688`); **PRESCRIBE** — exactly three heuristics (heartbeat-interval widening at risk 2, "consider cheaper model" at risk 3 with the literal placeholder value `review_needed`, description refresh at risk 1; `:731-884`) plus regression rollbacks and risk-3 tool removals; **APPLY** — auto-apply ≤ risk ceiling (2 standard / 3 full-autonomy, `config.py:633-634`), queue the rest as tagged board tasks with best-effort escalation (`:890-999`); **BASELINE** — snapshots and artifacts written as **files under `WORKSPACE_VOLUME_PATH`** (`:1126-1226`, `:1361-1383`; default `/workspaces`, `config.py:483`), with a W4-S12 best-effort dual-write to the `harness_prescriptions` table (`:1054-1100`). Dormancy gates: ≥3 active agents and ≥7 days of heartbeat history (`:35-36`, `:420-458`). Human actuation (`/approve`) routes through admin authz, an idempotency ledger, unresolved-target refusal, then applies and marks the board task done with the result (`api/harness_commands.py:188-292`) — but the policy-plane call is ceremonial: `evaluate_approval(..., override_auto_approve=True)` (`:238-240`) short-circuits to unconditional approve, so the decline branch (`:241-250`) is unreachable (**F048 partial**, confirmed in the Phase-0 residual map).

### B4. Agent-scheduled tasks (PRD-77) and playbook crons

Agents self-schedule via `platform_schedule_task` / `platform_list_scheduled_tasks` / `platform_cancel_scheduled_task` / `platform_get_schedule` (`modules/tools/discovery/actions_scheduling.py:9-140`). `ScheduledTaskService.create_task` validates cron with the shared util, enforces caps (10/agent, 25 recurring/workspace), inserts `agent_scheduled_tasks`, and registers an APScheduler job (`services/scheduled_task_service.py:40-171`, `:428-476`). Firing re-reads the row `status='active'` (defensive against stale jobs), increments run tracking **before** executing, marks one-shots completed **before** the execution attempt, then runs the target agent through `AgentFactory.execute_with_prompt` — with **no `context_mode`**, i.e. default TASK_EXECUTION, not the W9 heartbeat/planning composition (`:296-422`; factory default at `modules/agents/factory/agent_factory.py:865`). Playbook crons follow the same pattern (`services/playbook_scheduler.py:73-218`): jobs loaded at boot, `_fire_playbook` re-reads the playbook from the DB, self-heals deleted/non-cron rows, checks the concurrency guard, and launches through the engine seam.

### B5. Schedule truth (PRD-162) and the planning pack (PRD-164/W9)

`ActivityService.get_schedule` is a **stateless, DB-first** read of four isolated sources — heartbeats, playbook crons, scheduled tasks, Mission SLA deadlines — each fail-soft so one bad source never blanks the calendar (`services/activity_service.py:706-739`); recurrence math goes through the one `schedule_util` (croniter). `get_scheduler_health` is a worker-invariant advisory banner (last agent heartbeat < 2 h) that never gates render (`:741-774`). The frontend calendar consumes it via `use-activity-api.ts:177-207` into `components/command-center/calendar-tab.tsx`.

Planning intelligence proper: `modules/context/planning.py` (178 lines) is the ONE token-budgeted planning pack — header instruction ("do NOT repeat approaches that previously failed", `:33-39`), PRD-157 budgeter selection (`:83-178`) — consumed by MissionPlanner, board `plan_task`, and AutoBrain. Its diet comes from `core/services/mission_memory_service.py`: mission summaries (L2 importance 0.7/0.8 + L3, `:43-139`), permanent task failures (`:145-243`), retry recoveries ("what eventually worked", `:245-305`), with narrative builders that carry verifier feedback and output excerpts (`:311-459`).

**Also in the box, and worth naming honestly:** `modules/tools/execution/exec_planning.py` (339 lines) — `create_implementation_plan`, `write_technical_content`, `review_code`, `security_scan`, `generate_tests`, `run_tests`, `research_topic`, `analyze_data` — are **hardcoded template writers with zero LLM and zero analysis** (`exec_planning.py:44-98` writes the same three-phase boilerplate for any feature; `:300-317` writes "Analysis completed successfully" for any target). The docstring claims "Uses LLM to generate structured implementation plans"; it does not. Mitigating: these names exist only in the unified-executor routing map (`modules/tools/execution/unified_executor.py:143-154`) — no ActionDefinition, no seed, no schema exposes them to agents (grep-proven), so they are dead legacy rather than live deception. They are a kill-list item either way.

## C. Honest quality — inspected against real data

The recon evidence (`reports/dossiers/evidence/real-data-inventory.md`, `data/census.md`, `data/memory-short-term.md`, `data/board-tasks.md`, `data/notifications.md`) makes this the easiest module to judge, because it is the **most alive** plane in the platform — and the data shows exactly what it produces.

**What genuinely works:**

1. **The clock fires, daily, in production.** `heartbeat_results`, `llm_usage`, `agent_reports`, `recipe_executions` are all current to 2026-07-03 (census.md freshness table); daily playbook-cron board tasks run through 07-03 (board-tasks.md Q2). The fcntl-leader design has kept exactly-once firing (no duplicate-tick evidence in the data; the DB cooldown at `heartbeat_service.py:460-513` is the belt to the flock's braces).
2. **PRD-162 schedule truth is well built.** Stateless DB-first read, per-source isolation, honest advisory health, one recurrence math library shared by calendar/scheduler/tool (`activity_service.py:706-774`, `schedule_util.py`). This closed the July-era 1-of-4-workers empty-calendar bug and the design holds up.
3. **W1/W9 fixes really landed.** Heartbeat agents get workspace-field digests (F021 — `modes.py:80-88`, exercised from `heartbeat_service.py:928`; test `orchestrator/tests/test_prd179_field_read.py`), and the HARNESS approve path actuates instead of escalate-to-nowhere (F048 actuation half; test `test_prd179_harness_actuation.py`).
4. **Mission-memory writes are the right shape.** The `mission_summary` / `task_failure` / `retry_recovery` rows in the live DB (12 / 7 / 2 rows, memory-short-term.md Q2) are exactly the narratives the code promises — verifier reasoning, failure codes, what-eventually-worked. This is the best-quality content in the entire memory store.

**What the data convicts:**

5. **The heartbeat plane is ~90 % self-generated noise.** `heartbeat_results` holds **148,362 rows** — the largest table sampled (census.md). The mem0 probe fires every 30 s (`config.py:854`) and writes one `primitive_check` row *per workspace with an orchestrator heartbeat* per probe (`heartbeat_service.py:244-254`) — ~2,880 rows/day/workspace, `tokens_used=0` hardcoded. The daily summary then counts these as ticks: the live memory store contains `"Heartbeat Daily Summary … Total ticks: 13383 - Successful: 13383 - Errors: 0 - Tokens used: 0"` for a single workspace-day (memory-short-term.md Q1). 13,383 "successful ticks" with zero tokens is a monitoring artifact summarizing itself. There is **no retention/pruning job for `heartbeat_results` anywhere** (grep: only deliverable-report pruning exists, `services/deliverable_service.py:635`).
6. **The heartbeat loop is a top producer of the memory-quality problem.** The daily summary is stored **twice per workspace per day** — once as `heartbeat_log`, once wrapped in a synthetic `User: Daily heartbeat summary request / Assistant: …` transcript (`heartbeat_service.py:1049-1089`) — confirmed verbatim in the live rows (memory-short-term.md Q1: identical pairs, every workspace, every day). Combined with playbook-failure spam, heartbeat/transcript chatter makes up most of the ~87 % junk share of all 2,211 memories. The memory dossier's seed symptom is partly *this module's* output.
7. **Self-monitoring without self-repair, compounding daily.** `report_to=auto` creates a NEW BoardTask every tick with no dedup against an existing open one (`heartbeat_service.py:1305-1384`). Live board: "Review FIXER heartbeat — {'status': 'error', …}" and "Review VECTOR heartbeat …" raised **daily** (board-tasks.md rows 2065/2064/2059 …), for heartbeats that have been erroring for weeks. The loop notices its own failure every day, files a task about it every day, and repairs nothing. Meanwhile 1,701 of 5,423 notifications (31 %) are `heartbeat_complete` and another 2,099 are `report_submitted` — ~70 % machine chatter burying the single `action_required` row (notifications.md).
8. **HARNESS has never produced one persisted prescription.** `harness_prescriptions`: **0 rows ever** (census.md auxiliary counts) — across 15 months of platform life, 21 workspaces, 237 agents, with `HARNESS_ENABLED=true` by default. Root-cause chain, from code: (a) prescriptions require a *previous baseline* (`:741-743` — first run always prescribes nothing), and baselines persist as **files on the workspace volume** (`:1196-1214`, `:1276-1293`) — if the Railway volume isn't mounted/persistent across deploys, every week is "first run" forever; (b) the three heuristics have narrow trigger windows (2× average heartbeat cost AND −25 % task volume, `:770-775`); (c) even a produced prescription's actuation surface is dark by default (F048). Also note the dormancy "data" gate is fed by probe spam (`MIN(created_at)` over `heartbeat_results`, `:435-449`) — trivially satisfied, so dormancy isn't the blocker; production simply never reached PRESCRIBE with a baseline in hand. The `/self-learning` Command-Center tile (`api/harness.py:99-141`) faithfully reports this empty world.
9. **Cross-worker registration gap (probe question 2).** Only the flock-leader worker has a live APScheduler; the other N−1 workers hold `None`. An agent or user who creates/updates a schedule via an API request served by a non-leader worker gets: scheduled task → "Scheduler not running — task will be picked up on restart" (`scheduled_task_service.py:442-444`); playbook cron create/update → AttributeError swallowed to a warning (`api/workflow_recipes.py:34-47` → `playbook_scheduler.py:124`); cron-expression *changes* leave the leader firing the OLD cadence until the next deploy (`_fire_playbook` re-checks type and existence but not the expression, `playbook_scheduler.py:157-172`). Cancellation is defended for scheduled tasks (fire re-checks `status='active'`, `:306-313`) but a *pause→resume* or new task is silently dormant until restart with (workers−1)/workers probability. Nothing observes or reports which worker is leader.
10. **F041 is real and bites clients.** The entire `/api/heartbeat` router — including the user-facing agent config CRUD, run-now, workspace list, toggle — is locked behind `require_super_admin` (`api/heartbeat.py:28-32`; endpoints `:64-492`), while the product UI actively calls it: the agent-configuration modal loads/saves `/api/heartbeat/agents/{id}/config` and runs `/run` (`frontend/components/agents/agent-configuration-modal.tsx:352-356,603-625`), the heartbeats hook lists/toggles (`frontend/hooks/use-heartbeats-api.ts:84,121,179`). A non-super-admin workspace owner gets 403 on every heartbeat surface — **for real clients, recurring-agent configuration is unusable**; the live heartbeat traffic exists because the founder is the super admin.
11. **Fire-then-verify ordering flaws.** Scheduled-task run tracking increments and one-shots are marked `completed` *before* execution (`scheduled_task_service.py:320-362`); a failed execution leaves `last_error` set on a "completed" task with no retry. Small, but it is the same failed-marked-done family the board data convicts elsewhere.
12. **Zero-value stub tools still routed.** §B5's `exec_planning.py` potemkin implementations (dead but routed) — kill.
13. **Missed-run semantics are "skip".** Memory job store + no misfire/catch-up configuration anywhere: a daily 09:00 job missed during a deploy window simply doesn't run that day (APScheduler default misfire behavior; no `misfire_grace_time` set in any `add_job` in this module). No backfill concept exists.

### Maturity score: **2.5 / 5**

Justification: the substrate demonstrably fires in production every day, PRD-162's read layer is genuinely good, and the W1/W9 repairs landed (that's worth more than a 2). But judged by the North Star — does this plane make Auto autonomously *useful* — the answer today is "it makes Auto autonomously noisy": ~90 % of its largest table is probe spam, its daily self-report is a token-count that double-pollutes memory, its self-optimization loop has never produced one persisted prescription, its self-monitoring files duplicate tasks daily without repairing anything, its user-facing configuration surface 403s for everyone but the founder, and schedule mutations silently miss the leader worker. A 3 would require the loops to produce *signal*; they currently produce activity.

## D. Competitive teardown

**1. Temporal Schedules (durable-execution scheduling)** — [docs](https://docs.temporal.io/evaluate/development-production-features/schedules), [launch blog](https://temporal.io/blog/temporal-schedules-reliable-scalable-and-more-flexible-than-cron-jobs). What it does better, specifically: schedules are durable server-side objects with **create/backfill/pause/trigger/update/describe/list** operations, explicit **overlap policies** (skip/buffer/cancel-running), missed-run **catch-up windows**, and first-class observability of every run — sold explicitly as a replacement for cron *and* for in-process schedulers like APScheduler/Celery-beat. Every failure mode found above — leader-only registration, stale-cadence-until-restart, missed runs during deploys, invisible leader health — is a solved primitive there. Automatos's substrate (APScheduler 3.x + flock) is by its own documentation single-process-only with no interprocess signalling ([APScheduler 3.x FAQ](https://apscheduler.readthedocs.io/en/3.x/faq.html)); the platform works around that correctly but inherits the ceiling.

**2. LangGraph Platform cron jobs (agent-framework scheduling)** — [docs](https://docs.langchain.com/langsmith/cron-jobs). Scheduled *assistant runs* as a managed platform feature: cron + assistant + input, UTC semantics, and **thread-lifecycle policy per run** (`on_run_completed: delete|keep`). Thinner than Automatos's offering (no heartbeat persona, no unified calendar, no self-scheduling by agents) — but every scheduled run lands in the same observability/eval tooling (LangSmith traces). The gap it exposes: Automatos scheduled runs produce `heartbeat_results` rows and reports, but no run-level trace/eval hook.

**3. Devin Scheduled Sessions (agent-native recurring work)** — [docs](https://docs.devin.ai/product-guides/scheduled-sessions), [blog](https://cognition.ai/blog/devin-can-now-schedule-devins). The closest product comparable to heartbeats + `platform_schedule_task`: recurring or one-time agent sessions, **visual frequency editor with a custom-cron escape hatch**, per-schedule repo scoping as prompt hints, per-schedule notification routing (email/Slack), all self-manageable by the end user in Settings→Schedules — and Devin can schedule Devins (agent self-scheduling), which Automatos also has (PRD-77) but locks the *user-facing* half behind super-admin (F041). Where Automatos is genuinely ahead: the unified calendar across five schedule sources and the monitoring-persona heartbeat (prompt + tool loop + report chain) are richer than Devin's session-on-a-timer.

**4. ChatGPT Scheduled Tasks (consumer ceiling-check)** — [OpenAI help](https://help.openai.com/en/articles/10291617-tasks-in-chatgpt). Recurring/one-off tasks with notifications, capped at ≤1 run/hour and 15 active tasks even on Enterprise, no webhooks. Automatos's scheduling surface is strictly more capable (5-min intervals, cron, agent-to-agent, calendar) — an honest "competitor is behind" note. The lesson worth stealing is the packaging: tasks are a first-class sidebar page a non-technical user can own.

**5. DSPy / GEPA (what HARNESS wants to be when it grows up)** — [GEPA repo](https://github.com/gepa-ai/gepa), [paper: Reflective Prompt Evolution Can Outperform RL, ICLR 2026](https://arxiv.org/abs/2507.19457). The state of the art in "loop that improves agent configuration" is **eval-grounded reflective optimization**: propose a change, *measure it against a metric on real traces*, keep it only if the number moves (GEPA: +26 pts on MATH from instruction refinement alone). HARNESS's diagnose/prescribe is threshold heuristics over weekly aggregate deltas with placeholder proposed-values (`review_needed`) and **no eval anywhere in the loop** — it cannot know whether an applied change helped except by next week's noisy aggregate (its own rollback heuristic, `:1506-`, is the tacit admission). The T3 eval-harness thesis is the missing half of HARNESS.

**6. pg_cron (substrate alternative, honorable mention)** — [repo](https://github.com/citusdata/pg_cron). Postgres-native scheduling with durable job definitions and a queryable `cron.job_run_details` history — the "schedule state lives in the DB, not in a process" property Automatos already adopted for *reads* (PRD-162) but not for *firing*. Managed-Postgres availability on Railway is the constraint to check before leaning on it.

**Where Automatos actually stands:** ahead of consumer agents (ChatGPT Tasks) and roughly at feature parity in scheduling ambition with Devin — uniquely broad with the five-source calendar and agent self-scheduling — but on the weakest *substrate* of the group (in-process, leader-only, skip-on-miss, no run-level observability), and its self-optimization loop is a generation behind the eval-grounded state of the art.

## E. Build / extend / adopt / replace — the verdict

Three different verdicts for the three different things in this module:

**E1. Scheduling substrate — EXTEND (in-house, DB-first firing), with Temporal explicitly evaluated and declined at current scale.** The reuse-over-build bias was tested: adopting **Temporal** (Cloud or self-hosted) would genuinely solve durability, overlap, backfill, and observability — but it imports a second execution runtime (worker fleet, SDK rewrite of every job family, ops surface) into a Railway modular monolith whose *actual* observed failure modes are noise and registration gaps, not scale. The cheaper, platform-native fix is the pattern the codebase already proved in W1: **make firing DB-first like reads already are** — a single leader sweep that polls `agent_scheduled_tasks` / playbook `schedule_config` / heartbeat configs for `next_run_at <= now()` (computed by the existing `schedule_util`), claims rows `FOR UPDATE SKIP LOCKED` exactly like `board_dispatcher`, executes, and writes the next occurrence back. That one change erases the non-leader registration gap, stale-cadence drift, and restart-dormancy, gives a queryable run history for free, and adds catch-up semantics as a WHERE clause. APScheduler then shrinks to "wake the sweep every N seconds" or disappears. Revisit Temporal only if/when Missions need durable *long-running* execution generally (that is a missions-orchestration decision, not a scheduler one). Rough cost: the sweep is days-not-weeks by reusing `board_dispatcher` plumbing; Temporal would be weeks plus permanent ops.

**E2. HARNESS — REPLACE the heuristic core; keep the skeleton.** The 5-phase loop, risk-tiered apply, board-task review flow, ledger, and rollback machinery are sound scaffolding (and W9's actuation path works). The diagnose/prescribe brain has empirically produced nothing in 15 months and, by design, cannot verify its own changes. Replace it with the T3 eval harness as the measurement plane plus a GEPA-style reflective proposer over real traces (`llm_usage`, `heartbeat_results` real ticks, board outcomes, tool-routing affinities): propose → shadow-evaluate against the module metric → apply → confirm the number moved → keep/rollback. Concretely adopt **DSPy/GEPA** ([gepa-ai/gepa](https://github.com/gepa-ai/gepa), MIT) as the optimizer library where the target is prompt/description-shaped, and keep the existing apply/queue plumbing as the actuator. Move baselines off volume files into the already-existing `harness_prescriptions`/DB store (the W4-S12 cutover the code itself documents at `harness_service.py:1060-1062`). Until that lands, HARNESS should honestly report "never produced a prescription" on its tile rather than "completed".

**E3. Heartbeats, schedule truth, planning pack — KEEP BUILDING (nothing external wins).** No vendor sells "a monitoring persona with your agent's tools, memory digest, report chain, and a five-source workspace calendar" — this is the product, it is differentiated against Devin/LangGraph above, and its defects (noise, dedup, F041) are repairs, not architecture. **CUT:** the `exec_planning.py` stub vertical (dead, misleading, routed); the double memory write of the daily summary; probe rows in `heartbeat_results` (relocate to a status table or gauge).

## G. Quality metric

The module's quality is measurable today, and every number below is currently bad — which is exactly why they should be the tracked metrics (feeds T3):

1. **Schedule fidelity** — % of due occurrences that actually fired within a tolerance window (computable once firing is DB-first; today it is unmeasurable, itself a finding — the platform cannot answer "did Monday's 09:00 job run?" without grepping logs).
2. **Signal ratio of the heartbeat plane** — non-probe, non-boilerplate rows / total `heartbeat_results` rows. **Today: ~10 %** (13,383 zero-token "ticks"/workspace-day vs a handful of real LLM ticks; memory-short-term.md).
3. **Actionability of ticks** — % of heartbeat notifications a human acts on, and duplicate-open-task rate for `report_to=auto` (today: daily duplicate "Review X heartbeat" tasks; board-tasks.md).
4. **HARNESS efficacy** — prescriptions persisted / applied / confirmed-improved / rolled-back per month. **Today: 0 / 0 / 0 / 0 ever** (census.md).
5. **Memory pollution contribution** — heartbeat+playbook operational rows / total memory writes per week. **Today: ~87 % class-wide** (memory-short-term.md), of which the daily-summary double-write is this module's direct share.
6. **Planning-pack lift** (shared with context-assembly): plan-approval rate and replan rate with vs without the pack — the "learning demo" the pack header promises (`planning.py:33-39`).

## H. Cost note (informational)

- **Probe/primitive rows:** 0 LLM tokens, but ~2,880 writes/day/workspace into an unpruned table — cost is storage and query degradation on a 148 k-row (and compounding) hot table.
- **Orchestrator LLM tick:** context build + up to `AGENT_HEARTBEAT_MAX_TOOL_ITERATIONS` tool turns; at a 30-min interval inside 12 active hours that is ~24 LLM ticks/day/workspace, each a multi-turn tool loop — order of 100–500 k tokens/day/workspace depending on tool chatter (the live `llm_usage` plane, 31,081 rows, is the ledger; per-tick metrics are already rolled into reports via `compute_execution_metrics`, `heartbeat_service.py:1540-1552`).
- **HARNESS tick:** ~0 LLM (rule-based); cost is 10 concurrent analytics tool calls' DB reads weekly.
- **Daily summary:** 0 LLM (string counting) — which is also why its output is worthless; an LLM-synthesized daily brief would cost one small-model call/workspace/day (~$0.001–0.01) and would be worth it.
- **Scheduled tasks / playbook crons:** cost is the underlying agent/playbook execution; scheduling overhead negligible.

## I. UX / surface

**Today:** Command Center **calendar tab** (`components/command-center/calendar-tab.tsx` ← `use-activity-api.ts:177-207`) renders the PRD-162 unified schedule with the advisory health banner — the strongest surface in the module. Heartbeat config lives inside the **agent-configuration modal** (interval, active hours, prompt, auto-act, report_to; `agent-configuration-modal.tsx:352-625`); a **heartbeats list/toggle** hook exists (`use-heartbeats-api.ts`); HARNESS has the **self-learning tile** (`/api/harness/self-learning`). All heartbeat surfaces are dead for non-super-admins (F041).

**Concrete changes, in order of user pain:**
1. **Unlock the user surface (F041):** move agent-heartbeat CRUD/run/toggle off the super-admin observability router onto a workspace-scoped dependency — the July fix, still not done; without it no client can operate recurring agents at all.
2. **One digest, not a fire-hose:** collapse per-tick `heartbeat_complete` notifications into a daily/threshold digest with only error-state ticks surfacing immediately (today 31 % of all notifications are heartbeat chatter that buries the one `action_required`).
3. **Self-repair panel instead of duplicate tasks:** `report_to=auto` should upsert ONE open "agent X heartbeat failing since \<date>, N occurrences" task with an escalation policy, not a new task per tick.
4. **Visual recurrence editor** (Devin-style presets + custom-cron escape hatch) for scheduled tasks and heartbeats; humans should not need `0 9 * * 1`.
5. **Honest HARNESS tile states:** "never run / no baseline yet / produced N prescriptions (M awaiting review)" — with the awaiting-review queue linked; today the tile reads an empty store and the approve surface 409s.
6. **Scheduler health, truthfully:** the banner should include leader-worker identity and last-sweep time once firing is DB-first — "scheduler_active: true" hardcoded (`activity_service.py:739`) is a placeholder, not a signal.
