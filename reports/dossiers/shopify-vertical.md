## A. What it is

The Shopify vertical is Automatos's one end-to-end **commerce reference pilot**: the full path from a merchant installing the Shopify app, to a provisioned workspace with a Shopify agent roster and a minted widget key, to catalog + orders synced into a per-workspace commerce Knowledge Graph, to a live shopper-facing storefront widget that opens proactively with graph-grounded product recommendations. It is the concrete proof that the platform's generic machinery (agents, graph, widget, deliverables, tools) can be pointed at a real business and run largely unattended. After the W13 hardening wave (PRD-183) the Shopify-specific lifecycle logic was pushed behind a generic `VerticalProvisioner` seam, so the same install→provision→sync→serve flow is *meant* to stand up a second vertical without forking the Shopify routes. In production it is exercised by **exactly one merchant** — `28a228aa`, a UK building-products / smoke-ventilation store ("InBuildUK") — whose 42 MB commerce graph is the only real-world evidence of the vertical actually working.

## B. What it does (real implementation + data path)

**Install-time provisioning** (`orchestrator/integrations/provisioning.py:215-310`, generic; `orchestrator/api/verticals.py:95-126`, HTTP). The Shopify Remix app POSTs to `POST /api/verticals/shopify/provision` (mounted at `router_manifest.py:53`); `provision_vertical` looks up the `ShopifyProvisioner` in `PROVISIONER_REGISTRY` (`provisioning.py:229`), finds-or-creates a Workspace keyed on `settings.shopify_domain` (`:239-246`), clones the marketplace agent roster into the workspace with skills + tool assignments and `reports_to` wired to `shopify-ops` (`_seed_roster`, `:103-200`), and mints a public widget key scoped to the shop's origins (`:284-291`). `api/shopify.py:148-180` is now a thin compat delegate to the same flow. Idempotent — an existing active workspace is returned without re-seeding (`:281`).

**Vertical declarations** (`orchestrator/integrations/shopify/provision.py`). The `ShopifyProvisioner` object declares the roster (`SHOPIFY_AGENT_SLUGS`, 9 slugs, `:30-40`), the default proactive widget config (`:46-59`), minted-key permissions (`chat, documents:read, agents:read, agents:execute`, `:69`), the ops-manager slug, `site_type="shopify"`, `external_id_key="shopify_domain"`, and the allowed-origins rule that always permits `*.myshopify.com` plus any custom primary domain (`allowed_domains`, `:77-96`). Self-registers at import (`__init__.py` → `provision.register()`), which also registers the catalog/orders graph-source mappers into `GRAPH_SOURCE_MAPPERS`.

**Token connect** (`api/shopify.py:186-230`). `POST /api/shopify/connect` stores the 147-scope Admin token **encrypted at rest** via the canonical Fernet service (`_encrypt_secret`, `:45-49`, `:208`) into `workspace.settings.shopify_access_token`, backfills `shopify_domain`, and heals the Site (`ensure_shopify_site_for_workspace`, `:222-223`). A **second, dashboard self-serve path** stores the token as a Composio `shopifyAccessTokenApi` Credential row instead (`services/sites.py:_workspace_is_shopify_connected:196-209`) — the live pilot uses this path (its `settings` has `shopify_domain` but no `shopify_access_token`; the token lives in Composio's EntityManager, which is why its syncs ran).

**Catalog sync → commerce graph** (`api/shopify.py:452-640`). `_product_sync_impl` runs `SHOPIFY_BULK_QUERY_OPERATION` via Composio (`:527`, the `_SHOPIFY_BULK_CATALOG_QUERY` GraphQL, `:409-435`), downloads the signed-URL JSONL, maps it with `map_shopify_catalog` resolved through the vertical registry (`:494`), and hands the result to `GraphifyService.import_graph(..., merge=False)` (`:568`) for clustering + persistence. Writes a `product_sync` status block onto `workspace.settings` (`:571-584`). HTTP entry `POST /sync/products/start` is workspace-authenticated via `get_request_context_hybrid` + `_resolve_sync_workspace` (`:452-467`).

**Orders sync → Frequently-Bought-With edges** (`api/shopify.py:695-897`). `_orders_sync_impl` runs a privacy-scoped orders bulk-op (`_orders_bulk_query`, `:654-678` — requests only order id/createdAt/cancelledAt + line-item product refs, no customer/email/address), maps co-purchase pairs with `map_shopify_orders` (min_support gate, `graph_extraction.py:706-810`), **strips stale `frequently_bought_with` edges from the existing graph first** (`:809-830`), then merges the fresh FBT edges with `import_graph(..., merge=True)` (`:844`).

**Catalog webhook re-sync** (`api/shopify.py:309-396`, PRD-183 S1 / F032). `POST /events` (internal-key authed) matches catalog-mutation topics (`CATALOG_EVENTS`, `:315-319`), resolves the workspace by shop domain, and fires `_sync_catalog_for_workspace` as a detached task on its own `SessionLocal` (`:322-352`, `:388`). This runs the **full** `_product_sync_impl` (merge=False) per event.

**Graph-grounded proactive widget** (`orchestrator/integrations/shopify/widget_proactive.py`). `handle_widget_message` (`:417-495`, `PLUGIN_REGISTRY["shopify"]`) is called by the generic widget chat router. For a `proactive_opener` trigger it walks 1-hop graph edges from the seed product (FBT by co_count, then in_collection, then by_vendor — `_resolve_graph_related_products:50-135`) and builds a tightly-constrained directive (`_build_proactive_opener_message:239-313`); for `cart_idle` it aggregates FBT across cart items (`_resolve_cart_recommendations:138-236`) and builds a cart nudge (`:316-379`); for a normal turn it prepends a page-context grounding preamble (`_build_page_context_preamble:382-414`). Page-context field mapping lives in `context_fields.py` behind a CI grep-gate that keeps Shopify keys out of generic surfaces.

**Platform tools** (`modules/tools/discovery/actions_shopify.py`, `handlers_shopify.py`, PRD-183 S3 / F088). `platform_shopify_sync_catalog` (write) and `platform_shopify_sync_status` (read) are promoted ActionDefinitions with `workspace_id` threaded from the executor context, so Auto can re-sync the catalog and report deltas, or check freshness, through its own tool surface.

**GDPR compliance surface** (`api/verticals.py:158-248`). Machine-to-machine internal-key-authed `erase-subject` / `erase` / `export` endpoints back Shopify's `customers/redact` / `shop/redact` / `customers/data_request` webhooks, resolving the workspace by shop domain (404-never-fallback, `:34-77`) and delegating to the audited `gdpr_service` cascade.

**Real data path, end to end (live pilot `28a228aa`):** catalog bulk-op → 22.9 MB JSONL → `map_shopify_catalog` → **1,362 products, 12,354 variants, 161 collections, 41 vendors, 10,616 metafields**, persisted as a 42 MB `graph/graph.json` blob in `workspace_graphs` (product_sync: `node_count 24534, edge_count 29919, duration 46s`). Orders sync ran over **57 orders → 16 FBT edges** (min_support 3). The widget's real traffic is visible in the graph's `latest_diff.json` — proactive-opener and page-context turns against real product pages ("What smoke detectors do we sell", "manage inbuilduk my shopify store").

## C. Honest quality (inspected against real behaviour) — **Maturity: 2 / 5**

This is the platform's most complete vertical *by construction* and its code quality is genuinely good in places — but the **one production instance exposes that the highest-value capability (cross-sell) is silently broken in the live graph**, the pilot is a sample of one, and the KG the whole thing feeds is polluted. A 2 reflects "the plumbing is real and mostly correct, the client-facing intelligence is not yet trustworthy."

**What's genuinely strong (evidence):**
- **Catalog ingestion works at real scale.** The live graph holds 1,362 real products with correct labels ("Elta White Powder-Coated Metal Ceiling Air Supply Valve"), full variant/vendor/collection/metafield structure, and correct edge types (12,354 `variant_of`, 5,587 `in_collection`, 1,362 `by_vendor`, 10,616 `has_metafield` — counted directly in the 42 MB blob). A 46-second full sync of a 1.3k-SKU catalog is respectable. `map_shopify_catalog` is a clean, deterministic, IO-free pure function (`graph_extraction.py:503-660`).
- **The proactive-opener builder is the best-designed piece in the vertical.** `_build_proactive_opener_message` (`widget_proactive.py:239-313`) forwards only real page-context facts, cites FBT provenance naturally ("bought together in 12 of 57 orders"), and hard-instructs the model to ask rather than fabricate specs/pricing/compatibility — exactly right for a shopper-facing surface on a technical catalog. The FBT-first ranking, stale-edge stripping before re-merge, and cancelled-order exclusion (`graph_extraction.py:748-751`) show real domain care. This is a North-Star-positive component.
- **The July criticals are genuinely closed** (Phase-0 residual map): sync routes are workspace-authenticated (F003), the internal key is fail-closed with `hmac.compare_digest` (F004, `shopify.py:85-101`), the Admin token is Fernet-encrypted at rest (F058), catalog webhooks re-sync the graph (F032), first-connect autosync owns its DB session (F033), sync/status are platform tools (F088). These were real vulnerabilities; they are fixed.

**What's confirmably broken or weak (real-data evidence):**

1. **The cross-sell signal is destroyed by every catalog re-sync — and the live graph proves it. [HIGH, current, widened by W13]** `_product_sync_impl` calls `import_graph(merge=False)` (`shopify.py:568`), and `_import_graph_unlocked` with `merge=False` **replaces the entire graph** with only the imported nodes/edges (`graph_service.py:428-461`; the merge branch is skipped). The catalog bulk-op JSONL contains no FBT edges, so every catalog sync wipes the FBT edges the last orders sync computed. **Live evidence:** the pilot's `orders_sync` block boasts `fbt_edges_added: 16`, but the persisted `graph/graph.json` contains **zero** `frequently_bought_with` edges (counted directly). The timestamps confirm the mechanism: orders_sync completed 2026-05-23, product_sync completed 2026-05-29 (6 days later, merge=False) — the catalog sync ran after and erased the FBT work. **F032 made this worse:** catalog webhooks now fire `_product_sync_impl` (merge=False) automatically on every `products/update` / `inventory_levels/update`, so an ordinary inventory change silently deletes all cross-sell edges with no human in the loop. The entire "smarter over time" cross-sell story — the reason the orders sync exists — does not survive contact with normal store activity. This is the single most important finding in the dossier.

2. **The commerce KG is polluted with conversation memory. [MEDIUM]** The pilot's graph carries **510 `l2:` nodes** — raw proactive-opener directive strings and chat clippings ("User: [PROACTIVE_OPENER] Generate a contextual one-sentence opener…", "[22:38] Discussed: What smoke detectors do we sell") — mixed into the same graph as products. This is the same memory-pollution pattern the memory dossier root-caused, now spilling into the commerce graph and diluting both community detection and any graph traversal. Openers traverse a graph that is ~2% conversational noise by node count and growing per session (`latest_diff.json` is almost entirely new `l2:` nodes).

3. **Community detection clusters the wrong granularity. [MEDIUM]** `communities.json` community 0 has 191 members that are **almost entirely metafields** (`shopify_metafield_180526724022658`, …) plus two collections. Metafields (raw product key-value attributes) dominate node count (10,616 of ~25k) and pull community structure toward meaningless attribute-blobs. The graph's "god nodes" (`meta.json`) are **blog posts and SEO keywords** ("EN 12101 Smoke Ventilation Explained", "SEO-optimised blog post"), not commercial anchors — the KG's most-connected concepts are content-marketing artefacts, not the catalog. A merchant asking "what are my product clusters?" gets attribute noise.

4. **The co-purchase signal is intrinsically thin. [MEDIUM, data reality]** Even when the orders sync ran cleanly it produced **16 FBT edges from 57 orders**. For a long-tail technical catalog (1,362 SKUs), 57 orders in the window yields almost no statistically meaningful co-occurrence — most product pages will have **no** FBT recommendation, so the opener falls back to same-collection/same-vendor siblings (a much weaker signal). The pilot is a store type where the marquee feature has the least to work with; a fashion/consumables store would fare better, but there is zero production evidence of that.

5. **The pilot is a sample of one, and it is not being actively sold through.** One Shopify workspace exists in production. Deliverables platform-wide stopped 2026-06-16 (OpenRouter 402 outage). There is no second-vertical instance, so the F076 "generalized provisioner" claim is proven only by a mock-vertical unit test (`test_prd183_s5_vertical_provision.py`), never by a real second vertical.

6. **The commerce mappers have zero behavioural tests while F032 now runs them automatically (F091, widened).** `map_shopify_catalog` / `map_shopify_orders` have no direct fixture-driven tests (only a registry identity check); both headline golden journeys (J3 widget-plugin, J9 sync→FBT-opener) are still `pytest.skip`-ped (`test_golden_journeys.py:101,221`, the latter self-labelled "the highest-value gap to close next"). A mapper regression now corrupts every opener silently and faster.

7. **Webhook efficiency is naïve. [LOW-MEDIUM]** `/events` fires a **full** catalog re-sync per event with no debounce, coalescing, or already-running guard (`shopify.py:517` sets status=running but never checks it); a bulk edit emitting N webhooks fires N concurrent full Bulk-Ops, relying on Shopify's one-bulk-op-per-shop limit with the losers swallowed as warnings. `asyncio.create_task` at `:388` (and `tools.py:67`) keeps no task reference (GC-collectable mid-flight).

**Net:** the ingestion plumbing and the opener prompt-craft are real and good; the intelligence the client actually sees (cross-sell, clusters) is either wiped, thin, or noisy in the one place it runs for real. Maturity **2/5** — closer to 3 on plumbing, dragged down by the FBT-wipe and the pollution because those directly defeat the North Star (autonomous, client-quality output).

## D. Competitive teardown

The Shopify AI space splits into three archetypes; Automatos's vertical straddles the shopper-facing conversational lane while borrowing the merchant-copilot ambition.

**Rep AI** ([apps.shopify.com/rep-ai-sales-associate](https://apps.shopify.com/rep-ai-sales-associate), [hellorep.ai/product](https://www.hellorep.ai/product)) — the closest direct competitor. Shopper-facing sales agent: behavioural AI that **detects when a shopper is losing interest and steps in proactively**, personalized product recommendations, upselling/cross-sell, abandoned-cart rescue, and **automatic Shopify product-listing sync** so answers stay current. Merchant case studies cite 13% conversion rate and 20× ROI ([useoutly.com/en/blog/rep-ai-review](https://useoutly.com/en/blog/rep-ai-review)). **Where it beats Automatos:** (a) its proactive trigger is a *learned behavioural model* (dwell/scroll/hesitation signals), whereas Automatos fires on a fixed `time_on_page: 20s` timer (`provision.py:49-52`); (b) its recommendation engine is a purpose-built, continuously-updated model, not a co-occurrence graph that gets wiped on every catalog sync and needs dozens of orders to say anything; (c) it ships conversion analytics as a first-class surface. Automatos's *opener prompt-craft* is arguably better (stricter anti-fabrication), but Rep's underlying recommendation quality and its always-fresh sync are ahead.

**Shopify Sidekick / Magic** ([shopify.com/sidekick](https://www.shopify.com/sidekick), [wholesalehelper.io/blog/shopify-magic](https://wholesalehelper.io/blog/shopify-magic/)) — the platform-native **merchant** copilot, **not shopper-facing** (explicitly "can't chat with shoppers on your storefront"). Lives in admin, takes actions with approval, writes ShopifyQL, builds Flow automations and small internal apps, and in the Winter '26 editions added **Sidekick Pulse** — proactive anomaly/trend alerts (declining sales, well-performing products, discount opportunities). Included free in the Shopify plan. **Where it beats Automatos:** it has native, real-time, first-party access to the *entire* Shopify data model (payments, fulfillments, payouts) with no Composio bulk-op round-trip and no 42 MB blob; Sidekick Pulse is exactly the "morning brief / proactive ops manager" Automatos's `shopify-business-analyst` seed *describes* but has no production evidence of running. **Where Automatos differs meaningfully:** Sidekick is deliberately *not* a storefront widget — Automatos's shopper-facing proactive opener is a lane Shopify has chosen to leave to apps. That is Automatos's real space, not competing with Sidekick head-on.

**Gorgias AI Agent** ([apps.shopify.com/helpdesk](https://apps.shopify.com/helpdesk), [eesel.ai/blog/gorgias-ai-for-shopify](https://www.eesel.ai/blog/gorgias-ai-for-shopify)) — Shopify's Premier CX partner, 17,000+ brands, claims $500M revenue driven. Its AI Agent runs as either a **Support Agent or a Shopping Assistant**, grounded on help-center + website + Shopify data, across email/chat/SMS, 80+ languages, with **image understanding** (photos of damaged items, receipts); 26–60% automation rates. Ticket + per-resolution pricing ($0.90–$1.50/resolution). **Where it beats Automatos:** deep, battle-tested post-purchase automation (returns, order edits, WISMO) that Automatos does not implement at all; omnichannel (Automatos's shopper leg is web-widget-only); multimodal input; a proven at-scale grounding pipeline. **Where Automatos could differ:** Gorgias's shopping-assistant recs are shallower than a real co-purchase graph *when that graph works* — but Automatos's doesn't currently persist, so this is potential, not delivered.

**Where Automatos actually stands:** it has assembled a credible *shopper-facing proactive commerce widget* (the lane Sidekick avoids and Gorgias treats as secondary to support) on top of a real commerce graph, with better anti-hallucination discipline than the incumbents' marketing implies. But on the three things that decide merchant value — recommendation quality, sync freshness/robustness, and post-purchase support automation — it is behind all three specialists: the recommendations get wiped, the sync has no debounce, and support automation is unbuilt. It is a strong *architecture* trailing on *delivered outcomes*, evidenced by a single pilot.

## E. Build / extend / adopt / replace — **verdict: EXTEND (fix), do not rebuild; ADOPT for post-purchase support**

The vertical is not a candidate for wholesale replacement — its value is precisely that it exercises *Automatos's own* graph/agents/widget/deliverables as a reference, which a third-party app cannot do. The reuse-over-build bias points to **fixing the three defects that make the existing pipeline untrustworthy**, not re-architecting, plus **adopting** for the one lane Automatos has no business hand-building.

- **EXTEND — the commerce graph + sync (do not rebuild).** The catalog ingestion is real and correct at scale; the bug is a merge-mode error, not a design failure. The fix is small and high-leverage: make catalog re-sync **preserve FBT edges** (either `import_graph(merge=True)` with catalog-node replacement, or extract-and-reapply FBT edges around the catalog rebuild the same way `_orders_sync_impl` already strips-then-remerges), and **add debounce/coalescing + an already-running guard** to `/events`. This is days of work against the highest-value defect in the module.
- **EXTEND — separate the commerce KG from conversation memory.** The 510 `l2:` nodes and blog "god nodes" mean the graph the openers traverse is not a clean product graph. Scope catalog/orders extraction into its own graph partition (or filter `l2:`/content nodes out of the opener traversal in `_resolve_graph_related_products`), and down-weight or exclude metafields from community detection. This is the same **typed/partitioned graph** thesis (T1) landing concretely for commerce.
- **ADOPT — post-purchase support automation.** Do **not** build returns/order-edit/WISMO automation in-house. Gorgias / Rep already resolve 26–60% of support tickets with grounding pipelines Automatos would spend a year matching. If a merchant needs support automation, integrate (or let the merchant keep Gorgias) and position Automatos as the *proactive sell-side* agent, not the support desk. Building this would fail the earned-in-house test.
- **EXTEND (finish F076), don't over-invest.** The provisioner generalization is genuinely landed for the *lifecycle* but the mappers physically remain in generic `graph_extraction.py` and the proactive trigger vocabulary is still commerce-shaped in generic code (`chat.py` `PROACTIVE_TRIGGER_REASONS`). Finish those two only when a real vertical #2 is actually queued — do not speculatively generalize further for a second vertical that has zero demand signal (one pilot, no vertical #2). Surface this to Gerard as a sequencing call, not a silent deferral.
- **KEEP — the opener/cart-idle prompt layer.** Best-in-class discipline; nothing external to adopt here. If anything, borrow *from* it for the generic widget.

**Rough cost:** the FBT-preservation + debounce fix is small (single-digit engineer-days, no new dependency). The graph-partition/metafield-weighting is medium (ties into the T1 graph thesis). Support-automation adoption is an integration, not a build.

## G. Quality metric (feeds T3)

Today the vertical has **no quality number** — its own two golden journeys are skipped, and the only signal is a `product_sync`/`orders_sync` status block that reports success even when the resulting graph is unusable (the pilot's block says `fbt_edges_added: 16` while the graph has 0). That gap *is* the finding: the module measures that a sync *ran*, never that it *produced usable commerce intelligence*.

Proposed tracked metrics (offline + online):
- **FBT persistence integrity (P0):** `% of workspaces where (fbt_edges reported by last orders_sync) == (frequently_bought_with edges present in graph.json)`. Today for the live pilot this is **0% (16 reported, 0 present)** — a single query that would have caught the wipe. Alarm on drift.
- **Opener grounding rate:** `% of proactive-opener turns where related_products (or page-context facts) was non-empty` (the `related_count` telemetry already emitted by `handle_widget_message` — currently write-only). Measures how often the widget has something real to say vs falling back to a generic line.
- **Recommendation coverage:** `% of product pages with ≥1 FBT recommendation` (structural, from the graph). For the pilot this is near-zero once the wipe is accounted for.
- **Opener→engagement / conversion (online, the real number):** did the shopper reply to / act on the proactive opener? This requires wiring widget outcomes back — the same unfed-learning-plane gap the whole platform has (`rag_feedback`/telemetry write-only). This is the metric that matters and it does not exist yet.
- **Sync freshness SLO:** median lag between a catalog webhook and graph reflecting it; and syncs-per-day (to catch webhook-storm amplification).

First concrete number to publish: **FBT persistence integrity = 0% on the only production store** — start there.

## H. Cost note (informational)

- **Catalog sync:** one Composio `SHOPIFY_BULK_QUERY_OPERATION` (Shopify-side compute, Composio-metered) + a JSONL download (22.9 MB for the pilot) + a deterministic in-memory map (no LLM) + a graph import with clustering/embeddings. ~46 s wall for 1.3k SKUs. The embedding cost is in `GraphifyService.import_graph`, not the mapper. **Cost driver: F032 fires this full pipeline per catalog webhook** — a bulk merchant edit can trigger many full syncs (and many embedding passes) back to back. Debounce is a direct cost lever, not just a correctness one.
- **Orders sync:** same bulk-op shape over orders; the map is pure (combinations counting); cheap relative to catalog.
- **Proactive opener / cart-idle:** one graph load (`load_graph` deserializes the workspace blob — for the pilot that is a 42 MB JSON parse per proactive turn, non-trivial) + one short LLM call (`≤140 chars`, text-only, no tools — the cheapest possible completion). **The 42 MB blob load is the hidden per-turn cost**, not the LLM.
- **Storage:** 42 MB `graph.json` in a Postgres TEXT column, doubled by dated history snapshots per rebuild (6 history rows for the pilot, ~41 MB each) — a real storage smell that will not age well under frequent webhook-driven rebuilds.

## I. UX / surface

- **Command Center:** the vertical has no honest health surface. A merchant (or Auto) cannot see "catalog last synced X, N products, M cross-sell pairs live, opener grounding rate Y%". The `product_sync`/`orders_sync` blocks exist but report run-status, not *intelligence health*, and are not surfaced coherently. Add a **Commerce panel**: catalog freshness, product/collection/vendor counts, **live FBT-pair count** (which would visibly read 0 today), opener grounding rate, and last webhook received. This is the surface that would have made the FBT-wipe obvious to the one merchant using it.
- **The FBT-wipe needs a user-visible integrity indicator**, not just a fix — "cross-sell recommendations: 0 live (last computed 16; wiped by catalog re-sync)" until the fix lands.
- **Opener preview / dry-run:** let the merchant see, per top product, what the proactive opener *would* say — the fixtures (`expected_product_page_opener.txt`) prove the shape is testable; expose it so merchants trust the shopper-facing copy before enabling `widget_proactive.enabled`.
- **Second-vertical provisioning is API-only** (`POST /api/verticals/{v}/provision`) with no operator UI — fine while there is one vertical, but the "generalized provisioner" has no surface a human can drive. Not worth building until vertical #2 is real.
- **Deliverables tie-in:** the vertical's agents (business-analyst morning brief, SEO/content) are meant to produce Deliverables, but deliverables stopped platform-wide 2026-06-16; the Commerce panel should show the last merchant-facing artifact and flag staleness, since "silent stop with board tasks marked done" is exactly what happened.

## J. Upgrade path (prioritised by North-Star impact × effort)

1. **[P0, small] Stop the catalog re-sync wiping FBT edges.** Make `_product_sync_impl` preserve `frequently_bought_with` edges across the catalog rebuild (mirror the strip-then-remerge `_orders_sync_impl` already does, or use merge=True with catalog-node replacement). This restores the single most valuable client-facing capability. Add the **FBT persistence integrity** check (§G) to CI/alerting so it can never silently regress again. *Impact: high (the marquee feature actually works). Effort: days.*
2. **[P0, small] Debounce + coalesce + already-running guard on `/events`.** One re-sync per burst, not N; hold task references. Fixes correctness, cost, and the webhook-storm amplification in one change. *Impact: high (reliability + cost under real webhook volume). Effort: days.*
3. **[P1, medium] Give the mappers real behavioural tests and un-skip J3/J9.** The golden journeys are the acceptance proof the whole vertical is missing; recorded fixtures already exist (`tests/fixtures/`). Un-skipping J9 (sync→FBT→opener) makes the marquee journey a tracked, gated number. *Impact: high (turns "trust me" into a metric; guards #1). Effort: medium.*
4. **[P1, medium] Separate commerce KG from conversation memory; down-weight metafields.** Partition (or filter at traversal) the `l2:` nodes out of the opener graph and exclude/down-weight metafields in community detection so clusters and god-nodes are commercial, not content/attribute noise. Lands the T1 typed-graph thesis concretely for commerce. *Impact: medium-high (opener quality + honest KG). Effort: medium.*
5. **[P2, medium] Learned proactive trigger + opener-outcome feedback.** Replace the fixed 20s timer with a behavioural trigger and wire `related_count`/opener→engagement outcomes back into the learning plane (currently write-only), so the widget gets measurably better and can be compared against Rep AI's 13% CVR bar. *Impact: high but depends on the platform-wide feedback-plane fix. Effort: medium+.*
