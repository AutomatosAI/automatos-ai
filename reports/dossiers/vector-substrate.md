## A. What it is

The layer every semantic feature stands on: the embedding-model seam (`EmbeddingManager`, one singleton that turns text into vectors for RAG, memory, codegraph, agent matching and tool selection), the rerank seam (`RerankManager`, Cohere over httpx), and the vector stores those vectors land in. The capability map says "three substrates run in parallel"; the code census says it is really **five and a half**: AWS S3 Vectors (RAG documents, the only live document store), Qdrant (field memory), pgvector (codegraph symbols live; two dead legacy legs), JSONB-float-array sidecars with Python cosine (agent semantic index, NL2SQL examples, operating-graph clusters), an in-process FAISS index inside the legacy memory relic, plus the mem0 fork's own store on a separate pod. The seed symptom — fragmentation may be costing retrieval quality — is confirmed, but the deeper finding is worse: the substrate's *configuration plane* is broken end-to-end (placebo settings, four disagreeing dimension knobs, and a committed production env that the F005 tenancy fix refuses to construct), so the platform cannot currently say with confidence that its document-vector plane is even on.

## B. What it does (real implementation + data path)

**The embedding seam.** `EmbeddingManager` (`orchestrator/core/llm/embedding_manager.py:54-259`) is a thread-safe singleton (`:262-284`) that lazy-loads one provider: OpenAI, OpenRouter, HuggingFace-local, or a `DeterministicEmbeddingProvider` fallback. Resolution order: DB system-settings under category `embeddings` (`:31-37,70-73`), then env config (`:79-86`), then hash-seeded random vectors on any miss (`:90-93,113-118,137-140`). Production env pins OpenRouter + `qwen/qwen3-embedding-8b` (`orchestrator/.env:55-56`). The model natively emits 4096 dims; the provider **Matryoshka-truncates to the configured dimension** (`core/llm/clients/openrouter_embedding.py:117-119`), which resolves to **2048** (`config.py:911` default; `core/llm/clients/base.py:34` documents 2048 as the deliberate Qwen3 truncation). Batch embedding uses a single OpenRouter array call with a 5-way parallel fallback (`openrouter_embedding.py:132-216`). A Redis embedding cache exists on the ingestion path only (`modules/rag/ingestion/manager.py:1432-1437`, with a dimension check). Every live consumer genuinely rides this one seam: RAG query/ingest (`modules/rag/service.py:924`, `ingestion/manager.py:465-466`), Qdrant field (`modules/context/adapters/vector_field.py:86,335,422`), codegraph (`modules/codegraph/codegraph_service.py:1302`), agent semantic matching with model-id cache-busting hashes (`core/routing/semantic_indexer.py:129-153`), and the tool-selection `ActionSemanticIndex`. That unification is real and is the module's best property.

**The rerank seam.** `RerankManager` (`core/llm/rerank_manager.py:34-185`) posts to Cohere `v2/rerank` (default model `rerank-v3.5`, `:24`), degrades to identity ordering without a key. It has **exactly one caller** in the whole codebase — `modules/rag/service.py:650-652` — and (verified for the probe) is never invoked in practice: `rag_rerank_enabled` defaults false, the search endpoint hardcodes `enable_reranking=False` (`api/documents.py:1470`), and no `COHERE_API_KEY` exists in either env file.

**Store 1 — S3 Vectors (the live document plane).** `S3VectorsBackend` (`modules/search/vector_store/backends/s3_vectors_backend.py`) binds one workspace to one bucket resolved from a `{workspace_id}` template; W2's F005 fix makes the constructor **refuse a template without the placeholder** (`:51-55`), refuses filter/workspace mismatches (`:158-169`), and drops any hit whose metadata workspace differs (`:190-196`). Ingestion stamps `workspace_id` and a 500-char text preview into metadata (`:246-254`), batching 50 vectors per put (`:268`). The RAG service caches one initialized backend per workspace (`modules/rag/service.py:888-904`) and always passes the explicit workspace filter (`:936-941`). Every production call site hardcodes `backend="s3_vectors"` (`api/cloud_documents.py:550-556,599-604`; `modules/rag/ingestion/manager.py:456-460`); the ingest side is gated by `S3_VECTORS_ENABLED` (`api/documents.py:79`), the query side is not gated at all. The corpus behind it is real: **644 documents / 19,130 chunks** in Postgres ([census](evidence/data/census.md)) — chunk *text* in `document_chunks`, vectors only in S3.

**Store 2 — Qdrant (field memory).** `VectorFieldSharedContext` (`modules/context/adapters/vector_field.py`) keeps all field memory in **one collection** (`field_memory`, `:50`) with COSINE distance, on-disk HNSW and payload (`:123-132`), partitioned by `field_id`/`workspace_id` payload indexes (`:136-142`) — dimension from `FIELD_EMBEDDING_DIM` (2048 default, `config.py:861`), embedded through the shared manager. It carries GDPR erase/export (`:214-279`), cursor-resumable compaction (`:496-568`, the W8/F063 closure), and Hebbian reinforcement gated by `record_access`. Constructed via the PRD-108 factory (`modules/context/factory.py:19-50`, backend `vector_field` default). It is the only Qdrant consumer besides one ops script. Production contents are **not inspectable from this machine** — no `QDRANT_*` env var exists outside the compose-internal default ([data/qdrant.md](evidence/data/qdrant.md)).

**Store 3 — pgvector.** Three legs. (a) **Live:** `codegraph_symbols.embedding` — raw-DDL pgvector, 7,702 rows in prod ([census](evidence/data/census.md)), written in batches of 100 through the shared manager, searched with the correct cosine operator `<=>` (`modules/codegraph/codegraph_service.py:1277-1330`), with a runtime `ALTER TABLE` guard that mutates the column dimension to match settings (`:840-905`). (b) **Zombie:** `EnhancedVectorStore` (`modules/search/vector_store/store.py`) — the module's namesake — whose backing table `vector_documents` was **dropped in PRD-135** as "legacy RAG path… zero rows, zero inbound code edges" (`alembic/versions/prd135_drop_bucket_4.py:5-12,45`). Its only consumers are themselves dead: `SearchService` and `ContextRetrievalEngine` have **zero callers outside `modules/search`** (repo-wide grep; the F079 remnant), and `knowledge_system.py:32` imports it and never uses it. (c) **Dormant:** `document_chunks.embedding`, NULLed by the S3 migration script (`scripts/migrate_to_s3_vectors.py:78-116`) but still in schema — plus a `search_vector` tsvector column with GIN index and an auto-update trigger that fires on **every chunk insert** (`alembic/versions/20260218_rag_v3_hybrid_search_and_feedback.py:28-82`) and has **zero readers** anywhere outside the dead store's hybrid method.

**Stores 4/5 — the sidecars.** Platform convention keeps several embedding sets *outside* any vector engine: `agents.semantic_embedding` is JSONB with Python cosine (`core/models/core.py:261`; `core/models/database_knowledge.py:244` states the convention), NL2SQL examples and operating-graph intent clusters do the same (keyed by `embedding_model_key`, `core/models/tool_routing.py:89-98`), and `ActionSemanticIndex` holds action embeddings in a per-process dict (`modules/tools/discovery/action_semantic_index.py:33`). The legacy `/api/v1/memory` relic builds **FAISS IndexFlatL2/IVFFlat in process memory** (`modules/memory/operations/augmentation.py:386-389,450-453`) — non-persistent, per-worker. The mem0 fork (separate repo/pod) runs its own store with its own embedder config; the memory dossier covers it.

## C. Honest quality — inspected against real behaviour and data

**What is genuinely good.** One embedding seam actually used by everything live — most platforms this age have three ad-hoc embedding clients; Automatos has one, with model-aware cache-busting (`semantic_indexer.py:143-153`) and a real batch path. The model choice is excellent (see D: Qwen3-Embedding-8B is a top-of-MTEB model at $0.01/M). The Qdrant field design — single collection, payload partitioning, on-disk HNSW, GDPR erase, cursored compaction — independently matches Qdrant's own recommended multitenancy architecture (see D). The F005 code fix is real defence-in-depth at three layers. The S3 migration script exists and is idempotent-ish with dry-run.

**The defects, with evidence:**

1. **The committed production config cannot construct the live document-vector backend.** `orchestrator/.env` — the same file whose `DATABASE_URL` reaches prod ([real-data-inventory](evidence/real-data-inventory.md)) — sets `S3_VECTORS_ENABLED=true` and `S3_VECTORS_BUCKET=automatos-ai` (`orchestrator/.env:51,60`): **no `{workspace_id}` placeholder**. That is the exact shared-bucket shape July's F005 flagged, and W2's fix now refuses it in the constructor (`s3_vectors_backend.py:51-55`). The boot-time check raises too (`config.py:1038-1046`) but is swallowed by `run_stage` (residual map, F004 note). Net effect under this env: **every** `S3VectorsBackend()` construction raises → caught in `_get_candidates`' blanket handler → empty results → "No relevant context found" (the RAG dossier's silent-cliff, C.2, from the other side). And there is no shared-bucket→per-workspace migration tool: `migrate_to_s3_vectors.py` re-embeds from Postgres, it does not move vectors between buckets — so if the deployed env matches the committed one, the entire document-retrieval plane has been fail-closed dark since W2 merged, with zero signal. If Railway's env was rotated to a templated bucket, the old shared bucket's vectors were orphaned and a full re-embed must have run — nothing in-repo records one. **Either way this needs a one-curl verification (list buckets / get_index) by someone with AWS access, before anything else in this dossier.**
2. **The embeddings settings surface is a placebo — the DB config plane for this module does not work at all.** PRD-136 canonicalized the settings to `(embeddings, provider|model|dimensions|rerank_model…)`: the migration renames old keys to those (`alembic/versions/prd136_collapse_llm_tiers.py:70-82`), the seeder creates them (`core/seeds/seed_system_settings.py:356-393`), and the Settings → Models → Embeddings card renders and saves exactly those rows (`frontend/components/settings/LLMTierCard.tsx:100-102,163`; `LLMModelsSettingsTab.tsx:57-65`; save via `saveCategorySettings('embeddings', …)`, `SystemSettingsTab.tsx:233`). But `EmbeddingManager` reads the **pre-PRD-136 long keys** under that category — `embedding_provider`, `embedding_model`, `vector_store_dimensions` (`embedding_manager.py:70-73`) — which neither seeder nor migration ever produce. Same for `RerankManager`: it reads `rag_rerank_model` (`rerank_manager.py:61-65`), which PRD-136 renamed to `rerank_model`. And `modules/memory/__init__.py:38-52` queries columns `setting_key`/`setting_value` that don't exist on the table at all (`core/models/system_settings.py:59-60` — `key`/`value`), so it *always* silently returns 2048. **Consequence:** an admin changing the embedding provider, model, dimension, or rerank model in the UI changes nothing; env vars are the only real configuration; the tooltip "Dimensions are derived from the model" is false twice over.
3. **Four dimension knobs, three values, and the live index dimension is unknowable from the repo.** Effective embedding dimension is 2048 (defect-2 fallback chain → `config.py:911` default; env `VECTOR_STORE_DIMENSIONS` is unset — the .env instead sets `EMBEDDING_DIMENSION=4096` (`orchestrator/.env:57`), **a variable no code reads** (repo grep: one comment, `scripts/eval/tool_routing/run_eval.py:392`)). Meanwhile `S3_VECTORS_DIMENSION=4096` (`orchestrator/.env:62`) is what a fresh S3 index would be created with (`s3_vectors_backend.py:60,100-107`) — 2048-dim vectors put into a 4096 index fail at runtime; if the prod index predates the 4096 edit it is a 2048 index and the env is a lie; `_verify_or_recreate_index` only logs the discrepancy (`:118-131`). The dead memory models hardcode a third value, `Vector(1024)` (`knowledge_system.py:66,89`). The Qdrant field uses its own fourth knob, `FIELD_EMBEDDING_DIM=2048` (`config.py:861`) — currently consistent by luck, not by construction. Codegraph papers over the chaos by **ALTERing its column at runtime** to whatever it resolves (`codegraph_service.py:852-905`) — a fifth writer of schema truth (the W6/F051 complaint, in miniature). The RAG dossier's "4096-dim" production claim traces to the dead `EMBEDDING_DIMENSION` var and should be corrected to *effectively 2048, index dimension unverified*.
4. **The fallback embedding provider silently corrupts semantics.** On any missing key/credential-resolution failure/unknown provider, the manager swaps in `DeterministicEmbeddingProvider` — **hash-seeded `standard_normal` random vectors** (`base.py:200-228`) — with only a log warning. Combined with defect 2 (DB plane dead ⇒ env is the single point of truth) and the live OpenRouter-402 outage in the data (playbook LLM steps failing daily since ~06-16, [real-data-inventory](evidence/real-data-inventory.md) §3), the platform is one env-var typo or credit lapse away from *quietly meaningless* retrieval across RAG, field memory, codegraph and agent matching simultaneously — indistinguishable from working, since nothing measures retrieval quality (defect 8). Query-time 402s raise out of the provider (`openrouter_embedding.py:123-130`) and are swallowed to empty by every consumer's blanket handler.
5. **A third of the substrate is zombie code that still bites.** `EnhancedVectorStore` survives its own table's deletion (B, store 3b). Beyond dead weight it is *wrong* dead weight: its "cosine" mode actually issues pgvector's **L2 operator `<->`** (`store.py:625-634` — cosine is `<=>`; codegraph gets this right); its `workspace_id` filter targets a column its own CREATE TABLE never defines (`:150-164` vs `:618-621` — any scoped call would SQL-error to `[]`); its dedup hash uses salted Python `hash()` (`:273`, unstable across processes); and `initialize()` would happily re-create the PRD-135-dropped table plus two auxiliary tables on any future call (`:145-259` — a sixth schema writer). `SearchService`/`ContextRetrievalEngine` (F079) and the FAISS augmentation leg complete the kill list. The `vector_store_type` setting seeded as `faiss` with options `faiss|chroma|pinecone|weaviate` (`seed_system_settings.py:428-434`) describes engines the platform has never run — settings-as-fiction.
6. **Hybrid infrastructure was built at the DB layer and never wired** — the mirror image of the RAG dossier's "hybrid is decorative": the rag_v3 migration added `document_chunks.search_vector` with a GIN index **and a trigger that pays its maintenance cost on every insert** (`20260218_rag_v3_...py:28-82`), and no live query reads it (repo grep: only the dead store's `_hybrid_search`). 19,130 chunks carry a full-text index nothing uses.
7. **Backup asymmetry: Qdrant is the un-backed-up substrate.** F050's fix dumps Postgres (which covers codegraph + chunk text) and mem0 (`scripts/dr/backup.sh`; `docs/runbooks/DR-postgres.md`), but there is **no Qdrant snapshot anywhere** — no snapshot API call, no runbook line (grep: zero mentions). Field memory — the substrate the memory dossier proposes to *also* host durable L3 memory — has an RPO of infinity. Qdrant ships a first-class snapshot/recover API (see D); this is a dozen lines of cron.
8. **Nothing is measured.** No substrate emits candidates-returned/latency/error telemetry on the query path (`search_analytics` exists only inside the zombie store); recall@k exists for no store; embedding-model changes have no eval gate (the tool-routing eval harness exists but is offline-only, [repo-eval-artifacts](evidence/data/repo-eval-artifacts.md)). A substrate whose emptiness looks identical to success (defects 1/4) with no metric watching it is the T3 thesis in its purest form.

**Maturity score: 2 / 5.** The seam architecture (one embedding manager, one good cheap model, payload-partitioned Qdrant) deserves a 4; but the substrate is judged as an operated system, and as operated it cannot prove its main plane is on (C.1), its entire DB-config surface is a placebo (C.2), its dimension story is incoherent (C.3), its failure mode is silent random vectors (C.4), a third of it is dead-but-dangerous code (C.5), and half of what *is* live has no backup (C.7) and no metrics (C.8). North-Star framing: agents cannot deliver client-quality work over a retrieval plane that may have been silently empty for weeks — this module is currently a *ceiling* on RAG, memory, and codegraph quality, not a foundation.

## D. Competitive teardown

The right comparators here are not vector-DB vendors to buy, but the native capabilities of the engines Automatos already runs — plus the embedding-model frontier.

- **Qdrant-native (already deployed, underused).** Qdrant's own guidance for exactly this shape — many tenants, one cluster — is a **single collection with payload-based partitioning**, explicitly *not* per-tenant collections ("not recommended to create hundreds… of collections… increased costs and… cluster instability"), with `group_id`-indexed tenants, per-tenant HNSW building (`payload_m`/`m=0`) and tiered shard isolation for big tenants ([qdrant.tech/documentation/manage-data/multitenancy](https://qdrant.tech/documentation/manage-data/multitenancy/), [qdrant.tech/articles/multitenancy](https://qdrant.tech/articles/multitenancy/)). The field adapter already implements this pattern — honest credit — but the *document* corpus sits on a different engine entirely. Qdrant's Query API does **server-side hybrid (dense+sparse) with built-in RRF fusion** ([qdrant.tech/articles/hybrid-search](https://qdrant.tech/articles/hybrid-search/)) — Automatos fuses vector-only variants client-side and has no sparse leg. And Qdrant has first-class **collection snapshots + recover-from-snapshot APIs** ([qdrant.tech/documentation/snapshots](https://qdrant.tech/documentation/snapshots/)) — the missing C.7 backup is an API call, not a project.
- **pgvector-native (already deployed for codegraph).** pgvector 0.8.0 (Oct 2024) added **iterative index scans** that fix the classic filtered-ANN "overfiltering" failure (keep scanning until the filter is satisfied) plus better cost estimation for filtered queries ([postgresql.org/about/news/pgvector-080-released](https://www.postgresql.org/about/news/pgvector-080-released-2952/)); AWS measured up to 9× faster filtered query processing on Aurora ([aws.amazon.com/blogs/database — pgvector 0.8.0 on Aurora](https://aws.amazon.com/blogs/database/supercharging-vector-search-performance-and-relevance-with-pgvector-0-8-0-on-amazon-aurora-postgresql/)). Relevant because the chunk text, a dormant `embedding` column, *and* an unused tsvector GIN index already sit in `document_chunks` — a Postgres-consolidated hybrid path is one `UPDATE` + one index away, with the DR story (F050) inherited for free. The zombie `EnhancedVectorStore` predates all of this and reflects none of it.
- **AWS S3 Vectors (the current document engine).** Now GA with 2B-vector indexes; warm-query latencies reported ~100–380 ms at 10M vectors, but AWS positions it for **infrequent, cost-optimized querying**, and ~20% of queries returning K−1 results is a documented quirk ([aws.amazon.com/blogs/aws — S3 Vectors GA](https://aws.amazon.com/blogs/aws/amazon-s3-vectors-now-generally-available-with-increased-scale-and-performance/), [dev.to — S3 Vectors real performance numbers](https://dev.to/siddhantkcode/aws-s3-vectors-at-scale-real-performance-numbers-at-10-million-vectors-2lno), [docs.aws.amazon.com — limitations](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-limitations.html)). At 19k chunks its rest cost is pennies — but it is AWS-only (the open-core local edition therefore ships with **no functional document retrieval**: compose defaults `S3_VECTORS_ENABLED=false` with no fallback store, `envs/api.defaults:68`), it has no snapshot/export story comparable to Qdrant/pg_dump, and metadata filtering is coarse (the F005 fix had to post-filter client-side because the backend query carries no filter at all, `s3_vectors_backend.py:172-179`).
- **Embedding-model frontier.** Honest positive first: **Qwen3-Embedding-8B was the #1 MTEB multilingual model at release (score 70.58, June 2025), supports Matryoshka 32→4096** ([qwenlm.github.io/blog/qwen3-embedding](https://qwenlm.github.io/blog/qwen3-embedding/)) and costs **$0.01/M tokens on OpenRouter** ([openrouter.ai/qwen/qwen3-embedding-8b](https://openrouter.ai/qwen/qwen3-embedding-8b)) — Automatos' model pick is genuinely at the frontier and 13× cheaper than OpenAI's flagship. The competition: **Voyage** `voyage-3-large` beats OpenAI-v3-large by ~9.7% average across 100 datasets, and `voyage-3.5` ($0.06/M) adds quantization-aware training — int8@2048 cuts vector-DB cost ~83% vs float32@3072 with *better* retrieval ([blog.voyageai.com/2025/01/07/voyage-3-large](https://blog.voyageai.com/2025/01/07/voyage-3-large/), [blog.voyageai.com/2025/05/20/voyage-3-5](https://blog.voyageai.com/2025/05/20/voyage-3-5/)); **OpenAI** `text-embedding-3-large` remains the default-safe choice at $0.13/M, 3072-dim Matryoshka ([platform.openai.com/docs/models/text-embedding-3-large](https://platform.openai.com/docs/models/text-embedding-3-large)). Automatos' gap is not model quality — it is that **no eval could detect a model regression or justify an upgrade** (C.8), and the int8/binary quantization the frontier models are trained for is unused everywhere.

**Where Automatos actually stands:** model choice top-tier; Qdrant field design textbook; everything operational around them — config truth, dimension governance, hybrid, backup, telemetry, and the very liveness of the document plane — is behind what each engine offers natively and behind any managed competitor's baseline.

## E. Build / extend / adopt / replace — the verdict

**EXTEND the seams; CONSOLIDATE the stores onto the two engines already running (Qdrant for semantic workloads, pgvector for codegraph); REPLACE S3 Vectors as the document store; ADOPT no new vendor; KILL the zombies.** Reasoning against the reuse bias: nothing external needs buying — the platform already operates two engines whose native features exceed what it uses; the fix is subtraction and wiring, not procurement.

1. **Embedding/rerank seam — EXTEND (keep in-house).** A singleton wrapper over OpenRouter/OpenAI is not something LiteLLM or a vendor meaningfully improves at this scale, and the seam's design (model-id cache-busting, batch, Matryoshka) is sound. The work is repair: read the canonical `(embeddings, provider|model|dimensions|rerank_model)` keys the seeder/migration/UI already agree on (C.2), collapse the dimension knobs to that one authority (C.3), and make the deterministic fallback opt-in (`EMBEDDING_ALLOW_FALLBACK`, default false = raise loudly) (C.4). ~2–4 days.
2. **Document vectors — REPLACE S3 Vectors with a Qdrant collection.** The forcing facts: (a) the plane must be rebuilt anyway — the committed config can't construct the backend and there is no bucket-to-bucket migration, so a full re-embed (~$0.08, see H) is on the table regardless; (b) Qdrant is already deployed, already implements the recommended multitenancy pattern in this codebase, and brings server-side hybrid + snapshots (D); (c) it makes the **open-core local edition's RAG actually work** — today OSS deploys have no document retrieval at all; (d) one engine less. Shape: second collection (`document_chunks`), workspace payload partition exactly like `field_memory`, ingest/query behind the existing `_get_s3_backend` seam (rename it), reuse `migrate_to_s3_vectors.py`'s re-embed skeleton. ~3–5 days including the migration run. *Alternative if minimal motion wins:* stay on S3 Vectors — set a templated bucket in the real env, run the existing re-embed script, accept AWS-only open-core and no snapshots. Days cheaper now; keeps three engines and the local-edition hole. The Qdrant move is the North-Star answer (working retrieval for every deployment shape); the S3 stay is defensible only as a stopgap. Gerard's call which ships first — but C.1's *verification* (is prod dark?) precedes both.
3. **Codegraph — KEEP on pgvector** (aligned with the knowledge-graphs dossier: EXTEND, fix F064). Its vectors join relationally against symbols/projects; moving them buys nothing. Adopt pgvector ≥0.8 iterative-scan settings when filtered queries appear.
4. **Kill list (all zero-production-caller, grep-proven):** `EnhancedVectorStore` + `modules/search/service.py` + `retrieval/context_retrieval_engine.py` (F079), the FAISS leg with the `/api/v1/memory` relic (memory dossier E.4 concurs), the `Vector(1024)` models in `knowledge_system.py` (0 rows ever — keep only the still-referenced `MemoryItem`/`HarnessPrescription` model classes or rehome them), `s3_vectors_mock` out of prod imports, the `vector_store_type` faiss/chroma/pinecone/weaviate settings fiction, and the tsvector trigger **unless** J.6 wires it (then it's the hybrid leg for free). The JSONB sidecars (agents/NL2SQL/edges) are fine — small, joined, honest — leave them.
5. **Explicitly not adopting:** a managed vector DB (Pinecone/Weaviate/Zilliz — nothing they add is the bottleneck at 20k–100k vectors), and pgvectorscale/dedicated engines (premature below ~10M vectors).

## G. Quality metric

The substrate's job is *silent fidelity*, so its metrics are liveness and truthfulness, feeding T3:

1. **Retrieval-plane liveness (SLI, per store):** share of vector queries returning ≥1 candidate + hard-error rate, emitted from the query seams (`_get_candidates`, `vector_field.query*`, codegraph `semantic_search`) into the existing `slo_metrics` plane. **Today: unmeasurable — and the honest number for the S3 plane is plausibly 0% since W2 (C.1).** This metric existing would have caught both C.1 and the 402 outage within a day.
2. **Config integrity (CI gate, boolean):** one test asserting the effective embedding dimension == every store's declared dimension (Qdrant collection param, S3 index var, codegraph column atttypmod) and that the settings keys the managers read exist in the seeder. Today: **fails on at least three counts** (C.2/C.3).
3. **Retrieval quality (offline, per store):** recall@k / MRR on a ~50-query gold set over the real 19k-chunk corpus (shared with the RAG dossier's G), re-run on any embedding-model or dimension change. Today: no gold set, no number.
4. **Backup verifiability:** age-of-newest-snapshot per store (pg_dump exists; Qdrant snapshot = missing). Today: Postgres ≤24h by runbook; Qdrant ∞.

## H. Cost note (informational)

- **Embedding:** qwen3-embedding-8b via OpenRouter = **$0.01/M tokens** ([openrouter.ai](https://openrouter.ai/qwen/qwen3-embedding-8b/pricing)). Re-embedding the whole corpus (19,130 chunks × ~400 tokens ≈ 7.7M tokens) ≈ **$0.08 one-time**; a query embed (~50–200 tokens) ≈ $0.000002 — vanishing next to the LLM spend visible in `llm_usage` (31k rows). Voyage-3.5 at $0.06/M would still be corpus-trivial ($0.46) if quality ever justified it.
- **Storage/compute:** S3 Vectors at this scale ≈ pennies/month at rest; the Qdrant pod already runs for field memory, and +19k on-disk 2048-dim points ≈ ~160 MB — no new infra either way. pgvector adds negligible load at 7.7k symbols.
- **The real cost is operational:** three engines × config drift × zero telemetry = engineer-hours and silent outages, not dollars. Consolidation (E.2) is a cost *reduction* in the only currency that matters here.

## I. UX / surface

The substrate is invisible until it lies; every surface change is about making it stop lying:

1. **Settings → Models → Embeddings card (the placebo, C.2):** either rewire the managers to the canonical keys and keep the card, or delete the card — shipping a settings UI that provably does nothing is the worst option. When kept: render the *effective* resolved config from `get_provider_info()` (provider/model/dimension actually in use, and whether it came from DB or env), not the row values; show a red "deterministic fallback active" state instead of burying it in logs. Drop the `vector_store_type` fiction and the false "dimensions are derived from the model" tooltip.
2. **Command Center primitive-health strip (W10 pattern, honest-unknown over fake-green):** add three tiles — S3-Vectors/Qdrant/pgvector — showing reachability, index/collection dimension, point counts, and the G.1 liveness SLI. A "document retrieval returned 0 candidates for N hours" banner is the single highest-value observability pixel this module can buy; it would have surfaced C.1 immediately.
3. **RAG config panel (`components/system/rag-configuration.tsx`):** currently displays `embedding_model` from per-config rows that the manager ignores — same placebo family; fold into (1).
4. **No new user-facing surface is warranted** — this module should get *smaller* in the UI as it gets more honest.

Fix the truth-plane (J.1–J.4, roughly two weeks of work) before touching anything ambitious; consolidation (J.5) then falls out almost for free.
