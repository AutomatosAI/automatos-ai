# Module Dossier — Missions & Orchestration (coordinator + board spine)

**Module key:** `missions-orchestration` · **Tier:** deep · **Status:** live
**Reviewed:** 2026-07-04, against main (pinned tree) + live Railway Postgres (read-only, captured 2026-07-04)
**July baseline findings carried in:** F001, F023, F024, F025, F049, F090 (all graded FIXED in the Phase-0 residual map, with named residuals — see §C)
**Security/adversarial lens:** deliberately excluded — runs as the separate Opus hardening pass.

---

## A. What it is

Missions & orchestration is Automatos's headless execution plane — the machinery that lets Auto and the agent roster do multi-step work without a human driving each step. It is really two coordinated engines sharing one database. The **Mission engine** turns a natural-language goal into an LLM-planned task DAG, matches each task to a roster agent with explainable scoring, dispatches tasks in parallel under dollar-denominated budget bands, verifies outputs with a cross-model LLM judge, detects stalls, replans a bounded number of times, and synthesises a final deliverable — all driven by a stateless 5-second coordinator tick (`orchestrator/services/coordinator_service.py`). The **Board spine** is a Postgres-native task dispatch layer (`orchestrator/services/board_dispatcher.py`) — `FOR UPDATE SKIP LOCKED` claims, lease heartbeats, an honest requeue sweeper, and LISTEN/NOTIFY push — that executes standalone board tasks and mirrors every Mission onto the kanban surface humans watch. Between them sit a validated state machine with dual-write audit events (`orchestrator/services/orchestration_state.py`), a plan-approval workflow (policy, countdown, in-chat card), and the Mission-Zero onboarding consumer.

## B. What it does — implementation and data path

### B.1 Mission lifecycle (create → plan → approve → run → verify → complete)

**Create & plan.** `CoordinatorService.create_mission` (`coordinator_service.py:2157-2233`) writes an `OrchestrationRun` in PENDING, transitions to PLANNING, and either plans synchronously or — with `config.async_planning` — returns immediately and lets the tick sweep plan later (`_sweep_async_planning`, `:2476-2506`, PRD-163 S5). Planning (`_run_planning`, `:2235-2422`) loads the workspace's active agents (plus ephemeral onboarding clones for Mission Zero, `:2263-2273`), then calls `MissionPlanner.decompose` (`modules/coordination/planner.py:488`). Decomposition is template-first (a 1,447-line library of pre-built DAGs for common mission shapes, `modules/coordination/templates.py:1-11`) falling back to an LLM call with up to 3 validation-retry rounds; the raw plan is parsed (`planner.py:1099`), synthesis tasks are force-appended if missing (`:1208`), and the DAG is structurally validated against the roster (`:1386`). Complexity is scored by keyword heuristics — deliverable keywords, 10 domain clusters, word count, attachments (`planner.py:177-269`) — and maps to `max_concurrent` 1/2/3 (`:272-278`). Token budget is summed per-task from complexity tiers (`:169-174`).

**Agent-match preview.** Before approval, `AgentMatcher.compute_signals_for_tasks` ranks candidates per task with a weighted blend — skill 0.40 / tools 0.25 / model-fit 0.15 / availability 0.10 / history 0.10, plus additive semantic 0.35 (embedding cosine against the agent capability card) and field-signal 0.15 (PRD-164 S2 Q21) — each with a human-readable `reason` persisted onto the plan snapshot so the approval card can show *who* would run each task and *why* (`modules/coordination/agent_matcher.py:1-34`; `annotate_plan_with_matches`, `coordinator_service.py:122-145`). Threshold 0.4; explicit human overrides always win.

**Approval.** The plan is priced (`_estimate_cost_usd`, `:2424-2428` — flat `COORDINATOR_COST_PER_1K_TOKENS` $0.003/1k, `config.py:721`) and evaluated against the workspace approval policy (`core/services/approval_policy.py`): `always_ask` (the default), `auto_below_budget` ($ ceiling), or `full_auto` (only honoured when the §12.3 autonomy gate is on; otherwise downgrades to ask). Non-auto plans transition to AWAITING_APPROVAL and fire one `mission_plan_ready · action_required` notification (`:2398-2420`). An optional Devin-style countdown (`auto_proceed_after_seconds`) stores a deadline the tick sweep auto-proceeds past (`check_approval_countdowns`, `:2430-2474`) — but it is opt-in config, not the default. Approval-time plan editing is real: per-task `agent_role`/`title`/`description` edits apply through the pure `apply_plan_task_edits` (`:148-210`, PRD-163 S4/Q57) via `PATCH /api/missions/{id}/plan` (`api/missions.py:1222`), and whole plans can be imported without re-decomposition (`import_plan`, `coordinator_service.py:2637`; `api/missions.py:441`). `plan_only` always parks at approval (`:2355-2359`).

**Tick execution.** The coordinator registers a 5s job on the shared APScheduler (`start`, `:1186-1218`; wired at `main.py:441-443`), guarded by `max_instances=1` plus an in-process re-entrancy flag (`:1241`). Each tick processes every RUNNING run (`:1259-1264`): ensures the Qdrant mission field exists (stale-field re-create, `:1342-1377`), then a three-phase pattern that is one of the module's best pieces of engineering — **Phase 1** serial DB prep (`_prepare_task`, `:1837-2009`: ASSIGNED→RUNNING, upstream outputs injected as a token-budgeted field digest rather than raw stuffing (`:1863-1889`, PRD-164 S4 Q22), synthesis prompts built from full upstream text (`:1905-1943`), power-mode caps resolved from `system_settings` (`:213-250`; light/standard/max → tool-iteration and tier caps + scaled timeouts 120/240/600s, `:91-95`)), then an explicit commit so the connection is never idle-in-transaction across LLM awaits (`:1449`, the W1-S9 fix for the documented 9-hour leak); **Phase 2** parallel agent I/O via `asyncio.gather` with per-mode timeouts and zero DB access (`_run_agent_io`, `:2011-2069`); **Phase 3** serial result recording (`_record_task_result`, `:2071-2151`). Execution itself is the same `AgentFactory.execute_with_prompt` engine chat uses — Missions add no second executor.

**Dispatch & budget.** `MissionDispatcher.dispatch_ready` (`modules/coordination/dispatcher.py:557-729`) fills `max_concurrent − active` slots from queued/retrying then dependency-ready tasks, claiming each with an optimistic-locking raw UPDATE conditioned on `version_id` (`claim_task`, `:120-178` — no double dispatch under concurrent ticks). Every dispatch passes a budget admission gate (`_pre_dispatch_budget_check`, `:485-554`): dollar bands (HEALTHY/WARNING/CRITICAL/EXCEEDED) computed by the **shared** `services/budget_ceiling.py` helper (PRD-181 S2 — the same ceiling arithmetic Missions, board and Playbooks read; F060's "no parallel plane"), with synthesis/review tasks still allowed at CRITICAL, and EXCEEDED (or all-deferred) pausing the run with an audit event (`:643-717`).

**Verification.** On each tick the reconciler (`modules/coordination/reconciler.py:126-262`) moves COMPLETED tasks through VERIFYING: stage 1 is 8 deterministic check types (format_regex, min/max_length, required_sections, json_schema, url_valid, contains_keywords, word_count_range — `modules/coordination/deterministic_checks.py:10-12`) with must_pass short-circuit; stage 2 is a cross-model LLM judge — the verifier model is deliberately chosen from a *different* model family than the executor (`verification.py:102-141`), scores relevance/completeness/accuracy/format_compliance + confidence against thresholds 0.7 pass / 0.4 fail / 0.5 confidence-escalation (`config.py:683-685`), with an output-hash cache so identical retry output never burns a second judge call (`verification.py:311-354`). **What the verdict then does is the module's biggest honesty problem — see §C.3.**

**Stall handling & bounded replanning.** Tasks stuck ASSIGNED >60s or RUNNING >300s are recovered to assigned (`config.py:676-677`; reconciler stall pass). Above that sits the PRD-164 S4 joiner: a pure Magentic-One-style progress ledger (`modules/coordination/progress_ledger.py:42-134`) snapshots done/verified/attempt counts per tick, classifies progress/churn/idle, and at 3 consecutive churn observations issues REPLAN through the one existing `replan_mission` engine while `replan_count < 2`, else HALT → run FAILED with `stop_reason='stalled'` and a memory capture (`coordinator_service.py:1522-1661`). Every verdict is an audit event.

**Completion.** All-tasks-verified advances the run to VERIFYING then `_complete_verified_run` (`:3791-3889`): output summary, an informational cross-task consistency LLM check (`:3891-3969`; explicitly does not gate), COMPLETED transition, cost summary, `mission_complete` notification, and mission-memory capture. Completed runs' outputs are ingested into workspace knowledge by the flywheel sweep (`_save_pending_output_documents`, `:1150-1181`) — SQL-side terminal markers + `created_at DESC` ordering (the W9 F049 fix), poison runs stamped `output_ingest_failed` so they drop out next tick. `save-as-routine` extracts a reusable template from a finished run (`api/missions.py:1509`).

### B.2 Board spine (PRD-161 + W1/W10/W11 hardening)

`board_tasks` is the single work queue: `claim_tasks` (`services/board_dispatcher.py:64-181`) claims assigned tasks exactly-once via `FOR UPDATE SKIP LOCKED` with urgency-then-age ordering (`:43-46`) and optional per-agent slot caps computed in a windowed CTE (`:104-144`, default 2 slots, `config.py:507`); the claim flips rows to `in_progress` with `attempts+1` and a 600s lease in one statement. `requeue_expired_leases` (`:184-247`) is the honest sweeper: lease-lapsed rows return to assigned while attempts remain, else terminal `failed` with a reason — never silently closed done. `renew_lease` (`:272-308`) is the F024 fix: a wall-clock heartbeat task (`api/board_tasks.py:905-940`) renews at half-lease for the life of every run so only genuinely dead runs get swept; renewal never resurrects terminal rows. `scan_sla_breaches` (`:311-341`) fires once-only SLA notifications off the previously dead `sla_deadline` column. The background loop (`run_dispatch_loop`, `:484-538`, started as an asyncio task at `main.py:553-557`) wakes sub-second on `pg_notify` via a dedicated LISTEN thread (`:374-418`) with the 5s poll as fallback, sweeps, claims, and launches each task **individually** through the same `_launch_task_execution` the API uses — no more 3-tasks-into-1-prompt fold-in. Q44 rejected-task redo consumes reviewer feedback into the redo prompt exactly once (`:441-449`).

Execution (`api/board_tasks.py:997-1137`) runs the same `AgentFactory.execute_with_prompt`, brackets it with the lease heartbeat, and post-W1 fails honestly: an executor `status:error` dict becomes terminal `failed` with `error_message`, a failure dispatch and a report — same path as a crash (`:1043-1070`, F023). `review_mode='manual'` parks results in `review` instead of `done` (`:1072`). Before executing, every spine-launched task passes the W11 approval gate (`_board_task_blocked_pending_approval`, `:943-994`): an active ApprovalGrant proceeds; otherwise the **same** `evaluate_approval` primitive Missions use decides, and an ask blocks the task against a durable, expiring, revocable grant. Two honesty caveats live here (§C.4).

**Board ↔ Mission bridge.** Every Mission gets a parent BoardTask (`source_type='orchestration'`) and every mission task a child (`'orchestration_task'`), status-synced through an explicit vocabulary map (`services/orchestration_board_bridge.py:49-57, 76-128`); the spine's claim loop excludes recipe-sourced rows (`board_dispatcher.py:92,117,146`) and both PATCH launch paths exclude all three non-executable source types (`api/board_tasks.py:43-46, 561-568, 884-897` — the F025 fix). Board mutations push real LISTEN/NOTIFY SSE frames with per-workspace isolation (`services/board_events.py`, F090 fixed), consumed by the Command Center (`frontend/components/command-center/command-center-shell.tsx:74-75`, `hooks/use-board-event-stream.ts`) with the old poll deleted under a regression test.

**State machine.** All Mission state changes go through `transition_task`/`transition_run` (`services/orchestration_state.py:84+`): allowed-transition validation, timestamps, an `OrchestrationEvent` appended in the **same transaction** (dual-write consistency by construction), and `StaleDataError → ConflictError` optimistic locking. The probe question "is the dual-write consistent?" — yes at the mechanism level; the residual risk is that `run.config` JSONB mutations (progress ledger, field_id, approval deadline) happen *outside* this machine, so config state and event stream can drift on rollback-retry paths, though nothing observed in the data.

## C. Honest quality — inspected against real behaviour and real data

The live data (17 runs / 122 tasks; 1,449 board tasks; captured 2026-07-04 → `reports/dossiers/evidence/data/missions-orchestration.md`, `data/board-tasks.md`) tells a sharper story than the code.

### C.1 The Mission engine works when driven — and is almost never driven

The two completed missions verified all their tasks and burned 264k/430k tokens; per-task research outputs at 19-22k tokens each reached `verified`; failure semantics are honest (`dependency_failed`, `human_cancelled`, `skipped` downstream tasks). The machinery demonstrably executes end-to-end. But: **only one workspace out of 21 has ever run a Mission; no Mission has been created since 2026-06-13; 8 of 17 runs sit `awaiting_approval` with 0 tokens — some since April.** The engine's dominant live state is parked at its own approval gate. Root cause is structural, not a bug: the default policy is `always_ask` (`approval_policy.py` DEFAULTS), exactly **one** `mission_plan_ready` notification is ever sent (`coordinator_service.py:2410-2420`; the notifications sample shows a single `action_required` row, dated 06-13), the countdown auto-proceed requires opt-in config nothing sets, the tick loop only touches RUNNING runs (`:1259-1264`) so an awaiting run is invisible to the coordinator forever, and there is no reminder, no expiry, no escalation, and no prominent approval inbox. For the North Star — Auto operating autonomously — this is the single largest defect in the module: **the human-in-the-loop gate is a one-shot notification with no loop.**

### C.2 The Board leg is genuinely alive — and its surface lies about playbook health

Daily playbook-cron and heartbeat-review tasks flow through 2026-07-03. The spine itself post-W1 is honest: the only 2 `failed` rows in the table's entire history are dated 2026-07-03, right after the W1 honest-failure lanes landed. But **194/1,349 done tasks carry an `error_message` and 484/1,349 have no result at all** — the daily `Recipe:` playbook tasks whose LLM step has been failing with OpenRouter 402 since mid-June are still closed `done` every day. That completion path belongs to the recipe executor (playbooks module), which bypasses `_launch_task_execution` — but it lands on *this* module's board surface, so the kanban shows green over a three-week production outage. The board is the platform's operational truth surface; as long as any lane writing to it can close failures as done, "board truth" is only as honest as its least honest writer. (Cross-module fix; flagged to the playbooks dossier.)

### C.3 "Two-stage verification" never gates — FAIL verdicts pass anyway

The verifier's system prompt says it plainly: *"Your feedback is ADVISORY ONLY — it will NOT reject or retry the task"* (`verification.py:158`). The reconciler confirms it: after computing the verdict, it **always** transitions the task to VERIFIED — a FAIL or PARTIAL merely stashes `review_feedback` into `output_metadata` (`reconciler.py:457-479`). The full retry-with-feedback machinery (`_apply_verdict_fail` `:521`, `_apply_verdict_partial` `:600` — requeue with previous output + verifier feedback, escalate on exhaustion) is **dead code with zero callers**. Even a task returning *empty output* — which `verify_task` hard-FAILs (`verification.py:382-387`) — is marked VERIFIED and flows into synthesis. The revision-prompt path in `_prepare_task` (`:1901-1931`) that consumes `verification_feedback` can therefore only fire for tasks requeued by *agent-error* retries, not by verification. This was a deliberate retreat (retry storms burned tokens on heading-name guessing — the `required_sections` carve-outs at `reconciler.py:365-374` and `verification.py:521-543` document the scar tissue), and advisory-mode is a defensible resting point. But the result is that the module *advertises* a quality gate ("two-stage verification, cross-model judge") that in live behaviour is a quality *annotation* — the platform pays judge tokens on every completed task and then acts on none of it. Client-facing quality currently rests entirely on the executing agent's first attempt plus the synthesis agent happening to read upstream feedback.

### C.4 The board approval gate can never measure cost, and fails open

`_launch_task_execution` calls the gate without any cost estimate, so `evaluate_board_task_approval` defaults `estimated_cost_usd=0.0` (`api/board_tasks.py:968-970`; `services/board_approval.py:63-77`). Under `auto_below_budget`, $0.00 is always at-or-below any ceiling — **the dollar ceiling on board tasks is arithmetically incapable of tripping.** Only a flat `always_ask` can block a board task. This is consistent with the live data: `approval_grants` has **0 rows ever** (real-data inventory) while spine tasks execute daily — the gate has never once asked in production. Second: the whole gate is wrapped in a fail-*open* `except` ("a policy-read fault must not wedge board execution", `:989-994`) — a reasoned trade-off, but it means the governance gate degrades silently to off on any internal error. Missions' gate, by contrast, prices plans from real token estimates and fails closed into AWAITING_APPROVAL.

### C.5 Mission checkpoints are decorative

`checkpoint_service.write_checkpoint` (`services/checkpoint_service.py:40`) has **zero production callers** — grep finds only the definition and the `list_checkpoints` consumer behind `GET /api/missions/{id}/checkpoints` (`api/missions.py:1942-1952`). The advertised "checkpoint after each verified task for crash recovery" (PRD-123 Pattern #8, the module docstring) never happens; the endpoint always returns an empty list read from S3. Crash recovery in reality is coarser: a coordinator process death mid-`gather` loses all in-flight LLM work; the tasks sit RUNNING until the >300s stall threshold recovers them to assigned and they **re-run from scratch** (tokens re-burned, partial tool work discarded). The board leg is better protected (lease + sweeper + boot reaper), but "resume" everywhere means "restart the task", never "continue it".

### C.6 Residual double-execution and starvation edges (from FIXED findings)

Both carried honestly from the Phase-0 residual map, verified still present in code:
- **Mission-mirror double execution, narrower residual (from F025):** the claim loop filters only `source_type <> 'recipe'` (`board_dispatcher.py:92,117,146`); `run_task_now` (`api/board_tasks.py:828`) resets any non-running task to assigned and the inbox→assigned auto-transition (`:543-544, 592-599`) can do the same — an explicit Run-Now on an orchestration-mirror row puts it where the spine will claim and board-execute it **in parallel with the Mission engine**. The `_NON_EXECUTABLE_SOURCE_TYPES` frozenset exists (`:43-46`) but is not enforced in `claim_tasks`/`run_task_now`.
- **Flywheel markerless re-starve (from F049):** a COMPLETED run with zero VERIFIED tasks returns None with no marker (`coordinator_service.py:820-821` region), and `ingest_agent_output` has fail-soft None paths that also stamp nothing (`services/knowledge_flywheel.py:159,166,223`); a batch-size clump of such runs at the newest `created_at` positions permanently occupies the DESC batch.

### C.7 Scale posture: single-coordinator, one-workspace-proven

The coordinator is a singleton tick (`max_instances=1` + `_tick_running` guard, `:1207-1244`) processing all active runs of **all** workspaces serially within a tick, with parallelism only inside a run's dispatch batch. There is no per-workspace fairness, no sharding, no horizontal coordinator scale — a workspace's heavy mission delays every other workspace's tick work. The board spine, in contrast, is genuinely multi-worker-safe by construction (SKIP LOCKED). None of this has ever been load-tested by reality: the live maximum is 4 benchmark missions paused in one workspace. Fine for the pilot; unproven beyond it.

### C.8 Vocabulary and engine sprawl (probe: confirmed)

The DB layer still speaks "orchestration" (`orchestration_runs/_tasks`, `source_type='orchestration'`), live board data still stamps `Recipe:` titles and `created_by_type='recipe'` against the canonical Playbook term, and — bigger — the platform still mounts **five** ways to execute work: Missions, the board spine, Playbooks, the legacy workflow engine (`api/workflows.py`, 1,424 lines, still imported and mounted at `main.py:38,947`, with a live `execute-advanced` endpoint and a Composio-webhook-reachable leg — F078 residual), and `/api/tasks` direct-step. Every extra engine is a place governance, budget bands, honest-failure semantics and telemetry have to be re-verified; two of the five (legacy workflows, tasks direct-step) have none of this module's hardening.

### Maturity score: **3 / 5**

The mechanical layer is genuinely well-engineered — validated state machine with same-transaction audit events, optimistic claims on both planes, SKIP LOCKED + lease heartbeats + honest sweeper, the 3-phase tick that eliminated idle-in-transaction leaks, budget bands on a shared ceiling helper, a pure and tested bounded-replanning ledger. On code craft alone this would flirt with 4. Judged by the North Star — does it make Auto autonomously capable and the agents' client output high-quality — the live evidence caps it at 3: the autonomy loop dead-ends at a one-shot approval notification (47% of all missions ever created are parked there), the quality gate is advisory so it does not lift output quality, checkpoint recovery is decorative, the board gate has never asked, and adoption is one workspace with zero missions in three weeks. Strong skeleton; the autonomy and quality muscles it was built to carry aren't yet doing work.

## D. Competitive teardown

The relevant class is agent-orchestration runtimes: LangGraph, Temporal (+ OpenAI Agents SDK integration), Microsoft Agent Framework, CrewAI, OpenAI Agents SDK standalone.

### LangGraph (LangChain)
The reference open-source agent orchestrator; v1.x, actively maintained (1.2.4 shipped June 2026). What it does better:
- **Checkpoint-per-superstep persistence as a first-class primitive.** Every graph step persists a full state snapshot to a pluggable checkpointer (InMemory/Sqlite/Postgres), enabling pause/resume, fault tolerance, **time-travel and forking** of past states — resume means *continue from the last superstep*, not re-run the task ([LangGraph persistence docs](https://docs.langchain.com/oss/python/langgraph/persistence)). Automatos's equivalent (per-task S3 checkpoints) is dead code (§C.5); its resume is restart.
- **Human-in-the-loop as a runtime primitive.** `interrupt()`/`Command` and static `interrupt_before/after` pause any node, persist state indefinitely, and resume on human input — approval is *inside* the execution model, not a run-state parked outside it ([HITL patterns](https://dev.to/jamesbmour/interrupts-and-commands-in-langgraph-building-human-in-the-loop-workflows-4ngl)). Automatos's AWAITING_APPROVAL run is invisible to its own tick loop until a human finds the detail page.
- **Dynamic graphs.** Conditional edges, mid-run routing, subgraphs — versus Automatos's plan-then-execute DAG whose only structural adaptation is full bounded replan.
Where Automatos stands: ahead of stock LangGraph on the *product* layer LangGraph doesn't ship — priced plan approval with policy tiers, explainable agent matching, a kanban truth surface, budget bands, SLA scanning. Balanced against: the [Diagrid critique](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows) argues checkpoint-resume (LangGraph's and, implicitly, Automatos's lease/sweeper model) still isn't true durable execution — a fair frame for both.

### Temporal (+ OpenAI Agents SDK integration)
The durability ceiling. Deterministic-replay workflows: every agent/LLM invocation runs as an Activity; on any crash the workflow replays to exactly where it was — in-flight work is *not* lost and *not* re-executed ([Temporal for AI](https://temporal.io/solutions/ai)). The OpenAI Agents SDK integration went GA March 2026, making the agent loop itself durable with near-zero code change ([announcement](https://temporal.io/blog/announcing-openai-agents-sdk-integration), [cookbook](https://docs.temporal.io/ai-cookbook/openai-agents-sdk-python)). Temporal raised a $300M Series D (Feb 2026, $5B) on exactly this "durable agents" thesis; OpenAI, Replit and Lovable run agents on it. What it does better than Automatos: crash-proof in-flight recovery (vs restart-from-scratch, §C.5), horizontal worker scale-out with fairness (vs the singleton tick, §C.7), versioned long-running workflows (a Mission surviving a deploy mid-run is untested in Automatos), and battle-tested exactly-once activity semantics. What it doesn't give: everything product-shaped — planning, agent matching, verification, approval policy, the board. It is infrastructure, not an orchestrator of *agents qua agents*.

### Microsoft Agent Framework
AutoGen + Semantic Kernel's successor (AutoGen now maintenance-mode; v1.0 GA April 2026). Graph-based **workflows with type-safe routing, checkpointing, and human-in-the-loop support** as documented first-class features, plus sessions, middleware, telemetry, MCP tools, multi-language (.NET/Python) ([overview](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview)). Better than Automatos: checkpointed workflow state and HITL in the runtime; enterprise middleware/observability out of the box. Behind Automatos: no priced approval policy, no budget bands, no agent-matching over a persistent roster, Azure-gravity.

### CrewAI
Role-based crews + event-driven Flows; **checkpointing at task boundaries with resume-from-last-checkpoint** (CheckpointConfig, SqliteProvider in 1.9.x) and an enterprise control plane (AMP Suite: deployment, observability, governance) ([repo](https://github.com/crewAIInc/crewAI), [Flows docs](https://docs.crewai.com/en/concepts/flows)). Better: crew ergonomics, resumability. Behind: its "governance" is a commercial add-on shell, not a priced per-plan approval policy; no equivalent of the board truth surface; process model is simpler than Automatos's DAG + verification + replan loop.

### OpenAI Agents SDK (standalone)
Minimal primitives — agents, tools, **handoffs** (full-history agent-to-agent delegation), **guardrails** (input/output validators that *actually block*, running parallel to execution), sessions, tracing ([docs](https://openai.github.io/openai-agents-python/), [guardrails](https://openai.github.io/openai-agents-python/guardrails/), [handoffs](https://openai.github.io/openai-agents-python/handoffs/)). The instructive contrast: OpenAI's guardrails are the *enforced* version of what Automatos's verification became — a check that fails fast and stops bad output, rather than annotating it. Automatos is far richer everywhere else (this SDK has no planner, no scheduler, no board), but on "does the quality check gate?" the minimal SDK beats the elaborate judge.

**Net position.** No competitor ships Automatos's combination — LLM-planned DAG + explainable agent matching + priced approval + budget bands + cross-model judging + kanban surface — because frameworks leave the product layer to you; Automatos *is* the product layer. Conversely, every mature competitor beats Automatos on the one mechanical property that matters most for long autonomous work: **durable, resumable, in-flight execution state** (LangGraph checkpoints, Temporal replay, MAF/CrewAI checkpointing), and the enforced-guardrail pattern beats the advisory judge on output quality. Automatos's cross-model verifier is genuinely ahead of all of them in *ambition* — none ships cross-family judging natively — and behind all of them in *effect*, because it gates nothing.

## E. Build / extend / adopt / replace — verdict

**EXTEND** the in-house engines. Do not adopt LangGraph/CrewAI/MAF as the orchestrator, and do not move to Temporal now — with one named escalation trigger.

Reasoning against the §2 adopt-bias, which demands building be earned:
1. **The pains are product-layer, not framework-layer.** Every §C defect — approval dead-end, advisory verification, dead checkpoints, board-gate $0 estimates, engine sprawl — is in exactly the layer no framework ships. Migrating the mechanical substrate onto LangGraph would rewrite ~16.5k lines of working, hardened coordination code (state machine, dispatcher, reconciler, spine) to end up maintaining the same product layer on top of someone else's runtime, while re-verifying the W1/W10/W11 hardening from scratch. Cost >> gain.
2. **The Postgres-native spine is architecturally right for this stack.** SKIP LOCKED + leases + LISTEN/NOTIFY needs zero new infrastructure, is multi-worker-safe, and survived a real production outage honestly (the only dishonest lane writes from outside the module). Temporal would add an entire cluster + programming-model migration to solve in-flight durability that today costs, at observed scale, some re-burned tokens on rare crashes.
3. **What to adopt is the *patterns*, cheaply:** (a) LangGraph's checkpoint-per-step → wire the existing dead `checkpoint_service` (or persist the tool-loop transcript on `OrchestrationTask`) so recovery resumes rather than restarts — the model and API endpoint already exist; (b) OpenAI-guardrail semantics → let a FAIL verdict requeue once with feedback (the dead `_apply_verdict_partial` is already written and tested-shaped); (c) Temporal's fairness → per-workspace round-robin in the tick.
4. **Named escalation trigger for Temporal:** when Missions run for real clients with multi-hour DAGs and an SLA where re-running a half-finished task is unacceptable (or when >~50 concurrent runs across workspaces make the singleton tick the bottleneck), lift *execution* (Phase 2 agent I/O) onto Temporal activities behind the existing dispatcher seam — the state machine and product layer stay. Integration shape: Temporal OSS self-hosted (free, +ops) or Temporal Cloud (usage-based, roughly $50-200/mo at this scale); the OpenAI-Agents-SDK integration pattern shows the wrap-the-loop approach.
5. **Replace, not extend, applies to one thing:** the legacy workflow engine (`api/workflows.py` + `workflow_templates`) — retire onto the Mission path per the July prescription (F078). Five engines is three too many; this dossier's hardening only protects two of them.

## G. Quality metric

**Primary metric — Mission outcome funnel**, measurable today entirely from existing tables (`orchestration_runs.state/stop_reason`, `OrchestrationEvent`):
`created → planned → approved (+ time-to-approval) → completed / failed / stalled / cancelled`.
Today's numbers: **17 created all-time · 2 completed (11.8%) · 8 parked at approval (47%) · median time-to-approval: unbounded (some >2 months) · 0 created in last 21 days · 1/21 workspaces ever active.** The funnel's approval-conversion segment is the single number to move first.

**Supporting metrics, all cheap:**
- **First-pass verification PASS rate** — verdicts are already persisted in every `TASK_VERIFICATION_COMPLETED` event payload (`reconciler.py:417-432`); today they gate nothing, but they are a free, longitudinal quality signal per agent/task-type. Baseline: extractable now; not yet aggregated anywhere.
- **Board honesty rate** — `done`-with-`error_message` / done (today **14.4%**, 194/1,349) and done-without-result (**35.9%**) — both should trend to ~0 as the recipe-executor lane is fixed; keep as a regression alarm on the board's truth.
- **Stall/replan rate** — `run_stall_ledger` events per run; today ~0 observed (engine barely runs).
- **Tokens per verified task** (today ~19-22k on real research tasks) and **cost per completed mission** (see H) — efficiency trend lines.
- Feed all of these to the T3 unified eval harness as the module's scorecard; no offline gold set is needed here — the funnel *is* the eval.

## H. Cost note (informational)

- Completed missions: 264,193 and 430,423 tokens ≈ **$0.79 / $1.29** at the configured flat rate ($0.003/1k, `config.py:721`). Real spend differs by model mix; the flat rate is a pricing crudeness worth replacing with the W4 pricing table someday.
- Per verified task: ~19-22k tokens ≈ **$0.06**. Verification judge: one extra LLM call per completed task on a cheap fallback model (`openai/gpt-4o-mini`, `config.py:708`) — small, but currently buys annotations nobody consumes. Consistency check: one more call per completed run.
- Planning: 1 LLM call, up to 3 on validation retries; agent-match preview adds ~1 embedding call per task.
- Overhead plane (ticks, claims, sweeps, NOTIFY) is pure Postgres — negligible.
- Failure-mode cost: a stalled/crashed task re-runs from scratch (full token re-burn, §C.5); the four paused benchmark runs banked 95-163k tokens each with no output — pause-without-resume strands spend.
