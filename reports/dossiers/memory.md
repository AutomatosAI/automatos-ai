## A. What it is

The memory substrate is Automatos's answer to "Auto and the agents remember things between turns, tasks, and missions." It is **two active systems plus two mounted relics**. Active system one is the **5-layer UnifiedMemoryService stack** (`orchestrator/modules/memory/unified_memory_service.py:1-21`): L1 Redis session summaries, L2 Postgres `memory_short_term` rows with Ebbinghaus decay, and L3 durable facts in a **self-hosted mem0 fork** (`automatos-mem0`, OpenMemory server on Railway) reached over HTTP (`orchestrator/modules/memory/integrations/mem0_client.py`), fed by an LLM **distill pipeline** that extracts typed facts from chat turns (`orchestrator/consumers/chatbot/smart_memory.py:543-630`) and a lifecycle of decay/promotion/consolidation/archival jobs (`orchestrator/services/memory_jobs.py`). Active system two is **Qdrant field memory** (`orchestrator/modules/context/adapters/vector_field.py`): a shared semantic field per mission, merged into a workspace-persistent field at mission end, scored by three-factor resonance (similarity × stability × recency, `orchestrator/modules/context/field_scoring.py`), compacted on a cursor, and promoted into durable memory by the W8 taint-gated job (`orchestrator/jobs/promote_field_memory.py`). The two relics are the in-process **AdvancedMemoryManager** behind `/api/v1/memory` (`orchestrator/modules/memory/storage/manager.py`, `orchestrator/api/memory.py`) and the pgvector-era **MemoryKnowledgeSystem** models (`orchestrator/modules/memory/storage/knowledge_system.py`) whose tables are empty in production.

## B. What it does (real implementation + data path)

### B.1 Write paths

- **Chat turns (the only curated path).** `SmartMemoryManager.store_conversation` (`smart_memory.py:358-537`) skips trivial exchanges (`:387-393`), classifies global vs agent tier (`:402`), then runs `_distill_durable_facts` — one cheap-model LLM call per turn (`config.MEMORY_DISTILL_MODEL`, `orchestrator/config.py:275-290`) against a 7-type taxonomy (`tool_outcome`, `task_learning`, `playbook_pattern`, `user_fact`, `business_fact`, `preference`, `procedure`; prompt at `smart_memory.py:599-630`). PRD-159 S1: a failed distill writes **nothing** to L3 — no raw-exchange fallback (`:426-435`). Each fact goes to mem0 via `store_two_tier` with **`infer=False`** (`unified_memory_service.py:836`) — mem0's own server-side extraction/dedup is bypassed on purpose (the platform curates first). The verbatim turn is dual-written to L2 as a `transcript` row at fixed importance 0.6 (`unified_memory_service.py:1703-1710`).
- **Tool outcomes.** A post-execution hook in both the tool loop and the unified executor (`orchestrator/modules/tools/execution/tool_loop.py:60`, `unified_executor.py:609`) writes typed `tool_outcome` memories for failures and *notable* successes only, with an error-class noise gate and bounded content-hash dedup (`orchestrator/modules/memory/tool_outcome_capture.py:27-105`). This is the best-engineered writer in the module.
- **Playbook runs.** `playbook_memory_service.py` writes a playbook-level memory (importance 0.6, `:104-118`) **and** a per-step memory (importance 0.5, `:165-182`) — both `content_type="playbook_summary"`, both also pushed to mem0 — with **no dedup and no failure-repeat suppression**.
- **Heartbeats.** The daily summary writes **twice**: once through `store_conversation` wrapped in a **fabricated** `User: Daily heartbeat summary request / Assistant: …` exchange (`orchestrator/services/heartbeat_service.py:1053-1059`) — which then burns a distill LLM call on "Total ticks: 13383" — and once as a `heartbeat_log` L2 row at importance 0.4 (`:1070-1082`). Daily activity logs add more `heartbeat_log` rows (`smart_memory.py:811-818`).
- **Missions.** `mission_memory_service.py:106,205,272` writes `mission_summary` / `task_failure` / `retry_recovery` typed L2 rows (the planning pack's recall source).
- **Field injections.** Agents and the coordinator inject `key: value` patterns into the mission field; hash-dedup within the field reinforces instead of duplicating (`vector_field.py:318-330`); provenance (workspace/mission/task/source) travels on the Qdrant payload (`:344-357`).

### B.2 Read paths

- **Chat/agent prompt.** `MemorySection` (priority 6, `orchestrator/modules/context/sections/memory.py:32-101`) tries the `ContextRouter` first: regex signal detection (temporal/personal/session/knowledge/live-data, `orchestrator/modules/memory/context_router.py:331-358`), then concurrent budgeted fetches — L1 session, L3 mem0 search (relevance floor 0.3 applied server-side at `mem0_client.py:489-492`), L2 **only when a temporal regex fires**, daily logs on no-signal (`context_router.py:472-522`).
- **Heartbeat/planning field digests (W9/F021 fix).** `HEARTBEAT_AGENT` and `PLANNING` modes render a workspace-field digest via the shared scoring/budget pipeline (`orchestrator/modules/context/sections/field_memory.py:32-126`; `modes.py:80-88,144-152`) — recurring agents are no longer amnesiac by config.
- **Agent tools.** `platform_search_memory` (promoted, L3-only — `orchestrator/modules/tools/discovery/actions_search.py:47-82`, handler `handlers_search.py:87-140`) and the field tools `platform_field_query/inject/stability` (`actions_field.py:10-83`), with W8's fix binding field context to the calling task's own run (`platform_executor.py:897-904`) and workspace-recall fallback (`handlers_field.py:70-84`).
- **Mission trace inspector.** `POST /missions/{id}/field/query` reads the field with `record_access=False` so observing no longer mutates strength (F062 fix, `orchestrator/api/missions.py:1094`; `vector_field.py:460-466`).

### B.3 Lifecycle

Registered on the shared APScheduler when `MEMORY_JOBS_ENABLED` (default true, `config.py:121`; wiring `main.py:386-403`): hourly **contradiction consolidation** (pure SequenceMatcher/Jaccard planner, `orchestrator/modules/memory/operations/contradiction.py`; applied via mem0 deletes, `unified_memory_service.py:1507-1586`), hourly **L2 decay** (archive below 0.3, `config.py:106-110`), daily 03:00 **L2→L3 promotion** (criteria `importance > 0.7 AND access_count > 3`, `unified_memory_service.py:1922-1933`; `config.py:112-114`), monthly **graphify archival** (L2+L3 → workspace graph, `memory_jobs.py:93-107`). Field side: hourly workspace-scoped **compaction** with a persisted resume cursor (F063 fix, `vector_field.py:496-568`; cursor `modules/context/compaction_cursor.py`), and daily 04:30 **field→durable promotion** with the taint gate evaluated first — untrusted-provenance patterns never promote (`promote_field_memory.py:104-121`; `field_scoring.py:112-148`; thresholds `config.py:890-903`).

### B.4 Compliance & ops plumbing

GDPR export/erase cascades across SQL + Qdrant field + mem0 (`orchestrator/services/gdpr_service.py:90-236`), with an honest declared gap: field points carry no data-subject tag, so subject-level field erasure returns 0 with a reason (`vector_field.py:231-247`). mem0 calls ride per-workspace circuit breakers plus a proactive health probe that trips/resets them (`mem0_client.py:104-146,218-237`; probe wired via heartbeat, `config.py:853-854`). DR tooling dumps/restores the primary **and the mem0 Postgres** (F050; `docs/runbooks/DR-postgres.md:5,25,63-69`) — **Qdrant field memory has no backup story** (acceptable only if you accept field memory as regenerable).

## C. Honest quality — what the real data says

**The founder's seed symptom ("memory saves low-quality memories") is confirmed, quantified, and under-stated.** The production numbers (2026-07-04, read-only): 2,211 `memory_short_term` rows; **87% operational chatter** (playbook_summary 1,255 + heartbeat_log 346 + transcript 336 = 1,937); **0 rows ever promoted to L3** across the table's entire life; `memory_items` (legacy L3) 0 rows; `memory_access_log` has **6 entries ever, last 2026-03-11**; the only informative rows (`exchange`, raw chat clippings — several of them the user telling Auto it is lying) stopped 2026-06-07 (evidence: `data/memory-short-term.md`). The root causes are all in code:

### C.1 The durable tier is dead in production — and has been, silently

`MEM0_API_URL` in the orchestrator's env points at a Railway hostname that answers **edge 404 "Application not found" on every path** — the deployment no longer exists (`data/mem0.md`). Every L3 write (distilled chat facts, tool outcomes, playbook memories, field promotions) and every L3 read (chat memory section, `platform_search_memory`, Explorer browse, consolidation) has been silently no-oping: the client is built to "skip silently" when unconfigured/unreachable (`mem0_client.py:158-164`), the breaker fails fast, and every caller catches-and-returns-empty (`unified_memory_service.py:411-417`; `sections/memory.py:65-69`). **Auto has effectively been running without durable memory, and nothing on any dashboard said so.** The heartbeat probe (`run_health_probe`) knows — but its signal steers breakers, not an operator-facing alert.

Worse, the fork state resolves July's F011 in the bad direction: in the sibling `automatos-mem0` repo, the PRD-156 token-auth commit (`fe36e09f`) and PRD-159 metadata patches (`4bb3616c`) exist **only on `fix/pool-exhaustion@16b27eb2`, which is still not an ancestor of fork `origin/main` (`5cbb4c1f`)** — verified read-only via `git merge-base --is-ancestor` this session. The W3 human runbook step (`docs/runbooks/W3-HUMAN-STEPS.md` §3: merge, pin Railway, 401 probe) was never executed. So whatever mem0 was last deployed lacked the auth and metadata fixes, and the current deployment is gone entirely.

### C.2 The write side floods L2 with duplicated operational chatter

The distill quality gate exists **only on the chat path**. The playbook writer double-writes every run (playbook-level 0.6 + per-step 0.5, same `content_type`, `playbook_memory_service.py:104-118,165-182`), so the daily OpenRouter-402 cron failure (see `data/board-tasks.md` — failing daily since mid-June) memorises the *same* failure twice per run, every day, with no repeat-suppression. The heartbeat writer double-writes each summary and fabricates a fake conversation to do it (`heartbeat_service.py:1053-1082`). Importance is a hardcoded constant per writer (0.4/0.5/0.6), so "importance" measures *which code path wrote the row*, not how much it matters. The `tool_outcome_capture` module proves the team knows how to do this right (noise gate + error-class + hash dedup) — that pattern simply was never applied to the two noisiest writers.

### C.3 Recall is structurally near-dead, which starves promotion

L2 semantic recall does not exist: `search_short_term` is an **ILIKE full-substring match of the entire user query against content** (`unified_memory_service.py:971`), and the ContextRouter only invokes it **when a temporal regex fires** (`context_router.py:489,511-513`). A query like "what did we learn about the Shopify sync?" matches zero rows by construction. Since PRD-154 S3 made recall touches the only path that increments `access_count` (`unified_memory_service.py:1041-1048`), and promotion requires `access_count > 3` **and** `importance > 0.7` (`config.py:112-114`) against a population whose types average 0.40–0.60 (only `task_failure` at 0.80 and `mission_summary` at 0.75 clear the importance bar — 19 rows total), **L2→L3 promotion is mathematically unreachable: zero promotions in the table's lifetime is the expected output of this code.** It's a bootstrap deadlock: promotion needs access, access needs recall, recall can't match. The field→durable promotion has the same `access_count ≥ 3` gate (`config.py:894`) with Missions dormant since 2026-06-13 (`data/missions-orchestration.md`) — and its destination is the dead mem0 anyway.

### C.4 The code contradicts its own documentation at the promotion seam

`promote_to_long_term`'s docstring promises "sends its content to Mem0 with infer=True (enables fact extraction and deduplication)" (`unified_memory_service.py:1799-1801`), and `memory_jobs.py:15-17` repeats the claim — but the call chain lands in `store_long_term`, which hardcodes **`infer=False`** (`unified_memory_service.py:345`). Every platform write to mem0 passes `infer=False` (`:345`, `:836`; `tool_outcome_capture.py:6`). That's a defensible design (platform curates, mem0 stores) — but it means **mem0's headline value-adds (LLM fact extraction, ADD/UPDATE/DELETE reconciliation, graph memory) are unused by design**, the fork is a thin HTTP vector store, and the docstrings describe a system that doesn't exist. Had promotion ever fired, raw playbook-failure spam would have been copied verbatim into durable memory.

### C.5 The user-facing memory surface is locked, and its delete is broken twice

The router the Memory Explorer frontend calls (`/api/v1/memory/browse|health|stats/real`, `frontend/hooks/use-memory-explorer-api.ts:118-142`; used by `frontend/components/knowledge/memory-tab.tsx:43-45` and the Command-Center memory viewer) is **router-wide super-admin locked** (`orchestrator/api/memory_stats.py:27-31`, PRD-143 S7) — a workspace owner opening their own Knowledge → Memory tab gets 403s (same over-gating family as F041). Even for a super-admin, delete is broken: the handler calls `service.delete_memory(memory_id)` (`memory_stats.py:478`) but `UnifiedMemoryService.delete_memory` requires `workspace_id` as a positional arg (`unified_memory_service.py:455-460`) — guaranteed `TypeError`, caught and returned as `{"success": False}` (`:483-485`); and the ownership pre-check is built from L3-only scans (`memory_stats.py:72-100,470-476`), so L2 rows fail "not owned" first. **No memory displayed in the Explorer can actually be deleted from it.** Meanwhile the legacy router's delete returns fabricated success without deleting anything (`orchestrator/api/memory.py:638-650`) — a leftover of the F035/F038 dishonesty class W10 was supposed to end.

### C.6 Two rival stacks are still mounted and serve nothing

- **AdvancedMemoryManager** (`storage/manager.py`, 687 lines + `operations/{access_patterns,augmentation,consolidation,prompt_injection}` + `types/`) — an in-process, process-global hierarchical store whose only production consumer is `api/memory.py`. F039 remains half-fixed: writes are workspace-prefixed (`api/memory.py:101`) but retrieve/consolidate take the raw caller-supplied session key (`:143,283/298`) — simultaneously breaking intra-tenant recall through that endpoint and leaving the cross-tenant read shape July flagged. July §14 already called this a delete candidate; it was neither finished nor deleted.
- **MemoryKnowledgeSystem** (`storage/knowledge_system.py:55-137`: `memory_items`, `knowledge_nodes/edges`, `learning_outcomes`, `harness_prescriptions`) — imported by harness/workspaces/memory_stats as a "fallback"; **every one of those tables has 0 rows in production** (`data/census.md`). It is scaffolding wearing a production import graph.

### C.7 What is genuinely good

Honest positives, verified: the **distill taxonomy + no-raw-fallback** design is the right shape (junk never reaches L3 *from chat*); **tool_outcome_capture** is production-grade; **field memory** is the most distinctive and best-engineered piece — pure, unit-tested scoring (`field_scoring.py`), payload-indexed single collection, hash-dedup-reinforce on inject, workspace merge-at-terminal, cursor-resumed compaction, read-only tracing, and a promotion job whose taint-gate-first ordering (`promote_field_memory.py:104-112`) is exactly right; W8/W9 closures (F020/F021/F062/F063) all held under re-verification; the GDPR cascade reports its own gaps instead of lying (`vector_field.py:231-247`); per-workspace circuit breakers with a proactive probe are more operational care than most of this codebase's integrations get. None of this changes the deployed outcome, because the parts that work feed the part that's dead.

### Maturity score: **2 / 5**

Component engineering ranges 3–4 (field memory, distill, tool-outcome capture); the *system as deployed* is a 1: durable tier dead and silently so, L2 87% duplicated chatter, zero promotions ever, recall structurally unable to match, user surface 403'd with a doubly-broken delete, two dead rival stacks still mounted. A memory substrate is judged by whether yesterday's work makes today's work better — on the North Star ("does Auto get more autonomously capable?"), today's answer is measurably **no**: memories are written, never read, never promoted, never surfaced.

## D. Competitive teardown

Automatos deliberately curates facts platform-side and treats the store as dumb — that architectural bet is *shared* by the leaders; the difference is they run the loop end-to-end and measure it.

**Zep / Graphiti (the temporal-graph leader).** Zep replaces flat fact lists with a **bi-temporal knowledge graph**: every fact has a validity window (`valid_at`/`invalid_at`), contradictions are resolved by **temporal fact invalidation** (superseded, not deleted — full auditable history), entities resolve and accumulate summaries, and retrieval is hybrid (semantic + BM25 + graph traversal) without an LLM in the read path ([arxiv 2501.13956](https://arxiv.org/html/2501.13956v1); [github.com/getzep/graphiti](https://github.com/getzep/graphiti)). Zep reports 94.8% on DMR (GPT-4-turbo) and up-to-18.5% accuracy gains with ~90% latency reduction on LongMemEval ([paper](https://arxiv.org/html/2501.13956v1)); third-party comparisons put Zep at 63.8% vs Mem0's 49.0% on LongMemEval ([vectorize.io/articles/mem0-vs-zep](https://vectorize.io/articles/mem0-vs-zep)). Graphiti is Apache-2.0, ~20k stars, needs Neo4j 5.26+/FalkorDB/Neptune plus a structured-output LLM ([repo](https://github.com/getzep/graphiti)); Zep Cloud is credit-per-350-byte-episode, from ~$99/mo ([getzep.com/pricing](https://www.getzep.com/pricing/)). **What it does better:** contradiction handling over time (Automatos's SequenceMatcher/Jaccard consolidation, `contradiction.py:44-82`, cannot represent "was true, now isn't"); relationship/multi-hop recall; measured benchmarks. **Where Automatos is not behind:** Graphiti has no equivalent of the shared mission field with resonance decay, and its extraction pipeline relocates rather than erases the quality problem — garbage episodes make garbage graphs (T1's central caveat).

**Mem0 upstream (what the fork descends from).** The ECAI-2025 paper reports +26% relative over OpenAI memory on LOCOMO (66.9% vs 52.9%), **91% lower p95 latency and >90% token savings vs full-context**, with the graph variant Mem0g adding ~2 points ([hf.co/papers/2504.19413](https://huggingface.co/papers/2504.19413); [mem0.ai/research](https://mem0.ai/research)). Those numbers come from mem0's **extraction+reconciliation loop (infer=true)** — precisely the half Automatos switched off; the fork delivers none of the measured value, only HTTP vector CRUD. Self-hosted OpenMemory is Dockerized FastAPI + Postgres/pgvector + Qdrant and **ships with no auth middleware** — auth is expected at the proxy ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)), which is why the fork's unmerged token-auth patch matters. **What it does better:** the store-side dedup/UPDATE/DELETE reconciliation Automatos re-implemented weakly in `contradiction.py`; a maintained upstream (the fork is frozen at a 2025-era API and now diverges unmerged). **Honest read:** running a *forked server* to get worse-than-library behavior is the single most questionable architectural position in this module — mem0 is also usable as an in-process Python library over the platform's existing Qdrant, no service hop, no fork, no separate deploy to die.

**Letta (MemGPT lineage).** Apache-2.0, ~23k stars ([github.com/letta-ai/letta](https://github.com/letta-ai/letta)). Its distinctive moves: **memory blocks** — labeled, always-in-context segments the agent *self-edits* during its loop ([letta.com/blog/memory-blocks](https://www.letta.com/blog/memory-blocks/)) — and **sleep-time agents** that share a primary agent's memory and reorganize it during idle periods ([letta.com/blog/sleep-time-compute](https://www.letta.com/blog/sleep-time-compute/); [docs](https://docs.letta.com/guides/agents/architectures/sleeptime/)). **What it does better:** the agent is an *active participant* in its own memory (Auto never edits its memory; everything is passive pipeline), and consolidation is LLM-reasoned rather than string-similarity. Automatos's hourly consolidation job is a degenerate sleep-time agent — the concept is present, the intelligence isn't. **Where Automatos is ahead:** multi-agent *shared* memory. Letta's blocks are per-agent-shareable but there is no cross-mission decaying field.

**Cognee.** Apache-2.0, ~14k stars, $7.5M seed; ECL (Extract-Cognify-Load) pipelines unify relational + vector + graph stores into one memory layer with 38+ source connectors ([github.com/topoteretes/cognee](https://github.com/topoteretes/cognee); [cognee.ai](https://www.cognee.ai/)). **What it does better:** one engine over three storage kinds — the exact consolidation Automatos lacks (three vector substrates, three memory stacks). **Weaker fit:** it's closer to a knowledge/RAG substrate than a conversational-memory lifecycle; adopting it would collide with the RAG and KG modules more than with this one.

**Where Automatos actually stands:** behind all four on the durable tier (theirs work and are benchmarked; Automatos's is dead and has never been measured), ahead of all four on the shared-field concept (a real, working, tested implementation of decaying multi-agent shared context that none of them offer in that form), and roughly level with the *intent* of mem0/Zep's curation philosophy while failing its execution.

## E. Build / extend / adopt / replace — verdict

**Replace the durable tier's deployment shape; extend the field + distill half; kill the relics.** Split verdict, one sentence each:

1. **REPLACE — the mem0-fork-as-a-service.** With `infer=False` everywhere, the fork provides vector CRUD over HTTP — nothing the platform's existing Qdrant (already deployed for field memory) can't do in-process. Concrete shape: an in-process durable-memory store on a second Qdrant collection (or the mem0 **library** over that Qdrant if its reconciliation is wanted later), behind the existing `UnifiedMemoryService` seam, killing the dead Railway service, the fork-merge debt (C.1), the HTTP hop and its 3–5s timeouts (`config.py:836,844`), and the circuit-breaker apparatus in one move. Cost: ~1–2 weeks (the seam already exists; `Mem0Client` is one class); zero new infra. This is the reuse-biased answer: reuse *your own* already-running store rather than resurrect a dead fork of someone else's server.
2. **ADOPT-candidate (conditional on T1) — Graphiti for the temporal-graph upgrade.** If T1 lands "converge memory onto a typed temporal graph," do not build fact-invalidation/entity-resolution in-house — Graphiti is Apache-2.0, proven, benchmarked, and integrates as a Python library ([repo](https://github.com/getzep/graphiti)); real costs are the graph DB (Neo4j/FalkorDB — new infra) and the extraction pipeline's LLM spend/quality. This dossier's evidence cuts both ways for T1: the platform *already* extracts typed facts (the hard half Graphiti would also need), but the current failure is operational, not representational — a temporal graph on top of dead plumbing would still be dead. Sequence: fix the loop first (J.1–J.4), then decide T1 on measured recall data.
3. **EXTEND — field memory + the distill lifecycle.** Nothing external offers the mission/workspace shared field; it's working, tested, and the W8 hardening held. Extend it (semantic L2 recall can literally be "a second use of the same Qdrant + scoring stack") rather than replacing it.
4. **KILL — the relics.** `AdvancedMemoryManager` + its `operations/`+`types/` satellite files and the `api/memory.py` router (finish F039 by deletion, not scoping); the `MemoryKnowledgeSystem` fallback models and their empty tables (`memory_items`, `knowledge_nodes/edges` at 0 rows); the fake-success delete endpoint (`api/memory.py:638-650`). None has a production consumer that would notice.

Building a new memory engine from scratch is **not** justified: every deficit found here is either operational (dead deploy, thresholds, gating) or already solved by proven OSS at the layer where Automatos is weak.

## H. Cost note (informational)

- **Distill:** 1 cheap-model call/turn (~600-token prompt + exchange; `MEMORY_DISTILL_MODEL` defaults to the platform default model — at Haiku-class pricing ≈ $0.0003–0.001/turn). Currently also spent on fabricated heartbeat "conversations" (~1 call/workspace/day producing nothing durable).
- **Embeddings:** one per field inject and one per field/L2-semantic query (2048-dim, `config.py` FIELD_EMBEDDING_DIM) — sub-cent at any realistic volume; `query_workspace` reuses caller embeddings where threaded (`vector_field.py:398-405`).
- **Store I/O:** L2 writes are plain Postgres inserts (~4–6 junk rows/workspace/day at current spam rates); mem0 HTTP adds 3s read / 5s write timeout ceilings per call when alive — the in-process replacement (E.1) removes that hop entirely.
- **Perverse present-state economics:** the memory system is currently *cheap because it is broken* — dead L3 means most of the designed spend (mem0 calls, consolidation LLM-free but delete calls, promotion writes) never happens. Fixing it will *raise* cost; budget ~$0.001–0.003/turn all-in, still far below the >90%-token-saving alternative of stuffing history into context ([mem0 paper](https://huggingface.co/papers/2504.19413)).

## I. UX / surface

Memory is user-owned data presented as if it were super-admin observability. Concrete changes, in order:

1. **Unlock the workspace views.** Move `/browse`, `/health`, `/stats/real`, `DELETE /{id}` off the router-wide `require_super_admin` (`memory_stats.py:27-31`) onto workspace-scoped auth — these endpoints already scope by `ctx.workspace_id` internally; the lock is pure PRD-143 collateral (F041's sibling). Without this, the Knowledge → Memory tab (`memory-tab.tsx`) and Command-Center memory viewer are dead UI for every real user.
2. **Make delete work and honest.** Fix the missing `workspace_id` arg (`memory_stats.py:478`), add an L2 delete path (browse shows L2 rows it can never delete), and delete the fake-success legacy handler (`api/memory.py:638-650`). Right-to-correct is table stakes for a memory product — Zep, Mem0's dashboard, and Letta's ADE all ship memory CRUD.
3. **Tell the user when memory is dead.** The health banner component exists (`frontend/components/activity/memory/health-banner.tsx`) and `/health` already computes degraded-vs-unavailable (`memory_stats.py:488-560`) — surface durable-tier reachability *in the Command Center primitive strip*, not only inside a locked tab. Six weeks of silent memory outage is the headline UX failure.
4. **Show provenance and let users teach.** Each memory should show *where it came from* (chat turn, tool call, playbook run — the metadata already stored) with one-tap "forget this" / "pin this". The SSE `memory_stored` event is already honest about fact counts (`smart_memory.py:511-513`) — surface it as a subtle chat affordance ("remembered 2 facts — review"), which doubles as the human-accept signal T3 wants.
5. **Field viz stays.** The PRD-166 S4 field visualization on the GraphView shell is the right surface for the field half; add the workspace-field toggle Gerard still has an open call on (per PRD-166 notes).
